Lucy · 权限治理优化汇报

把 Agent 接入数据的能力,做成可审计、可交付的产品

面向 CIO · 2026-06-22 · v1.0

汇报人 Lucy 产品 / 平台治理团队 材料基础 docs/lucy-platform-goal-checklist、docs/project-overview、inbox/access-governance-design 汇报时长 约 5 分钟阅读
本次优化把 Lucy 平台的"谁能用什么工具、看哪些数据"从手写配置,升级为预置角色 + 写入即审计的治理闭环。
P0 安全写路径已落地;剩余 P1 工作可在两周内闭环,无新增技术债务,不影响现有客户交付节奏。

一、本次优化在做什么(一句话)

把"为 AI Agent 配数据访问权限"这件事,从需要懂 YAML 的工程师才能做的隐式配置,变成选模板、点确认、留审计记录的标准化产品能力。

二、为什么现在做(背景)

  • 2026-06-21 内部审计发现: admin 写入路径仍可创建"全部表全部工具"通配 Agent,与 v1.2 设计冲突,属于 P0 安全风险。
  • 2026-06-21 spec 评审 Opus 二次审阅: 把访问治理写入路径定性为可重新引入过度授权 Agent 的安全风险,优先级需高于纯文档同步。
  • 客户接入门槛: 当前只有 kx_readonly 一个角色,新客户接入时要手写 selector,容易出错。

四、用户价值(对内 + 对外)

受益方 变化前 变化后
客户(管理员) 新建 Agent 要手写 selector + connections + tools,容易出错,撤销延迟最长 30s 从下拉菜单选模板;改动必走 dryRun → 确认;审计日志自动留痕
Agent 使用者 需要懂"mysql-aliyun / dataforai.kx_*"等技术字段才能配通 只需配 URL + Bearer token,能力由模板自动限定
合规 / 法务 权限变更无统一审计通道,事后追溯靠人工查 yaml 差异 所有配置变更进 config_change_log,可按 user / 文件 / 时间查询与导出
运维 / SRE 升级时担心覆盖客户自定义的 role 模板与 role 实例分离,升级不会覆盖客户配置
产品 / PM 新增一类客户要重新设计 role,反复造轮子 复用 5 个预置模板覆盖 80% 场景;新增模板由产品维护,与 role 解耦

五、关键事实(给非技术读者)

  • 事实源仍然是 YAML: 没有引入新的配置系统,客户现有的 access.yaml 继续作为唯一权威源,git 可 diff。
  • 运行时裁决不会回退到旧配置: 角色解析失败一律拒绝,绝不回退到"全部允许",这是已落地的硬规则。
  • 明文密钥管理规则不变: 数据库密码仍然只在服务器本地 secrets 目录,管理员 UI 不可见。
  • WebUI 仍仅本机访问: 没有引入新的登录系统,远程访问能力不在本阶段范围。

九、给 CIO 的 3 个确认项

决策 1 · 安全边界

是否同意"P0 写入路径已强制 role-first、撤销 30s TTL 内仍可能放行"作为可接受的产品安全等级?若需更严,请拍板是否进入主动 reload 优先路线(W27 之前可完成)。

决策 2 · 模板覆盖范围

本次 P1 拟交付 5 个预置模板(kx_readonly / superstore_readonly / wiki_only / guard_test / dev_superstore)。是否需要在 v1 额外覆盖某类客户场景(如财务扩展域、研发只读)以减少首次上线摩擦?

决策 3 · 长期演进节奏

列级 / 行级权限(增量 2)在 §3.2 留有 spec 锚点但不在 P1 范围。若业务侧出现 PII 脱敏或租户隔离需求,请提前 1 个季度预警,以便排期。
