Lucy 继续使用当前版本与 SQLite。**本 Spec 在 `0.30` 不开发**；已落盘的盘点／差集／验收设计保留在需求池，作为**下一期开发目标**（开线后另确权、另授权）。当前输出是源码盘点、风险差集、后续分批设计和可证伪的验收方案。以下运行合同是供未来评审的候选，不能依据本草案实施。当前不修改任何代码、数据库 schema、依赖、运行配置或客户数据；不运行 Docker、备份、压测、迁移、故障注入或服务采样。

## 架构决策草案（ADR；待确权）

D1：保留 SQLite；单实例／单副本边界沿用 DEVELOPMENT。备选是现在迁 PostgreSQL（用户已明确暂不升级）或只预留配置开关（不足以证明可迁移）；推荐存储边界＋实演路线，承担后续两种后端的维护与合同验证成本。

D2：按事务能力而非逐条 SQL 定义异步可适配的存储接口。事务上下文不能跨连接；不要在同步 SQLite transaction 回调中 await。数据库提交与文件发布之间继续遵守原恢复协议。

D3：任何同库原子操作保留原子性，尤其预算更新、幂等认领与关联审计。派生统计能否延后、是否拆库逐项评审。安全库显式 FULL 等现行承诺不为性能默认放宽。

D4：客户默认仍 SQLite。PostgreSQL 应用后端只有覆盖完整声明范围、两后端合同测试与迁移恢复证据具备后才可声称受支持；KTX 本地状态单列，不改上游。

## 候选验收（均未执行）

| ID | 局部合同承诺 | 证伪检查 |
|---|---|---|
| SC-01 | 原子性不退化 | 事务中间失败不留半份预算／幂等／关联行；验证无重复提交 |
| SC-02 | 安全提交后才释放 | 注入真实写失败；未提交不能返回业务成功；恢复后合法调用成功 |
| SC-03 | 等待、重试与取消有界 | 真实双连接持锁，结束后无遗留事务；准确区分未提交与提交结果未知，不盲目重试 |
| SC-04 | 观测不写业务状态且开销有界 | 前后状态核对，观测失败不阻塞原主路径；数值先冻结 |
| SC-05 | 清理遵守保留与关联要求 | 边界内外记录、不可删除状态、关联证据核对；失败不部分删事实 |
| SC-06 | 后端 SQL 与类型语义一致 | 两种真库相同输入与期望；覆盖 NULL、UTC 时间精度、JSON、排序、64 位 ID、唯一性与序列 |
| SC-07 | schema 演进可控 | 旧版本夹具到候选版本；中断后拒绝错误版本或可恢复，不默默跳过 |
| SC-08 | 文件／数据库边界诚实 | 领域写入在文件与账本之间中断，按原协议恢复／明确拒绝；合法恢复路径可达 |
