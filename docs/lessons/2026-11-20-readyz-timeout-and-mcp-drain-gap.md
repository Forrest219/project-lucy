## 1. 症状与影响

旧版真实诊断读取不返回时 readyz 超时，但 livez 正常。候选内存探针保持可用，诊断却可持续陈旧；候选还在真实10秒纯MCP查询执行中，将 TERM 关停误判为已排空，提前截断请求。后者在诊断正常对照中同样复现。

## 2. 复现要点

在隔离卷实际 reload state 路径放置持有写端且不结束的FIFO，观察Node线程pipe_read；候选120秒探针全200。仅恢复路径仍未解除旧读取，释放原句柄后下一采集恢复fresh。另在独立MySQL观察User sleep确认查询已执行，再TERM，三轮均在约0.7–1.6秒退出且无查询结果。

FIFO是受控真实OS等待机制，不代表客户使用FIFO；不将本机机制复现写成客户PVC或Pod根因。

## 3. 根因

- P1-61：采集函数忽略AbortSignal；5秒截止只标stale，未完成取消或真实执行上界，single-flight持续占用。许可不应提前释放，但也不能以此宣称超时自愈完成。
- P1-63：Web路由登记了在途，MCP Proxy未接入同一实际工作登记和settle，协调器可能看到0在途而退出，再停止KTX。
- 后续实际入口复测又发现npm启动器PID先退出，实际Node虽在排空仍被父进程视为已结束。已改为直接启动并等待真实Node PID；修复登记与PID等待两处后，三轮10秒查询TERM均完成结果后退出。

## 4. 为何漏检

此前单元／组件通过只证明受控采集器和协调器局部行为，未证明真实readFile消费取消，也未证明标准entrypoint到真实MCP业务链的在途计数接线。没有完整UAT通过记录；不能把单测绿等同功能合同收口。

## 5. 举一反三

1. 对取消、超时和排空，必须核对底层线程／子进程／DB操作是否真正结束；客户端超时、Promise.race或返回码不是资源终态。
2. 多入口共用协调器，必须从每个真实入口发起业务并与信号竞争；只测协调器类或Web钩子会漏掉MCP主路径。
3. 恢复路径名、取消等待者、终结原I/O要分开观测；不能通过提前放许可制造隐形后台堆积。
4. 已验证的隔离成功、真实停止失败和恢复后可用分别判定；恢复成功不抵消中途被截断的合法请求。

## 8. 1883表持续补验后的收敛

[约1h补验](../qa/uat/suites/core-availability/runs/2026-11-20-codex-fde-1883-soak.md)已实跑59分45秒，12次真实提交重载、8次完整恢复；未自然复现客户readyz长期不返回。5次预算相关MCP应用503与FDE入口摘流503是不同证据层；该冻结候选未含后续18b63d01既有预算持久化修复，不能重复立项或写成修复后回归。

主线程有CPU热点与同步存储等待；诊断子进程单在途、自然窗无pipe_read观察，不等于所有I/O都无等待。连续CPU profiler停止／导出可能放大长尾，已保留前段与无采样客户端对照；不把样本全200当预算内响应。进度计数包含失败尝试，成功数须按原始回执重算。用户要求收敛后停止，不把未跑满2h或未执行的1883表后置FIFO冒充通过；全量审计读取60s超时保留GAP，不能只看complete。
