## 1. 结论

1. **不能只换镜像。** 目标 Chart 必须是 0.2.6。Chart 0.1.0 不能承载这次升级：它把 Secret 只读挂到 `.ktx/secrets`（新建数据源 `EROFS`）；`LUCY_PUBLIC_MCP_URL` 缺失时 WebUI 进入 MCP fallback（目录能看、数据查不了）。镜像、Helm Chart、values 三者一起升。

2. **当前 r6 不能直接发放，也不能在现有文件上补做原生验收后就放行。** `lucy-k8s-integration-delivery-20261021-r6.tar.gz` 的归档验证 JSON 仍是 `localGate = PASS`、`nativeAmd64UpgradeAndRecovery = PENDING_DEPLOYER_ACCEPTANCE`、`productionReady = false`。它的升级入口还不会写入内容根和信任代理（见 §5.1）。放行身份是白名单补齐之后的**一次**新构建；原生 amd64 升级和恢复演练打在这个构建上。验收通过后不再出包。

3. **有停机。** 单副本 + RWO PVC + `strategy: Recreate`，切换期间 WebUI 与 MCP 不可用（秒级到数分钟）。需维护窗口。本计划不承诺零停机。「平滑」指保留 PVC 上的连接、语义层、权限、Token 和审计，并继续使用现有 https 域名。

4. **进入 2.0 后，WebUI 从开放模式变为管理员登录。这是本计划已经选定的产品范围，同时关闭 V-01。** 只消除 `MCP initialize request is required before session traffic.` 时，已发布的 `lucy-k8s-integration-20261009-v1`（Lucy 0.17.0 / Chart 0.2.4）可以修复并保持开放模式；该包不含 2026-10-18 的会话归属与撤销屏障，不在本计划范围内。2.0 的 customer 模式在无管理员时是 `bootstrap`，不会是 `open`（`admins-store.ts:227-243`）。Chart 把 `LUCY_DEPLOYMENT_MODE` 与 `LUCY_CHART_DEPLOYMENT_MODE` 都钉为 `customer`。只改前者会启动失败；把两个变量一起改成 `development` 是不被支持的清单修改，不是可选项。Agent Token 不因认领而重签。WebUI 没有只读角色，首个 owner 认领后，其余需要管理面的人由 owner 建成 operator。

5. **最高危的隐性断点是角色能否编译，不是镜像或 Chart。** 绝对拒绝工具名会使整个角色编译失败（§5.3）。启用表范围缺省等于空集，带 selector 或 `catalog_bound` 的角色会编译失败（§5.4）。两者都不挡住 Pod Ready。仓库里没有该客户的 `access.yaml` / `ktx.yaml`，不得把任一条写成已经命中。P1-7 用目标镜像对 PVC 副本做只读编译，给出每个角色的证据。

6. **现场步骤以放行包内的文档和脚本为准。** 包内有 `scripts/deploy.sh`、`scripts/acceptance.sh`、`scripts/preflight-upgrade.sh`、`scripts/preflight-helm.sh`、`scripts/probe-customer-auth-state.mjs`，以及 `CUSTOMER-UPGRADE.md`、`ACCEPTANCE.md`。恢复模板是 `examples/RECOVERY.open-mode.md`；填写后放在实例目录，文件名必须是 `RECOVERY.md`。本计划规定阶段、门禁和断言。包内入口与本计划冲突时，以本计划的门禁为准，并从供应方修正版重新准备实例。

`POST` 探针必须带浏览器会发送的 `Origin`。不带 `Origin` 的请求会穿过 CSRF 检查，不能用来证明域名映射可用。网关若保持原始 `Host`，该探针在未改写 Host 时通过；网关若把 `Host` 改成上游 Service 地址，探针返回 403，须先修正网关或可信 `X-Forwarded-Host`，再重新验收。

### L5 恢复层

| 断言 | 工具 | 证据 |
|---|---|---|
| 还原旧卷 + 旧版本后业务可用 | 实例目录 `RECOVERY.md` | 恢复记录 |

### 5.2 三类 preflight 已覆盖的漂移

`scripts/preflight-upgrade.sh` 默认只报告不修改。`--apply-types` / `--apply-access` 是显式开关。

|---|---|---|---|
| Deployment 被手工 patch（`command` / `args`、多余 volume / volumeMount / initContainer） | 渲染新 chart → `kubectl apply --dry-run=client` → 与 live Deployment 比对（`preflight_upgrade_drift.py:62-95`） | 人工 review JSON Patch → `kubectl patch`。patch 表达不了时才考虑 `helm upgrade --force`（重建 Deployment，PVC 不受影响） | 不是默认选项。不处置会 `Init:Error` 或探针超时 |
| 语义层列 `type` 不是 `string` / `number` / `time` / `boolean` | 容器内扫描 **P1-8 确定的实际语义层目录** | `--apply-types` 只改有映射的类型（SQL Server 映射表），改前自动写 `.backup.<timestamp>` | 无映射类型（如 `geometry`）只报告、不写，preflight 仍判 FAIL。脚本默认路径 `/data/lucy/semantic-layer` 在 `config/` 布局下不存在，`preflight-upgrade-lib.mjs:110-112` 返回空列表，`:230-233` 以退出码 0 结束 |

### 5.4 preflight 未覆盖、由 P1-7 编译判定的漂移

## 7. 回滚

**触发条件**：`acceptance.sh` 失败；`/api/health` 不通；连通测试或真实取数失败；管理员认领无法完成；L4 的域名 POST 返回 `CSRF_ORIGIN_DENIED`；角色编译失败导致取数全断。

`helm rollback` 不恢复 PVC 上的 `admins.yaml` / `security.sqlite`，也不恢复被 2.0 改写的卷内容。顺序：

1. 隔离对外访问。
2. 保存失败现场（`helm history`、Pod image digest、阶段结果、`.diagnostics/` 脱敏诊断）。
3. 按实例目录 `RECOVERY.md` 还原初始备份（含数字属主还原）。模板来自包内 `examples/RECOVERY.open-mode.md`，部署入口校验的文件名是 `RECOVERY.md`。
4. 再 `helm rollback <last-good-revision> --wait`。
5. 验证：`/api/health` 200、原 https 域名的 WebUI 与 `/mcp` 可达、连通测试通过、MCP `tools/list` 成功。
6. 若回滚到 chart 0.2.3 之前：旧 Chart 会把 Secret 重新只读挂到 `.ktx/secrets`。升级后由 WebUI 新建的连接会失败（文件仍在卷上，被挂载遮蔽）。用 `--skip-secrets-check` 验收，并尽快再次前滚。

不删除 PVC。不删除 `admins.yaml` 来强制重新认领。未审查访问边界时，不把旧开放模式重新对外。

## 8. 禁止事项

1. 只换镜像、不升 Chart / values。
2. 用 `kubectl set env` 注入 `LUCY_PUBLIC_MCP_URL`、内容根或信任代理。这些值写在 Helm 渲染结果里。
3. 删除 PVC，或删除 `admins.yaml` 强制认领。
4. 把 KTX 端口 `7878` 暴露到 Service / Ingress。
5. 现场修改脚本、校验或摘要来绕过绑定。修正来自供应方的新包，并复用原签发状态。
6. 用可变 tag 作为不同构建的身份，或用可变包覆盖已分发的正式资产。
7. 用 `--token` 传参，或把 Token 贴进报告与截图。
8. 把 r6 或任何 `productionReady = false` 的包当作客户正式版发放。
9. 用本地演示或合成集群回归结果代替原生 amd64 验收。

## 10. 已知缺口

1. **升级 UAT 脚本不随包交付。** `package.json:67-68` 已有 `upgrade-uat:snapshot` 与 `upgrade-uat:verify`，参数走 `--config-root` / `UPGRADE_CONFIG_ROOT`。个人目录硬编码在 `scripts/upgrade/assemble-upgrade-uat-config.sh:5-6` 与 `package.json:65`。现场 L3 用包内 `acceptance.sh` 与 `UPGRADE.md` 的指纹命令。下一版再考虑把 snapshot / verify 收进包内 `scripts/`。
2. **preflight 类型扫描路径固定为 `/data/lucy/semantic-layer`。** 该目录不存在时退出码为 0。P1-0 决定布局；布局不是 `"."` 时，默认扫描无效。`access.yaml` 的扫描路径两种布局都可用。
3. **preflight 不覆盖 §5.4。** 启用表空集与角色编译失败没有启动期报错。P1-7 的只读编译是这次的证据；它还不是包内一条命令。
4. **`--apply-access` 只删不补。** 旧工具名是否改为 `lucy_*` 由决策表记录。
5. **五层断言没有单一入口。** L1 用归档验证 JSON，L5 用原生环境的 `RECOVERY.md` 演练。L2/L3/L4 分散在多个脚本和人工记录中。
6. **r6 的 `productionReady = false`。** 在 P0-1 的白名单进入某一次构建、且该构建通过 P0-6 之前，没有可发放的包。
7. 现场若为标准 Kubernetes，镜像导入按该 CRI 执行。`deploy.sh` 的自动导入要求节点免交互 `sudo -n`。
8. **CSRF 403 取决于网关是否改写 `Host`。** 限速共用网关地址不取决于这一点。L4 探针区分这两种结果。
