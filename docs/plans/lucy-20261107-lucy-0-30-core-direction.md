## 1. 一句话

> **0.30 的核心不是让 Agent「更能自由发挥」，而是在已有约 100 名真实用户的前提下，把每天的稳定、准确、可靠交互，从靠模型临场发挥的玄学问题，变成有科学机制保障的系统工程。**

现有功能的用户体验优化仍然要做，但它们是**辅线**：服务可读、可点、可理解。主线是**可信度工程**——答对、答稳、答错能被立刻识破并当天修正。

## 2. 为什么现在必须聚焦这件事

| 事实 | 含义 |
|---|---|
| 约 100 人已在用 Lucy | 最贵的失败形态不再是「答不出来」，而是「答错了而且没人知道」 |
| 2026-11-06 CFO 事故 | 权限内的**语义误报**（选错表）＋ **口径被 AI 自行加工**；ACL 越权已排除 |
| 止血已落地 | 改语义文件「指定表 + 固定口径」，客户真实账号复测通过——证明**硬约束可行** |
| 已对客户承诺 | 「每天跑测评、每天迭代」「发现问题当天修正」——**目前全靠人力盯后台** |
| C-level 体感最关键 | 一两次误报就会毁掉整条产品信任，与功能多少无关 |

因此：0.30 的投入标准，不是「把 Eval 做漂亮」或「多几个 Agent 技巧」，而是——

> **让公司已经对客户承诺的「每天迭代、当天修正」，不再依赖某个人一直盯着后台。**

## 3. 双轨：辅线体验 × 主线可信

```text
┌─────────────────────────────────────────────────────────────┐
│  辅线：现有功能 UX / 治理台打磨                              │
│  （发布工作台、帮助中心、访问关系图、遗留验收、拒绝码统一…） │
│  → 降低操作成本，不单独定义 0.30 成败                        │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  主线：存量用户每日可信交互（本文件核心）                      │
│  稳定 · 准确 · 可靠 · 可检出 · 可当天修正                     │
│  → 定义 0.30 是否「升级成功」                                │
└─────────────────────────────────────────────────────────────┘
```

**排序原则**：与主线冲突时，辅线让路；辅线可并行，但不得挤占主线的 Spec / 评测 / 告警带宽。

## 4. 从「玄学」到「科学」：四道机制闸

Agent 自由发挥本身不可消灭；0.30 要消灭的是**无护栏的自由发挥**。把问数拆成四道闸——任一道失效都视为产品缺陷，而不是「模型今天状态不好」。

### 4.1 约束闸（Prevent）——先缩小自由度

| 机制 | 要达成的效果 | 池内锚点 |
|---|---|---|
| 问题类型 → 唯一表 + 固定口径绑定 | 常见业务域不再让 AI 现场拼口径 | REQ-030-027 |
| Catalog 携带业务语义（描述 / 同义词 / 粒度 / 适用域） | Agent 不再只能按表名字符串猜 | REQ-030-023 |
| 多表命中先问 + 表级歧义门闩 | 不确定时失败关闭或澄清，禁止静默错表 | REQ-030-024 |
| 宽表字段暴露裁剪 / 孤儿路径治理 | 权限内可见面本身干净，减少「能查但不该查」 | REQ-030-012 / 015 |

> 语义层硬约束是已验证的止血轨；0.30 要把它从「逐题人工改 YAML」升级为**可复用的绑定与门禁机制**。

### 4.2 呈现闸（Verify in situ）——答错当场可识破

| 机制 | 要达成的效果 | 池内锚点 |
|---|---|---|
| 答复可核对块（来源表 / 口径 / 数据截止期）强制露出 | CFO 级用户不打开审计台也能核验 | REQ-030-022 |
| 空结果 / 拒答的结构化下一步 | 「没数」不等于瞎编或死循环；模型与人都能接着做 | REQ-030-018 |

Provenance 资产多数已在 `_meta.lucy`——缺口是**对人强制可见**，不是重新造一套溯源。

### 4.3 检出闸（Detect）——发布前与每日都能抓住回归

| 机制 | 要达成的效果 | 池内锚点 |
|---|---|---|
| Eval 选表正确性可测（禁把金标表名喂进 prompt） | 「选错表」在结构上能被测出 | REQ-030-025 |
| 真实问句回灌 + 五域覆盖（损益 / 资金 / 资产 / Token / GPU） | 评测集来自生产与客户场景，不是实验室玩具 | REQ-030-025 |
| 路径断言可编排；审计旅程 → Eval 草稿 | 从一次事故到一条用例有管道 | REQ-030-019 / 020 |
| 发布后 / 每日跑批可触发 | 「每天测评」成为系统行为 | REQ-030-025 及运维面 |

Eval 是**检出器**，不是修复器：它证明缺陷存在并阻止静默上线；修复仍走语义绑定、Skill、工具面修订。

### 4.4 运营闸（Operate）——100 人规模下的当日闭环

| 机制 | 要达成的效果 | 池内锚点 |
|---|---|---|
| 存量用户体感仪表盘 | 首次成功率、空结果率、拒绝率、慢查询可见 | REQ-030-026 |
| 主动告警（复用既有通知通道） | 「发现问题当天修正」有信号，不靠人刷后台 | REQ-030-026 |
| 失败 → 工具面 / Skill 反哺队列 | 迭代有入口，禁止只改 prompt 碰运气 | REQ-030-021 |

## 5. 「稳定 · 准确 · 可靠」的操作定义

| 词 | 0.30 的可操作含义（非口号） |
|---|---|
| **稳定** | 同一问题类型、同一角色、同一发布基线下，选表与口径不漂移；发布后有回归，不靠「再问一遍碰运气」 |
| **准确** | 选对表、用已发布口径；权限内错表与自行加工口径均视为缺陷，而不是「有权即可」 |
| **可靠** | 答错可当场核对；不确定则澄清或 fail-closed；异常有告警与当天修正路径；承诺不依赖单个人力值守 |

三者同时成立，才叫「能和现有用户每天交互」；只优化 UI 文案或只加模型指令，**不算** 0.30 主线完成。

## 6. 科学机制的最小闭环（每日）

```text
  绑定与门禁（Prevent）
        │
        ▼
  真实问询（100 用户） ──► 可核对答复（Verify）
        │                        │
        │                        └─► 用户可当场否决误报
        ▼
  审计旅程 / 失败指纹
        │
        ▼
  Eval 用例（Detect）──► 每日 / 发布跑批
        │
        ├─ 通过 → 基线保持
        └─ 失败 → 告警 + 语义/Skill/工具修订（Operate）
                      │
                      └──► 回写绑定与门禁
```

任何一环断裂，系统就退回「玄学」：只能指望下一次 Agent 发挥更好。

## 7. 与辅线（现有 UX）的关系

以下工作**允许且鼓励**在 0.30 推进，但默认优先级低于 §4 主线，且不得单独宣称「0.30 核心已达成」：

- 发布工作台分文件勾选、帮助中心、访问关系图与审计口径、遗留验收矩阵执行
- 行权限编译门禁与拒绝码统一、explain 诊断形状等**正确性/安全辅线**（它们服务准确与稳定，但解决的是「权限与合同」，不是「语义误报主战场」）
- 纯视觉 polish、文案微调、非关键路径交互

**正确性辅线**（行权限、OIDC、语义恢复等）与主线可并行；**体验辅线**在主线关键路径未立 Spec 前，避免大范围开新交互。

## 8. 明确不做（本方向下的非目标）

- 不把 Lucy 改造成 Wren / Vanna 式「对话式 BI 宿主」；Lucy 仍是 **MCP 数据面 + 语义治理**。
- 不以「换更强模型 / 加更长 instructions」代替门禁、绑定与 Eval。
- 不把 ACL 改造成语义裁判；ACL 继续只答「有没有权」，语义正确性走绑定 / 门闩 / Eval。
- 不引入第二套不同步的知识库或记忆层作为生产口径来源。
- 不在本方向文档内授权任何代码实现。

## 9. 0.30 主线成功的判据（方向级，非功能验收）

方向拍板后，实施仍按条目 Spec 验收。版本级「主线是否站住」用下面四条一起判断：

1. **常见问题类型**可配置「唯一表 + 固定口径」，且运行时偏离可被拒绝或强制澄清。
2. **终端用户**在正常客户端里能看到足以否决误报的来源 / 口径 / 时效信息。
3. **选表错误**能被 Eval 检出；五域（损益 / 资金 / 资产 / Token / GPU）具备可日更的用例骨架；跑批不依赖人工把金标表名写进 prompt。
4. **运营侧**能看到存量用户体感趋势，并在关键指标恶化时主动告警——「当天修正」有系统信号，而不是靠人肉刷日志。

四条未齐，即使辅线 UX 全部打磨完成，也不宣称 0.30 核心升级完成。
