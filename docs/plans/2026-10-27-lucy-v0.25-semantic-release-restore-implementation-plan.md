## 1. 目标与实施原则

将“批量修改语义并成功发布后，恢复到所选批次发布前”实现为独立、可审计的新发布流程，交付：

1. 所有正式语义内容写入口的批次前快照；
2. 发布历史中的可恢复性、恢复预检、整批 CAS、确认恢复和状态追踪；
3. 恢复自身的新批次、新快照、故障恢复、索引与审计；
4. 固定保留策略和只读恢复包导出；
5. SRR-01–SRR-24 对应自动化与分环境证据。

实施原则：

- 复用 L25-11 的共享发布协调器、统一校验、CAS、幂等、失败恢复和审计，不另建并行发布引擎。
- 长期快照与短期故障恢复日志共享必要的构建逻辑，但独立存储、独立生命周期、独立清理。
- 先完成所有写入口快照覆盖，再开放恢复 UI；不得只做批量导入路径后宣称全功能完成。
- 默认冲突零写入，不提供 force overwrite；恢复不改写来源历史。
- 任何实现完成声明均不自动等于 SRR 验收或客户交付通过。

## 2. 开工前置与冻结合同

### S0 需求审查与开工裁决

1. 以 **v0.11 主 Spec** 为输入。恢复语义、可恢复状态、30 分钟预览、24 小时幂等、最多 20 个记录仍存在的可恢复批次 / 30 天 / 512 MiB 保留参数和只读恢复包边界沿用 v0.8–v0.10 已审定的产品语义。第 4 轮复核只改正锁事实与写入口清单。
2. 确认 L25-15 独立编号、P0 优先级和 SRR 验收矩阵；确认它不是 L25-11 的补丁章节，也不改变 L25-11 的 V01–V22 状态。
3. 核对当时代码中的共享协调器、恢复日志、幂等、发布记录、内容镜像和 KTX 实际读取面的合同，形成偏差清单。既有 `confirmOverwrite` 等 L25-11 遗留项不在本功能顺带修改；如需改动，另行授权和评审。
4. 写入口清单已在主 Spec §2.2 按 2026-10-30 源码冻结。S1 按该表接线。再发现正式内容写点时，先改 Spec 清单再编码。SRR-01 按该表逐项验收。
5. 沿用已审定的安全裁决：expected absent 与计划内受控镜像删除、实际 KTX 兄弟视图扫描范围、写前 promoting 与 snapshotId 关联、三态幂等、全目标 CAS、§8.1 六类启动对账、受理审计前置、持久 lease、恢复写集与镜像同步写集分离、索引重建模式与删除方向语义读回、终态审计可恢复协议。发现新证据时先修订 Spec，不在实施中静默降级。
6. 确认全局术语标准和 Design System 是否需新增条款；双区恢复预检若超出现有模式，先登记临时设计决策。
7. 单独批准实施阶段和验证范围。默认不执行浏览器或移动窄屏测试；只有任务或已批准计划明确要求时才增加浏览器运行。
8. **锁生命周期按主 Spec §5.2.1 的现行源码执行。** 提交 `3b7e8d32` 已让批量发布的锁留到 `verifyFinalTargetDigests`、`semantic_publish_terminal`、`published` 与 `completeRecoveryJournal` 之后，手动 reindex 的历史记录写在 `withPublishCoordinator` 回调内。S1–S6 把快照接在该临界区内部，不得把释放点提前到 reindex 返回时。`semantic_restore` 锁同样留到自身终态之后。提交前重读基线，并拒绝与未终结批次重叠。`writeSourceYamlImport` 与 `applyConnectionIdChange` 当前仍在窗口外，按 S1 对照表接入。并发注入计入 SRR-23。L25-11 的 V01–V22 仍未执行；本功能不把 `3b7e8d32` 写成 L25-11 验收通过，也不改 L25-16 的 G31 登记。
9. **冻结「恢复写集 / 镜像同步写集」判定与枚举口径**：确认镜像同步写集的枚举范围（四类内容目录的内容根→兄弟视图漂移）、预检披露字段与提交时的一致性核对方式；确认其在 journal 中的排除规则与方向断言；确认两种布局（正常 / `LUCY_CONTENT_ROOT=.`）下的退化处理。**并确认镜像侧允许变化集合为「恢复写集的受控镜像目标 ∪ 已确认的镜像同步写集」，两类变化方向分别可核对**。口径写入 Plan 实施记录，并计入 SRR-24。
10. **冻结删除方向语义读回的预期模型**：按 Lucy 双层合并模型（Manifest 提供表结构、overlay 提供业务扩展）确认各类删除目标的读回预期分类——删除 overlay 断言业务扩展不可见但表结构仍可见，删除 Manifest 中表才断言整表不可检索／不可读取；确认读回预期由恢复计划推导并持久化的方式。口径写入实施记录，并计入 SRR-04。
11. **冻结索引重试的范围确认对象**：确认「只确认索引范围、不重算内容恢复计划」的确认对象契约（绑定 releaseId、实际扫描集合、镜像同步写集、reindexMode），以及重试前对 `prepareSemanticLayerForKtx` 全量同步副作用的处置方式（核验漂移一致或改走受控同步路径，不一致即阻断）。口径写入实施记录，并计入 SRR-17。
12. **冻结镜像同步的受控路径**：确认所有触发镜像同步的内部调用（索引前准备步骤、启动恢复的 runtime mirror 同步）如何改为「只针对已核验集合」的受控变体，以及垃圾清理与历史目录迁移（含 rename／rm）这类独立平台行为的边界与执行时点。口径写入实施记录，并计入 SRR-09／SRR-24。

**退出条件**：v0.11 已完成。写入口清单与锁顺序已冻结，阶段范围为 S1–S6。S7、浏览器验证、镜像与客户交付仍须单独授权。

## 4. 分阶段实施

### S1 批次前快照与所有正式写入口接线

**目标**：先建立可恢复数据基础；此阶段不开放恢复提交。

任务：

1. 在 `semantic-release-snapshots.ts` 定义 `semantic-release-snapshot/v1`、可空 digest、持久实例 UUID 和可恢复性类型；规范化项目相对路径并复用内容根解析，禁止共享 `lucy-default` 回退。
2. 从完整发布计划的**实际写盘目标**构建快照，包含原 bytes / absent、原 digest、预期新 digest / absent、资产类型和完整表身份；只读依赖与完整索引范围不进入写盘集合。
3. 先计算精确序列化字节并做容量预检，再同目录临时文件 + rename，写后回读核验；release.snapshotId 关联必须确认记录存在且更新成功，任何失败均在正式写入前返回。
4. 快照函数只按本进程 holder 身份断言调用方已持锁，不自行取锁，兼容 with / acquire 两入口。所有内容批次按“完整计划与基线复核 → 校验通过 → promoting / 幂等 intent → 快照及关联 → journal → 受理审计 → 正式写入”接线。
5. 按 S0 冻结清单和以下对照表逐一接线，单表保存同时改写共享 Manifest 时两者都入批并解析全部影响表；纯手动 reindex 不生成伪内容快照：

   |---|---|---|
   | 单表保存 | `semantic-layer.ts::writeSourcePatch` | `withPublishCoordinator("semantic_table_save")` 内、正式 `auditedWriteFile` 前 |

### S2 恢复领域服务与 API

**目标**：完成只读预检、整批提交和真实状态闭环。

任务：

1. 实现来源资格审查：仅 `published / reindex_failed` 且有正式内容写入、快照完整且同持久实例的记录可预检；`promoting / reindexing` 等待，其他状态按 Spec 返回稳定原因。
2. 预检从服务端快照重建恢复后候选，逐目标分类 `restore / delete / unchanged`；unchanged 仅指 originalDigest==expectedNewDigest，外部改回批次前仍属 CAS 冲突。
3. 根据当前 `projectRoot/semantic-layer/` 兄弟视图与恢复计划枚举**恢复候选的实际 KTX 扫描集合**；已知待同步变化逐项返回，无法可靠判定的差分返回 unknown 覆盖率，不新建索引账本、不以内容根集合或伪造空清单替代。
4. **枚举并披露镜像同步写集（审阅 R02）**：按 S0 第 9 条冻结的口径枚举内容根↔兄弟视图漂移文件，逐文件给出两侧 digest / absent，在预检中作为独立分区展示；明确标注这些文件不由本次恢复写入、变化方向是「镜像向内容根对齐」。
5. **确定索引重建模式（审阅 R03 / 复审）**：**按语义删除集合判定** `incremental` 或 `force_rebuild`——集合由恢复前后合并模型差异推导，包含 Manifest 原地回写删表（文件仍为 restore）；**不得只统计 absent 目标**。模式写入 `planDigest` 并持久化到 release 记录；预检即显示将采用的模式。删除 overlay 文件**不构成**表消失（表结构仍可见），但其「业务扩展不可见」读回仍必须执行。
6. 对全部快照目标检查当前 digest / absent == 来源批次 expectedNewDigest / absent，包括 unchanged；对差异目标同时核验 KTX 镜像基线与内容根一致。混合场景只写差异目标，全部 unchanged 才 no_change，且在创建 release、幂等和索引前返回。
7. 预览固定 30 分钟并登记 preview lease，绑定实例、操作者、来源 releaseId、snapshotId 和完整计划；每次重新预检生成新 planDigest 和新幂等键。
8. 恢复使用 `semantic_restore` acquire / release，锁覆盖后台 reindex 直到终态；临界区内重读权限、来源、快照和完整范围，重建计划并统一校验，helper 不再次取锁。
9. **幂等查询前移至取锁之前（审阅 R07 / 终审）**：鉴权与恢复准入检查后先做**严格只读**的幂等查询；`applied` 重放直接返回既有批次状态；**`intent` 在锁外只允许「读取并返回真实进行中状态」，需要结清时必须转入锁内**（协调器未取得锁只会抛 busy，锁外不得执行结清或修复等写操作）；需要新 attempt 时再取锁，并在锁内**完整重做三态判定（含 `failed` 且零写入未证明 → recoveryRequired）、计划一致性与恢复准入检查**。
10. 依次持久化 promoting release → 幂等 intent → 新快照及 release.snapshotId → 支持 expected absent 且覆盖内容根／镜像双面写集的 journal → staged 受理审计；**promoting 与幂等 intent 的持久化必须纳入同一个写前异常处理块**（终审 F01），按已成功持久化的对象分别结算为 promote_failed／failed；结算本身再失败时必须持久保留恢复准入义务（recoveryRequired），不得留下无主的 promoting 记录，也不得只依赖重启清理。
11. 对差异目标原子恢复 bytes 或删除 absent；恢复删除调用计划专用的精确相对路径镜像删除并回读两面 absent，通用 content-mirror 的 never-deletes 不变。**journal 只登记恢复写集，不登记镜像同步写集**。**全量 upsert 前先核验漂移集合与预检披露一致，出现未披露漂移立即阻断、不得先写后查；upsert 只复制已核验集合内的文件**；upsert 后确认除「恢复镜像目标 ∪ 镜像同步写集」外无镜像文件被改动，再枚举实际扫描集合并核对。失败按 journal 逆序恢复两面，未知状态触发 recoveryRequired，镜像未删或结果未知不得 published。
12. **按 §5.5 模式执行索引并做语义读回（审阅 R03 / 终审 N01）**：**模式由「语义删除集合」判定**——集合非空即执行 `--force` 强制重建并做删除方向语义读回；**集合必须由恢复前后合并模型差异推导，包含 Manifest 原地回写导致的删表（文件仍为 restore，不是 absent）**，不得只统计 absent 目标；**读回预期按双层合并模型分类并由恢复计划推导持久化——删除 overlay 的目标断言业务扩展不可见但表结构仍可见，语义删除集合中的表才断言整表不可检索／不可读取**；读回失败记 `reindex_failed / unconfirmed` 并保持 journal 未终结。**files-saved 阶段标记必须在幂等转 applied 与 release 转 reindexing 之前完成并纳入失败处理**（终审 R01）。
13. **实现恢复批次索引重试（审阅 R05 / 终审）**：提供绑定原 releaseId 与新 attemptId 的批次级索引重试入口，不重复恢复写盘、不用纯手动 reindex 代替、保留原失败 attempt、沿用 release 记录的 `reindexMode`；重试使用新幂等键。**索引范围确认必须独立于内容恢复预检**——建立只确认索引范围、不重算内容恢复计划的确认对象（绑定 releaseId、当前实际扫描集合、当前镜像同步写集与 reindexMode）；**重试前须处理 `reindexProject` 内部 `prepareSemanticLayerForKtx` 的全量同步副作用**：核验当前漂移集合与该 release 记录一致，或改走只针对已核验集合的受控同步路径，不一致时阻断并要求重新确认。
14. **实现终态审计可恢复协议（审阅 R04 / 终审 / 复审）**：**只实现 §8.1 的唯一一套顺序**「落终态审计 → 写 release 终态并置 pending → 核对审计并清 pending → 终结 journal」，不得另存第二套；`terminalAuditPending` **只有一个设置点（与 published 同一次写入）、一个清除点、一个含义（终态审计尚未被核对）**；公开投影在服务端统一实现（列表、详情、状态 API、CSV、筛选计数一律「生效待确认」）；终态审计唯一身份 `releaseId + attemptId + "terminal"` 防重复追加；**启动对账按 §8.1 的六类互斥分类执行**（A 终态证据补写 / B journal 补写 / C 终态核对 / D 索引续跑 / E 零写入结清 / F 阻断与重试判定），**补写类（A/B/C）必须先于索引续跑类（D）**，归入补写类即不得再产生新的索引调用。
15. applied 重放必须回读真实 release 和快照关联；intent 重放进入实际状态对账，若对应 promote_failed 且零写入可证明则先结清 failed；failed 仅在零写入已证明时允许同键同计划新 attempt。500 条容量不得提前淘汰未过期记录。
16. 复用 `reindexing → published / reindex_failed` 和状态查询。启动对账执行主 Spec §8.1 的六类互斥分类（A 终态证据补写 / B journal 补写 / C 终态核对 / D 索引续跑 / E 零写入结清 / F 阻断与重试判定），补写类先于索引续跑类。分类为 D 且内容与镜像可证明时，才从索引阶段重跑一次并沿用记录的 `reindexMode`。结果未知时结清为可重试的 `reindex_failed / unconfirmed`，不重复写盘，不无限停留 `reindexing` 或 `terminalAuditPending`。

### S4 保留策略、恢复包与故障加固

**目标**：收口长期运行的容量、安全和运维边界。

任务：

1. 实现最多 **20 个发布记录仍存在的可恢复批次**、30 天、512 MiB 三上限的最旧先清；计数只包含仍存在的 `published / reindex_failed` 内容批次记录关联的快照，失败或 `promoting` 批次不占可恢复名额，也不获得长期保留承诺。
2. 发布侧车 100 条上限导致记录淘汰时，将对应快照归为 `orphan`：不可恢复、不占 20 个名额，但仍计 30 天与 512 MiB，并作为最旧非活跃对象优先清理，防止绕过容量或永久滞留。
3. 用持久 lease 登记 `publish / restore / preview / export` 活跃引用，包含 leaseId、snapshotId 和 expiresAt；快照创建、lease 变更与清理使用同一串行机制，导出 lease 持续到流结束，启动仅清理已过期 lease。
4. 新快照先计算包含 Base64 和 manifest 的**精确序列化字节数**，再逐出最旧、非活跃快照并预留名额，最后原子落盘和回读核验；仍无法完整保存时在正式写入前阻断。清理只删快照，不删发布记录，可用性投影记录 `expired / count_limit / size_limit / orphan / missing / corrupt / instance_mismatch`，不改写来源历史。
5. 实例标识使用 `.ktx-ui` 下首次生成并持久保存的 UUID；已有部署级持久唯一 ID 可作来源，禁止回退到共享 `lucy-default`。快照缺失、损坏、回读 digest 不符或实例不符均明确披露，不得自动从历史 Diff 或单表版本重建。
6. 构建只读 ZIP 恢复包，内含 `semantic-release-snapshot/v1` manifest、原 bytes / absent 和 digest；导出前自检、下载时重新鉴权，无对应上传路径。使用 `restorePackageMaxEntries / restorePackageMaxMetadataBytes / restorePackageMaxUnpackedBytes / restorePackageMaxZipBytes` 独立键执行 200 entry / 1 MiB / 512 MiB / 544 MiB 上限和流式下载，维护包限值不变；快照本身不限 200 entry，超限可恢复但不可导出，超限或不能完整流式导出时明确失败。
7. 复核进程崩溃后的 promoting、reindexing、**`terminalAuditPending` 成功记录**、幂等、快照与 journal 生命周期：故障日志可终结，长期快照按独立策略保留；未终结故障先恢复，再开放写入。重点覆盖 expected absent、内容根／镜像删除后故障、snapshotId 关联失败、index 边界 reindexing 结算、**终态审计落库失败后的结算（§8.1 的 F 类，不得悬挂）**与**索引重试沿用记录模式**。**启动恢复路径中的 runtime mirror 同步必须同样走受控镜像集合**，不得执行无参全量同步；垃圾清理与历史目录迁移须在恢复前完成并纳入范围复核。
8. 做路径穿越、符号链接、重复目标、计划外镜像删除保护、精确容量及 +1、20 个可恢复批次及 +1、orphan、清理与活跃 lease 竞争、普通 staging GC 隔离等负向测试；**补充遗留布局 `LUCY_CONTENT_ROOT=.` 下双面退化不重复登记／不重复执行专项，以及目录重命名与恢复互斥的并发注入**（审阅 R09 / SRR-23／24）。
9. 检查日志、API 和导出错误不泄露宿主绝对路径、凭据或越权 YAML；所有 TTL、计数和容量统一落在 `SEMANTIC_BATCH_LIMITS`。

测试重点：SRR-01、SRR-04、SRR-15–SRR-16、SRR-19–SRR-21、**SRR-23／SRR-24**。

**退出条件**：精确容量与清理边界、活跃 lease 并发、持久实例、损坏披露、恢复包四项上限和故障恢复测试通过；不存在无限保留、提前清理活跃快照或任意包导入的隐式路径。
