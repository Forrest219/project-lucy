## 1. 目标与实施原则

将“批量修改语义并成功发布后，恢复到所选批次发布前”实现为独立、可审计的新发布流程，交付：

1. 所有正式语义内容写入口的批次前快照；
2. 发布历史中的可恢复性、恢复预检、整批 CAS、确认恢复和状态追踪；
3. 恢复自身的新批次、新快照、故障恢复、索引与审计；
4. 固定保留策略和只读恢复包导出；
5. SRR-01–SRR-22 对应自动化与分环境证据。

实施原则：

- 复用 L25-11 的共享发布协调器、统一校验、CAS、幂等、失败恢复和审计，不另建并行发布引擎。
- 长期快照与短期故障恢复日志共享必要的构建逻辑，但独立存储、独立生命周期、独立清理。
- 先完成所有写入口快照覆盖，再开放恢复 UI；不得只做批量导入路径后宣称全功能完成。
- 默认冲突零写入，不提供 force overwrite；恢复不改写来源历史。
- 任何实现完成声明均不自动等于 SRR 验收或客户交付通过。

## 2. 开工前置与冻结合同

### S0 需求审查与开工裁决

1. 以经 Claude Code 两轮审查修订的 v0.3 主 Spec 为输入，逐项审查恢复语义、可恢复状态、30 分钟预览、24 小时幂等、最多 20 个记录仍存在的可恢复批次 / 30 天 / 512 MiB 保留参数和只读恢复包边界。
2. 确认 L25-15 独立编号、P0 优先级和 SRR 验收矩阵；确认它不是 L25-11 的补丁章节，也不改变 L25-11 的 V01–V22 状态。
3. 核对当时代码中的共享协调器、恢复日志、幂等、发布记录、内容镜像和 KTX 实际读取面的合同，形成偏差清单。既有 `confirmOverwrite` 等 L25-11 遗留项不在本功能顺带修改；如需改动，另行授权和评审。
4. 一次性核实并冻结全部正式内容写入口清单：单表保存、单表 YAML 导入／单表版本恢复落地、Manifest 上传、批量导入、恢复，以及核查发现的其他正式写入路径。纯手动 reindex 明确排除内容快照；SRR-01 以冻结清单逐项验收。
5. 审查并确认 v0.3 的关键安全裁决：expected absent 与计划内受控镜像删除、实际 KTX 兄弟视图扫描范围、写前 promoting 与 snapshotId 关联、三态幂等、全目标 CAS、promoting / reindexing 启动对账、受理审计前置和持久 lease；发现新证据时先修订 Spec，不在实施中静默降级。
6. 确认全局术语标准和 Design System 是否需新增条款；双区恢复预检若超出现有模式，先登记临时设计决策。
7. 单独批准实施阶段和验证范围。默认不执行浏览器或移动窄屏测试；只有任务或已批准计划明确要求时才增加浏览器运行。

**退出条件**：Spec 需求审查签核、实施授权和阶段范围明确；未满足时后续阶段保持未开始。

## 4. 分阶段实施

### S1 批次前快照与所有正式写入口接线

**目标**：先建立可恢复数据基础；此阶段不开放恢复提交。

任务：

1. 在 `semantic-release-snapshots.ts` 定义 `semantic-release-snapshot/v1`、可空 digest、持久实例 UUID 和可恢复性类型；规范化项目相对路径并复用内容根解析，禁止共享 `lucy-default` 回退。
2. 从完整发布计划的**实际写盘目标**构建快照，包含原 bytes / absent、原 digest、预期新 digest / absent、资产类型和完整表身份；只读依赖与完整索引范围不进入写盘集合。
3. 先计算精确序列化字节并做容量预检，再同目录临时文件 + rename，写后回读核验；release.snapshotId 关联必须确认记录存在且更新成功，任何失败均在正式写入前返回。
4. 快照函数只按本进程 holder 身份断言调用方已持锁，不自行取锁，兼容 with / acquire 两入口。所有内容批次按“完整计划与基线复核 → 校验通过 → promoting / 幂等 intent → 快照及关联 → journal → 受理审计 → 正式写入”接线。
5. 按 S0 冻结清单和以下对照表逐一接线，单表保存同时改写共享 Manifest 时两者都入批并解析全部影响表；纯手动 reindex 不生成伪内容快照：

   | 写入口 | 当前真实写点 | 快照接入点 |
   |---|---|---|
   | 单表保存 | `semantic-layer.ts::writeSourcePatch` | `withPublishCoordinator("semantic_table_save")` 内、正式 `auditedWriteFile` 前 |
   | 单表 YAML 导入／单表版本恢复落地 | `semantic-layer.ts::writeSourceYamlImport`；`POST /api/sources/:conn/:schema/:table/import` 且 `dryRun=false` | 先接入 `withPublishCoordinator("semantic_table_save")` 或独立内容写入 kind，在 preview.files 首个正式写入前建立 promoting、快照和 journal |
   | Manifest 上传 | `catalog-assets.ts` Manifest 写入服务 | `withPublishCoordinator("manifest_upload")` 内、首个正式写入前 |
   | 批量导入发布 | `semantic-assets.ts::publishSemanticAssets` | 现有 acquire 锁内、recovery journal 与 promote 前 |
   | 整批恢复（S2 开放） | `semantic-release-restore.ts` | `semantic_restore` 锁内、恢复写盘前 |

6. 扩展 release 的 promoting、快照、恢复与生效字段以及旧记录 unknown；`webui_restore` 在服务端筛选、前端归一化和 CSV 全链路保留。
7. 扩展 recovery journal 的 `newContent / expectedNewDigest=null`，证明删除落地后仍能按原 bytes 故障恢复；该 L25-11 类型扩展单独记录评审。
8. 将快照目录排除于 Agent 检索、发布候选、语义维护包和普通 staging GC；所有 TTL 与容量写入 `SEMANTIC_BATCH_LIMITS`。

测试重点：SRR-01、SRR-02、SRR-04、SRR-15 的删除恢复、SRR-20 的旧记录 / 实例部分、SRR-21 的隔离部分。

**退出条件**：S0 冻结清单和上述对照表逐项有 promoting、写前快照、snapshotId 关联和失败零写入测试；普通发布与恢复 helper 在 with / acquire 两入口不二次取锁、不误 busy，各入口仍互斥；失败恢复及单表草稿恢复回归不破坏。

### S2 恢复领域服务与 API

**目标**：完成只读预检、整批提交和真实状态闭环。

任务：

1. 实现来源资格审查：仅 `published / reindex_failed` 且有正式内容写入、快照完整且同持久实例的记录可预检；`promoting / reindexing` 等待，其他状态按 Spec 返回稳定原因。
2. 预检从服务端快照重建恢复后候选，逐目标分类 `restore / delete / unchanged`；unchanged 仅指 originalDigest==expectedNewDigest，外部改回批次前仍属 CAS 冲突。
3. 根据当前 `projectRoot/semantic-layer/` 兄弟视图与恢复计划枚举**恢复候选的实际 KTX 扫描集合**；已知待同步变化逐项返回，无法可靠判定的差分返回 unknown 覆盖率，不新建索引账本、不以内容根集合或伪造空清单替代。
4. 对全部快照目标检查当前 digest / absent == 来源批次 expectedNewDigest / absent，包括 unchanged；对差异目标同时核验 KTX 镜像基线与内容根一致。混合场景只写差异目标，全部 unchanged 才 no_change，且在创建 release、幂等和索引前返回。
5. 预览固定 30 分钟并登记 preview lease，绑定实例、操作者、来源 releaseId、snapshotId 和完整计划；每次重新预检生成新 planDigest 和新幂等键。
6. 恢复使用 `semantic_restore` acquire / release，锁覆盖后台 reindex；临界区内重读权限、来源、快照和完整范围，重建计划并统一校验，helper 不再次取锁。
7. 依次持久化 promoting release → 幂等 intent → 新快照及 release.snapshotId → 支持 expected absent 且覆盖内容根／镜像双面写集的 journal → staged 受理审计；任一前置失败零正式写入并结清明确失败。
8. 对差异目标原子恢复 bytes 或删除 absent；恢复删除调用计划专用的精确相对路径镜像删除并回读两面 absent，通用 content-mirror 的 never-deletes 不变。镜像同步后重新枚举实际 KTX 扫描集合，核对一致才把幂等转 applied、release 转 reindexing；失败按 journal 逆序恢复两面，未知状态触发 recoveryRequired，镜像未删或结果未知不得 published。
9. applied 重放必须回读真实 release 和快照关联；intent 重放进入实际状态对账，若对应 promote_failed 且零写入可证明则先结清 failed；failed 仅在零写入已证明时允许同键同计划新 attempt。500 条容量不得提前淘汰未过期记录。
10. 复用 `reindexing → published / reindex_failed` 和状态查询；启动时对账 **promoting 与 reindexing**、幂等、snapshotId、journal 与实际 bytes。全部写入和镜像可证明时从索引阶段重跑确认；结果未知或失败结清为可重试 reindex_failed / unconfirmed，不重复写盘、不无限停留 reindexing。
11. 接入三个新 API、发布历史和 trigger 筛选；预览、提交、轮询和导出重新检查权限。审计按 validated / exported / staged / blocked / failed / published 映射，受理审计前置，终态失败不留 published / confirmed。
12. 审计关联 sourceReleaseId、newReleaseId、sourceSnapshotId、newSnapshotId、planDigest 和各阶段结果，不修改来源历史。

测试重点：SRR-02–SRR-18、SRR-20。故障注入覆盖 promoting、intent、snapshotId、journal、内容根／镜像写盘与删除、实际扫描范围、索引 / 终结记录边界，并含 intent + promote_failed 和死 releaseId 重放防回归。

**退出条件**：服务端 API 在临时内容根与临时 KTX 兄弟视图完成完整恢复闭环；混合 unchanged、三态幂等、双面 CAS、受控镜像删除、中断、reindexing 结算和索引失败均有可复核 hash、范围、记录与状态证据。

### S4 保留策略、恢复包与故障加固

**目标**：收口长期运行的容量、安全和运维边界。

任务：

1. 实现最多 **20 个发布记录仍存在的可恢复批次**、30 天、512 MiB 三上限的最旧先清；计数只包含仍存在的 `published / reindex_failed` 内容批次记录关联的快照，失败或 `promoting` 批次不占可恢复名额，也不获得长期保留承诺。
2. 发布侧车 100 条上限导致记录淘汰时，将对应快照归为 `orphan`：不可恢复、不占 20 个名额，但仍计 30 天与 512 MiB，并作为最旧非活跃对象优先清理，防止绕过容量或永久滞留。
3. 用持久 lease 登记 `publish / restore / preview / export` 活跃引用，包含 leaseId、snapshotId 和 expiresAt；快照创建、lease 变更与清理使用同一串行机制，导出 lease 持续到流结束，启动仅清理已过期 lease。
4. 新快照先计算包含 Base64 和 manifest 的**精确序列化字节数**，再逐出最旧、非活跃快照并预留名额，最后原子落盘和回读核验；仍无法完整保存时在正式写入前阻断。清理只删快照，不删发布记录，可用性投影记录 `expired / count_limit / size_limit / orphan / missing / corrupt / instance_mismatch`，不改写来源历史。
5. 实例标识使用 `.ktx-ui` 下首次生成并持久保存的 UUID；已有部署级持久唯一 ID 可作来源，禁止回退到共享 `lucy-default`。快照缺失、损坏、回读 digest 不符或实例不符均明确披露，不得自动从历史 Diff 或单表版本重建。
6. 构建只读 ZIP 恢复包，内含 `semantic-release-snapshot/v1` manifest、原 bytes / absent 和 digest；导出前自检、下载时重新鉴权，无对应上传路径。使用 `restorePackageMaxEntries / restorePackageMaxMetadataBytes / restorePackageMaxUnpackedBytes / restorePackageMaxZipBytes` 独立键执行 200 entry / 1 MiB / 512 MiB / 544 MiB 上限和流式下载，维护包限值不变；快照本身不限 200 entry，超限可恢复但不可导出，超限或不能完整流式导出时明确失败。
7. 复核进程崩溃后的 promoting、reindexing、幂等、快照与 journal 生命周期：故障日志可终结，长期快照按独立策略保留；未终结故障先恢复，再开放写入。重点覆盖 expected absent、内容根／镜像删除后故障、snapshotId 关联失败、index 边界 reindexing 结算和终态审计失败。
8. 做路径穿越、符号链接、重复目标、计划外镜像删除保护、精确容量及 +1、20 个可恢复批次及 +1、orphan、清理与活跃 lease 竞争、普通 staging GC 隔离等负向测试。
9. 检查日志、API 和导出错误不泄露宿主绝对路径、凭据或越权 YAML；所有 TTL、计数和容量统一落在 `SEMANTIC_BATCH_LIMITS`。

测试重点：SRR-01、SRR-04、SRR-15–SRR-16、SRR-19–SRR-21。

**退出条件**：精确容量与清理边界、活跃 lease 并发、持久实例、损坏披露、恢复包四项上限和故障恢复测试通过；不存在无限保留、提前清理活跃快照或任意包导入的隐式路径。
