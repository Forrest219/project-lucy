## 1. 背景

### 1.1 现象：状态行存在两套语言

`docs/governance/DEVELOPMENT.md:149-159` 规定：一条功能的现行状态只有一个事实源，即 Spec 头部的「状态」行；配对 Plan、两个索引 README、执行总账「跟进状态」、`project-overview.md` §9 都是它的镜像，且必须**同句**。

实际盘点下来，这个事实源有**两套并行的措辞体系**：

- `docs/specs/`（新规范）多用中文自由句，其中夹杂规范原子：「终稿已确权」「开发授权已获得」「功能合同已收口」
- `webui/docs/*-spec.md`（存量数字流水号）用英文：`Implemented` / `Approved for planning` / `Superseded` / `Draft` / `Ready for Review`

两者指向同一批闸门语义（终稿确权 → 开发授权 → 实现落地 → 功能合同收口），但用词不同。

**机器门禁的真实作用面（须分清）：**

| 现象 | 是否进 `AUTH_PHRASE`／交互合同门禁 | 本轮是否处理 |
|---|---|---|
| `webui/docs` 英文状态词（约 62 份） | **否**（numbered module 只跑 `filename`） | 本轮不扫；不宣称已解决 |
| `docs/specs`／`docs/plans` 再引入英文状态词 | 英文本身不解锁授权；会污染开发台事实源 | **是**——硬门禁拦英文状态词 |
| `docs/specs` 中文近义（`已获开发授权`／`开发已授权`／`授权开发`／`已批准开工` 等）不含「开发授权已获得」 | **是**——AUTH 子串不命中，门禁当未授权 | **否**——属正向词表／文法问题，另开条；本轮不宣称修复 |

**v0.2 结论（收窄）：** 本轮解决的是「开发台扫描面再引入英文状态词」的漂移入口与 PR CI 缺口；**不是**「AUTH 近义中文已统一」，也**不是**「全仓库状态词已中文化」。

### 1.2 盘点（可复现）

```bash
# 全量 Spec 状态行取值分布
for f in docs/specs/*.md webui/docs/*-spec.md; do
  head -30 "$f" | grep -m1 -E "^\|\s*(状态|Status)\s*\|"
done | sed 's/^|//;s/|$//' | sed 's/^ *//;s/ *$//' | sort | uniq -c | sort -rn
```

| 目录 | 文件数 | 状态行命中推荐中文原子（子串） | 状态行使用英文状态词 |
|---|---|---|---|
| `docs/specs/*.md` | **约 151**（含状态行约 **138**；口径≠「全仓 Spec」） | 多数为自由句；规范原子命中不等同「已统一」 | **0**（整词英文状态词） |
| `docs/plans/*.md` | **约 233** | 同上 | **≥1**：`2026-10-21-customer-20260828-v1-to-lucy-2.0-upgrade-plan.md` 状态行含独立词 `Draft`（`当前 Draft \`r6\` 不是放行包`） |
| `webui/docs/*-spec.md` | 189 | — | **62**（本轮扫描面外） |

明细分布（部分，webui）：`Implemented` 47、「已实现」15、`Approved for planning` 3、`Draft / Ready for Review` 2、`Superseded` 2，其余为带括注的长句。

**specs 侧额外事实（对抗复核）：** 大量状态行不含九个推荐原子（自由描述／「已实现」「功能合同收口」缺「已」等）。这证明：若本轮宣称「中文词表已机器强制」，与存量事实冲突——故 v0.2 把中文原子降为推荐写法。

### 1.3 归因：约束缺位，不是执行不到位

规则侧本来就有要求状态行存在且同句（`:151`/`:153`/`:157`），但**没有任何一条规则要求状态行禁止英文状态词**，也没有正向中文枚举。规则只约束"有没有写""写得一致不一致"。

于是：

- 机器门禁 `lint:spec-docs` 有 `metadata`、`stale-status`、`close-layer`，**没有 `status-vocab`**
- 评审靠人眼，用词差异不会被当成问题提出来
- `lint:terminology` 只扫产品禁用词，管不到文档元数据

**"禁止英文状态词"此前不在任何机器或人工检查项里**——这是本轮硬门禁要补的缺口。中文近义统一是**另一缺口**，见 §2.2。

### 1.4 为什么可以现在补

本条不依赖任何在途功能条（含标识符大小写一致性工作）。现在补的理由只有两条：治理窗口空闲、且 PR CI 缺口已有实证（§4.3.1）。**不**把「与某功能条同一窗口」写成必要性。

## 2. 目标与范围

### 2.1 目标（v0.2 正式范围）

1. **硬门禁：状态行禁止英文状态词**——`docs/specs/` + `docs/plans/` 头部「状态」行不得出现 §3.3 禁用词表中的独立英文状态词。
2. **可机器判定**：`lint:spec-docs` 新增规则 `status-vocab`（deny-list + 词边界）；独立 script `lint:status-vocab` 挂进 `lucy-ci.yml`，让违规在 PR CI 阻塞。
3. **本规则落地前清零本规则违规**：不申请 `status-vocab` 基线豁免；已知存量 `Draft \`r6\`` 须在落地前改写或改匹配确认不命中（§5 第 7／8 条）。缺状态行不归本规则。
4. **不产生第二份口径**：禁用词表与推荐写法只在 `docs/governance/DEVELOPMENT.md` 一处定义；lint／CI 复用同一实现，禁止第二份词表拷贝。
5. **软约束：推荐中文写法**——§3.3 九个中文原子写入规则正文作推荐；**本轮 lint 不做正向强制**，不改写存量近义中文。

### 2.2 非目标

- 不改任何运行代码、不改产品界面、不改任何 Spec／Plan 的现有状态**语义**（仅允许为过 `status-vocab` 而改写英文状态词或易误伤措辞）
- 不要求把 `webui/docs/` 英文状态词存量改写——见 §3.2 与 §8 R3
- 不定义状态行的**文法**（句式、分隔符、原子顺序），不做「必须含某中文原子」的正向判定——见 §8 R2；中文近义／AUTH 口令统一另开条
- 不做"整个文档中文"——见 §2.3
- 不动 `docs/qa/uat/INDEX.md` 的测试台判定词表（`PASS` / `PASS WITH GAP` / `FAIL` / `NOT RUN` / `BLOCKED` 属独立枚举 SOT）
- **本轮不加** agent hook（L1）

### 2.3 约束范围：只管「状态行」上的禁用英文状态词

写成"文档一律用中文"是**不可执行的口令**——仓库里大量内容天然是英文标识符（路由、类名、`SC-01` 验收编号、UAT 套件名、`npm run` 命令、Design System 章节名）。守不住的约束等于没写。

| 受本条约束 | 不受本条约束 |
|---|---|
| 头部元数据表里「状态」行中的**英文状态禁用词**（词边界匹配） | 版本号（`v0.1-draft`、`v1.0`）——即使含字母序列 `draft` |
| 元数据表的**表头词**（用「状态」，不用 `Status`） | 日期、提交号、套件 ID、跑次链接 |
| — | 括号内的限定说明、自由描述句中的**中文近义**（本轮不拦） |
| — | 文档**正文**中引用英文词（如本文件禁用词表本身） |

**扫描面＝头部元数据表的「状态」行**，不是全文。这一点必须写进规则，否则本建议书自身就会违规。

| ④ | **测试门禁登记** | `docs/governance/test-layers-and-release-gates.md`（§2 Current Commands／§8 CI Mapping） | 登记 `lint:status-vocab` 与 `lucy-ci.yml` 接线 | 落盘清单第 8 条 |

**为什么落①在「状态登记只有一份现值」这一节**：该节已定义「状态行是唯一事实源」（`:151`）、6 处镜像清单（`:153`）、「以头部状态行为准」（`:157`）。状态措辞跟状态登记是同一件事的上下游，单独新开顶层章节等于多一份口径。

**为什么扫描面不含 `webui/docs`**：`lint-spec-docs` 的 `collectDocViolations` 只跑 `docs/specs/*.md` + `docs/plans/*.md`（顶层、非递归，调用点 `:512-523`）。`webui/docs/*-spec.md` 只过 `filename` 规则（`:508-511`）。**注意：** `DEVELOPMENT.md:369` 正文写「并递归检查各模块 `<module>/docs/`…」——与当前代码（numbered 只跑 filename）不完全同句；本条**以代码行为为准**划扫描面，不借本条去「对齐扩扫」。

**上线前不是「零命中」而是「零本规则违规」：** 对抗复核已发现 plans 侧至少 1 处独立词 `Draft`。落地顺序见 §5：先处置该处（或确认词边界规则不误伤后仍须改掉状态语义上的英文状态词），再开 CI，**不**把该文件写入 `status-vocab` 基线。

新规则接入现有分流通道即可自动获得：

- `classifyViolations`（`:441-449`）：已跟踪文件 → 阻塞；未跟踪在途草稿 → 只 `WARN`
- 基线豁免（`:447`）：除 `stale-status` 外均走基线键判定；**本规则上线时基线改动量须为 0**（与「不申请本规则豁免」一致）

### 3.3 写入 ① 的正文草案

```md
#### 状态措辞用中文

Spec 与 Plan 头部「状态」行禁止使用下列**英文状态词**。匹配须同时满足：
（1）大小写敏感；（2）词边界；（3）**显式版本段排除**（见下）——版本号豁免不得只靠（1）或（2）。
表头写「状态」，不写 `Status`。扫描面是头部元数据表；正文引用英文词不受本条约束。

禁用状态词（硬门禁，`status-vocab`）：
`Implemented`、`Approved for planning`、`Superseded`、`Draft`、`Ready for Review`。

推荐状态词（软约束；本轮 lint 不强制；近义中文不改写存量）。
阶段码对照官方表见漏斗 Spec §3.1（S4／X_DEF 一对多；X_REL 无推荐原子）：

| 状态词 | 阶段码（软） | 含义 |
|---|---|---|
| 草案 | S1 | 设计未定稿，终稿未确权，未获开发授权 |
| 终稿已确权 | S2 | 文档级闸门通过，设计冻结 |
| 开发授权已获得 | S3 | 允许改运行代码（与 AUTH_PHRASE 同句） |
| 实现已落地 | S4 | 代码已合入工作树或已提交 |
| 待验收 | S4 | 实现完成，验收条目未关闭 |
| 功能合同已收口 | S5 | SC 全部关闭且有收口记录 |
| 被取代 | X_SUP | 被后继 Spec 取代 |

```

### 3.4 匹配规则（硬门禁实现约束）

| 规则 | 要求 | 反例／注意 |
|---|---|---|
| 大小写 | **敏感**；只拦表内大小写写法。未经版本段排除，**禁止**改成大小写不敏感 | 单独靠本条**不能**论证 `v0.1-draft` 安全；见下一行 |
| 词边界 | 禁用词须为独立词：匹配处左侧、右侧皆非 `[A-Za-z]` | `Draft \`r6\`` **命中**。**注意：`v0.1-draft` 在「两侧非 ASCII 字母」定义下也会命中 `draft`**（`-` 不是字母）——词边界**不**承担版本号豁免 |
| **版本段排除（B1）** | 在 deny-list 之前，从状态单元格中剔除或忽略版本段：匹配 `/[vV]?\d[\w.]*-draft\b/`（及同形 `v0.2-draft`）的子串**不参与**禁用词扫描。这是 `v*-draft` 不受本条约束的**唯一正当理由** | 无版本段排除时，大小写不敏感实现会命中扫描面约 47 处状态行中的 `-draft` |
| 短语 | `Approved for planning`、`Ready for Review` 按整短语匹配 | 不拆成单字拦 `Ready` |
| **表头（B2）** | 表头须为「状态」。检测**不得**经 `statusCell()`：该函数只认中文「状态」（`lint-spec-docs.mjs:619-623`），对 `Status` 恒返回空，规则会永假。实现须**独立**扫描文件前 60 行表格行，凡表头单元格（去 `*`）为 `Status` 的行 → 报 `status-vocab`（可附带扫描该行英文禁用词） | `| Status | Implemented |` 必须能触发；不得因 `statusCell()===""` 而静默跳过 |
| **缺状态行** | **不归本规则。** 前 60 行找不到「状态」行时，由既有 `metadata` 报缺；`status-vocab` **不**再报、不申请为本规则新增基线豁免 | 实测约 70 份缺状态行已在 `metadata` 基线；若本规则再报则与「零基线新增」互斥 |
| 完成态推荐 | 推荐写法用「已X」；便于日后正向枚举时与「未X」区分 | 本轮不做正向命中 |

**实现顺序建议：**（1）前 60 行找表头 `Status` → 违规；（2）找表头「状态」解析单元格——找不到则**跳过本规则**（交给 `metadata`），不报 `status-vocab`；（3）对单元格先做版本段排除，再跑大小写敏感＋词边界 deny-list。

## 4. 执行点选择：Lint 还是 Hook

### 4.1 逐维度对比

| 维度 | Lint（`lint:spec-docs`） | Hook（`.claude/` / `.codex/`） |
|---|---|---|
| 能否阻塞 | **能**，exit 1 | 不能，只是 `systemMessage` |
| 覆盖写入路径 | 全部 | 仅 agent Edit／Write |
| 可审计 | 退出码 + 违规清单 | 无 |
| 可测试 | 有单测 | 无 |
| 配置份数 | **1 份** | **N 份** |
| 生效时机 | 事后（commit／CI） | 当场 |
| 绕过成本 | 改基线（只减不增，需批准） | 直接忽略提示 |

**结论：Lint 是硬门禁。** Hook 本轮不做（§0 C8）。

### 4.2 若日后加 hook 的硬约束（记录，本轮不实施）

> **hook 命令体只「指路」，不复述词表。**

仓库内 `.claude/settings.json` 与 `.codex/hooks.json` 已有逐字复制反例；词表进 hook＝第 N 份口径。

### 4.3 CI 接入现状：一个必须先修的前提

```bash
grep -rn "lint:spec-docs\|lint:spec\b" .github/workflows/
```

现状：

- `.github/workflows/lucy-release.yml:86` → `npm run lint:spec-docs` ✅
- `.github/workflows/lucy-ci.yml:70` → `npm run lint:spec` ✅；**无 `lint:spec-docs`** ❌

即 `lint:spec-docs` 目前是**发版流水线**的门禁，不是 PR CI 的门禁。

#### 4.3.1 这个缺口已经发生过一次（2026-11-22 实证）

本次建议书落盘时跑 `npm run lint:spec-docs`，**HEAD 已经是红的**：

```
docs/plans/lucy-20261122-prepack-closure-multi-agent-plan.md [plan-parts] …
docs/plans/lucy-20261122-prepack-closure-multi-agent-plan.md [metadata] …
```

该文件由 `d4615f8e` 提交进 HEAD，已跟踪、不在基线内。能进 HEAD 而没被拦，**正是因为 `lucy-ci.yml` 不跑 `lint:spec-docs`**。

两个接入方案：

| 方案 | 优点 | 风险 |
|---|---|---|
| **A. 新增独立 script `lint:status-vocab`，只挂 `lucy-ci.yml`** | 风险低；不牵动其余形态规则 | 须与 `lint-spec-docs` **共用同一规则实现**，禁止第二份禁用词表 |
| B. 把整个 `lint:spec-docs` 挪进 `lucy-ci.yml` | 一步到位 | 可能一次性冒出既有形态违规。**属独立一件事，不与本次混做** |

**建议取 A。**

### 4.4 防线分层（v0.2）

| 层 | 机制 | 定位 | 建议 |
|---|---|---|---|
| **L0 事前** | `docs/specs/_TEMPLATE.md`（若采纳） | 新文档起点带中文状态占位 | **有条件采纳**：须先定模板不被 `filename`／`index`／`close-layer` 误伤（排除名、或不进 `docs/specs/` 扫描名、或索引特例）。不是「几乎零成本」 |

| **L2.5** | `lint:status-vocab` 挂进 `lucy-ci.yml` | 不等到发版才拦 | **必需**（方案 A） |
