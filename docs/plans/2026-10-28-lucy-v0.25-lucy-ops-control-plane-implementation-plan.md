## 1. 目标与实施原则

把当前只能从 WebUI 点击、且一次只能操作一个对象的运维管理动作，暴露为 **Agent 可直接调用的 MCP 控制面工具**（`lucy_ops_*`），支持一次调用处理一批对象。

首期交付三个工具：

1. `lucy_ops_connection_tables` —— 启用表范围 / 移除 Schema 的批量配置；
2. `lucy_ops_source_import` —— 源表语义导入 / 校验 / 版本回滚的批量执行；
3. `lucy_ops_semantic_publish` —— 语义发布的批量发布通道（工作流 W-B）。

实施原则：

- **复用既有服务层，不另建并行引擎**：控制面是「调用通道」，不是能力本身。批量校验必须复用 `runSemanticTableCheck`（`webui/server/semantic-checks.ts`），发布必须复用 L25-11 的发布服务与协调器。
- **身份与授权分离**：控制面授权（`role.allow.ops`）与数据面授权（`role.allow.tools`）是两个独立维度，互不影响；未显式授予即为拒绝。**授权判定逐条 grant 进行，不跨 grant 拼接。**
- **保留 preview→commit 两段式**：不提供跳过人工复核的直写旁路。commit 必须消费已预览的计划与确认摘要。
- **效果确认先于成功记录**：写入与生效确认完成后才写 committed 审计与幂等终态；失败可定位、可重放，失败痕迹不被覆盖。
- **键分层**：业务幂等键（跨重放稳定）与审计事件键（含 attempt）分离，二者不得复用同一列值。
- **锁顺序固定**：`withKtxYamlWriteLock → withDisplayWriteBarrier → withPublishCoordinator`，与既有实现一致，不得颠倒。
- **不越界**：不改 L25-11 的冻结合同与其状态行（**唯一例外是经 PM 授权的状态行陈述更正，已于 2026-10-28 完成并记于该 Spec §1.5**，不构成实质修订），不顺带修它的遗留缺陷，不改 KTX 源码，不新增 REST 批量端点。
- **任何实现完成声明均不自动等于 VOPS 验收或客户交付通过。**

## 4. 分阶段实施

### S1 控制面骨架与授权模型

1. `ToolClass` 增加 `ControlPlane` 态；`classifyTool()` 对该态返回新分类，**未登记工具仍 fail-closed**。
2. **改通 MCP 发现与判权路径（G12）**：`absoluteDenyOrUnclassifiedReason` 不再把控制面判为未分类；`allowedToolNames` 新增控制面分支（可见性只取决于 `allow.ops`，**不要求数据面能力**），且必须**先于** `lucy_` 前缀分支判定，避免 `lucy_ops_*` 被误要求数据能力；`defaults.known_tools` 登记；控制面判权路径同样执行全局 `deny_tools`。
3. 定义控制面工具描述结构（工具名、适用域、是否连接域、是否 owner-only、读/写），首批登记三个首期工具。
4. **三份 schema 同步（G3）**：`proxy/identity.ts`、`admin/agents.ts`、`admin/access-config.ts` 均新增 `role.allow.ops` 与 `user.delegated_from`；**`admin/roles.ts` 的 `allow` 键白名单放行 `ops`**，且规范化输出保留控制面字段。
5. 实现 `ops-grants.ts`：多角色并集、**单条 grant 完整匹配**（工具 + 域 + 连接三项须来自同一条 grant）、域覆盖判定、连接域 fail-closed、`*` 禁止；判定结果区分三种不匹配原因。
6. 实现 `ops-delegation.ts`：`delegated_from` → `admins.yaml` 解析；委托人非 owner / 未启用 / 不存在 → owner-only 操作拒绝；委托**只提升 owner-only**，不扩大已声明域与连接范围。
7. **补委托与 Token 的 owner 门禁（G13）**：设置/修改/撤销 `delegated_from`、为 owner 委托的 Agent 签发 Token、修改含 owner-only 工具的 role、修改 Agent 的 `role`/`roles`/`allow.ops` —— 全部 `requireOwner`。
8. 扩展 `ConfigAuditActorType`，控制面来源有独立取值；审计可区分 Agent 来源与委托人。
9. 扩展 `scripts/lint-spec.mjs`：`allow.ops` schema 校验（含 `role`/`roles` 互斥）与工具分类一致性校验。
10. 确认控制面工具**不出现在数据面行级策略强制过滤路径**（`proxy/row-policy.ts`、`forcedFilters`）。
11. **逐对象授权判定（N02 回归防护）**：grant 匹配必须**逐对象**进行——对每个目标对象，存在**一条自身完整匹配**（工具 + 域 + 该对象连接）的 grant 即授权该对象。**不得**要求单条 grant 覆盖整批（那会把「A grant 授连接 A、B grant 授连接 B」的合并调用误拒）。禁止跨 grant 拼接（不得用 A grant 的域配 B grant 的连接）。

**退出条件**：VOPS-01–VOPS-08、VOPS-22（公共归因段）、VOPS-26、VOPS-27、VOPS-33、VOPS-34、VOPS-36、VOPS-42、VOPS-47、VOPS-48 有直接测试证据；未授予 / 越权 / 委托缺失 / 跨 grant 拼接四类负向路径全部可区分，且多 grant 多连接的合并批量调用可正常放行。

### S2 控制面调用框架与批量编排

1. 实现 `ops-tools.ts`：参数校验（`targets`、`dry_run`、`idempotency_key`、`plan_id`、`confirm_digest`）、统一信封、工具描述生成。
2. 实现 `ops-idempotency.ts`：**独立业务幂等存储**——`operation_key` / `target_key` 的原子认领、查询、终结；**认领先于任何正式效果**；崩溃后可判定「意图已存在但效果未确认」并进入核验分支。
3. **键分层落地（R10）**：配置审计行的 `idempotency_key` 列填**含 attempt 的审计事件键**；业务幂等记录存于独立存储。二者不得复用同一列值。
4. 实现 `ops-batch.ts` 通用编排：preview（逐目标 before/after 与 blockers、持久化 plan 与 planDigest、30 分钟有效期）、commit（过期 / digest 不符 / actor 不符 / 工具不符 / 确认摘要不符 → 拒绝）。
5. **重放顺序（R09）**：commit 先定位并核验已有幂等记录，对已 `succeeded` 目标直接返回原结果；**只有尚未执行的目标**才做基线比较与计划有效性检查。
6. 部分成功可重放：单目标失败不阻断其余目标；失败目标保留原因码与阶段；重放复用 `target_key`，不产生重复副作用；**重放成功追加 target 级审计，不覆盖首次失败行**。
7. 实现 `ops-audit.ts`：operation 级 1 条 + target 级 N 条（每目标每次尝试一条）；`writeStatus` 走 `pending → committed / failed`。
8. 实现 `ops-locks.ts`：固定锁顺序封装；协调窗口占用时返回稳定 busy 原因码，**不自旋、不排队**。
9. 接入审计事件分类与用量计量。
10. **计划对象再授权（R01）**：commit 阶段必须以**计划内对象**（`plan.perTarget`）重新执行 §6.1 步骤 3–8 的授权判定，并与调用方提交的对象集比对；权限收窄后旧计划不可提交。
11. **崩溃恢复收敛（N07 / R08）**：实现 `recoverPending`——按「全部已成功 → 补记 operation 终态；部分已成功 → 只继续未终结目标；已写入未确认生效 → 核验实际生效状态并补记或组回滚；不可判定 → 阻断并给稳定原因码」四分支收敛，**不得静默重跑**。幂等记录须持久化 `before`/`after`/`effect_phase`/`attempt`/`auditId`。
12. **幂等两级认领（R08 / N07）**：operation 键与 target 键**分别**原子认领，均先于任何正式效果；同尝试内审计状态按 `auditId` 更新而非重插（同键重插会被 `ON CONFLICT(idempotency_key) DO NOTHING` 丢弃）。
13. **preview / commit 摘要共用规范化载荷（N01）**：preview 与 commit 使用同一 `canonicalPayload` 计算摘要；preview 返回 `plan_id` 与 `confirm_digest`，调用方原样带回即可通过 commit 校验。
14. **组级状态机（N03 / F02）**：组级 prepare → 认领 → 执行 → 确认 → **统一终结**。组内任一成员**运行失败** → 该组全部 claimed 成员不得单独发布成功终态，必须先整组撤销并核验；撤销未完成则该组标记 `recovery_required`，不写任何成员终态并阻断该组读写。**不得出现「一败一成」**。
15. **target 级认领与 attempt 初始化（F03 / R08）**：operation 与 target **两级**原子认领，均先于任何正式效果；每次 attempt 都要创建并绑定 operation 级与 target 级 pending 审计行及其 `auditId`；`failed → 新 attempt` 的转换必须原子且保留旧 attempt 痕迹。
16. **恢复的排他所有权（F04）**：`recoverPending` 取得排他所有权后再恢复，排除仍在执行的活跃请求（并发同键返回 `ops_operation_in_flight`）；按持久化组日志恢复，先核验整组再统一更新成员、审计与 operation。
17. **重放子集与组完整性（F05 / F7-02）**：本次执行集 = 原计划 ∩ 本次参数；摘要仍绑定原计划；子集触及某组时该组全部未成功成员必须在子集内，否则拒绝；此前已成功的成员幂等复用，不进入基线比较与效果执行。**⚠️ 语义发布例外**：其执行集 = **整个已确认原子组**（完整影响集），不按参数收窄——批次索引整批生效，只执行子集会造成组不完整；语义发布已在适配器内完成完整影响集的授权确认。
18. **残留效果处置（F06）**：写盘成功但生效确认失败时，必须区分「无残留效果」与「有残留效果」；后者先核验并补齐生效或回滚，无法确认时保持恢复状态并阻断相关读写，**不得直接终结为可重试的 `failed`**。
19. **计划适配器（F01 / Q03）**：语义发布必须经计划适配器接入通用门禁——授权对象取**完整实际影响集**（`effectiveTargets` = candidates ∪ unrelatedDiskChanges，可能大于调用方提交的 targets），无法解析为受管对象时拒绝；语义发布不得另建授权、幂等或审计合同。
20. **⚠️ 目标结果四分类（Q01）**：实现 `ops-outcome.ts`——目标结果用 `kind` 区分 `succeeded` / `failed` / `pending_activation` / `recovery_required`，**判定成败一律读 `kind`，不得读 `ok`**；`pending_activation` 与 `recovery_required` 的 `ok` 恒为 `null`。组回滚**只**由 `kind == "failed"` 触发。
21. **⚠️ operation 级五态聚合与穷尽重入（Q02）**：operation 幂等记录同样使用五态，按 Spec §4.2 聚合规则由目标状态推导；重入分支必须穷尽五态——`recovery_required` / `pending_activation` **拒绝新 attempt**（返回 `ops_operation_recovery_required` / `ops_operation_pending_activation`），不得落入「当作 failed 重试」。
22. **⚠️ 非终态持久化（Q02）**：`pending_activation` / `recovery_required` 目标必须写入 `state` / `release_id` / `effect_phase` / `attempt` / `audit_id`；其审计行**保持 `pending`**（既不 `committed` 也不 `failed`）；operation 记录持久化聚合状态与未终结目标清单，作为恢复的唯一依据。
23. **⚠️ 认领与审计原子绑定（Q05）**：把「认领 + 写审计 + 绑定 `auditId`」实现为单次原子操作 `claimAndBindAudit`；恢复分支 0 按 `(opKey, attempt)` **查回**既有审计行后补建绑定，**不得重插**（同键会被 `ON CONFLICT(idempotency_key) DO NOTHING` 丢弃）。
24. **⚠️ 执行子集绑定 attempt（F5-02）**：子集计算与组完整性校验**前移到认领之前**（非法子集不得遗留 pending operation）；`execSet` / `groupIds` 随 attempt 持久化；恢复**只处理该 attempt 的持久化范围**，调用方本次参数不得扩大恢复范围（超出返回 `ops_operation_scope_mismatch`）。
25. **⚠️ 组执行异常边界（F5-03）**：逐组捕获 `executeGroup`、取锁与审计写入的异常——效果前异常 → 稳定失败 `ops_group_error`；效果后异常 → 进入核验 / 回滚 / 恢复分支，**不得判为失败**；一个组的异常不得中断后续组，已完成组结果不得丢弃；审计写入失败不得继续产生正式效果。
26. **⚠️ operation 状态聚合唯一化（F6-01）**：`aggregateOperationState` 只有一个实现，§6.2 的重入分派、终结与恢复后聚合**三处共用**；「存在未终结成员时不得转 `failed` 终态」；成员状态出现五态之外的值 → 返回 `ops_state_corrupt`，**不得**当作失败重试。
27. **⚠️ 同一原计划可分多次提交（F6-02）**：区分三个范围——`plan.perTarget`（原计划全集，operation 的成员集合与请求合法性边界）、`execSet`（本次 attempt 的执行范围，认领与恢复按它）、`opRec.execSet`（上一 attempt 的范围，**只**用于恢复，**不得**限制新 attempt）。首次只提交 A 成功后 operation 保持 `pending`；随后可提交 B 且不重复执行 A；全部成员终态后 operation 才终结。
28. **⚠️ 唯一 Outcome 构造器（F6-06）**：所有分支经 `Outcome.succeeded / failed / pendingActivation / recoveryRequired` 产出结果，`kind` 与 `ok` 始终成对；`keep=` 保留既有字段（如 `release`）；**任何分支不得只改 `state` 不改 `result`**。
29. **⚠️ 认领与审计绑定的事务边界（F6-07）**：明确业务幂等存储与配置审计表**同库不同表**，`claimIdempotency + claimAndBindAudit` 与 target 级 `claimTargetAndBindAudit` 均在**同一事务**内完成；若不具备同事务能力，**必须删除「原子」声明并完整定义每个崩溃窗口的补建协议**。
30. **⚠️ 非终态收敛入口（F6-01 / G33）**：实现①按 operation 记录扫描**非终态** operation 的恢复扫描入口；②把 release 终态回写到目标与 operation 的收敛路径；③收敛动作的排他所有权；④收敛后按 `auditId` 更新既有审计行。既有 release 状态查询端点**只返回记录、不会回写控制面状态**（`webui/server/index.ts:2409-2422`），不能充当收敛入口。
31. **⚠️ 组级异常边界扩到撤销与核验（F6-05）**：try 边界覆盖「执行 → 撤销 → 核验 → 结论持久化」整条组内链；**锁必须覆盖到撤销与核验完成**，回滚不是「锁外补偿」。
32. **⚠️ 既有成员状态必须完整恢复（F7-01）**：C5 加载既有 target 记录后，**完整保留**其持久态、`attempt`、`result` 与 `auditId`；既有状态不在五态之内 → 立即 `ops_state_corrupt` 拒绝；**不得**把既有失败成员改成「未执行」（会抹掉失败痕迹并让全集聚合出错）。
33. **⚠️ 失败成员可单独重放（F7-01 / D3）**：`failed` 成员可在新 attempt 中重新认领执行；旧 attempt 的失败审计行**保留不动**（`audit_key` 含 attempt，天然不覆盖）。C4.1 的「可继续执行成员」= 未执行（`pending` 且 `attempt==null`）∪ 已失败（`failed`）；已成功成员幂等复用，不重复执行。
34. **⚠️ 执行态与持久态分离（F7-07）**：`claimed` 只是内存执行态，**不落库**；落库持久态写 `pending` 且 `attempt = <attempt 号>`。废止 `skipped` / `reused` 残留（伪代码、持久化字段、断言中均不得出现）。聚合函数只接受持久态，收到执行态或废止值 → `ops_state_corrupt`。
35. **⚠️ 异常协议覆盖认领与终态结算（F7-04）**：target 认领 + 审计绑定（同一事务）、终态审计更新、target 终结、operation 终结/进度写入**全部**纳入异常协议；任一失败转入可恢复路径（`recovery_required` + 阻断），**不得**静默吞掉，**且已完成组的结果必须保留并返回**。
36. **⚠️ 恢复分支保留既有结果字段（F7-05）**：C6 的**全部**结果重建分支一律用 `Outcome.recoveryRequired(keep=existingResultOf(t), ...)`，不得把 `release` / `activation` 降级塞进 `detail`。
37. **⚠️ operation 与 attempt 的审计关系（F7-06）**：一个 attempt = 1 条 operation 级审计 + N 条 target 级审计；**多个 attempt 各有各的 operation 级审计行**，不存在「挂到全集完成才终结」的一行。attempt 之间不互相改写对方的审计行；含非终态成员的 attempt 行保持 `pending`，且因「非终态 operation 禁止新 attempt」，该行必有恢复路径负责闭合，**不产生悬垂 pending 行**。
38. **⚠️ 恢复合同单一化（F7-10）**：`recoverPending` 返回信封 `{ operation_state, recovered, still_unfinished, next_submit_required, next_submit_hint }`；恢复**只收敛已认领未终结的成员**，**绝不执行任何新的范围**；剩余成员必须由调用方**再次提交**才执行。

**退出条件**：VOPS-09–VOPS-16、VOPS-21、VOPS-23–VOPS-25、VOPS-31、VOPS-38–VOPS-40、VOPS-46、VOPS-49、VOPS-51、VOPS-52、VOPS-57、VOPS-58、**VOPS-59、VOPS-60、VOPS-62、VOPS-64、VOPS-65、VOPS-70、VOPS-71、VOPS-72、VOPS-73、VOPS-74、VOPS-77、VOPS-78** 有直接测试证据；各崩溃点收敛路径有直接证据（复用／补记／组回滚／阻断四分支），并发同键不进入恢复，两种锁占用行为可区分，**受理态不触发回滚、不终结**且非终态在进程重启后仍可判定。

10. **⚠️ 受理态不得当作成功或失败，且 release 是【两个独立轴】（Q01 / F6-06 / G28）**：发布返回的是**受理态**——源码明确「`reindexing` is NOT 已生效」（`semantic-assets.ts:2615-2619`）。release 有两个**相互独立**的字段（`webui/server/semantic-release-status.ts:10-29`）：
   - `recoveryRequired`（`true | false | "unknown"`）：是否存在需要人工核验的未完成回滚；
   - `activationStatus`（`unconfirmed | confirmed | unknown`）：是否**已知** Agent 能读到新语义。

   源码列举的组合（`semantic-release-status.ts:14-19`）：reindex 失败 → `recoveryRequired=false` + `unconfirmed`（文件已保留）；回滚失败 → `recoveryRequired=true` + `unconfirmed`（文件半写）；完整发布 → `false` + `confirmed`。**必须先判恢复义务、再判生效状态**：`recoveryRequired == true` → `recovery_required`（不得回滚——回滚会二次破坏；不得终结）；否则 `activationStatus == "confirmed"` → `succeeded`；其余（含 `reindex_failed`）→ `pending_activation`（`kind`，`ok = null`，**不回滚、不终结**），等待 release 终态回写收敛。
12. **⚠️ 执行集 = 整个已确认原子组（F7-02）**：语义发布的执行集**不是**「计划 ∩ 参数」，而是**完整影响集 `effectiveTargets`**（= candidates ∪ unrelatedDiskChanges）。原因：批次索引整批生效，附带的其他待生效磁盘变更与本批候选同批写入；只执行子集会造成组不完整而被拒。控制面按**两个范围**处理——`requestedRefs`（调用方声明，须属于批次 `refs`）与 `effectiveExecutionSet`（实际写入，须整体授权）。`U` 中存在未授权对象时**在认领前**即拒绝。
13. **⚠️ staged 批次归属与消费（F7-03 / D8）**：底层读计划严格校验批次 actor 与 instance（`webui/server/semantic-assets.ts:2941-2950`），既有 staging 走管理员身份（`webui/server/index.ts:2188-2216`、`security/request-actor.ts:64-80`）⇒ **Agent 无权消费管理员创建的批次**。首期设计：**只允许消费本 Agent 身份创建的批次**；跨操作者 / 跨实例消费一律拒绝（`ops_batch_not_owned`）；**不得**伪装 actor、删除底层校验或以管理员身份代读。D8 未拍板前本阶段保持未开始。
14. **同键重放返回原 release（N06 / F5-07）**：包装层必须**先**按受信 actor + 幂等键 + 确认摘要查询既有操作，再读取 validation/plan；底层发布在读 snapshot 之前就做幂等查询，正是为了让成功后的重放返回同一 release 而非撞 `snapshot not found`（`webui/server/semantic-assets.ts:2190-2223`）。**计划过期拒绝只适用于「尚未发生任何执行」的新提交**；已有 operation 记录的重放必须用其**持久化的计划对象**再授权后复用或恢复，**不得**因计划过期或快照已删（成功后 `:2657-2658` 删除快照）而把合法重放变成「找不到计划」。

**退出条件**：VOPS-20、VOPS-28、VOPS-35、VOPS-43、VOPS-50、VOPS-56、**VOPS-59、VOPS-61、VOPS-63、VOPS-68、VOPS-69、VOPS-72、VOPS-75、VOPS-76**、VOPS-22（W-B 发布归因段）有直接测试证据：语义发布的阻断语义与部分成功工具族明确区分，同键重放返回原 release，语义发布经计划适配器走通用授权与幂等门禁，**preview 返回的 `plan_id` 确为既有 staged 批次的 `validationId`（非 `taskId` / `operationId`）**、**未授权连接上的附带待生效磁盘变更会阻断发布**、**真实调用链可受理且不自报 busy**、**受理态不回滚不终结且 `recoveryRequired` 优先于 `activationStatus` 判定**、**计划过期后的成功重放仍返回原结果**、**执行集不被参数收窄**、**跨操作者批次消费被拒**。

| **VOPS-72** | **S2、S5、S6** | **结果字段完整一致**：唯一 `Outcome` 构造器；`kind` 与 `ok` 成对；release 先判 `recoveryRequired` 再判 `activationStatus`；成功路径保留 `release` 不覆盖（F6-06） |

每项状态只能记 `passed / failed / not_run / blocked_environment`，另将交付依赖标为 `blocked_delivery`；不得以「代码已覆盖」替代实际执行证据。**每项 VOPS 必须在对应阶段的退出条件中被覆盖**——阶段退出条件与本表必须逐项对应，不得出现「表里有、阶段里没有」的验收项（首轮即因此漏掉 VOPS-31 与 VOPS-42）。

## 6. 完成定义与非目标复核

### 6.1 实现完成

- 控制面工具分类、发现、授权判定、委托校验与 fail-closed 行为按 Spec 落地，且**不绕过全局 deny 与数据面门禁**。
- 授权判定**逐对象**进行：多 grant / 多角色的合并批量调用不被误拒，同时不出现跨 grant 拼接。
- commit 阶段对**计划内对象**重新授权；权限收窄后旧计划不可提交。
- 幂等在 operation 与 target 两级原子认领，均先于正式效果；崩溃后有可执行的收敛路径，不静默重跑。
- 业务幂等键与审计事件键分离；同尝试按 `auditId` 更新，重放另建 attempt，失败痕迹不被覆盖。
- 批量写与**旧写入口**在同一把 `withKtxYamlWriteLock` 内互斥；锁占用语义按队列 / 拒绝分别定义。
- 组划分按实际写集交集；组内全成全败，组级回滚不撤销他组记录。
- 批量编排具备 preview/commit、逐目标幂等（含认领先于效果）、部分成功可重放、双层审计与键分层。
- `ktx.yaml` 批量为一次合并写，全链在同一把写锁内，整批在一个显示写屏障窗口内完成。
- 源表批量导入按**同写集原子组**执行，组级回滚可恢复，失败无半写。
- **目标结果按四分类 `kind` 判定**（succeeded / failed / pending_activation / recovery_required），**不以 `ok` 二值判定**；受理态不回滚、不终结。
- **operation 级五态聚合与穷尽重入**：`recovery_required` / `pending_activation` 拒绝新 attempt；两种非终态在进程重启后仍可判定。
- **执行子集绑定 attempt**，恢复不越界；非法子集不遗留 pending operation。
- **组执行有异常边界**，效果后异常进入核验 / 恢复分支而不判为失败。
- **语义发布锁由底层独占**，控制面不外层再取；授权基于 `effectiveTargets`；**工具消费既有 staged 批次的 `validation_id`**，不把 check 产物当计划、不自建 batch 快照。
- **operation 状态聚合唯一化**：重入 / 终结 / 恢复后共用同一聚合函数；有未终结成员不得转 `failed`；未知状态显式拒绝。
- **同一原计划可分多次提交**：operation 覆盖原计划全集，attempt 覆盖本次执行范围；恢复不越界。
- **唯一 `Outcome` 构造器**，`kind` 与 `ok` 成对，既有字段不被覆盖。
- **非终态有收敛入口**（恢复扫描 + release 终态回写 + 排他所有权 + 审计更新）。
- **执行态与持久态分离**，既有成员状态完整保留，失败痕迹不被抹掉；失败成员可单独重放。
- **一个 attempt = 一条 operation 级审计 + N 条 target 级审计**；多个 attempt 各有各的审计行，无悬垂 `pending` 行。
- **语义发布执行集 = 整个已确认原子组**；`requestedRefs` 与 `effectiveExecutionSet` 分离。
- **staged 批次归属校验不被绕过**；跨操作者消费一律拒绝。
- **旧 Schema 移除纳入同一临界区**，版本历史裁剪延后到组终结之后。
- **三份 access schema 同步**，`roles.ts` 键白名单放行 `ops`，控制面授权可经正式角色保存路径落盘。
- 委托与 Token 的 owner 门禁到位；底层发布服务审计可区分控制面来源。
- 文档、术语、类型与验收追踪一致。
