## 1. 决策

1. 新建长寿命集成分支 `lucy-v0.25`，用于下一轮功能集成、回归和候选发版。
2. 该分支明确对应下一次产品发版 `0.25.0`；分支名称与目标产品版本保持同一 `0.25` 标识，避免与功能波次名称混淆。
3. 删除本地和远端的旧 `lucy-v2.5` 分支。删除前其指向 `ffeb1d1ef391da938b62fed6d472ea9e120d446d`；新分支不继承、不合并该旧分支的独有提交。
4. `main` 继续作为发布主线。日常功能先合回 `lucy-v0.25`，只有准备随 `0.25.0` 交付的批次才通过 PR 合回 `main`。

## 2. 版本切线例外

现行版本矩阵默认规定：普通客户可见交付将产品版本第二段 `+1`，大能力、破坏性配置或捆绑 KTX 主版本变化将第二段 `+10`。本次由项目所有者明确选择 `0.20.0 → 0.25.0`，作为下一次产品发版的一次性显式例外，不改写为普遍适用的 `+5` 规则。

本记录只确定下一次目标版本，不代表版本已经发布，也不允许在同一 `0.x` 版本线中倒退或复用历史版本号。

真正候选切线时必须：

1. 以仓库根 `VERSION` 为事实源，将 `0.20.0` 一次性切换为 `0.25.0`，并同步全部版本投影。
2. 收敛 CHANGELOG，并更新 `docs/governance/version-matrix.md` 与 `docs/runbooks/lucy-release-train-workflow.md`，登记本次例外及新的当前基线。
3. 通过 `npm run lint:version` 与 `npm run lint:version:test`。
4. 按发布台账规则建立 `docs/releases/v0.25.0.json`，完成 PR、Required checks、tag、Release 和实际交付物证据闭环；不得仅因分支或 tag 存在就宣称已经发布。

## 3. 开发期版本边界

开分支时不提前切产品版本。当前 `VERSION`、package、Docker、Helm 和 WebUI 版本投影继续保持已发布的 `0.20.0`，直到候选发版切线。

本阶段不创建 `v0.25.0` tag，不创建 GitHub Release，不新增已发布状态的 `v0.25.0` 台账，也不因开分支合回 `main`。

## 4. 后续开发规则

1. 单需求实现分支从 `lucy-v0.25` 切出，建议使用 `feature/lucy-0.25/<需求编号>-<slug>`。
2. 每项需求仍须先满足对应 Spec 的冻结与实现授权状态；位于本集成分支不等于自动获得实现授权。
3. 需求验收后合回 `lucy-v0.25`，不得把日常开发直接合回 `main`。
4. 缺陷、审计、文档和杂项沿用既有 `fix/`、`audit/`、`docs/`、`chore/` 命名。
5. 产品版本与 Docker、Helm Chart、纯 Manifest 等部署制品继续解耦；每种制品分别记录支持状态和门禁结果。
