### 3.2 每个 track 的共同交付要求

1. **实现而非骨架**：每个声明的执行项都要有可执行断言或明确的 `blocked` 判定逻辑，禁止只写文件不写断言。
2. **可跑合同级测试**：每个 track 至少交付一组**在本机可跑且通过**的 `node --test` 用例，覆盖该 track 的编号完整性、断言词汇合法性、状态判定语义、失败即停语义。
3. **不伪造验收**：任何执行项在本轮**没有真实运行证据**时，其状态只能是 `not_run` 或 `blocked`（带 `blockedReason`），不得写 `passed`。
4. **不碰冻结目录**：`scripts/e2e/contracts/case-catalog.yaml` 与 `case-catalog.lock.json` 只读。
5. **不碰并发文件**：见 §2。
6. **不提交**：所有 track 只在工作区交付，由协调者统一 commit。

## 4. s2：重建 Docker → 模拟用户 UAT → 测试报告

前置：s1 全部完成。

1. **重建镜像**：按仓库既有出包流程重建 linux/amd64 客户镜像（`lucy-amd64` builder + QEMU），过 G1–G4 硬门禁（含 `scripts/release/assert-image-elf-arch.sh`），**不推送 registry**（G-06 未解锁）。
2. **重建 compose 栈**：重建本地 compose 栈（含 Postgres 夹具库），确认健康。
3. **模拟用户 UAT**：以真实浏览器（桌面 Chromium）+ 真实 Agent 客户端（Claude Code，已登录）跑 `J25-01` 全旅程；按 `docs/qa/manual-gui-e2e-checklist.md` 补人工客户端证据位。
4. **输出测试报告**：报告必须分列 **实现完成／验收通过／客户交付通过** 三栏，`blocked`／`not_run`／`not_applicable` 单列，**不得聚合成通过**。

### 4.1 s2 的证据边界

- 真实 HS2／JDBC、真实客户 amd64 K8s、真实旧版升级、真实备份恢复在本地环境**不可得** → 对应执行项记 `blocked`（`environment`／`delivery`），报告不得声称通过。
- Docker 重建成功**不等于**客户交付通过；本地 compose 结果**不等于**正式 Kubernetes 交付证据。
