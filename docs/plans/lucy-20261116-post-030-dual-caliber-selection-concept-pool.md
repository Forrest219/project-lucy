## 概念摘要（非合同）

同一句「本月收入怎么样」，财务侧（如确认收入）与销售侧（签约／订货／回款等，须业务确认）常常不是同一件事。硬合成单一「标准收入」或系统静默选边，都会造成答非所问。

候选最小方向（建议书方案 B，**仅概念**）：在试点范围内登记**两条**业务已确认的独立收入定义；用显式意图、轻量域标签、受治理定义优先与歧义追问做选择；结果展示口径含义与版本；选择与权限分轨；质量只披露、不新增拦截。**不做**数值化 OntoRank／职级加权／流行度排序／SQL 自动学习口径平台。

### 评审意见留档（2026-11-16，概念评审；非 Spec 裁决）

**认同（保留进未来评审）**

1. 财务／销售收入同名异义是真实产品问题；硬 SSOT 或静默选边都应避免。
2. 结构化双口径 + 确定性规则（方案 B）优于纯 prompt 与完整排序平台。
3. 选择≠授权、质量只披露不拦截、标签错即失败（即使数字碰巧对）、角色不静默绑定——与 Lucy 既有原则同向。
4. 文档纪律（待评审／实施前门槛／示例≠生产公式）适合继续沿用到未来 Spec 起草。

**反对／保留（升 Spec 前必须处理）**

1. 与 P0-1「唯一表 + 固定口径」有哲学张力：双口径须落成**多个问题类型／多条 binding／独立 metric_id**，不得把「固定口径」冲成「会话内任选加工」。
2. Databricks 优先级场景是湖仓多定义排序；Lucy 已验证痛点是错表 + 临场加工口径——对象错位，不宜以「复刻 OntoRank」为动机。
3. MCP 主消费面更适合**硬门闩 stop**，不宜只靠对话追问。
4. 未与 P0-1／P0-3／P0-4 做差集前，独立「口径选择模块」有重复建设风险。
5. 「恰好两条」对财务（actual／forecast／budget 等）可能过窄；业务确认成本才是主要代价。
6. 部门／角色软提示仍有诱导错口径风险；更稳默认是无显式意图即并列候选并 stop。

**较贴 Lucy 的候选落点（供开线后选型，非已定设计）**

把「收入」拆成两个（或多个）已发布问题类型绑定 + 表／口径歧义时硬停并列 + 可核对块强制写出本次口径——用现有三件套表达「上下文最优解」，而不是另起一套会话态选择器或排序引擎。

### 升格门槛（未满足不得开 Spec／不得改代码）

1. 下一产品线已开线，本条已迁入该线执行总账（可标不入核心分母）。
2. 试点租户、两条（或 N 条）真实业务确认定义、适用范围与金标已书面关闭。
3. 与 P0-1／P0-3／P0-4（或其继承合同）的组合差集已写清：新增什么、复用什么、禁止什么。
4. 委托人立项并授权开 Spec（概念入池≠立项）。
