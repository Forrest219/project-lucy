## 2. 方案与取舍（D1–D5 已确认）

### D1：单表拒绝仍保持 400；增加可验证的表级错误细节（推荐）

保留 `READ_FAILED`、HTTP 400 和原文案。在 `error.detail` 增加可选 `tableRejection`：

```ts
{
  tableRejection: {
    scope: "table",
    table: "t0",
    reason: "permission" // 既有原因枚举的受限白名单
  }
}
```

- 仅实际 `read.rejections` 中**已判定为该表终态**的拒绝可产生该字段；普通连接失败、全局预算、平台鉴权、网络和未知故障不得伪装成表级拒绝。
- 首版白名单：`permission`／`missing`／`ambiguous`／`timeout`／`too_large`／`too_wide`。`unreadable` 兼有连接级含义，不进入可继续白名单；如需纳入须另给能区分作用域的合同与测试。
- `server/index.ts` 的 `supportedErrorDetail` 只放行 scope、表名与枚举，不泄露 SQL、driver stderr、连接密钥。伪造／缺字段／表名不匹配都应中止。
- 客户端只在单表批次收到 `ApiError.code=READ_FAILED` 且标记合法、表名等于本次请求时记录 failure，移出 pending，继续其余表。不能按中文文案正则或笼统 `catch` 判断可恢复。
- 普通单表用户仍看到原 400；401／403、会话过期、`STALE_RESPONSE`、未知 READ_FAILED、5xx 和断网仍按现有路径中止，不吞掉全局故障。

备选：新增批量意图参数让单表也返回 200＋rejections，会扩大 API 输入及调用点改动；直接放开所有单表 200 会改变 LS-08。两者均不采纳。

### D2：按进展保证有限收敛，移除全局 100 次硬上限（推荐）

对有效唯一表集，设 N 为表数。每轮先校验请求表的结果划分，保证无遗漏、无重复归属、无越界表；再更新终态集合。

```text
pending = 请求表集；batchSize = 50；readSet = {}；failureSet = {}
while pending 非空:
  batch = pending 前 batchSize 张
  try: response = 真实预览 HTTP(batch)
  catch error:
    若单表且是 D1 可验证的表级拒绝: 记 failure；移出该表；继续
    否则: 原样失败关闭
  校验 columns / rejections / deferred 对 batch 精确划分
  读到字段或明确 rejection -> 移入唯一终态集合，移出 pending
  若无终态且 batch.size > 1: batchSize 必须严格减半（最小 1）
  若单表 deferred: 同一表连续两次后记失败；第一次允许再读一次
  合并实际字段；进度 = readSet.size + failureSet.size
最终有失败则汇总一次；无失败才返回成功
```

有终态时 pending 严格减少；无终态的大批次严格缩小；单表最多两次无进展后终止。由此请求次数有界，保守分析上界为 `2N + ceil(log2(min(50,N)))`（N>0）；它是算法证明／检出断言，不以与输入无关的常数中止合法任务。LS-19 的特定 50×400 夹具仍保持 ≤100 次，不把这一场景阈值推广成全局产品上限。

不得自动扩大单请求时限来补救；不得用自动重新增大批次引入新的振荡路径。正常快速夹具的既有 60 秒总耗时合同保持；故障注入变体的注入耗时、恢复后耗时与总时长单列，不能借变体放宽正常门槛。

### D3：修复复验使用新候选身份，不覆盖历史复现场景

新增 `UAT-FDE-FIX-*` 模式。原 `UAT-FDE-R0` 及历史 cases 继续服务旧 3b1c62af 与三个基线的复现；修复模式要求包含 d8c3f097 及本次整改的干净完整 SHA、`gitDirty=false`、固定 image ID、运行文件哈希和隔离夹具。

原始红证据可引用准确 SHA 的已有记录；不为关闭旧 R0 强制每次重建全部历史基线。原断言在修复前 d8c3f097 上先红、修复后同断言转绿；新增防回退对照不强求先红。任何历史差异不得靠改低期望消除。

### D4：当前 demo 的审计证据缺口单独处理

当前 demo 正式导出因 `attribution_journal_baseline_unknown` 失败关闭，lag=0。它不是 F01 旧 lag 误拒。本计划先用**独立干净运行时**通过正常初始化与真实调用形成完整账本／投影基线，再验证正式 CSV／ZIP；不写假基线、不补造历史、不更改真实 demo。

若干净实例仍无法经正常初始化建立基线，UAT-FDE-FIX-01 必须 FAIL／BLOCKED，登记同一 P1-57-G6 发现后回到设计裁决；不得用 mock 或 diagnostic 代替正式导出。对外只证明此候选在受测完整基线实例可交 FDE 复验，不宣称旧 demo 数据已修复或产品已发布。

### D5：真实 lab 无法自然触发时的受限故障注入（已确认）

既有授权中的「延迟注入代理」不自动包含伪造 SQL 错误。建议本次一并确认一个**仅沙箱、受控降级**的兜底：先记录全真构造尝试；若 lab 方言不能自然产生 F02／F03 的慢语法拒绝，或元数据权限只隐藏表而不返回拒绝，则允许代理仅对指定测试请求／指定 t0 注入明确的语法拒绝或表级权限拒绝及延迟。最终合法语法与其余合法表的字段仍从真实数据库读取；不得伪造成功字段、截断标记、投影、HTTP 或客户端结果。严格固定规则、命中次数、关联用例与撤除步骤。

该项**已由委托人本轮明示授权**，只在全真构造无法实现并留证后使用。结果必须在 case／run／INDEX 标「受控降级」，与全真验证分列；不据此宣称真实客户驱动兼容。如不确认 D5、真实构造也失败，则对应项维持 BLOCKED，不降低期望求绿。F01 的投影进度替身仍按已有独立授权先全真后降级，不与 D5 混为同一授权。
