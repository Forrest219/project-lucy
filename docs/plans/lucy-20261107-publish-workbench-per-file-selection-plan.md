## 目标

把 REQ-030-001 从「池内登记」推进到「可实施的功能合同」，并且在开工前把两件最容易出错的事先钉死：

1. **把「索引实际影响」与「确认面」绑成同一个可验证事实**。现行 `POST /api/semantic-assets/reindex` 是整批语义：`reindexProject` 跑的是无范围参数的 `ktx admin reindex`（`webui/server/ktx.ts:186-213`），索引前 `prepareSemanticLayerForKtx` 会把**整个内容根**无过滤 upsert 进兄弟视图（`webui/server/ktx.ts:131-140`、`webui/server/content-mirror.ts:156-181`）。本条要在**兄弟视图这一层**把索引真正读取的字节集合收缩到「已发布基线 ∪ 勾选范围」，并让逐路径摘要一致成为验收项（SC-03）。
2. **把现行「整批同步、不可分文件勾选」的合同显式修订掉**，而不是绕过去。需求池硬约束 3 要求逐条修订或取代（Spec §8 的 R1–R21），其中 R8／R9 直接触碰 20261030 §3 的「不引入分文件选择发布」与「不能用本页范围缩小索引实际影响」。

**不做**：不做「选了但不生效」的半真半假交互（SC-13 为否定式验收项）；不把「仅审阅聚焦多选」写成已交付分文件发布；本轮不做同页条目阴影一致性等视觉 polish；不改 KTX 上游；不新造第二套发布引擎。

## 开工前置

开工前必须全部满足，缺一项即停：

1. **开工授权**：PM 评审通过 Spec 与本 Plan 并明示授权实现。未授权前 S1 之后的任何步骤都不得开始。
2. **合同修订批准（硬前置）**：Spec §8 的 R1–R21 **逐条**获 PM 批准并落成对既有 Spec 的显式修订（尤其 R8「取代 20261030 §3 的不引入分文件选择发布」与 R9「保留禁令＋补判别口径」）。未批准即开工，等于 silently 绕过现行合同，本条直接判不成立。
3. **术语登记**：本条新术语（本次勾选范围／索引消费范围／未选中项／有效内容集合／分文件发布）先登记进 `webui/docs/00-product-terminology-standard.md` §4.3，并同步改写 `Sync Change List` 行与 `docs/qa/selector-contract.md` 的 `workbench-batch-sync-hint` 契约。先实现后登记属术语违规。
4. **上游能力核实（可改变设计）**：向 KTX 上游确认 `ktx admin reindex` 是否存在范围／路径过滤参数。本仓内**已枚举 9 处**调用，形态有三种（裸 `reindex`／`--force`／`--json`｜`--force --output json`），**九处均无范围／路径参数**，但**上游能力现状未核实**（Spec §1.4）。若上游其实支持范围索引，Spec D1 的物化层可大幅简化，须回到 Spec 评审而不是在实现里临时改道。
5. **恢复侧支持度核实**：打开 `webui/server/semantic-release-snapshots.ts` 与 `webui/server/semantic-release-restore.ts`，确认既有恢复预检／提交对「分文件批次」的支持度（Spec §1.4 记为未核实）。恢复侧若需改动，**单独走一轮 Spec**，不得在本条里顺手改恢复模型。
6. **布局事实确认**：确认目标部署形态下内容根与项目根**不是**同一目录。legacy 布局（`LUCY_CONTENT_ROOT=.`）下本条明确阻断（Spec D8），若客户现场正是该布局，本条不得开工，须回到需求池重判。
7. **批次归属确认**：本条预计改 `webui/server/publish-workbench-state.ts`、`webui/server/publish-impact.ts`、`webui/server/content-mirror.ts`、`webui/server/index.ts`、`webui/src/pages/publish/PublishWorkbench.tsx`。开工前对照 `0.30` 批次地图确认这些文件的归属，避免与在途批次抢同一文件。
8. **设计系统临时决策**：在 `webui/docs/design-system/99-governance.md` 登记左栏批量勾选控件的临时决策（设计系统无独立 checkbox 章节；既有复选框原语为 `.pl-checkbox`，`webui/src/app/app.css:632`），落代码前完成。

### 4.2 证据等级

- 本条收口证据以**本机自动化**（服务端／组件用例、真实进程内 HTTP 用例）＋**CI job** 两级为准。
- 「索引实际影响＝确认面」这一条**不得**用 mock 冒充：必须由**逐路径摘要比对**给出（对物化后的兄弟视图与「已发布基线 ∪ 勾选范围」逐条断言）。用「reindex 命令返回 0」代替这条断言视为未验证。
- 真实客户环境、真实 Agent 客户端、镜像构建与客户交付**不在本条出口**；需要时按 `docs/governance/DEVELOPMENT.md` 归发布取证层处理。
- 浏览器走查与视觉验收**不在本条出口**（Spec「闭口层级」），组件测试不能冒充视觉验收。

## 风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 半真半假 | 实现时把勾选做成审阅聚焦，索引仍整批 | SC-13 否定式验收；SC-03 逐路径摘要比对；S3 的「未调用全量镜像」断言 |
| 部分失败语义被做成分批成功 | 索引没有按路径撤销能力，部分成功不可回退 | Spec D5 写死整批失败；SC-09 四条失败路径各自为证 |
| 与既有恢复流程冲突 | 既有恢复围绕整批快照／镜像写集设计，分文件批次可能算不准「恢复到发布之前」 | 恢复侧支持度**未核实**；开工前置第 5 条先核实，恢复侧改动单独走 Spec |
| 索引与内容根漂移 | 兄弟视图停在「基线∪勾选」态；后续任一次 `prepareSemanticLayerForKtx` 会把兄弟视图拉回脏字节，执行面读到未生效口径而索引面没有 | 确认面与发布记录显式登记「未勾选项仍在待发布」；只读诊断暴露该态；「下一次整批同步收敛」写入文案；不得出现「已全部生效」表述 |
| 容器启动即整批重建索引 | `scripts/runtime/docker-entrypoint.sh:379-383` 在启动时跑一次 `ktx admin reindex`，会抹平分文件生效 | 在确认面与发布记录披露该边界；是否改启动路径由 PM 裁定，本条不擅自改启动脚本 |
| 合同被静默绕过 | 只改工作台不改 Spec 119／123／20261030／145 与术语标准，界面上出现勾选框而合同仍写「不可分文件勾选」 | S0 是硬前置：R1–R21 未批准即不得开工；S1 同步术语与选择器契约 |
| 基线合并推进写错 | `advancePublishBaseline` 是整表替换，合并写错会丢失其它路径摘要 | 合并表由服务端从基线＋勾选派生，不接受客户端提交；SC-10 推进后逐路径比对 |
| evals/skills 漂移被静默带入 | 不在勾选范围却会被整批索引消费 | Spec D9：分文件发布前必须确认这两个目录相对内容根无漂移，否则阻断 |
| legacy 布局下被降级成整批 | 内容根＝项目根时没有第二个面可暂存 | Spec D8 明确阻断并给可读原因；开工前置第 6 条先确认部署形态 |
| 与 `0.30` 其他批次争同一文件 | 本条改 `publish-workbench-state.ts`／`publish-impact.ts`／`content-mirror.ts`／`index.ts`／`PublishWorkbench.tsx` | 开工前置第 7 条确认文件归属；同一文件同一时刻只允许一个写入方 |

## 回滚

- S2–S7 均为服务端判定与界面改动，回滚＝还原对应提交，无数据迁移、无配置写入。
- 术语标准与选择器契约的登记项在回滚时同步撤回。
- 兄弟视图的物化态在失败路径上由 S3 的回退逻辑还原；回滚代码后若遗留物化态，须按既有镜像诊断路径处理，**不得**手工改写兄弟视图冒充一致。
- 本条不产生新的持久化状态目录；基线与 attempt 仍走既有 `.ktx-ui/publish-workbench/`，回滚不删历史证据。
