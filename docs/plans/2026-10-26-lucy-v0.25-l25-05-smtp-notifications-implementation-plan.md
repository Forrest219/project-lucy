## 2. S1.1 收口补丁（已实施）

### 2.1 背景

S1 最终复审把 F-21 标为「已关闭」，其关闭依据是「audit schema 3→4，notifier 初始化幂等创建 `audit_meta` 并以 `INSERT OR IGNORE` 登记版本、迁移说明和 `system:notifier-init`」。S1 签核后的代码走查发现三处未闭合：

1. **登记在入队热路径上**：`ensureNotificationOutbox()` 同时承担建表与 `audit_meta` 登记，而 `enqueueNotification()` 每次入队都调用它 ⇒ 每条通知都在 `audit.sqlite` 上多一次治理表写。
2. **两种语义挤在同一行**：`audit_meta.audit_db_schema_version` 是 PRIMARY KEY，被 notifier（schema bump 的 provenance）与 audit-trust backfill（`recordBackfillRun` 的运行记录）共同使用。后者用 `INSERT OR REPLACE`，必然覆盖前者那一行。
3. **无共存回归**：F-21 的断言只覆盖「notifier 独自写」，从未与 backfill 共存过。

### 2.2 口径裁定

**版本事实恒成立**：`audit_meta` 里存在 `audit_db_schema_version = <当前版本>` 的行，这个不变量在任何写者顺序下都成立——两个写者都只写同一主键、都不删除行。因此 F-21 的原始诉求（audit schema 3→4 有登记）**成立且可持续**，不存在「登记被抹掉后永不恢复」。

**真正要守的是**：版本行存在，且任一写者都不能把对方的记录擦成空。

| 写者 | 语句 | 语义 |
|---|---|---|
| notifier（`registerNotificationAuditSchema`） | `INSERT OR IGNORE` | 先到先得；不覆盖已有的运行记录 |
| backfill（`recordBackfillRun`） | `INSERT OR REPLACE` | 「最后一次迁移运行」拥有该行，符合其既有幂等合同 |

### 2.3 改动

| 文件 | 改动 |
|---|---|
| `webui/server/notifications/outbox.ts` | `ensureNotificationOutbox()` 只保留建表与索引（纯 schema 操作）；新增 `registerNotificationAuditSchema()` 承担 `audit_meta` 登记，并说明两写者语义 |
| `webui/server/notifications/init.ts` | 启动路径调用登记，独立 try/catch——登记失败**不得**关闭通知 |
| `webui/server/proxy/audit-write-health.ts` | 计时器回调早触发时**重排剩余窗口**而非静默放弃（见 §2.4） |
| `webui/server/__tests__/notifications-l25-05.test.ts` | 27 项（新增 3 项，见 §2.5） |

### 2.4 计时器窗口重排

S1 的计时器回调在 `current - since >= WINDOW` 不成立时**直接返回且不重排**。而 `ledgerFailureSince` 仍非空 ⇒ 后续 append 也不会再排新计时器 ⇒ **「账本挂了且之后没有任何 append」这一最需要通知的场景会静默丢通知**。

现改为：计时器到点即窗口成立；早触发则按剩余时间**重排**，直到窗口真正满足为止。失败与恢复两侧同构。

### 2.5 新增回归用例（含变异验证）

| 用例 | 锚定的行为 | 变异 → 结果 |
|---|---|---|
| F-14 启动路径同步登记 audit schema 版本与 audit_meta | 登记由启动路径完成，版本行存在 | — |
| **F-14 入队路径不写 audit_meta：登记不是热路径** | 入队不写治理表 | 把登记放回 `ensureNotificationOutbox()` ⇒ **转红**（`expected { audit_db_schema_version: 4 } to be undefined`） |
| **F-14 audit_meta 与 audit-trust backfill 共存：版本事实恒成立** | 版本行不被任一写者抹掉；重复登记不擦除 backfill 记录 | 登记改 `OR REPLACE` ⇒ **转红**（`expected 'system:notifier-init' to be 'operator:test'`） |
| **SMTP-08 计时器早触发时重排窗口，不静默放弃通知** | 早触发不丢通知 | 去掉重排 ⇒ **转红**（`expected [] to deeply equal ['audit_ledger_unavailable']`） |

> 每次变异精确只让对应用例转红，其余 26 项仍过——证明断言锚定的是被测逻辑，不是恒真。

## 3. S2 SMTP worker 与 API（本轮）

### 3.1 波次表与文件所有权

并行边界：**W2 只写 `webui/server/notifications/worker.ts`；W3 只写 `webui/server/admin/notifications.ts`；W4 只写 `webui/server/notifications/template.ts`**；W1 由主持者自持；W5–W7 串行收口。

| 波次 | 内容 | 退出条件 |
|---|---|---|
| W0 | 实施计划落盘（波次表、文件所有权硬约束、选型依据、验收矩阵映射、风险与阻断） | 本文件 §3–§7 |
| W1 | 传输层：SMTP 客户端封装、**强制 TLS／STARTTLS**、分阶段超时、封闭错误码映射、**不落 SMTP 对话与原始响应** | 传输层单测；无出网连接 |
| W2 | outbox worker：单 worker、单封在发、5 秒轮询、领取 ≤20、租约与崩溃重领、有界退避、sent／dead、过期转 dead、保留期清理 | worker 单测；at-least-once 语义有断言 |
| W3 | owner API：`POST /api/admin/notifications/test`（202 queued；**两类 503 分码**）、`GET /api/admin/notifications/:id` | 路由测试；401／403／404／503／202 齐备 |
| W4 | 固定模板与 Bcc：三种封闭主题、纯文本正文、实例显示名消毒、**地址只在 Bcc** | 模板测试；正文无地址／无凭据 |
| W5 | 集成：fake SMTP 协议测试（`smtp-server`） | SMTP-06／07／12～18／20 有断言覆盖 |
| W6 | Code Review：`code-review` skill ＋ 独立 `verifier` 对抗式审查 | 发现逐条处置并记录 |
| W7 | 汇总 → 交付审阅 → commit | 实施记录更新 |

### 3.2 S2 必须遵守的合同（摘自 Spec）

- **不等待 SMTP**：请求线程不等待发信；`POST /test` 返回 202 `queued`，**不得**显示「发送成功」。
- **两类 503 分码（F-15）**：配置不可用 ⇒ `NOTIFICATION_UNAVAILABLE`；队列满／outbox 不可用 ⇒ `NOTIFICATION_QUEUE_UNAVAILABLE`。
- **403 文案（F-16，已定稿）**：通知路由统一「仅所有者可管理邮件通知」，复用 S1 的 `requireOwner` 可选文案参数。
- **有界**：连接 10 秒／总发送 20 秒；退避 1m／5m／15m／1h／4h／8h／12h／24h；总尝试 ≤8；pending ≤1000；领取 ≤20；发送成功后才标 sent。
- **at-least-once（D04）**：SMTP 接受但未标 sent 时崩溃会重发，重复风险必须被测试并记录。
- **秘密与内容最小化（D09／§8）**：日志只含 notificationId、eventType、attempts、封闭错误码；邮件正文不含错误原文、host、username、密码、收件人列表、审计 diff、查询与表内容。

## 4. 依赖选型（已落定）

### 4.1 SMTP 客户端：`nodemailer@10.2.1`

| 维度 | 事实 |
|---|---|
| 许可证 | **MIT-0**（MIT No Attribution）——比 MIT 更宽松（免署名义务），但名称不是 MIT，交付前需在 SBOM／依赖说明中如实标注 |

**排除项**：`smtp-client@0.4.0`（2022-06 后无发版，维护状态不满足 Spec §1.1「维护中的 SMTP 库」）。

### 4.2 fake SMTP：`smtp-server@3.21.1`（devDependency）

| 维度 | 事实 |
|---|---|
| 许可证 | MIT-0 |
| 运行时依赖 | `nodemailer@10.2.1`、`punycode.js@2.3.1`、`ipv6-normalize@1.0.1` |
| 用途 | W5 的协议级测试服务端：4xx／5xx、超时、STARTTLS 升级失败等场景可控 |

## 6. S4 真实验收（⛔ 不启动）

Forrest 2026-10-26 裁定 **S4 本轮不启动**：无客户目标 SMTP，也无 linux/amd64 K8s 环境。

- **SMTP-26 保持 ⛔ blocked**，且 S1–S3 的单元与交付证据**不得**记作 SMTP-26 通过。
- S1–S3 的证据只能支持「实现行为正确」，不支持「真实链路已验证」。
- 解除条件：客户提供目标 SMTP（账号、地址、端口、证书链）＋ linux/amd64 候选镜像与 K8s 环境。

## 8. 风险

| 编号 | 风险 | 处置 |
|---|---|---|
| R-05 | 通知初始化失败拖垮启动 | `initNotifications()` 全程 try/catch，失败只关闭通知；登录／MCP／审计不受影响。**S1.1 追加**：登记失败亦只告警，不关闭通知 |

| **R-11** | **`audit_meta` 两写者竞争** | 版本事实恒成立；任一写者都不删除行；共存回归用例锁住该不变量 |

## 9. 实施边界

- **不连接任何 SMTP 服务器**，不打开出网连接，不发信（S2 只用本机 fake SMTP）。
- 不改 `security.sqlite`／安全库 schema 版本；不改 MCP／登录／权限合同。
- 不执行浏览器测试（仓库默认约束）。
- 不宣称 SMTP-01–26 任何一项验收通过。
- **S4 不启动，SMTP-26 保持 blocked；本轮不交付**。
