## 开工前置

### 2.1 通用前置（五条共用）

1. **开工授权**：PM 评审本 Plan 并明示授权执行。未授权前 A0 之后的任何步骤都不得开始。
2. **口径冻结**：每条验收执行前，须先实读该 Spec 的**头部「状态」行**与验收编号段，确认编号段未被后续修订改动过；编号对不上即停。
3. **证据等级**：按 `docs/governance/DEVELOPMENT.md`「证据等级门槛：本机 ＋ CI 即可」——验收证据以本机自动化 ＋ CI job 两级为准；只有客户目标服务、真实升级、真实备份恢复、现场实例或真实身份源才能取得的结论，归发布取证与交付层。**不得用 mock 或本地替身冒充客户环境结论**。
4. **缺陷出口**：验收发现真缺陷时，**不得在验收批次里直接改代码**。处置是：回 0.30 需求池登记新条目（写明缺陷、证据、影响范围），另走需求澄清 → 独立 Spec → Plan → 开发授权。
5. **状态同步**：任一条目在归属 Spec 里关闭时，须在同一次改动里同步**五处镜像**（Spec 头部状态行、Plan 头部状态行、`docs/README.md`、`docs/plans/README.md`、`docs/governance/project-overview.md` §9）**＋需求池条目状态**（共 6 处现值），并把需求池条目的状态改为对应现值。

### 2.2 REQ-030-014 的特殊前置（归属 Spec 已收口）

行权限视图 Spec（`lucy-20261030-row-policy-view-presentation-spec.md`，v0.6，SC-01–SC-30 已收口）**当前处于已收口态**。新增一条 templateRefs 验收项意味着该 Spec 要重开。处置：

1. **须 PM 明确批准重开**该 Spec（不得由执行方自行重开）。
2. 重开后，**新增的验收编号不得改动既有 SC-01–SC-30 的语义**，只能在尾部追加（现状值以 Spec 头部与 §7.1 为准）。
3. 重开与追加完成前，REQ-030-014 的验收**不得开始**。
4. **归口不变**：templateRefs 的语义仍属行权限视图合同，本 Plan 不另立新 Spec 承载它。
   ⚠️ **编号体系只认一套**：`RTV-01–RTV-08` 是**父 Spec** 的编号体系（`lucy-20261030-row-policy-view-presentation-spec.md:8` 明写「父 Spec 的 RTV-01–RTV-08 不在本条出口」，`:14` 明写「权威仍是 …§6.2、RTV-01–RTV-08」）；本条（呈现 Spec）自己的编号是 **SC-01–SC-30**。
   ⇒ 重开申请里必须指明**唯一归属**：新增验收项编入**父 Spec 的 RTV-01–RTV-08 体系**，还是编入**本呈现 Spec 的 SC 序列**（尾部追加）。**不得两套并列**，否则同一验收项有两处权威编号，实现方无从判断该改哪一处、断言该写在哪。

## 风险

| 风险 | 说明 | 缓解 |
|---|---|---|
| 验收编号段与现行 Spec 漂移 | 既有 Spec 可能已被后续修订改过编号 | A0 强制实读 Spec 头部与验收段，对不上即停 |
| 验收变成隐性改代码 | 发现缺陷就地修，绕过 Spec/Plan/授权四步 | §2.1 第 4 条把缺陷出口固定为「回池登记 + 另走四步」 |
| mock 冒充客户环境结论 | OIDC 真实身份源、SRR 真实备份恢复都需要客户侧条件 | §2.1 第 3 条的证据等级门槛；只有客户环境能证明的项归发布取证层 |
| 已收口 Spec 被随手重开 | REQ-030-014 归属 Spec 处于已收口态 | §2.2 写死「须 PM 批准重开 + 只在尾部追加编号」 |
| 把「验收通过」读成「可上线」 | 验收只是功能合同层的证据 | §4.2 明写「本 Plan 收口不表示任何功能已收口，更不表示可上线」 |
| 与其它批次争同一文件 | A 步骤的取证记录落 `docs/reviews/`，命名需唯一 | 取证记录文件名带条目号，避免冲突 |

## 回滚

- 本 Plan 只做验收执行与记录，不改运行代码、不改配置、不写业务数据。
- 回滚＝删除取证记录中不成立的结论条目，并把归属 Spec 的状态行改回原值，同时同步其余镜像。
- 若某步骤的取证依赖了临时脚本或夹具，随步骤一并清理，不得留在仓内。
