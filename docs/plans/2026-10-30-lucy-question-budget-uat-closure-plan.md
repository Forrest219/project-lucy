### R1 结算挂载点

改 `webui/server/proxy/mcp-proxy.ts` 里数据调用的预算结算，对齐 Spec §6.2。

- `res.finish` 仍是正常结束的结算点，按当时的单调时钟记账。
- `res.close` 只销毁在途上游请求，并记下客户端已断开。这里不调用 `settle`，也不清掉绝对执行时限的定时器。
- 上游请求在销毁之后发出 `close` 或 `error`，视为取消确认，再按确认时刻结算，并带上 `clientDisconnected`。
- 尚未捕获上游句柄时，没有正在进行的上游工作，按断开时刻结算。
- 取消一直没有确认时，沿用现有的 `QUESTION_BUDGET_ABS_EXEC_MS`（120 秒）定时器：封顶记账、释放在途槽、审计标记超时且取消未确认。不新增环境变量，不把 120 秒改短。
- `settle` 保持幂等。`finish` 与上游结束都触发时，只记一次。

用例放在代理测试，不放在只调用 `QuestionBudget.settle` 的结算层测试。上游用假的 HTTP 服务：客户端断开后，上游再过一段短延迟才结束。断言 `busyMs` 大于断开时刻、等于确认时刻。延迟用几百毫秒，不真实等待 120 秒。另用一条断言锁住：单纯的 `res.close` 不得清掉绝对时限定时器。取消未确认的封顶仍由现有 SC-14 覆盖。

### R2 不计预算的四类调用

在现有 MCP 测试装置上加一条，不靠 `isQuestionDataTool` 的布尔断言充数。

初态是全新作用域。依次调用一种协议方法、`lucy_catalog`、`lucy_skill_search`，以及对调用者 ACL 拒绝的 `lucy_read_source` 或 `lucy_query`。然后做一次该角色允许的数据调用。

验收：四类调用之后作用域仍未创建，或 `calls` 与 `busyMs` 仍为 0；第一次放行后 `calls=1`，`busyMs` 只含这一次。再测已有窗口：先放行若干次，再来一次 ACL 拒绝，`calls`、`windowId`、`round` 不变。

## 风险

- `res.close` 里若清掉绝对时限定时器，上游又不发出结束事件，在途槽会留到进程退出。R1 的断言专门锁住这件事。
- 正常结束和取消确认可能先后到达。第二次 `settle` 必须是空操作，不能把时长再加一次。
- 提前做 R4，会把还没核对的口径写成 Spec 162 的现行事实源。
- 共享索引只改问询预算这几句。其他条目的在途草稿不代改。

## 不在本方案内

- 重开 D1–D9，或改 20 次、120 秒、绝对执行时限的数值。
- `lucy_certified_route` 的 schema 与 connection 入参闸不一致。这是既有现象，实现记录已登记。
- 把续查生效从数据调用行改成另一条审计事件。SC-30 的验收句是「两条可区分事实，且能关联到该次数据调用」。现有形状若能对上这句，R3 照实记录，不改存储形状。
- 客户镜像、Kubernetes 交付、回改历史审计行。
