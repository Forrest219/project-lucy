## 已验证的结果

**未自然复现 FDE 所述 readyz 长期不返回及入口摘流型 503。** 本机实际出现的是 MCP 应用层预算 503、变更窗口的上游／恢复门闩拒绝，以及长尾。两种 503 的层级和证据不同，不能把本机应用层错误写成客户根因已经闭环。

- 1884 张真实 MySQL 物理表、1884 个 Manifest 条目，启用表数在 1883 / 1884 间交替，始终至少 1883。每表 3 列、4 行，1882 个 Overlay；短名修改选无引用的原始表，权限使用正式 V2 显式物理表清单。
- 12 个活跃合成 MCP 身份轮转，不关闭 ACL、预算或持久化失败关闭。独立查询 oracle 为总数 4、金额合计 100。
- **12 次真实校验、上传、保存、显式重载均成功**；保存确认及真实 KTX PID 变化留有回执。**8 / 12 次完成变更后的短名读取与恢复查询**，4 次在短名读取阶段返回 `503 audit_unavailable / question_budget_unavailable`，不能算整轮成功。
- 普通鉴权 HTTP：**3585 次成功、1 次 3 秒截止超时**。普通 MCP 数据查询：**481 次成功、8 次失败**；另 1 次停止时在途，后续回执保留为截尾样本，不计自然窗成功。变更周期里的额外握手／短名检查／查询另计，不混入普通查询吞吐。
- 普通 MCP 的 8 次失败为 6 次 `upstream_unavailable`、1 次 `semantic_recovery_required`、1 次稳态 `question_budget_unavailable`。前 7 次与写入／重载窗口相交；仍是用户可见失败，保留数量和耗时，不删除。加上 4 次恢复读取，共 **5 次预算相关应用层 503**。
- 普通 MCP 成功样本 p50 5.614s、p99 30.690s、最大 49.573s。完成的查询结果均核对 4 / 100；本轮未完成逐段链路归因，不能把全部耗时直接归给数据库或某一个 Lucy 函数。

过程进度中的 `mcp` 计数包含失败尝试，早期“成功数”标签不准确；上述数值按原始回执重算。原始进度、失败、停止后的 22 条事件都保留，未改写历史。原计划每 5 秒一个普通 MCP，但顺序工作线程受响应时长限制，实际完成约 0.136 次/秒，低于计划 0.2；不以闭环降速宣称达到吞吐目标。

## 原第一、二、三批对本问题的作用

- **第一批仍是直接修复诊断等待链路的必要措施**：内存探针、独立采集、真实取消和恢复已有小夹具证据；它不能让被其他同步工作或调度压力占住的主线程继续及时响应。本轮没有自然复现其原始挂起机制，1883表故障恢复仍缺控制证据。
- **第二批有助于削减并发资源峰值**，但一个任务内部同步段、普通MCP预算事务争用、重复元数据解析不会仅靠总容量上界消失。本轮未跑完整三类别饱和矩阵。
- **第三批改善TERM时在途业务和真实PID等待**，前次三轮真实查询排空已通过；它不消除稳态卡顿。配置重载另有生命周期，不能用TERM通过推导热重载已无中断。

先组合已有预算修复并验证，再按测得的剩余同步片段补齐，最后完成组合发布取证；不再以“三批都做了”推导所有503已经解决。客户根因仍需现场同窗的readyz完成／事件循环／容器配额／存储等待证据。
