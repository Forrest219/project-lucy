## UAT-OPS-STEP-R0

1. 记录容器名、WebUI／MCP 端口、git 版本、镜像摘要和内容根，不记录口令。
2. 在挡板关闭时请求全部 `/api/admin/ops-step-uat/*` 声明路由，均为 404；确认管理台可登录、MCP 可做一次只读问数。
3. 按 fixtures 开启挡板，确认挡板需要管理员鉴权。重置步骤账，验证 reset 不改变业务配置、审计水位和数据库表。
4. 创建重载、单表和 51 表批量夹具；验证真实 `lucy_ops_connection_tables` preview 可用，记录原 `enabledTables`。
5. 验证 `access_log` 与 `access_trace_span` 只读水位可查询；建立本套件的审计证据表。
6. 验证标准输出可按起始时间和 `op_id` 过滤，管理读接口可访问，真实前台浏览器为 1920×1080。

期望：以上全部成立才跑 01–08。任一真实夹具或审计水位不可构造则 BLOCKED，不得用 mock 凑绿。

## UAT-OPS-STEP-01

1. 记录日志与审计水位。调用真实诊断挡板，同时托住 `read_project` 和 `read_ktx_yaml` 10 秒，保存返回的 `op_id`。
2. 托住开始后 1 秒内读取该时间窗容器标准输出，按本次 `op_id` 过滤。
3. 同时请求存活与就绪探针，分别记录耗时和正文。
4. 等待自然释放，再读同一 `op_id` 的全部标准输出、文件行和管理读模型。

期望：

- 释放前两支均已有 `enter`，且两支都没有对应 `leave`／`fail`；证明等待没有串行化读取本体。
- `read_ktx_yaml` 的 `enter` 在采集结束前已可见，没有使用旧日志。
- 两个探针均在 1 秒内返回，正文没有运维步骤行。
- 释放后每支恰好有一条成功 `leave`，没有重复终态；文件与管理台使用同一操作号。

## UAT-OPS-STEP-04

### A. 单表失败、原句与哨兵

1. 记录日志与审计水位。按 fixtures 在真实前台浏览器选中 `uat_ops_step_sentinel`，删除底层表后执行读字段。
2. 记录导航到错误详情可见的即时时间，并分列对应读字段 API 耗时；保存错误响应 `detail.opsStepId`。
3. 按该操作号读取标准输出、文件副本和管理台；对当次全部步骤行做 JSON 解析、冻结键、512 字节及哨兵检查。

期望：

- 界面仍为 `表「uat_ops_step_sentinel」没有读到字段。`，既有错误详情另显同一操作号；两种耗时分列。
- `read_columns` 的 `fail` 精确为 `reason_code=missing`，不得接受其他码。
- 三处操作号一致；行内没有 `uat_ops_step_sentinel`，大小写不敏感地没有 `SELECT` 或 `information_schema`。
- 所有行只有 Spec 冻结键，含换行不超过 512 字节。另附真实序列化自动化对 511／512／513 字节和超长构造的结果。

### B. 跨请求批量失败

1. 按 fixtures 选中 51 张表，删除 `_00` 与 `_50` 后执行读字段。
2. 保存两次部分失败响应的 `data.opsStepId` 及界面中两张失败表的决定信息。

期望：两个操作号不同；`_00`、`_50` 各显示所属请求的操作号，不交叉、不复用。批量原失败句结构保持既有合同。

## UAT-OPS-STEP-05

1. 重置步骤账。前台浏览器首次打开 `/admin/ops-steps`，记录 E1／E2；随后产生一个已结束同步段，并托住一个诊断操作 120 秒，保存两个 `op_id`。
2. 记录导航到非空列表可见的即时时间，与同一次列表 API 耗时分列。对照标准输出验证两个操作号，覆盖 E6。
3. 按 fixtures 分别注入一次管理读延迟和一次管理读错误，完成 E3／E4；用不存在的操作号筛选并清除，完成 E5。
4. 保持诊断托住，再执行至少 1001 次 `holdMs=0` 同步段，使历史超过 2000 行；检查 E7，并确认当前进行中仍可按操作号找到。检查 E8／E9。
5. 未登录请求管理读接口，记录与其他管理接口一致的结果；随后再产生一个真实步骤，确认标准输出未因未登录请求停写。
6. 检查 `stdoutWriteFailed`、`fileWritable`、三类丢行计数及截断原因。附真实进程自动化对最近 1 小时边界的证据。
7. 释放诊断。另托住一个步骤并等其 `enter` 已写入文件后终止并恢复 demo 容器；重新打开页面，检查该历史操作号。

期望：

- E1–E9 都有前台浏览器证据，证据含路由、1920×1080 视口及 E 编号逐项结果。
- 进行中只含当前进程孤立 `enter`，已结束含 `leave`／`fail`；操作号与标准输出一致。
- 截断原因、分通道写健康和丢行计数可见；刷新是唯一 primary。
- 重启后文件历史仍可读，上一进程孤立 `enter` 显示“上次进程未完成”，不在当前进行中。该重启只验证 SC-14，不作为故障修复。

## UAT-OPS-STEP-07

1. 按 fixtures 将步骤目录改为只读，跑一次 `holdMs=0` 的真实同步段；随后恢复原权限并再跑一次。
2. 分别武装一次标准输出 `error` 和 `short`，各跑一次真实同步段；保存写调用次数、操作结果、内存行、文件行和分通道计数。
3. 用真实进程自动化持续执行快速同步段，实际写入超过 8 MiB，检查滚动文件数量、大小和 JSON 可读性。
4. 恢复全部权限与写者状态，记录恢复结果。

期望：

- 文件不可写时操作完成、标准输出仍有 `enter`、`fileWritable=error` 且 `fileDroppedCount` 增加；恢复并再次成功写入后为 `ok`。
- 两种标准输出故障下操作均完成，内存和文件行仍可读，`stdoutWriteFailed=true`、`stdoutDroppedCount` 增加；每次故障只有一次写调用，无等待或重试。
- 短写残行不被管理台拼成有效 JSON。
- 滚动后只有当前文件和一份滚动文件；当前可读行均合法。不得直接预写伪 JSON 代替真实写者。
