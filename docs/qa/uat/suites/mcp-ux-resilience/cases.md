## UAT-MCPX-02 — 策略重载期间并发握手＋权限负向

### 步骤

1. 记录当前 `policy_version`。
2. 按 fixtures 连续 3 次触发 `policy_version` 变化；每次变化期间并发 20 次 `initialize`。
3. 变化后抽 1 次握手，比对 instructions 中的 Visible Scope 与新策略一致。
4. **权限负向①**：用 fixtures 的两个身份 A、B（同角色集合，B 另有 Agent overlay 或 capability 差异）各握手一次；比对两份 instructions 的 Visible Scope 与工具清单，必须与各自有效权限一致且**不相同**。
5. **权限负向②（三组，分别记录）**：对 A 收窄权限，以 commit 返回时刻为界——(a) **撤权保密**：构造一个构建开始于 commit 前、但**响应发送发生在 commit 之后**的握手（夹具用只读延迟钩子或在构建期间触发收窄）；其响应**不得出现被收回的 Source／Skill 名称**（要么按新代重建，要么返回可重试错误）；commit 前已**发出**的响应不受约束；(b) commit **后**开始的 20 次握手：均不得包含被收回的 Source／工具；(c) 跨越 commit 才完成的旧构建完成后，再发一次新握手，仍须命中新代（旧构建不得写入新代）。
5b. **skills 失效三类**：对 A 可见的 Skill 做①文件原地改写②删除③ACL 收窄；经写入事件路径的变更，下一次握手必读到新内容；另做一次**绕过事件的外部直接改文件**，在 ≤ 一个复核周期（Plan 冻结值，≤ 30 s）内必被新握手读到，并记录实测陈旧窗口。
6. **缓存命中读取计数**（若采用缓存修复）：命中的握手上，catalog／skills 读取计数增量为 0（读只读计数入口）。
7. 还原变更；确认 `policy_version` 已回到可解释状态并记录。

### 期望

- 每个变更窗口 P99 ≤ 5 s、0 次 > 30 s；instructions 内容与新策略一致；A、B 的 instructions 不串；(a)(b)(c) 三组均满足（(a) 组无任何撤回名称泄露）；skills 三类失效与外部改文件窗口满足；命中时读取计数为 0。

### 清理

还原策略变更与身份差异；确认无遗留变更。

## UAT-MCPX-06 — 重复被拒的提示与边界

### 步骤

1. 按 fixtures 对泛化歧义词 `begin` 后以身份 A 提交未钉选 `lucy_query`，得到拒绝。
2. 60 s 内同会话原样重提一次；读响应。
3. **边界①（策略变化）**：触发一次无害 `policy_version` 变化后，原样重提；不得再出现「请勿原样重试」提示（状态已失效）。
4. **边界②（跨身份）**：身份 B 在无会话头的默认会话下提交同样请求；B 的响应不得暗示「相同请求刚被拒绝」（除非 B 自己 60 s 内重提）。
5. **边界③（TTL）**：间隔 > 60 s 后重提，无该提示；读只读状态计数入口确认该键的内存项已消失。
6. **边界④（LRU 容量，固定值：单身份 64、全局 1024）**：单身份内依次造 65 个不同被拒请求，第 1 个键已失效、第 65 个仍命中；身份 A 的淘汰不影响身份 B 的键；全局造 1025 个键（跨身份）后，最久未用的键被淘汰、最近的仍命中。**全局淘汰需 ≥ 17 个测试身份**（每个身份先填满 64，再由第 17 个身份触发全局淘汰；fixtures 的多身份脚本交付，若 demo 造不出 17 个身份则按 CONVENTIONS 记 BLOCKED 并停表，不降级为单身份推算）。**不得**只看一个截断计数器。
7. **边界⑤（`rejection_fingerprint`）**：同一请求换键序、`orderBy`／`order_by` 别名、`filters` 对象／字符串形态——指纹相同且仍提示；仅改一个过滤值或度量——指纹不同且不提示。
7b. **指纹不可反推**：在测试副本上用测试脚本对已知 canonical 入参计算**无密钥** SHA-256，断言审计列 `rejection_fingerprint` 的哈希段**不等于**该公开哈希的任何前缀；并断言导出文件与审计库里找不到 HMAC 密钥材料。
8. 用调用流水的 `rejection_fingerprint` 计算 M3 的分子分母（只在同一版本前缀内比较）。
9. 对照：按提示钉选后提交。

### 期望

- 第 2 步响应含「请勿原样重试」与下一步；第 3、4、5 步按上述边界；M3 可计算；对照成交。

### 清理

还原策略变更；清理造数。

## UAT-MCPX-08 — 会话失效后自动恢复（每工具每形态独立失效）

### 前置

Plan 步骤 0 已在 demo 真实重启 KTX 取证 400／404 的响应形态（Spec O6）。取证未覆盖的形态，其子步骤 **BLOCKED**；已取证形态可先跑。

### 步骤

对每种已取证的会话失效形态 × 每个工具（`lucy_query`、`wiki_search`、`lucy_read_source`、`ping`），**各自独立**重复：

1. 建立一个新会话并确认可用。
2. 用夹具使该会话的上游会话失效（真实重启 KTX，等待就绪）。
3. 只调用**这一个**工具；读响应、调用流水、上游调用计数。
4. 断言：客户端无感拿到正确结果；审计有 `session_recover`；原请求 1 次、握手（`initialize`＋`notifications/initialized`）至多 1 次、重试至多 1 次，**上游调用总数 ≤ 4**。

### 期望

- 每个（工具×形态）组合都满足；任一组合需要多次恢复握手或重试即 FAIL。不得「第一个工具恢复后其余工具沿用新会话」充数。

### 清理

确认 KTX 就绪、上游会话已重建。

## UAT-MCPX-09 — 持续失效短路（U3b 伴生，夹具待 O7，未闭合＝BLOCKED，不阻塞本条收口）

### 前置

Spec O7 已闭合并有可重复、可计数的**持续**会话失效夹具（恢复握手本身也失败）。**未闭合时本用例记 BLOCKED 并停表**；不得用本机代理或替身冒充，除非委托人另行书面授权降级（CONVENTIONS 第 3 条）。

### 步骤

1. 用夹具使上游持续返回会话失效。
2. 同一会话连续发起 30 次 `lucy_query`／`wiki_search` 混合请求。
3. 统计上游收到的 HTTP 请求数（原请求、`initialize`、`notifications/initialized`、重试逐类）、调用流水行数与理由码。
4. **四类恢复失败各做一轮**（各用独立会话）：恢复 `initialize` 失败；无合法 session id；`notifications/initialized` 失败；重试仍会话失效。每类都断言计 1 次、不因异常路径绕过计数。
5. **guard 键隔离三组对照**：同 Agent 两个不同 Token；同 Token 两个不同显式会话；无头默认会话。一方进入短路，另一方不受影响。
6. **间歇故障不累计**：夹具交替「失效（恢复也失败）→ 一次正常成功 → 失效…」，累计失败次数跨越 N 但中间始终有健康响应；断言**不进入短路**。
7. **窗口与半开**：进入短路后持续发请求（不刷新窗口）；最后一次恢复失败起 60 s 无新失败，夹具恢复后下一个请求即重新探测上游成交。
8. **initialize 洪泛**：短路期间对同会话连续发 `initialize`（≥ 30 次，间隔 < 1 s）；统计上游 `initialize` 请求数。

### 期望

- 第 N（N=5）次恢复失败**完成后**，第 N+1 个请求起返回 `session_lost`＋重连提示，不再打上游；该会话上游调用总数 ≤ 4N（20）；30 次请求都有调用流水行，短路行理由码为 `session_shortcircuit`；四类失败都能累计到阈值；键隔离成立；恢复时上游 session id 轮换不重置计数；交替序列不短路；短路请求不刷新窗口、60 s 后自动半开；**initialize 洪泛期间上游 `initialize` 尝试 ≤ 每 5 s 1 次，60 s 窗口总上游调用 ≤ 44**。

### 清理

还原夹具。

## UAT-MCPX-10 — 按提示重连后恢复（U3b 伴生，夹具待 O7，未闭合＝BLOCKED，不阻塞本条收口）

### 前置

同 UAT-MCPX-09。

### 步骤

1. 接 UAT-MCPX-09：处于短路状态，**上游仍不可达**。
2. 客户端重新 `initialize`：断言该 `initialize` **确实访问了上游**（间隔 ≥ 5 s 时必有一次真实尝试，未被计数短路），得到本地降级响应；随后再调用 `lucy_query`。
3. 夹具使上游可达但 `notifications/initialized` 被拒：客户端依次 `initialize`→发 `notifications/initialized`（被上游拒）→调用——计数不清零，仍短路；另测**客户端不发 notification**：同样不清零。
4. 夹具完全恢复上游；客户端执行 `initialize`→`notifications/initialized`（被上游 2xx 接受）→调用 `lucy_query`：显式记录三步的上游请求与响应；断言**清零发生在 notification 被接受之后**，而不是 initialize 响应时。

### 期望

- 第 2 步：`initialize` 访问了上游；计数**不**清零，随后调用仍短路；响应提示是「上游暂不可用，稍后重试」；审计可区分降级 initialize（P1-36 `local_handler(initialize_fallback)`）。
- 第 3 步：notification 被拒或缺失，计数**不**清零，仍短路（60 s 无新失败仍会自然半开，另行记录）。
- 第 4 步：notification 被接受后计数清零，`lucy_query` 成交；整个过程不依赖 person／宿主 attestation。

### 清理

无。
