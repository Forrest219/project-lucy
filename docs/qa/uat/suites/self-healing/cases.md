## UAT-HEAL-R0 — 环境门禁与假活构造

### 步骤

1. 冻结候选：`gitSha`、`gitDirty`、镜像 digest、compose 中 `restart` 与 `healthcheck` 的实际配置。
2. 启动隔离实例，规模与 [`f5e4b14d` 夹具](../interactive-read-resilience/fixtures.md)同口径，或记录降规模及原因。
3. 独立探针进程以 1 Hz 采样：`livez`、`readyz`、一条已鉴权展示读、一条纯 MCP 合法问数。所有请求写入账本。
4. 选一种触发方式并记录：
   - **N（自然重放）**：重放 P1-75 T2 混压，约 15 分钟。
   - **C（受控资源）**：对容器施加 CPU 限额，并对冷展示槽并发读，使展示读持续 503。现场已有 0.5 CPU、150 并发读复现 150/150 503 的先例，见总账 v2.58。
5. 判定「假活」：持续 ≥ W 的窗口内，业务探针 100% 失败，同窗 `readyz` 与 `livez` 为 200，且不在启动、排空或计划重载内。

### 期望

- 取得至少一段符合第 5 点的真实假活窗口，并保留原始账本。
- 记录进入假活时刻 `t_stuck`，作为 T_A、T_B 的起点。

### 禁止

- 用桩服务、关闭业务路由、手工改状态来「制造」假活。
- 把压力期间的普通 503 当作假活，必须满足 100% 失败与探针绿。
- 构造失败时判 PASS。记 BLOCKED 并保留尝试记录。

## UAT-HEAL-01 — 假活可观测

### 步骤

1. 在 R0 假活窗口内，只使用对运维可见的入口读取状态：`/api/health`、`/api/livez`、`/api/readyz`、容器 `docker inspect` 健康状态、容器日志。
2. 不允许进入容器执行内部诊断，也不使用测试私有控制接口。
3. 判断运维能否仅凭上述入口得出「进程活、业务失败」。

### 期望

- 至少一个入口显式给出业务失败信号，例如转红、专用字段或日志事件，并带时间。
- 信号与独立探针账本的失败窗口吻合，不得早于真实失败超过 W，也不得晚于 T_B。

### 判定

- 所有入口全绿且无业务失败信号 → **FAIL**。改前基线预期如此，记录原始值。

## UAT-HEAL-02 — 停压后同实例恢复（A）

### 步骤

1. 在 R0 假活窗口中，记录容器 `StartedAt`、主进程 PID。
2. 停止全部外部压力，记为 `t_stop`。其余探针保持 1 Hz。
3. 观察至 `t_stop + T_A`。

### 期望

- 在 `t_stop + T_A` 内，展示读连续 10 次返回 200，纯 MCP 合法问数返回独立 SQL 核对值。
- `StartedAt` 与 PID 不变。
- 恢复期间 `readyz` 不得先转红再自行转绿掩盖失败；若转红须登记为 B 的触发。

### 判定

- 到 T_A 仍未恢复 → **FAIL**。
- 恢复伴随重启 → 本用例判 FAIL，并转 03 判定 B。不得把重启计为同实例恢复。
- 保留 `f5e4b14d` 的 134 秒无恢复结论作改前对照。

## UAT-HEAL-03 — 探针联动自动替换（B）

### 步骤

1. 在 R0 假活窗口中**不撤压**，或在 02 判 FAIL 后继续观察。记录 `t_stuck`、容器 `StartedAt`、`RestartCount`、健康状态。
2. 全程不执行 `docker restart`、`docker kill`、`compose up`。
3. 观察至 `t_stuck + T_B`，并持续到恢复探针稳定。
4. 重启后用 1 Hz 探针采集恢复序列；纯 MCP 客户端用同一合法 Agent Token 重新握手、列工具、查询。
5. 对照前后审计行数与水位，核对自愈期间已受理的写入。

### 期望

- `t_stuck + T_B` 内探针转红或进程自退出，容器被 Docker 监管器替换，`StartedAt` 变化且 `RestartCount` 增加。
- 重启后展示读与合法问数恢复，数值与独立 SQL 一致。
- 审计前后行数守恒，无静默丢失；有自愈事件记录（类型、触发依据、时刻）。
- 无人工命令参与。

### 判定

- 超过 T_B 仍未替换 → **FAIL**。改前基线预期：容器无 `restart` 策略，Docker 不会重启 unhealthy 容器。
- 替换由测试者手工触发 → 作废，不计 PASS。
- 重启后合法纯 MCP 用户需 WebUI Cookie 才能恢复 → **FAIL**（违反主路径可用性）。

## UAT-HEAL-04 — 误杀防护

### 步骤

1. **合法负载**：同候选跑 [CAV STD 档](../core-availability/retest.md) 30 分钟，记录自愈重启次数。
2. **短暂忙碌**：构造单次展示读 503 后在 W 内自行恢复，期间业务探针有成功。
3. **TERM 排空**：真实 TERM，记录排空期间探针被拒是否触发自愈。
4. **冷启动**：冷启动窗口内 `readyz` 为 503、业务探针失败，不得被判假活。

### 期望

- 四类场景自愈重启次数均为 0，自愈事件为 0。
- 合法业务探针在 STD 档上的结果不低于不带自愈候选的同档基线。

### 判定

- 任一场景误触发自愈 → **FAIL**。必须附触发依据与探针账本。

## UAT-HEAL-05 — 强退与排空对照（可选）

对 03 的自愈重启，在重启触发时刻保持一个真实在途问数与一个已受理写入。记录它们在有序排空与强退两种路径下的结果。仅用于 OQ-4 裁定，不影响必做判定。

---

## UAT-HEAL-06 — 自愈抖动上限（可选）

持续压力不撤，观察至少 3 个 T_B 周期。记录自愈次数、最小间隔、每次重启后到可用的时长，并检查有无无限重启。仅用于 OQ-2 补充最小重启间隔。
