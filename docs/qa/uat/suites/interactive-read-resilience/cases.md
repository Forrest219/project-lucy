## 冻结的分母与计时

- MCP 从客户端开始发送到收到并解析完整匹配的 JSON-RPC 响应。完整旅程到收到并解析首条正确查询结果为止，包含建连、通知、工具列表与目录。通知用其现有协议回执语义。服务端阶段、网络首字节、写出和客户端超时分别报告。所有分位使用最近秩 `sorted[ceil(p × N) - 1]`。每组保留计划、发出、到达、成功、错误、超时和仍在途的记录，超时按截止记入且独立判失败。除具名故障和合同允许的重载拒绝，必做首尝试须全部成功。
- 正常读和纯备注保存的合法名册首响应须为 `200`，所有类型的首个 503 均记失败。对真实授权切换或具名快照故障，关联写入已进入可核验终态或故障已解除的可观察事件。由独立已授权前台会话在事件后 1 秒内发起首个逻辑复读，记录默认重试及所有实际响应。从恢复事件到正确名册首个 `200` 且页面显示当前已提交代次须在 10 秒内，无需重启、清缓存或手工恢复。该组首响应和连续 503 时段单列，同样适用于 G2 的授权窗。事件不可验证则记缺证，禁止用成功响应反推恢复起点。
- `01` 每类控制至少 3 次，含正常、已知慢请求、客户端断开。详细观测开关用同一候选交替执行关／开／开／关，每小组各 20 个相同的暖态业务样本，分别比较 `initialize`、独立 `lucy_catalog` 与摘要 API 的客户端 P95。相对增加 >20% 且绝对增加 >50 ms 即失败。保持现行每请求和全局 span、日志队列及审计容量上限，完整性缺失按未知留痕。模拟观测接收端丢弃，验证合法主路径不受影响。

### 正式 `lucy_admin` 身份验收

- `UAT-READ-RES-R0` 核验测试 Agent 绑定的正式角色 ID 与运行时生效的角色一致。用本轮的合成 Manifest 和启用表清单冻结期望目录。
- `UAT-READ-RES-02` 在首轮全局规模档按原分母执行该身份的握手门槛。校验 `tools/list`、握手指引和独立 `lucy_catalog` 的实际回执。目录逐连接比对启用 Source 集合，未启用 Source 与 `lucy-ops` 不进入默认全局范围。至少两个业务连接分别完成一条带预期值的 `lucy_query`，同时验证连接路由和查询结果。该身份的统计与受限身份分列。
- 四档交叉对照均执行该身份的目录与查询校验，分列冷读和同代次复用。保留每档连接、Source、缓存状态及首失败。缺正式角色回执时，依赖该身份的用例记 `BLOCKED`。

|---|---|
| 无配置写入 | MCP 持续问数，名册会话 C 进入与刷新页面。核对各角色查询结果、会话隔离、名册与统计，获得同资源下的读取对照。 |
| 纯备注保存 | A／B 从同一版本打开同一 Agent，并从真实 UI 尝试保存不同备注。一方成交，另一方取得明确 `409`；若初遇既有发布占用，保留原草稿并显式再提交，核对旧基线明确冲突。读到当前版本并重新确认后原意图成交。C 对两次成功保存各做一次写中首读及写后首读，核对一致视图及各自新备注。 |

### 调度与重叠证据

1. 每类窗口 120 秒，各 3 轮。每轮还原专用夹具与权限，服务端按 R0 预热，提前冻结查询、角色、到达计划与已知结果。正式分母每轮固定 50 个 Agent。背景用预检会话按每个 Agent 每 20 秒一次均匀错峰，计划每轮 300 条真实查询。每个入口的 `livez`、`readyz`、普通鉴权读各 1 Hz（120 次）。预检、背景和正式批次分别计数，到点停止发出并等待已有请求的绝对截止。
2. **并行握手。** 每轮 50 个 Agent 从同步点各建一个全新会话。客户端预开连接，`initialize` 的 50 个首尝发送时刻跨度 ≤50 ms，再按真实协议执行 `notifications/initialized` 和 `tools/list`。查询批次沿用 ≤50 ms 同发口径。按反代的起止回执分别重算首尝有效在途，各要求不同 Agent 峰值达 50；产品处理与上游执行分列。保存每个会话的完整握手与工具回执。
3. **并行业务查询。** 同批 Agent 完成建会话后，在第二个同步点各发一条授权稳定的真实 `lucy_query`，逐条核对 SQL 结果。独立重算首尝 `lucy_query` 同时在途的不同 Agent 峰值，要求至少 50。请求覆盖三个角色及约定的业务连接，核对 Lucy／KTX 与数据源执行证据。撤权目标的正负例独立发起。因握手失败未进入查询的 Agent 仍记入旅程分母。在这种情况下，可用同一批 Agent 的预检会话单独发起整批查询作为诊断，并另列结果。
4. A／B 通过真实 WebUI 并发提交，C 同步导航或刷新名册。每轮写窗须证明第二个保存请求到达时第一个尚未结束，且至少一刻同时存在进入真实保存阶段的成功写入、C 当前摘要请求及整批 50 路业务查询在途。纯备注窗还须有两次成功保存分别与 C 的首读取相交。无写轮至少一次 C 的读取与业务查询在途相交。单列握手批次是否与写入重叠。使用自然业务和正式保存，可用真实阶段事件协调放行，人工延迟单列控制，保留未命中及已有失败。

| 10-J 持续核验失败越界 | 在独立实例注入同一作用域持续 `reconcile_failed`（遵守安全注入约束），超过 180 秒；计时期间持续发新请求与自动重试。 | 180 秒内 `200`＋`pending`（无数据字段、无旧内容）；超过 D_max 后返回 C 类 503（`DISPLAY_RECONCILIATION_FAILED`），带恢复入口、无旧内容；计时不因新请求重置；撤除注入、核验成功后 10 秒内重新成交 `fresh`，计时清零；同窗纯 MCP 合法 Agent 不受影响。 |

## 组合发布取证候选

`UAT-READ-RES-R01` 供 [P1-13／R-CAV](../core-availability/suite.md) 评审接入。复用现有核心可用性重档同候选自然窗，按正式复测档的 30 分钟、12 个周期执行初始比较，R-CAV 适用的完整时长仍按其合同。在同一窗口并行跑真实前台 Agent 名册、纯 MCP 新会话查询、一条实际宿主 Agent 复现、普通鉴权 HTTP 和直连／反代探针。保留本机等价多源宽权限、审计写入、真实配置变更、资源条件及原有预算。每条用户旅程按实际结果判定，复算统计尾部和原始失败。入 R-CAV 前保持候选设计身份，独立于本套件功能合同。
