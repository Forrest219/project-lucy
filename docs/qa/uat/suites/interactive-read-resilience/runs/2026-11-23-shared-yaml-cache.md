## G1 严格规模预检与 SC-02 暖态首失败

独立候选 `688cbd4e` 在本机隔离 Docker 使用 2 CPU／2 GiB。R0 的严格规模脚本退出 `0`，16 项检查全部通过。实测 500 Agent、200 角色、1,500 凭据、302 个 Wiki 文件、101 个符合预检口径的 Skill、2,006 张物理表和 1,000,507 条历史审计。正式 `lucy_admin` 经本机反代完成两个纯 MCP 旅程，分别核对 MySQL 查询结果 1,000 和 3。完整 R0 的 A/B 配对及其余取证仍待补齐。

并发组 20 个请求均关联到审计。服务端总耗时 P50 为 807 ms，`catalog_resolve` 为 1 ms，`skills_load` 为 695 ms。各阶段单独统计分位数。同一镜像、同一数据再测 20 路，直连 P50 为 581.79 ms，反代 P50 为 608.66 ms，两组均超过门槛且全部返回完整指引。`skills_load` 同时包含磁盘发现、Markdown 解析、授权快照和可见性过滤。当前握手每次调用 `loadAllSkillsFresh()`，该函数使列表缓存失效后重新递归扫描。现有样本确认了主要慢段，段内各项占比待设计复审时再测。

兼容性收尾后，从干净的 `fa9457ef` 构建原生 arm64 镜像 `sha256:43f88d0746e47e9624b2a608abf44a7204498013eece1f562f5854a77406f6a3`。在相同卷和配额上仅替换 Lucy 容器。严格规模再次退出 `0`，两个真实 SQL 核对值均复现。顺序 200 次全部成功，P50／P99 为 64.68／131.73 ms。20 路同发全部返回完整指引，P50／P99 为 660.19／763.05 ms，仍判 FAIL。服务端并发组总耗时 P50 为 629 ms，其中 `catalog_resolve` P50 为 1 ms，`skills_load` P50 为 533 ms。

按 Spec §2.2，保留暖态首失败并进入设计复审。候选 A 尚未封存，G1 其余组、G2 和 P1-77 双宿主 PERF／MIX 待执行。原始回执位于同一 `inbox` 目录。首轮见 `global-scale-check.log`、`g1-02-*.json`、`g1-audit-spans.json` 和 `g1-stage-summary.json`，收尾复跑见 `g1-final-*`。
