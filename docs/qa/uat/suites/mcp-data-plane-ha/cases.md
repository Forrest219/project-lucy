## UAT-MCPHA-R0 — 环境、规模与故障命中门禁

### 步骤

1. 冻结候选源码、镜像、KTX、测程与资源，启动独立 Compose 环境。执行 `npm run uat:scale-baseline`，记录全维度结果。
2. 核对 A／B／C 是不同 Agent，A 使用基线内多个 Token 和多个独立 Session；B 与 A 使用 conn-a，C 使用 conn-b，D 无目标 Source 权限。
3. 用独立 SQL 核对 conn-a／conn-b 的行数与聚合值。通过完整 `initialize → tools/list → lucy_query` 验证三个合法身份，不使用 WebUI Cookie。
4. 分别做故障校准：
   - 发起 conn-a 慢查询，确认数据库真实在途与 Lucy operation／attempt 对应。
   - 用冷展示槽和受控资源压力产生真实 WebUI 局部 503，确认目标展示作用域与回执。
   - 在执行中断开一条 TCP，确认服务端观察到断连与上游取消，而不是仅客户端取消计时。
   - 发送分块大结果，确认实际超过当次响应上限，且未用客户端提前截断冒充服务端背压。
5. 校验测程负控：错误 SQL 值、假成功、假并发、未命中慢查询、把下游 close 当上游 close、缺前台计时、缺故障交叠均应判失败。

### 期望

- 全局规模达标，独立 SQL 与四个身份的权限正确，真实故障命中证据齐全。
- 改前与改后夹具、请求序列、资源、客户端和判定脚本一致。
- 任一项未命中，只将依赖该事实的断言记 `BLOCKED`，不得以替身成功继续计分。

## UAT-MCPHA-01 — 单 Agent 跨 Token／Session 总限额

### 步骤

1. 记录当次裁定的 Agent、Token／Session、连接和全局上限，验证配置满足 `agent < connection <= global`。
2. A 同时使用基线内多个 Token，并在每个 Token 下建立多个独立 Session，混合调用 `lucy_query`、`lucy_read_source` 和另一个实际可见的上游语义工具。
3. 让 A 的真实在途达到 Agent 总限额，再发起超额调用。记录每个请求是否获得租约、是否启动上游和实际数据库在途。
4. B 在 conn-a、C 在 conn-b 各执行合法小查询，独立 SQL 核对结果。
5. 结束或取消 A 的工作，观察真实释放，再让 A 重试原合法问题。

### 期望

- A 的所有 Token／Session／工具合计不能超过 Agent 总限额；Token 间拆分不能绕过。
- 超额请求在 OQ-1 草案预算内返回 HTTP 200＋MCP `isError`，复用 `query_concurrency_exceeded` 并带 `capacityScope=agent` 与重试建议；没有新增上游工作。
- B／C 均返回独立 SQL 正确值，不因 A 达到自身限额而全局失败。
- 容量拒绝与权限拒绝、预算耗尽分别记录；A 的真实工作结束后可以重试成功。

### 反例保留

- 只限制 `lucy_query`，却让 `lucy_read_source` 或其他上游语义工具穿透 → **FAIL**。
- 仅把客户端并发数字改小，数据库仍有超额执行 → **FAIL**。

## UAT-MCPHA-02 — 同连接公平性与全局舱壁

### 步骤

1. A 在 conn-a 达到自身 Agent 上限并保持慢查询，额外尝试增加 Token／Session 以继续占用 conn-a。
2. B 在 conn-a 发起合法查询，C 在 conn-b 发起合法查询。记录连接级实际占用、各自身份成交与拒绝。
3. 增加 B 和其他合法身份的负载，使 conn-a 达到连接上限；再发一条 conn-a 请求，确认没有新上游工作。
4. 在保持 conn-a 连接饱和时重复 C 的 conn-b 查询。
5. 用额外身份使全局容量达到上限，验证全局拒绝；随后逐步解除真实工作，观察分层释放与恢复。

### 期望

- A 不得占尽 conn-a 或全局容量，B 在同连接至少有合同约定的有限成交，C 全程不受 conn-a 阻塞影响。
- conn-a 整体饱和和全局饱和都快速返回对应 `capacityScope`，不发生无界等待或新上游执行。
- 数据库连接、KTX 调用和数据库在途均不超过各自已证明的安全上界。
- 真实工作结束后各层占用按实际关系回落，合法请求恢复成交。

## UAT-MCPHA-03 — WebUI 局部 503 时独立 MCP 主路径

### 步骤

1. 在前台 Chromium 1920×1080 打开一个既有展示页面，记录导航开始、网络回执和 `primaryReady`／错误可见时刻。
2. 用冷展示槽和受控资源压力产生真实局部展示读 503；记录 `DISPLAY_SNAPSHOT_BUSY` 的内部原因与目标作用域，不能用反代手工写死 503。
3. 故障窗口内，两个不同 Agent 分别通过纯 MCP 完成握手、工具发现和真实查询，其中至少一个使用 conn-a，另一个使用 conn-b。
4. 保持前台可见，解除故障，记录正确内容恢复可见的时刻和截图；同窗口 API 状态／耗时单独列表。
5. 恢复后重复两个 Agent 的查询，核对没有因前次失败而重复执行 `indeterminate`。

### 期望

- 页面真实显示既有可重试错误或恢复内容，前台导航→错误可见、解除→正确内容可见均有即时计时。
- 两个 Agent 在 Spec 引用的既有 MCP 预算内返回独立 SQL 正确值；不得要求 WebUI Cookie。
- Web 局部错误与 MCP 错误各自分类，不把 `DISPLAY_SNAPSHOT_BUSY` 直接统计为 KTX 不可用。
- 本用例不覆盖 WebUI 进程崩溃；若实际变成整进程不可调度，则记录为超出本阶段边界的失败证据，不得改写成局部场景通过。

## UAT-MCPHA-04 — 断连、取消与真实释放

### 步骤

1. 分别在“已接纳未执行”“上游执行中”“响应提交前”三个时点断开客户端，重复至少 10 轮。
2. 每轮记录断连、取消请求、上游 close、最终截止和容量释放时刻。用数据库在途证明取消是否已生效。
3. 在取消未确认期间让同一 Agent 和另一 Agent 发起新查询，核对容量是否仍被原工作占用。
4. 对响应丢失但数据库执行结果未知的一组，观察 Proxy 与客户端是否自动重试。
5. 注入撤权和最终截止，重复核对租约只能释放一次，最后全部计数归零。

### 期望

- 每次取消只发起一次；上游未结束时保持 `CANCEL_PENDING` 和租约，真实 close 或最终截止后才释放。
- 断连的下游 response `close` 不直接归还执行容量；后续请求不会与旧执行无界叠加。
- `indeterminate` 的自动重放次数为 0，保留可人工核查的 operation／attempt 和数据库侧证据。
- 至少 10 轮后无租约、内存或在途计数泄漏；合法新查询最终可成交。

## UAT-MCPHA-05 — 上游响应与全局内存背压

### 步骤

1. 分别发送“低于上限”“恰好上限”“上限＋1 字节”的分块响应，记录读取停止点与实际内存。
2. 发送持续分块的大响应，验证在流越过允许上界时停止上游读取，而不是完整读入后才由 `ResponseGate` 拒绝。
3. 并发多个单独未超限的响应，使合计超过全局内存预算；随后发送一个合法小查询。
4. 在超限期间检查错误日志、审计字段和响应正文，确认不含完整结果行或敏感内容。
5. 释放后重试小查询并检查容量恢复。

### 期望

- 恰好上限按合同处理；上限＋1 在读取流上提前失败并触发真实取消，内存不会先增长到完整大包。
- 合计越界时后续请求快速繁忙，不发生无界缓冲；其他 Agent 的合法小查询在预算内完成。
- 超限、容量拒绝和上游错误分类正确，审计无敏感结果正文；恢复后无内存租约泄漏。

## UAT-MCPHA-06 — 容量与失败分类可观测

### 步骤

1. 依次产生 Agent 容量拒绝、连接容量拒绝、全局容量拒绝、Agent D 权限拒绝、上游超时、审计存储异常和一条 `indeterminate`。
2. 读取既有健康／审计／运行观测入口，按 operation／attempt 关联获取、拒绝、取消和真实释放。
3. 对 HTTP 200＋JSON-RPC 错误分别统计，检查是否被误计为问数成功；对 TCP 可连但查询失败的窗口检查健康叙事。
4. 检查所有指标、日志和导出证据中的 Token、密码、问题正文与结果行。

### 期望

- 每类失败都有既有、稳定且互相区分的分类与容量作用域，不能把容量拒绝写成 ACL 拒绝，把 `indeterminate` 写成成功。
- TCP 可连、`readyz=200` 或 HTTP 200 均不单独构成真实问数成功证据。
- 能还原某次请求从取得到真实释放的完整生命周期，证据不含明文凭据、密码或敏感结果正文。
- P1-81 可消费这些事实，但本条不新增通用假活 watchdog 或重启逻辑。

## UAT-MCPHA-07 — 权限、撤权与审计守恒

### 步骤

1. 让 Agent D 请求未授权 Source，验证权限拒绝且零上游执行；再让 A 触发容量拒绝，比较两类审计。
2. 在 A 的一个 Token 在途执行期间吊销该 Token，确认目标请求被中止或无法继续发送内容，B／C 的合法会话和查询不受影响。
3. 在容量拒绝、上游失败和正常成功三类请求上，核对 `request_admitted`、`response_prepared` 与终态序号及 access_log 归因。
4. 检查客户端配置和数据库在途，确认所有业务查询均经 Lucy MCP Proxy，未绕过到内部 `7878`。
5. 对断连和响应丢失的请求核对是否产生重复执行或重复成功行。

### 期望

- 权限、容量、预算和上游失败分类保持独立；任何业务内容都在既有 `response_prepared` 持久化成功后才交付。
- 撤权只影响目标 Token／Agent，其他合法 Agent 继续成交；无旧授权内容在确认收窄后继续发送。
- 审计序号、operation／attempt、Source 与执行结果可关联，无未提交内容、无重复不确定执行、无内部 KTX 直连旁路。

## UAT-MCPHA-08 — 混压后容量回落与主路径恢复

### 步骤

1. 在同一最终候选上复用 P1-75 T2 的 15 分钟混压方法，叠加 A 多 Token／多 Session 慢查询、B 同连接合法查询、C 跨连接合法查询和 WebUI 局部展示压力。
2. 全量保留成功、容量繁忙、权限拒绝、客户端取消、超时和 `indeterminate`，不得删除慢样本或只选成功分母。
3. 每分钟核对各层实际在途、连接公平性、数据库执行、Web 前台和审计终态。任一脚本宣称的并发必须由真实交叠证明。
4. 停止外部压力但不重启容器，继续观察容量释放、合法查询和页面恢复，直到真实工作归零并稳定成交，或达到 Spec／相邻合同允许的最终截止。
5. 重跑 R0 的正常路径与独立 SQL，复核改前／改后数值、事件和清理。

### 期望

- 混压中单 Agent 超额有界，B／C 合法主路径按各自容量继续；conn-a 故障不扩散到 conn-b。
- 停止压力后，所有租约在真实工作或最终截止后归零，无持续内存／在途泄漏；合法查询无需手工重启即可恢复正确值。
- 权限与审计守恒、无未提交内容、无重复不确定执行；R0／01–07 的证据能与本窗口逐次关联。
- 若进入 P1-81 定义的假活，保留事实并由其套件判定自愈；本条不得用人工 `docker restart` 冒充容量恢复。

## UAT-MCPHA-09 — 持续公平性与恢复观察（可选）

在合法混合负载下延长观察到至少 30 分钟，周期性改变 A 的 Token／Session 组合和 conn-a 压力。记录各身份成功率、分位耗时、容量峰值、取消未确认数量、自动重启次数与恢复趋势。该用例只补充阈值和长期稳定性，不替代 R0／01–08，也不把持续运行本身解释为公平性或 HA 证明。
