## 1. 裁决

当前文档的证据意识和权限底线较好，但仍存在两类核心缺口：

1. **机制缺口**：缩短写屏障不等于纯备注写中首读不再 503；减少目录／Skill 重复工作也不等于握手具有确定的超时逃生路径。
2. **验收缺口**：部分性能预算、夹具、重叠样本数和失败分母尚未冻结，现有测试脚本也不能原样承担新合同。

因此，本报告支持在既有授权边界内继续文档、基线和测程设计；观测及测程改造可单独申请授权。写屏障重构、权限编译复用和跨请求目录／Skill 复用，应先完成本报告阻断项，再进入终审和开发授权。

当前 UAT 可以证明若干局部改善，但尚不能证明原 503 不再发生，也不能证明现场 30 秒级握手超时已经修复。

## 2. 认同项

| 编号 | 认同项 | 理由 |
|---|---|---|
| A1 | 区分现场事实、待验证假设和本机复现 | Spec 未把共同延迟直接写成共同根因，也明确现场 26.8–43.3 秒握手尚未复现，避免伪归因。见 Spec §1 |
| A2 | 纯备注快速路径按持久化后的实际差异分类 | 混合 PATCH、未知差异和核验失败走完整路径，避免仅按请求字段白名单误判权限等价 |
| A3 | 禁止延长等待、提前确认或读取撤权前权限来修绿 | 符合主路径可用性与失败关闭必须同时验收的原则 |
| A4 | MCP 复用保持每请求身份、权限和终态独立 | 不允许跨请求身份权限缓存，且要求发布、外部文件变化和撤权负例 |
| A5 | UAT 使用真实 Docker、纯 MCP、真实查询 oracle 和前台浏览器 | 能覆盖实际用户入口；保留首次 503／超时，而不是只记录自动重试后的成功 |
| A6 | 功能合同与组合发布取证分离 | SC-01–06 为功能合同，R-CAV 扩展独立评审，符合三层证据边界 |

## 3. 阻断项与整改要求

### B1：缩短写屏障不能推出纯备注写中首读不 503

**意见：反对以现有机制描述闭合 SC-04。**

Spec §2.1 只承诺优先缩短共享写屏障，SC-04 却要求纯备注窗口合法读取首个响应成功。当前实现仍在写入 pending 时使用共享恢复等待预算，超预算即返回 `DISPLAY_SNAPSHOT_BUSY`：

- `webui/server/display-snapshot.ts:60-64`：恢复等待总预算为 1500 ms。
- `webui/server/display-snapshot.ts:638-647`：写入未在剩余预算内结束时记为 `write_pending`。
- `webui/server/display-snapshot.ts:713-716`：最终抛出 `DisplaySnapshotBusyError`。

已有扩容跑次出现约 6.5 秒正式 PATCH 窗口及连续两次名册 503，见 `docs/qa/uat/suites/interactive-read-resilience/runs/2026-11-23-kscc-scale-recheck.md:29-35`。因此，只要备注提交仍超过读取预算，故障就能复现。

**整改要求：**

1. 明确纯备注写中读取语义，不能只写“尽量缩短”。
2. 优先评审将备注展示代次与权限代次解耦：纯备注提交期间可返回最近一次已核验权限和旧备注；提交完成后首次读取必须看到新备注。真正授权变更不得走该路径。
3. 增加纯备注提交被人为拉长到超过 1.5 秒的对抗用例；若仍返回 busy，SC-04 必须失败，不能借用 SC-05 的故障语义豁免。
4. 不得通过增大 1.5 秒预算获得通过。

### B2：Plan 按现有范围无法达到 Spec 自己的完整出口

**意见：反对在范围矛盾未处理前把 SC-01–06 全部作为可达出口。**

- SC-04 继承 P1-66 冷读预算；P1-66 已有冷读五次超过 10 秒的反例。
- SC-06 继承 FUP-03 探针预算；既有正式跑次已有 `livez` 最大值越线。
- Spec §2.3 又将名册摘要独立冷构建留作后续候选；首轮 Plan 没有对应冷构建或探针修复任务。
- Suite 同时规定功能合同 `R0／01–06` 全部必做。

这意味着即使首轮所有开发任务完成，完整合同仍可能按设计必然失败。

**整改要求：二选一明确写入 v0.3：**

1. 把冷构建和探针越线修复纳入实施范围；或
2. 将本条 scoped 出口缩到“备注写中 503＋MCP 指定并发反例”，保留 P1-66／FUP-03 原失败，不让本条继承其完整预算。

不得一边把已知红色项写成必做出口，一边没有对应实施任务。

### B3：现场完整名册路径仍有验收逃逸口

**意见：反对仅用摘要 PASS 代替原受影响入口的修复证明。**

现场证据是完整名册 `view=roster` 返回 503；错题记录还保留完整响应下载 11–19 秒的事实。当前 SC-04 主要验收 `projection=summary`，旧完整接口只要求保留契约，没有写中可用性或传输预算：

- `docs/specs/lucy-20261123-interactive-read-resilience-spec.md:27`
- `docs/specs/lucy-20261123-interactive-read-resilience-spec.md:91`
- `docs/lessons/2026-11-23-roster-busy-and-mcp-latency.md:11-14`

**整改要求：**

1. 查明现场完整名册请求究竟是实际浏览器主路径还是诊断调用。
2. 若仍属于用户入口，必须覆盖其写入重叠、503 和完整响应下载。
3. 若实际页面已经只使用摘要，应记录代码及网络证据，并明确完整接口只是兼容性对照，避免用摘要 PASS 代替原入口修复。

### B4：MCP 方案只能降低长尾概率，尚未形成确定的超时逃生路径

**意见：认同先归因和最小复用，反对据此声称已经消除握手超时。**

当前实现中目录完成后才开始 Skill 加载， initialize 响应必须等待整个指引构建结束：

- `webui/server/proxy/mcp-proxy.ts:2130-2138`
- `webui/server/proxy/mcp-proxy.ts:4344-4355`

首轮 Spec 主要是补观测，只有证明重复工作后才选择并发合并或解析复用。这是合理的实验纪律，但不是完整的可用性修复设计。UAT-02 还保留“未被历来预算覆盖的工况按定稿校准”的开口，可能在看到候选结果后再决定冷态／代次变化门槛。

**整改要求：**

1. 在查看候选结果前冻结暖态、冷态、代次变化和正式变更窗的样本数、测量端与阈值。
2. 性能门槛落在客户端完整响应上，不能只用服务端阶段计时替代。
3. 评审“指引构建有界等待，超预算走既有上游原始 initialize 响应，后续再刷新可选指引”的止血候选；ACL、`tools/list` 和查询门禁仍按当前权限执行。
4. 若不采用任何有界逃生，应把承诺收窄为“减少重复工作与长尾”，不得声称已消除现场超时。

### B5：UAT 的样本分母和负载条件不够确定

**意见：反对当前用例直接作为最终性能 PASS 依据。**

当前缺口包括：

- 纯备注重叠没有最小样本数，少量碰巧未重叠的成功也可能通过。
- Plan 的“10 次热读、5 次失效首读”是基线采样上限，不是候选的明确通过分母。
- “所选 P1-66 档位”未冻结具体档位。
- UAT-06 引用 P99，却没有冻结注入窗口时长、请求到达率和最小探针样本数。
- 冷态／变更窗阈值存在后校准空间。

**整改要求：**逐用例冻结夹具、资源、样本数、真实重叠数、开放到达率、持续时间、百分位算法和超时样本处理。正常性能组要求 100% 有效成交，任何非预期 503／超时直接 FAIL。未真正与写入重叠的样本只能进入热态统计，不能计入写中修复分母。

### B6：现有脚本不能原样承担新合同

**意见：认同复用既有资产，但必须先改造测程。**

- `scripts/uat/mcp-ux-resilience-wide.mjs:24-38` 只汇总 initialize，没有覆盖完整查询链路和严格结果判定。
- `scripts/uat/agent-roster-summary-browser.mjs:89-90` 计算 P95 时只保留无错误样本。虽然错误另进 `failures`，但不能直接提供本事故要求的完整尾部与失败分母口径。
- Plan §验收步骤已承认旧脚本只有 initialize 汇总，需补确定性采集。

**整改要求：**

1. 先改造或新增确定性 runner，再执行正式候选 UAT。
2. 输出 planned／dispatched／completed／failed／timedOut／inflight 的守恒关系。
3. 明确 200 次顺序和 20 次并发中完整 MCP 旅程的覆盖粒度；至少每个身份、每种工况都有真实 `tools/list` 和查询 oracle，不能用“200 次握手＋最后一次查询”代表全部新会话可用。
4. 所有正常性能样本的状态、RPC 结果和查询正确性必须可独立复算。

### B7：写事务与复用负例不足以覆盖改动风险

**意见：反对只验名册读取收益而弱化共享写入回归。**

备注快速路径会触及共享 `access.yaml` 持久化、运行时确认、审计和响应绑定。当前 UAT 只明确列出混合 PATCH、版本冲突和审计失败回滚，覆盖不足。

**整改要求：**至少复用或明确引用以下既有 RACS 对抗组，并保留其原始成交要求：

- 不同对象、同对象并发保存及最终成交：`docs/qa/uat/suites/roles-agent-concurrency-scale/cases.md:135-159`。
- 预览后依赖变化与撤权：`docs/qa/uat/suites/roles-agent-concurrency-scale/cases.md:161-192`。
- 配置写失败、运行时确认失败、审计终态失败及恢复：`docs/qa/uat/suites/roles-agent-concurrency-scale/cases.md:220-244`。

同时补测响应丢失／幂等重放、`after.agent` 与提交版本一致，以及正式保存本身延迟，避免“读变快、写更难用”。

对目录／Skill 复用，还需冻结缓存层级、键、容量、失效和 singleflight 取消归属，并覆盖原子替换、删除重建、损坏／不可读文件、解析期间撤权、共享构建发起者断开后其他等待者继续成交。

## 4. 非阻断但应补齐的观测约束

Plan 要求确认新增观测不放大现有延迟，但没有可判定预算。建议增加同候选 A／A 对照，分别记录启用与停用详细观测时的：

- initialize、独立 `lucy_catalog` 和名册 API 的客户端耗时；
- 每请求日志／span 数、总量和容量上限；
- 观测失败不影响合法主路径的负例；
- 脱敏及高基数检查。

该问题本身不否定观测先行，但“没有放大”应有预先冻结的容许误差和原始分母。
