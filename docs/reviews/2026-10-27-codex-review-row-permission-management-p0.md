## 发现的问题（按严重度）

### B-01【阻塞】最终行约束预览未绑定保存；共享窗口缺少最终预览与完整基线复核

**合同位置：** Spec §3.2 L143–144、§5.3 L350–358、V13 L502、D6 L538；P0-3 §7.1–7.2 L131–139 要求基线复核、最终校验、写入、生效及终结持久化处于同一协调器窗口。

**代码事实：** `21de5168:admin/roles.ts:1003–1013,1053–1075,1117–1159` 的 PATCH 只接受 `dryRun/version/patch/override`，通过通用角色解析后直接写配置，未调用 `previewRowPolicyDraft`，没有 `confirmedCandidateDigest` 或最终预览基线字段。`row-policy-preview.ts:413–417` 返回的 candidateDigest／basePolicyVersion 没有被该入口消费。`21de5168:admin/access-config.ts:208–212,227–245` 获取共享窗口时，完整候选已由外部构造，窗口内没有再次预览或 CAS。

HEAD 的 `admin/roles.ts:1254–1257` 与 `admin/access-config.ts:256–260` 已补 PATCH 的锁内 access.yaml 版本复核，这是有效的局部修正；**仍未绑定 R2 最终预览，也未验证其源目录／生效基线**。HEAD `RoleDetail.tsx:638–667` 的保存确认只校验本地 draftHash；`RoleRowPolicyPanel.tsx:197–205` 的独立预览没有形成保存所需的成功凭据。

**影响：** 缺少预览、预览失败或源目录已变化时，保存仍可能进入 intent／落盘。尤其是 draft 对角色自身合法、却使关联 Agent 的个人行限制交集不可满足时，通用假用户角色解析不能代替最终预览。这与 §13.5 对两个入口不得混用的裁决直接冲突。共享锁只串行磁盘写，不能证明被确认候选仍是最终生效候选。

**修订建议：** 在 §5.3 和 V13 明确保存 API 必填的候选摘要、预览基线、受影响表集合及拒绝码；锁内重新读取基线、构造候选、调用同一最终预览并比对确认摘要，所有失败均在 intent 前拒绝。定义 access 配置、源映射／目录、启用表和工具分类等编译输入如何进入确认基线。P0-3 的只读并行许可保留，提交复核不可省略。

### H-01【高】恢复步骤自身失败时，未保证进入 recovery_required；V15 未覆盖真实恢复失败

**合同位置：** §3.4 L160、§5.3 L366–373、§7 L463、V15 L504。恢复配置和重新 commit 在 `rollbackVerified()` 之前；若任一步抛错，伪代码并没有保证执行后面的关闭动作。

**代码事实：** `21de5168:admin/access-config.ts:284–339,384–403` 仅捕获恢复文件失败；正常生效的 `await commitEffectivePolicy()`（L385）及恢复中的同一调用（L309）均可直接抛出闭包。恢复文件失败后，L294–298 又先持久化 marker，再执行降级 commit；`access-recovery.ts:84–87` 在文件写成功后才设内存状态。marker 写失败会使关闭流程提前退出。`access-recovery.ts:48–58` 还把 marker 不可读／损坏与不存在统一视为无需恢复。

`commitEffectivePolicy` 并非类型或实现上保证不抛错：`21de5168:acl.ts:2447–2452` 有未在该函数局部捕获的异步依赖调用，L2559–2565 返回可拒绝的 Promise。以上是静态异常路径判断，未声称已复现权限泄漏。

**既有测试限制：** `access-config-audit-closure.test.ts:309–332` 虽命名为「恢复不可验证」，实际 L319–320 先手动写 marker，再验证写入被拒及 runtime 降级；没有驱动 terminal 失败 → 恢复文件／恢复 commit 失败 → 自动置闸。L246–278 的成功回滚测试在检查旧 runtime 前又调用一次 commit，也不足以证明闭包返回前就已换入旧策略。

**修订建议：** §5.3 增加恢复异常的嵌套保护和最终关闭分支；明确 runtime commit reject、恢复写 reject、恢复 commit reject、marker 不可写／损坏的处理顺序。必须先在进程内可靠阻断受影响读取与后续写入，再尝试持久化恢复状态；明确重启后的保守处理与经核验解锁方式。V15 要求由实际故障路径触发关闭，并在不额外 commit 的前提下读取运行态证据。此项涉及现行恢复合同，不要求多副本能力。

### H-02【高】回滚成功仍返回已写入，V15 的对外失败合同不够具体

**合同位置：** §5.3 L365–376 要求回滚返回 FAIL，只有终结审计与生效均可证明才返回成功；V15 L504 没有规定 API／UI 结果。

**代码事实：** `21de5168:admin/access-config.ts:336–347` 返回 `rolledBack:true/runtimeAck:false`，但 `admin/roles.ts:1155–1167` 无条件返回 `ok:true/written:true`，丢失 rolledBack。HEAD PATCH 的对应返回仍在 `admin/roles.ts:1302–1316`；后续为删除入口添加的回滚错误处理不能推定覆盖 PATCH。`row-policy-audit.test.ts:255–269` 明确接受 HTTP 200，仅检查磁盘和 runtimeAck=false。

**影响及边界：** API 调用方不能把「新策略已写入」与「旧策略已恢复」清楚区分。HEAD UI 的 `RoleDetail.tsx:116–120` 已对 runtimeAck=false 显示保存未生效，因此本项**不声称 UI 必然弹出保存成功**；问题是服务端合同仍与 §5.3 不一致。

**修订建议：** 在 §5.3／V15 定义 committed、rolled_back、recovery_required 的 HTTP／业务结果，回滚不得返回 written:true；保留 actor、operationId／intentId、失败原因、候选及恢复后摘要，区分目标摘要与实际生效摘要。增加「恢复成功但补写 rolled_back terminal 仍失败」的证据口径，不能伪称已完成终结审计。

### M-01【中】目录能力未知只有显式注入分支，缺少产品入口的能力来源

**合同位置：** §3.5 L170、§5.5 L397–402、V20 L509 要求适配器／部署不能证明目录能力时归因未知。

**代码事实：** `row-policy-catalog.ts:521–545` 仅当 `schemaManifestCatalogProven === false` 才进入未知分支，缺省值继续读取本地 Manifest。`compileScopedRowGrant` 的能力参数可选（`row-policy.ts:295–320`）；非测试调用方未提供该能力声明，独立预览 L287–291 也未传。现有 `row-policy-catalog-attribution.test.ts:220–278` 由测试直接传 false，证明分类函数支持该分支，未证明真实 Admin／runtime 入口可到达。

**修订建议：** 在 §5.5 定义能力事实源、默认语义及支持的适配器／部署边界；若当前部署统一可证明，写清证明依据，并把未知场景列为受控注入验收。若有不能证明的部署，必须由服务端能力解析结果贯穿预览和保存，不能要求客户端自行声称。V20 应区分函数级故障注入证据与产品入口证据。此问题与 G5 修复无关。

### M-02【中】「可靠装载」缺少结构校验落地，V20／V21 可能错分

**合同位置：** §5.5 L397、L408–420 要求 YAML／结构均有效且目标表目录成功建立，才可据此判定字段不存在；V20／V21 L509–510 据此分流。

**代码事实：** `row-policy-catalog.ts:338–358` 仅做 YAML parse 与 TypeScript 类型断言，不做运行时结构校验；`pickManifestTableEntry:276–285` 接受 truthy entry，`columnsFromManifestEntry:288–295` 将缺失 columns 视为空。比如 `tables: { fin_ledger: {} }` 会被标记 loaded，再把绑定失败归为字段不存在；非数组 columns 还可能在迭代时直接抛错，绕过稳定归因。这是源码推导，未执行该样例。

**修订建议：** §5.5 明确何种表／列结构才算可靠目录，以及合法零列目录如何证明；落实与声明一致的结构验证，将结构错误稳定归入 parse／catalog 阶段。V20 增加「YAML 可解析但结构非法」，V21 仅使用已证明完整的目录。不能把目录构建失败当成用户写错字段，也无需等待 D-03。

### M-03【中】全局 Role 并集与逐 Agent 并集口径需明示，避免 V12 比错对象

**合同位置：** §5.2 L293–312 先循环所有允许该表的 Role 得到 effective，再对 Agent 求交；L306–309 的 capabilityRefs 来源未定义。V08–V12 L497–501 未明确全局预览并集与逐 Agent 实际角色集合的关系。

**代码事实：** `row-policy-preview.ts:255–269,306–328` 得到全局角色并集；L367–392 则为每个 Agent 按其实际 roles 编译 finalRows。实际实现比伪代码的文字展开更准确，不能为贴合伪代码而把所有角色都授给每个 Agent。

**修订建议：** §5.2 定义全局并集只是管理展示；每个 Agent 的 FinalRows 必须是「该 Agent 实际 Role Set 的并集 AND 自身 Constraints」。V10／V12 增加 Agent 仅持有部分 Role、Agent 无 constraints、另一个无关 Role 为 all 的组合；与运行时比较该 Agent 的 finalRows，不能比较全局 effectiveRowGrant。保留无授权与不可满足均失败关闭的现行含义，不新增权限代数。
