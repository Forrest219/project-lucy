## 结论

- **重复立项：未发现需要撤销或合并的条目。** P1-61 只补探针请求 I/O 与诊断快照差集；P1-62 只补三类重任务跨类别容量和许可接缝；P1-63 只补整实例准入关闭与在途排空。既有 worker、恢复水位、局部队列和发布门禁继续归原合同。
- **合同冲突：发现 7 组问题，已在草案和配套 UAT 中直接修订。** 未修改 Spec 191 正文；P1-63 开工前仍须取得其关停顺序的具名修订确权。
- **主路径：原验收存在“轻接口可用／恢复后可调用”代替真实业务成交的缺口。** 现已在原 28 个 SC 内补强，不新增编号：三组均要求在对应约束窗口及恢复后，以不带 WebUI Cookie 的纯 MCP 完成 `initialize`→`tools/list`→合法轻量数据查询并核对结果。
- 本轮只改 Markdown 文档，不改运行代码、运行配置、runner、旧合同状态或历史 UAT 结果。

|---|---|---|---|

| 4 | P1-62 后台重试与提交事实 | “固定 5 秒重试一次”可被理解为只重试一次；发布前撤权也可能把已提交事实改写为未提交；回执要求未区分原本有无回执 | 改为准入失败后至少间隔 5 秒再试且 dirty 不丢；已提交事实不被后续撤权改写；仅原合同有回执的操作要求查回执，不新造通用 job API |

| 6 | P1-63 关停竞态与有界性 | 外部 TERM 到 DRAINING 确认之间有未命名交接窗；后台等待项可能漏计；20 秒后才发取消且取消耗时不纳入预算，可能突破总退出上界 | 明确交接窗内已受理工作全部登记；后台等待项不启动并保留 dirty；启动后抛错但底层已受理的工作仍按真实 settle 计数；取消通知与剩余状态记录包含在 20 秒内，其余收尾使用独立预算；SC-01／04／06 与 UAT 同步 |

| 9 | 回执与既有恢复边界 | 原稿对“丢响应查回执”表述过宽，可能迫使无回执模块新增 job API，形成旁路功能 | 三条合同及 UAT 统一限定为原合同已有回执；继续复用 P1-45／50 水位与恢复，不新增恢复表或通用任务 API |
