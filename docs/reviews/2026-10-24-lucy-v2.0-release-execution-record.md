**修复 #7 时实现期发现的第二个缺陷**：超时拆卸期间 `'close'` 事件会抢先 reject `run()` 的 promise，外层 catch 随即 `process.exit(1)`，脚本在进程组 kill 执行**之前**就被杀掉 → 孙进程残留（`PPID=1`）。修法是让 `'close'` 在 `timedOut` 为真时不参与结算，并在顶层失败分支补 `killTrackedGroups()`。

### 2.2 教训：依赖链上的 job 可能从未执行过

#9 #11 都是**第一次真正运行**才暴露的——它们此前因 `needs: docker-smoke` 而一直 `skipped`。**推论**：`needs` 链上游一旦长期红，下游 job 的"通过"不代表任何东西，它们连代码路径都没进过。发版列车上每解锁一层，都要假设新一层从未被验证过。

### 2.3 门禁治理原则（本轮固化）

| 原则 | 落地 |
|---|---|
| 门禁只可能"带诊断失败"，不可能静默挂死 | 每条 spawn 的命令都有超时上限；超限报出**命令名 + 上限时长**；拆卸走**进程组**而非单个进程 |
| 超时上限是门禁治理的一部分，不是兜底 | 工作流里每个重 job 都要有 `timeout-minutes` |
| **每个 job 单一职责** | WebUI 套件只归 `spec-and-webui`；`docker-smoke` 不再重跑它（`--skip-webui-suite`）。重复执行会把 flake 概率翻倍 |
| 修复优先于放宽断言 | 11 项修复**没有一条放宽断言**；拒绝类语义、审计 `outcome`、`413`、`403 / -32003` 全部保持原样 |
| 平台参数由脚本按宿主推导，不由 compose 猜 | compose 默认值假设 Apple Silicon；脚本按 `process.arch` 取默认并允许显式 env 覆盖 |
| **判绿看退出码，不看用例计数** | vitest 会在"全部断言通过"时仍因未处理 rejection 退出 1（见 §4.18） |

### 8.3 打 tag 的时序：必须等 main 的 push run 变绿

`v*` 标签受 ruleset `protect-release-tags`（`25742587`）保护，**禁止删除、禁止移动**。因此 tag 一旦打歪就**没有补救余地**——先打 tag 再等 CI，等于把「CI 可能红」这个风险变成不可逆。

本次的顺序是：**先等 main 的 push run `40051808741` 四项 Required 变绿 → 再打 tag**。

tag push 会触发一次 `v*` tag 事件的工作流（run `40052825697`）。**那次跑批不是走过场**——它暴露了一个此前从未暴露的缺陷：`customer-amd64-native` 的条件是 `startsWith(github.ref, 'refs/tags/v')`，在 push / PR 跑批里一律 skipped，**只有在 tag 跑批里它才真跑**，而它真跑就失败了（候选镜像推不上 GHCR，见 §8.5 与评审 §4.23）。

**教训**：**所有 push / PR 跑批都绿，不代表发布路径被验证过。** 被 `if` 条件跳过的门禁，在真正发布的那次跑批里才执行——而那次没人盯。这次之所以能发现，纯粹因为台账机制要求把 tag 跑批也纳入记录。

### 8.4 台账回填的时序：为什么回填必须是一个后续提交

台账条目在 tag 打好之前只能写 `commit: "PENDING"`——**提交自身的 SHA 不可能在提交它之前被知道**。所以必然是：

1. 提交 A：台账写 `PENDING`
2. 打 tag `v0.2.0` → A
3. 提交 B：`fill-ledger-commit.sh` 把 A 的 SHA 写回台账

于是**最终 main HEAD（B）≠ tag 指向的提交（A）**。这不是缺陷，是自引用问题的必然解：tag 指向的是**被发布的内容**，B 只是把「发布的是 A」这件事**记下来**的那一笔。两者都在，才能追溯。
