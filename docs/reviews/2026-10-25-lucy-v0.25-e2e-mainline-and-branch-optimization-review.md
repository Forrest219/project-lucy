## 1. 结论

**原送审稿有条件通过；修订稿已按 §4／§7 定稿并获签核，作为 v0.25 E2E 优化的设计基线。** W0 可启动；F-01／F-02 未在 W0 内关闭前，不得退出 W0 或进入 W1，其余实施仍须另行授权。

理由分两面：

1. **认同面（§2，11 条）**：单主线 + 六旁线的结构、证据不可替代矩阵、冻结目录不动纪律、§7 编号映射，都经得起核对。其中 §7 的 160 个 `requirementId` 映射**数值完全忠实**于各权威源 Spec，零遗漏、零虚构、零计数偏差。
2. **反对面（§3，11 条）**：其中 **F-01、F-02 属阻断项**——Spec 反复声称的两条机械可校验目标（「MECE」「每个编号唯一 owner」）在现有编号体系下**当前无法被验证**，因为文档内部存在两个互不相交的编号宇宙，且六个责任域里有**两个域没有任何编号空间**。此外，用户在审查入口中点名的两条旁线——**「连接数据库的类型」**与**「多次问答后日志分析」**——在冻结目录与 P0／P1 两侧都缺落点，属于设计遗漏而非表述含糊。

修订量不大：F-01、F-02 需要补一套编号映射与两个域的编号空间；其余 9 条为实施前待办，不退回设计基线。

## 3. 反对意见

> **F-01、F-02 为阻断项**：不修订则 W0 的机械完备性检查无法达成 Spec 自述的目标。其余 9 条为**不退回**的实施前待办。

### F-01（阻断）冻结 255 未纳入责任映射，「MECE」与「唯一 owner」当前不可机械校验

- **现象**：冻结目录的 255 条 required variant 分布为 SEC-01–23 = 193、UX-01–07 = 39、OPS-01 = 7、GATE-01 = 16；v025 设计登记的是 160 个 P0／P1 `requirementId`。新旧执行编号零交集本身是防串号的正常结果，真正缺口是文档中没有把 255 条冻结 variant 映射进六个责任域的表。
- **影响**：
  1. 无法机械回答「某条冻结 required variant 由哪个旁线负责」；W0-2 的完备性断言只覆盖 P0／P1 集合，因此 Spec §1.2、§10.2 的 MECE 声明尚未覆盖既有目录。
  2. SEC-01–23 的 193 条是用户原则 ② 所说的单点功能深度测试；没有编号级归属会造成报告和 flake 统计断链。
  3. Spec §6 归并表把 `E2E-AGENT` 定位为「承接 UX-02–UX-05」，但仍需编号级映射。
- **处置**：独立 v025 映射清单必须同时登记 255 条冻结 required variant 的 `ownerBranch`，保留原 catalog ID；W0-2 增加「每条冻结 required variant 有且仅有一个 owner」断言；W0-3 的 legacy map 扩展到全部 255 条；Spec §6 补齐 32 场景逐条去向。不得为建立映射修改冻结 catalog 或 lock。

### F-02（阻断）AGENT 既有编号未显式归域、CONN 仅 Hive —— 数据库类型矩阵缺执行落点

- **现象**：§7 的 11 个新增编号前缀按责任域归类是：`OBSERVE` = AUD25／ARV25／ACM25，`ACCESS` = ROW25／RTP25／RTV25／ASV25，`SEM` = SEM25，`CONN` = HIV25，`LIFECYCLE` = UPG25／RVC25。UX-02–UX-07 虽能支撑 AGENT／OBSERVE，但未在编号级归域；`CONN` 除 Hive 外没有编号。
- **影响**：
  1. 如果只统计 `*25-*`，AGENT 域会表现为零用例；必须直接复用既有 UX ID，而不是复制一批 AGT25 重复用例。
  2. 冻结目录检索 `mysql|starrocks|oracle|sqlserver` 命中 0，P0／P1 的 160 个 id 也没有多库类型编号。MySQL 在数据库支持矩阵中为 `verified`，这里的问题是**未进入两套 E2E 编号清单**，不是产品不支持。
  3. Spec §5.1 CONN 行列出的 PostgreSQL／MySQL／既有支持类型、错误凭据、网络和 TLS，需要可执行对象和支持状态边界。
- **处置**：UX-02–UX-06 直接作为 AGENT 既有执行编号，UX-07-S01 直接承接现有多轮日志与调用监控对账；只为未覆盖的新场景增加 `CON25-*`／`LOG25-*`，后续新增 Agent 场景才使用 `AGT25-*`。CONN 对齐数据库支持矩阵，明确 verified／gated／experimental／roadmap 的不同证据要求。

### F-03 「多次问答后日志分析」在两份文档中都没有落点

- **现象**：Spec §5.1 在 OBSERVE 的「典型深度场景」列写了「多轮日志」，Plan §5.4 写了「多轮问询日志深度归此域」；但 W2-OBSERVE 的 5 个执行组（屏障与恢复／状态与关联／导出与回放／只读对账／交付证据）**无一是多轮日志**，§7 中 OBSERVE 的编号（AUD25／ARV25）也全部是审计域编号。
- **影响**：用户原则 ② 明确点名的这一支，在设计里出现、在实施计划里消失。跨轮次调用链重建、每轮 token／版本／耗时／预算关联、慢标记与 eval 排除对账这类可交付物没有承载对象。
- **处置**：增设 `LOG25-*` 用例组，并明确其可交付物；该组内容与冻结目录 `UX-07-S01`（「调用监控窗口、慢标记、eval 排除与真实事件对账」）高度对应，应直接复用其口径而非另造。

### F-04 `UX-06`（离线 Eval，8 条）与 `UX-07`（现场提问／安全候选，5 条）在两份文档中出现 0 次

- **现象**：在 Spec 与 Plan 中检索 `UX-06|UX-07`，计数为 **0 / 0**。这两条场景共 13 条冻结 required variant 无论证归属。
- **影响**：13／255 的冻结变体在新模型里凭空消失；`UX-07-S01` 恰是 F-03「多轮日志」最接近的既有资产，丢掉它使该支更无从落点。
- **处置**：Spec §6 补两行——`UX-06` → AGENT 主导（Eval 结果正确性）＋ ACCESS 主导（角色／runner／hash 拒绝）；`UX-07` → OBSERVE 主导（候选池与对账）＋ ACCESS 主导（真实权限拒绝的归因）。

### F-05 `J01-01…J01-08` 阶段编号与 `executionId` 体系未打通，「J-01 是一个还是八个」未裁定

- **现象**：§4.2 用阶段号描述主线，§7 的编号规则只覆盖 P0／P1；`J01-01…J01-08` 既不是 `executionId`，也未声明与 `executionId` 的关系。W1-2 的 `j01-state.json` 是状态交接机制，不是编号体系。
- **影响**：若把 J-01 拆成 8 个 `executionId`，「失败即停」会让其中 7 个永远 `not_run`；若不拆，则 §4.2 阶段表的 8 行没有可被报告、门禁、flake 统计引用的标识。Spec §10.2「每个 requirementId 只有一个 owner」因此无法机械成立。
- **处置**：明确裁定 **J-01 = 1 个 `executionId`（如 `J25-01`）**，八个阶段作为该 id 的 `stages[]` 子属性；「失败即停」体现为 stage 级 `not_run` 标记与整体 `failed`，而不是 8 个独立 id。

### F-06 §6 归并表不完整：冻结 32 场景只点名 24 个

- **现象**：§6 覆盖 J-01／UX-01、`E2E-PUB-01`、`E2E-ONBOARD-EVAL`、`E2E-AGENT`、`E2E-USER-JOURNEY`、`SEC-*`、`OPS-*` 及两份文档，**未点名 UX-02–UX-07 六个场景共 36 条变体**。
- **影响**：与 F-01 同源。归并表是「不新增平行主线」这一主张的落地载体，缺项即缺证明。
- **处置**：§6 改为 32 场景逐条列表（场景 id → 新定位 → 主责任域 → 保留／改名的执行体），不再用类别统称。

### F-07 Plan §8.3 的 `npm run lint:spec` 当前即为红，且 12 条 P1 新增 API 未登记进 `03-api-spec.md`

- **现象**：实测 `npm run lint:spec` **exit=1**，12 条 `api-spec` FAIL，全部是 P1 新增路由未登记到 `webui/docs/03-api-spec.md`（该文件 git 状态未修改）：`/api/admin/access-map`、`/api/admin/authorization-summary/agent/:userId`（及其 `/preview`）、`/api/admin/authorization-summary/role/:roleId`（及其 `/preview`）、`/api/admin/hive/connections`（及 `/:id`）、`/api/admin/row-policy/templates`（`/:name`、`/validate`）、`/api/admin/row-policy/views/table`、`/api/admin/row-policy/views/tables`。`npm run lint:terminology` 通过（960 files scanned）。
- **影响**：① Plan §3.4 把 `lint:spec` 写进 W0 退出条件的验证命令清单，而该命令当前为红，W0 会在与 E2E 无关的原因上受阻；② W5 的「事实源收敛」只更新 `impact-map.json`，**没有把 `03-api-spec.md` 纳入范围**，因此 W5 结束时 `lint:spec` 仍然是红的；③ 这批缺失路由正是 F-01／F-04 所涉 P1 功能面，文档债与本次工作面直接重叠。
- **处置**：① W0 退出标准把 `lint:spec` 改为「本次不引入新失败」（与基线差集）而非「全绿」，并在 Plan 中显式记录这 12 条为**既有欠账**；② W5 增加一项，把 12 条路由补进 `webui/docs/03-api-spec.md`——它既是 E2E 影响面分析的前置事实源，也属 P1 功能交付欠账，应显式认领而非留白。

### F-08 v025 清单与既有 catalog schema 字段重叠，存在第二真源风险

- **现象**：冻结 catalog 已有 `executors`（B/P/D/A/O/V）、`requires`（能力门禁）、`assert`（14 个 token）、`artifacts`、`gold`、`repeat`、`matrix`；Plan §2.3 又引入 `requiredEvidence`、`environment`、`blockedReason`、`ownerBranch`。其中 `requiredEvidence` 与 `executors` 语义重叠，`environment`／`blockedReason` 与 `requires` 重叠。
- **影响**：两套字段若各写各的，就会重演「多份 Spec 各自使用 V01」那类串号问题——**正是本 Spec 立意要解决的那个问题**。
- **处置**：v025 清单以 `case-catalog.yaml` 为底扩展（新增 `executionId`、`sourceRequirementId`、`ownerBranch` 三个字段），而不是另建平行 schema；schema 校验直接复用 `scripts/e2e/lib/schema.mjs` 的 `validateAgainstSchema`。

### F-09 W1-6「gold 不暴露给 Agent」缺可执行判据

- **现象**：Spec §4.1 第 3 条要求「不得替 Agent 调用 `lucy_query`」，但全篇没有给出可机械检查的判据；W1-6 只写「gold 不暴露给 Agent」。
- **影响**：§4.4 明确允许「MCP `initialize`／`tools/call` 验证 Token」作辅助证据，而 `mainline-journey.spec.ts` 已引入 `mcpCall` helper——没有判据时，「辅助证据」与「代答」无法区分，Spec 最核心的反作弊主张不可验证。
- **处置**：复用冻结目录已有的现成判据（`mainline-scenarios.mjs:198-199` 的 `prompt === gold.question` 逐字一致），并补一条「客户端 transcript 必须含 ≥1 次工具调用记录，且与服务端 trace 的 `tool_call` 事件一一对应」。

### F-10 §5.3 legacy 旧清单路径未写全，语义表述可更精确

- **现象**：Spec §5.3 只写「旧 `upgrade-feature-checklist.md`／`upgrade-features.yaml`」，未给完整路径。实际路径为 `docs/qa/upgrade-feature-checklist.md` 与 `scripts/e2e/contracts/upgrade-features.yaml`（yaml 在 `scripts/e2e/contracts/` 下，**不在** `docs/runbooks/`）。
- **影响**：低——但 `docs/runbooks/customer-v2-upgrade-release-checklist.md` 不含任何 UPG 编号，读者可能误指。
- **处置**：补全两个路径；并把「旧 UPG-01–14 与新 UPG-01–16 是不同清单」精确为「两者语义完全不相交，但裸编号字符串 `UPG-01–14` 与新 `UPG-01–16` 重叠（前者为后者真子集），故必须加 `legacy:upgrade-feature:` 命名空间」，避免读者误判为可数集包含关系。

实施过程中由测试暴露并已修正的三处**真实**问题（非测试自身缺陷）：

1. **Spec §7.2／§7.3 的 executionId 形式并不统一**：`AUD25-A01`／`ROW25-V01`／`SEM25-V01`／`ARV25-V01`／`ACM25-SC-01`／`HIV25-V01` 保留完整来源 id，而 `RTP25-01`／`RTV25-01`／`ASV25-01`／`UPG25-01`／`RVC25-01` 去掉来源字母前缀。清单**按批准表逐字对齐**，不按推导规则统一；`executionIdFor()` 把这一差异显式编码并被测试锁定。
2. **裸来源编号天然有歧义**：`V01` 同时存在于 ROW25／SEM25／ARV25／HIV25 四个命名空间。消歧依据是**来源 Spec**（四者文件不同），因此 legacy map 的解析键是 `(sourceSpec, sourceRequirementId)` 而非裸 id。
3. **「单一层级通过不等于通过」需要声明式必测层**：仅按已执行维度聚合会把「只跑了 P 层」判成 `passed`。`statusFromDimensions()` 因此显式接收 `required`（取自清单的 `executors`），缺任一必测层即 `not_run`。

#### W0-01（须 PM 裁决，不在 W0 范围内）`test:e2e-harness` 存在 1 项既有失败

- **现象**：`scripts/e2e/__tests__/case-catalog.test.mjs` 报「D-xx is fixed without verifiedBy」。根因是 `docs/qa/security-findings.yaml` 中 **15 条** finding（D-04…D-10、D-12、D-13、D-15、D-11、D-16、D-23、D-24、D-25）处于 `status: fixed` 而 `verifiedBy: []`，违反该台账自身合同。
- **归属**：**既有欠账，非本次引入**。`git show a3f45f0^` 显示 D-04 在更早时为 `status: fixed` + `fixedIn: null`（同样触发该断言），`a3f45f0` 只回填了 `fixedIn`、未补 `verifiedBy`；该文件当前与 HEAD 一致，未被本次工作触碰。
- **影响**：W0 的 e2e harness 基线因此是 **780/781**，不是全绿。Plan §3.4 已按「不得新增失败」记录该基线。
- **处置（PM 裁决）**：① 若这些修复尚无冻结目录中的真实 E2E 证据，`verifiedBy` 应保持为空，状态回退为 `open`（P0／P1 允许）；② 若确有对应冻结变体可引用，则补入真实 catalog id。**不得为让门禁变绿而填入不存在的证据。** 该台账状态属安全缺陷口径，不在 W0 授权内，故本次未改动。
