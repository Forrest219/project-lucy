## 2. 实际改动

| 文件 | 改动 |
|---|---|
| `webui/server/notifications/profile.ts`（新增） | profile／password／CA 的严格解析与校验；封闭错误码（`smtp_profile_invalid`／`smtp_secret_unavailable`／`smtp_ca_unavailable`／`smtp_auth_incomplete`）；**拒绝内联 `password`／`pass`／`secret`**；地址与主机的注入防护 |

| `webui/server/notifications/outbox.ts`（新增） | `notification_outbox` 表与索引（**由通知自身初始化路径创建**）、入队去重、pending 上限 1000、payload 4 KiB／收件人 8 KiB 上限、过期转 dead、保留期清理、事故行查询 |
| `webui/server/notifications/state.ts`（新增） | 通知自身故障的封闭错误码；不改变审计结果 |

| `webui/server/notifications/init.ts`（新增） | 启动初始化：建表 → 读配置 → 订阅健康事件；任何失败只关闭通知本身 |
| `webui/server/proxy/audit-write-health.ts` | **F-13 抖动抑制**：稳定窗口（连续 3 次或持续 60 秒）后才升级为事故／恢复；转换事件订阅；测试重置同步扩展 |
| `webui/server/admin/notifications.ts`（新增） | `GET /api/admin/notifications/status`（owner-only），不进入公开 API 白名单 |
| `webui/server/index.ts` | 监听端口前初始化通知；注册状态路由 |

## 3. 合同落点（F-13–F-17 逐条）

| 发现 | 实现落点 | 证据 |
|---|---|---|
| F-13 抖动抑制 | `audit-write-health.ts`：连续 3 次失败或持续 60 秒才升级为事故；恢复同理；一次事故共用同一 `incidentId`；`recordLedgerAppend` 仍不等待任何 I/O | 测试：3 次失败→1 次事故；ok／unavailable 抖动 10 轮→**0 事件**；恢复复用同一 incidentId；无事故→无恢复 |
| F-14 建表责任与 audit schema 版本 | `outbox.ts` 的 `ensureNotificationOutbox()` 由通知自身初始化路径调用，不依赖 admin 句柄是否已打开；`AUDIT_DB_SCHEMA_VERSION` 的登记留在 S3 随迁移一并处理 | 代码位置 `webui/server/notifications/outbox.ts`；S3 已在 Plan 列为待办 |

### 4.1 实施中确认的一个测试陷阱

L25-04 的新测试首轮出现 4 项失败，根因是 `admin/audit.ts` 的 `getAuditDb()` 持有**进程级单例句柄**：审计库路径无法逐测试切换，跨测试串库。**单跑通过、全跑失败**才暴露。L25-05 的测试沿用同一隔离手法（整轮固定审计库路径 + 每例前清空 `config_change_log` 与 outbox 表），未再复现。
