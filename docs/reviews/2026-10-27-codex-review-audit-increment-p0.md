## 发现的问题

### 阻塞

### 高

#### F-01：N20 以已成功落账集合定义预期分母，无法证明入口无漏记

**位置**：P1 §8.2(b) L333–355、§12.1 L530、§18.5 N20 L882–888；§18.8 L938；A01／A02／A12 L693–704。

**事实与影响**：冻结正文要求 D 来自独立入口计数或受控边界凭据，N 是具有持久 received 的匹配请求；无独立证据必须 unknown。N20 却规定 `D = canonical received IDs ∪ auth_failure_log refusal IDs`，并称这“不改检查项定义”。对已到达但 received 提交失败的合法请求，两个集合都可能没有它，漏记项随之从分母消失；增加一个只记录拒绝的旁路表，不能使成功 received 集合成为自身的独立预期集合。反之，拒绝行进入 D，却按定义没有 received 可进入 N，也没有规定跨两个 ID 空间的映射与合法排除规则，会把正常拒绝混成审计丢失。这不是仅补一个数据源名称的消歧。

**静态佐证**：[实施Plan](../plans/2026-10-25-lucy-v0.25-p0-implementation-plan.md) §4.3 D2 L159 只支持 HTTP 拒绝另表记录，不足以证明所有到达请求均进入 received／拒绝二者之一。当前 `reconciliation-ports.ts` L132–166 仍将除投影追平外的五项来源留为unknown，并未证明N20分母已可独立计算；这与P1 L938的遗留声明一致，不能据回写直接改成pass。

**修订建议**：保留“不让未鉴权请求写业务账本”的部署选择；另明确入口覆盖的声明范围、独立到达凭据与请求身份映射。received与拒绝记录作为被核对的观察集合；正常拒绝按事先声明的边界单列，不直接冒充有received的已接收集合。没有独立到达集合时继续unknown。修订N20的“不改变”论证及L355／L530锚点；若确需更换冻结D／N定义，按§17记录批准来源和新Spec／profile，不能由Plan静默覆盖。A02补“合法到达但received失败且拒绝表无行”，A12保留缺独立证据为unknown的硬断言。

#### F-02：N18 承认精确 as-of S 未完成，正式导出的范围门禁却只检查列存在

**位置**：P1 §12.5 L613–630、§18.6 N18 L916–922、§18.8 L938、元数据L10；A08／A10 L700–702；P4 §3.1 L80、§4.2 L194、§6 L259–260。

**事实与影响**：冻结要求所有基础事实、修订、关联与聚合都可按S重建，且明确禁止只过滤seq便声称一致。N18仍称基础行 `ledger_seq<=S` 是“安全的保守上界”，同时承认该值取写入时账本MAX、access_log在response_prepared前写入、精确视图未实现。写入时MAX并不是该行内容已由哪些提交事件证明的序号；它不能单独保证S后才出现的内容不进入旧S，也不能恢复已覆盖的旧值。“未宣称精确实现”不足以约束一个仍可能发布正式完整包的路径，整体“已实现”还容易掩盖A08／A10的前置能力缺口。

**静态佐证**：`21de5168` 的 `webui/server/admin/audit-export-v2.ts` L509–522 用 `present.has("ledger_seq")` 作为asOfBoundEnforced，再折入scopeComplete；当前L570–583仍是同一判据。当前 `proxy/audit.ts` L599–607说明MAX(seq)口径，L786回退到resolveLedgerSeq；这证明“有列”与“可重建S时刻事实”是不同条件。本项不声称已在线复现错包。

**修订建议**：保留§12.5严格要求，修订N18／§18.8和实施完成范围，明确何时可以证明基础版本及修订均为as-of S；无法证明时 `scopeComplete=false`，正式导出拒绝，只能显式诊断不完整。继续保持三项AND，**不增加第四项**。把此能力列为P0-4正式上下文的前置边界。A10增加捕获S后基础调用结果／delivery发生变化、归属有效值覆盖、迟到ACK的子例，要求相同S的事实与集合不漂移；不能只检查>S新行不混入。后续实现修复另行推进，本次不改代码。

### 中

#### F-03：N24 将预算终止固定为 authorization=not_evaluated，覆盖已发生的授权事实

**位置**：P1 §4.3(b) L120–128、§12.1 L519–524、§18.3 N24 L854–860；A05／A06 L697–698。

**事实与影响**：三视图原义要求authorization按Lucy真实裁决时刻记录，预算终止不能伪装权限拒绝。N24却进一步规定同场景一律not_evaluated，并称为“唯一相容解读”。“不是denied”不能推出“未评估”：先通过授权再被预算停止时，已知allowed仍是事实。该补记把独立轴变成由预算桶反推，可能让API／CSV／P0-4失去真实授权结果。

**静态佐证**：`21de5168` 的 `proxy/mcp-proxy.ts` L3591–3592先aclCheck，不允许则返回；L3663起才consumePersisted。因此预算耗尽路径实际可发生于授权已通过之后。该提交 `proxy/audit-derivation.ts` L223–227及当前同位置按budgetStopped默认not_evaluated，说明此歧义会指导实际派生，而非纯术语问题。

**修订建议**：N24仅固定 `execution=not_executed` 和主状态budget_stopped；authorization优先保留实际裁决凭据：已评估通过为allowed，确实未评估才not_evaluated，证据不足为unknown。保留“预算终止不能编造denied”。同步修订L128锚点说明，A05／A06补“授权先于预算”与“预算先于授权”两个顺序子例；若改变冻结事实轴语义，履行版本与批准记录，不能只称消歧。

#### F-04：A02／A03 未明确覆盖新增的 ACK 闭包及预算持久化失败

**位置**：P1 §10.5 L468–471、§12.1 L528、§12.2 L540–542、§12.6 L639–652；A02／A03／A06 L694–698；§11.1 L483。

**事实与影响**：A02明确只列received、admitted、response_prepared三屏障，这三类覆盖充分；但S01／S07还新增client_observation、delivery_evidence及预算持久化的失败分支。A03只写一般观测重投，A04／A09聚焦ACK有无与错配，A06聚焦耗尽／连续性；均未明确断言“观测已落账、ACK闭包失败后同ID重投必须补闭包”的中间态，也未明确预算读／写失败均须拒绝分派且不伪造budget_stopped。仅按当前表的字面场景全部执行，仍可能遗漏这些分支。

**修订建议**：在既有A编号下增加命名子例并登记预期事件ID／关系／证据：①client_observation提交失败，无ACK；②观测成功而delivery_evidence失败，保留pending，重启／同ID重投只补审计闭包一次、不重执行业务；③预算读取及写入失败，503、不分派、无虚构预算耗尽凭据；④失败响应自身提交失败按durableFailureOrBlock阻断。对于发送已发生后的delivery／terminal追加失败，只要求独立告警和恢复核对，不要求撤回已发送内容。Stage适用性按U9单独登记，所有新增子例继续未执行。
