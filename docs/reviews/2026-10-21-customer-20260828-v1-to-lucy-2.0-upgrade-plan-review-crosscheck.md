## 1. 结论

那份评审的代码锚点大部分核得上，可以作为修订意见的起点。三件套同升、开放模式到 `bootstrap`、绝对拒绝名导致整角色编译失败、审计库只加表加列、`helm rollback` 不恢复 PVC、r6 仍是 Draft，这些认同项成立。

需要改口的是严重性，不是方向：

1. 反向代理这一项必须补进计划。其中「全站共用 Ingress 地址做限速」是 https 域名映射就能推出的后果；「认领和登录当天被 403」取决于网关是否改写 `Host`，不能写成已经必然发生。
2. `enabled_tables` 缺省等于空集，这条代码事实成立。把它说成「对本客户接近必然」超出了仓库里能核到的证据。
3. 「必须登录」在 2.0 customer 模式里是代码事实，在「为了修 400 而升级」这个更大问题上是产品决策。计划应写明后者。评审把「先升 0.17.0、再升 2.0」写成推荐路径，超出了这份计划已经声明的 2.0 范围。
4. 评审建议的几处改法，按现有 `deploy.sh` 升级合并规则落不下去：升级入口不会采纳计划里新加的 `extraEnvFrom` 或 `LUCY_CONTENT_ROOT`。只改计划文档不够。
5. 把执行文件名全部改成 `examples/RECOVERY.open-mode.md` 会和部署契约冲突。包内模板是这个名字；真正执行的填写稿必须叫 `RECOVERY.md`。

### 2.2 反向代理必须写进计划

计划全文没有 `LUCY_TRUST_PROXY` 或 `LUCY_TRUSTED_PROXY_CIDRS`。`deploy/k8s/helm/lucy/` 下也没有这两项。Chart 只在 `values.yaml:240` 留了空的 `extraEnvFrom`。

限速这条是确定的。`webui/server/auth/rate-limit.ts:48-58` 的 `clientSource()` 只有在 `LUCY_TRUST_PROXY` 开启、且直连 peer 落在 `LUCY_TRUSTED_PROXY_CIDRS` 内时，才采用 `X-Forwarded-For`。否则用 socket peer。客户流量从 https 域名进来时，Pod 看到的 peer 是网关地址。计划 §5.5 的「登录 5 次失败 / 15 分钟、bootstrap 5 次失败 / 15 分钟」会变成全站一个计数器。`K8S_CONTRACT.md:165` 已写明这个后果。

CSRF 判定也是真实代码。`web-security.ts:36-54` 对带 `Origin` 的 `/api/` POST / PUT / PATCH / DELETE 比较 `Origin` 的 host 与 `effectiveHost()`。`effectiveHost()`（`:29-34`）只在 `LUCY_TRUST_PROXY` 开启时读取 `X-Forwarded-Host`，否则用请求的 `Host`。该钩子在 `index.ts:603` 注册，认证钩子在 `:643`，所以 403 发生在认领和登录之前。`POST /api/auth/bootstrap` 与 `POST /api/auth/login` 都在这组方法里。`/api/health` 是 GET，不会暴露这个问题。

Cookie 这条评审也核对了：`session.ts:171-178` 的 `Secure` 只看 `resolveCookieSecure()`，而 `deployment-mode.ts:46-68` 只看环境变量。TLS 在网关终止、Pod 侧是 HTTP，不会因此丢掉 `Secure`。`security.access=https` 会发 HSTS（`web-security.ts:77-79`）。

公开 MCP 地址不会从 `Host` 推断。`runtime-config.ts:33-47` 在 `LUCY_PUBLIC_MCP_URL` 为空时回落到 `http://127.0.0.1:7879/mcp`，状态是 `fallback`。这就是「目录能看、数据查不了」。

WebUI 与 Agent 的分界也成立：`App.tsx` 的路由表没有 `/ask`、`/chat`；问数走 Bearer Token。`guard.ts:38-52` 的免登录 API 就是评审列出的那 9 条。`admins-store.ts:10` 的 WebUI 角色只有 `owner` 与 `operator`。计划只写了认领首个 owner，没写其余使用 WebUI 的人如何建成 operator。这个缺口应补进 §5.5。

### 2.3 快路径确实还能保持开放模式

`git merge-base --is-ancestor 34d0a51 e08de17` 退出码为 1。`e08de17:webui/server/auth/deployment-mode.ts` 不存在。该提交的 `resolveAuthMode()` 在无管理员且未设 `required` 时返回 `open`，`_helpers.tpl` 没有 `LUCY_DEPLOYMENT_MODE`。`customer-mcp-session-400-upgrade.md:88-97` 把 `20261009-v1`（Lucy 0.17.0 / Chart 0.2.4）标为已发布的 400 修复路径。V-01 在 `docs/qa/security-findings.yaml:11-16` 是 P0，`status: fixed`，`fixedIn: eb4f6f2`。客户现在的无登录、无管理员状态，就是这条已修复缺陷在旧版本上的敞口。

因此：在 2.0 包内，开放模式没有合法开关；在「这次升级要解决什么」上，直接到 2.0 是一次产品选择，同时关闭 V-01。计划 §1.4 和 §5.5 应写成这个意思。

## 3. 反对

### 3.1 R1 的 403 不是 https 域名映射的必然结果

`csrfDenied()` 在没有 `Origin` 时直接放行（`web-security.ts:44-45`）。浏览器从登录页发 POST 时会带 `Origin`。比较的是 `new URL(origin).host` 与 `Host`（或被信任的 `X-Forwarded-Host`）。

网关如果保持浏览器原始 `Host`（Ingress-NGINX 的常见默认是 `$host`），host 与 `Origin` 一致，不配 `LUCY_TRUST_PROXY` 也不会 403。只有网关把 `Host` 改成上游 Service 地址，例如 `proxy_set_header Host $proxy_host`，才会 403。评审 §7 自己也把网关行为标成现场待证，但 §1.2 和 R1 标题把「升级当天无法登录」写成了主结论。应拆成两句：

- 限速共用网关地址：只要流量经过反代且两个变量都没配，就会发生。
- 认领 / 登录 403：P1 要记录网关实际转发的 `Host` 与 `X-Forwarded-Host` 之后才能判定。

评审建议的探针也不够。不带 `Origin` 的 `curl POST /api/auth/login` 会穿过 CSRF 检查，得到 401 或其他认证错误，造成假通过。探针必须走客户正在用的 https 域名，并带上 `Origin: https://<该域名>`。通过标准是这条请求不是 `403 CSRF_ORIGIN_DENIED`。

另外，CSRF 的 `effectiveHost()` 不看 `LUCY_TRUSTED_PROXY_CIDRS`，限速才看。只打开 `LUCY_TRUST_PROXY` 会让任何能直连 Pod 的客户端用 `X-Forwarded-Host` 影响 Origin 比较。Service 应继续只让已核对的网关访问。

### 3.2 R2 把「空集语义」说成了「这个客户几乎一定会中」

`acl.ts:1037-1046` 对每个连接执行 `new Set(conn.enabledTables ?? [])`。`isInEnabledTableRange()`（`:1076-1082`）在集合缺失或为空时返回 false。Spec 182 写明：缺省、空数组、连接不存在都是空集，不能退回该连接的全部 source。过滤发生在 `selectorMatches` 之后（`:1209-1213`），滤空则 `selector_zero_match`（`:1225-1237`）。`catalog_bound` 走同一个判断（`:1085-1094`）。没有 table selector 的纯元数据角色，Spec 182 §3 明确不受这条规则影响。

由此可以推出的是：某连接没写 `enabled_tables` 时，点到该连接的 selector 角色和 `catalog_bound` 角色会编译失败，Pod 仍然 Ready。推不出的是：这份 2026-08-28 的现网 `ktx.yaml` 一定没写该字段，角色也一定都用 `tableSelectors`。这两份文件不在仓库里。评审 §7 已承认这一点，R2 的「接近必然」与 §7 冲突。

处置力度上，评审是对的：P1-7 的一次人工扫描不够，应用目标镜像对 PVC 副本做只读角色编译，记下每个角色是否编译成功以及有效 source 数。L4 现在的「每个角色仍有可用的有效 source（P1-7 基线对比）」只保证「还有 source」，一个角色从 10 个 source 剩 1 个也会通过。硬断言应是逐角色有效 source 数不少于基线，编译失败的角色单列。比较键是 `normalizeRef(physicalTable)`，形如 `schema.table`，不能用源名称做字符串交集代替编译。

### 3.3 R3 的三选一里，推荐项和 OIDC 项都越界了

计划的适用范围已经写成 0.16.0 → 2.0.0 / Chart 0.2.6。在这个范围内，customer 模式不会开放，这是代码，不是修辞。

应补的是范围说明：若本次目标只是消除 `MCP initialize request is required before session traffic.`，已发布的 0.17.0 / Chart 0.2.4 可以修，并且仍是开放模式；它不含 2026-10-18 的会话归属与撤销屏障。选择 2.0 是为了带上这些加固，并关闭 V-01。客户沟通稿应这样写。

评审把选项 A（两个维护窗口，先 0.17.0）写成推荐，等于改写了这份计划的目标。那是另一次产品决定，不应作为本计划执行前的必修项。

选项 C 把「继续开放访问」的出路写成等 2.5 OIDC，依据是 `docs/plans/2026-10-18-lucy-2.5-upgrade-proposal.md:111-115`。该节写的是对接客户身份源，Lucy 仍保留本地账户，用于首个 owner 和 break-glass。OIDC 不恢复匿名开放管理面。2.0 上保持开放访问没有被支持的配置；这句到此为止。

### 3.4 R4 把「私有 CA」写成了所有 https 客户的必经路径

C03 的原文是：明确选择 HTTP 或 HTTPS；Cookie 与公开 MCP URL 与该选择一致；https 使用私有 CA 时，私有 CA 随实例交付。`CUSTOMER-UPGRADE.md:27` 写明没有私有 CA 就删除 `tlsCaFile`，使用系统信任库。公有 CA 的域名不需要随包带 CA 文件。

计划确实漏了 https 分支，应补三条，而不是把私有 CA 当成必经：

1. 实例 `access` 与 `webuiUrl`、`publicMcpUrl` 同为 `https`。
2. 外部网关已核对时设 `externalTlsReviewed: true`。Chart 自管 Ingress 则走 Ingress TLS，而不是这个标记。
3. 只有证书链是私有 CA 时才填 `tlsCaFile`，并让取证机信任该 CA。取证不得用 `-k`。

### 3.5 R5 对 `RECOVERY.md` 的改法是错的

包内没有与 `CUSTOMER-UPGRADE.md` 并列的 `RECOVERY.md`。打包脚本把它复制为 `examples/RECOVERY.open-mode.md`（`scripts/gates/build-k8s-delivery-package.sh:224`）。计划 §1.6 把三个文件并列，这句不准确。

执行契约用的是另一个名字。`CUSTOMER-UPGRADE.md:24` 要求把模板抄成私有配置目录里的 `RECOVERY.md` 并填写。`prepare-customer-instance.py` 再把它放进客户目录，文件名固定为 `RECOVERY.md`。`customer-deployment-helper.py:258-259` 要求 `instructionsFile == RECOVERY.md`，并校验该文件哈希，否则 `RECOVERY_CONTRACT_INVALID`。两个升级样例 JSON 的 `instructionsFile` 都是 `RECOVERY.md`。

评审建议把 P0-3、P4、L5、§7、§9 全部改成 `examples/RECOVERY.open-mode.md`。按那个名字执行，部署入口会拒绝。正确写法是：模板为 `examples/RECOVERY.open-mode.md`；填写并执行的文件为实例目录中的 `RECOVERY.md`。

`schema_unsupported` 是真分支（`webui/server/security/schema.ts:141-146`）：security 库版本高于本二进制支持的版本时拒绝，不降级。这个客户没有 `.ktx-ui/security.sqlite`，2.0 会新建当前版本的库。该分支不会在 20260828 → 2.0 的首次升级触发。它约束的是以后从更新的 security 库回退。计划把 `security/schema.ts` 和审计库的「纯增量、旧库直接可用」写在同一条证据里，容易混成一个库。应拆开，不必把它列为这次现场会踩的文档错误。

### 3.6 评审给出的 values 改法，现有升级入口不会采纳

`deployment_values()`（`customer-deployment-helper.py:119-146`）在 `intent == upgrade` 时只从实例配置叠加 `lucy.version`、`lucy.bundledKtxVersion`、镜像、`publicMcpUrl`、`security.access`。随后在需要引导密钥时写入 `bootstrap.existingSecret`（`:311-313`）。Service 类型、Service 端口、`extraEnvFrom`、`LUCY_CONTENT_ROOT` 都留在现场 Helm 旧值里。旧值没有的键，升级后仍然没有。

因此：

- 评审 R1 建议「在 §5.1 增加 `extraEnvFrom`」只改文档时，`deploy.sh` 不会把这两个变量送进 Pod。
- 计划要求 pre-M31 设置 `LUCY_CONTENT_ROOT: "."`，同样不会经这条升级合并生效。现场 `ls` 只能决定该写什么，不能让当前脚本把它写进去。
- 计划 §5.1 第 13 项「`LUCY_PUBLIC_MCP_URL` 原样保留」与脚本行为不一致。脚本用实例 JSON 的 `publicMcpUrl` 覆盖该环境变量（`:139`）。应把客户 Agent 实际调用的 `https://<现有域名>/mcp` 写入 `publicMcpUrl`。旧 Helm 值只有在与这个地址相同的时候才被抄进去。

要让信任代理和内容根在这次升级里生效，需要改 `deployment_values()` 的升级白名单，并给实例 JSON 增加对应字段。只改计划正文，现场按包内 `deploy.sh` 执行时这两项仍然缺失。

## 4. 评审未覆盖、计划里仍然有的问题

1. **§5.1 第 6 项与升级入口相反。** 计划要求改成 `LoadBalancer` 并对外暴露 8276/8277。这是 `UPGRADE.md` 里 K3s 实验室那一行。客户模板默认是 `ClusterIP` 与 5174/7879。`deployment_values()` 保留现场 Service。客户已经有 https 域名时，应保留该域名指向的 Service 类型和端口，只把容器监听端口拆成 5174/7879，并核对 `/` 到达 WebUI、`/mcp` 到达 7879。不要为了实验室端口再加一个 LoadBalancer。
2. **L3 与 §5.3 互相否定。** L3 要求 `access.yaml` 哈希不变，且 `webui/config/` 指纹 diff 为空。绝对拒绝名或启用表交集需要改 `access.yaml`；认领会新建 `webui/config/admins.yaml`。判定应改成：除决策表记录的权限变更和 2.0 新建的管理员文件外，业务文件哈希不变。
3. **P0-5 放在验收之后会作废刚验收的包。** C19 要求新包名、提交和摘要唯一，旧包作废。P0-1 至 P0-4 验收的是 r6，P0-5 再跑出包入口会得到另一个包。顺序应是缺陷修完后只出一次正式包，原生升级和恢复验收打在这个包上；验收失败才重出包并整段重跑。
4. **P4 不应在客户生产上还原旧卷。** `ACCEPTANCE.md` 与 `RECOVERY.open-mode.md` 把恢复演练放在同类测试环境。生产上还原初始备份会第二次停机，并撤掉刚认领的管理员。P0-3 已经覆盖供方演练。客户现场只在升级失败时走 `RECOVERY.md`。
