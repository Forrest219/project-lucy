### 4.1 隔离验证协议（本轮全程遵守）

共享工作区有**外部 agent**（Cursor Agent，PID 2942，cwd ＝ 本仓库）并行改 P0-4 审计对账线，并把 `reconciliation-ports.ts` 写成语法损坏。本轮据此建立隔离协议：

1. **类型检查与测试一律在隔离检出 `inbox/p1-verify`**（由 `git archive HEAD` ＋ 本轮产出构成），**不污染也不被污染**。
2. **硬判据**：`npx tsc --noEmit` 的错误数必须等于 HEAD 基线 **70**，且**本轮文件不得出现在错误列表中**。本轮实测：**70**，本轮文件 0 命中。
3. **外部 agent 的文件一律不改、不修、不提交**（清单见 §9；清单随其产出实时扩展，本轮收尾时为 **20 个**）。
4. **提交按路径显式 `git add`**，禁用 `git add -A`。
5. 隔离同步脚本的「排除」**必须还原为 HEAD 版本**（不能只是「不再复制」），否则早前扩清单前被污染的外部测试文件会残留 —— 本轮已修（`RESTORED_COUNT` 计数可见）。
6. ★ **验证树必须物化在仓库内**（如 `inbox/p1-verify`），**不能放在 `/tmp` 等仓库外路径**。原因：`resolveProjectRoot()` 从启动目录**向上**找 `ktx.yaml`；`ktx.yaml` 是 gitignore 的本地文件（不入库），仓库外的树向上找不到它 ⇒ 依赖内容路径的用例会以 `Could not find ktx.yaml` 假红。仓库内的树向上会落到仓库根、捡到那份本地 `ktx.yaml`，口径与真实运行一致。

   > 本轮收尾时实测过这个坑：把已提交的 HEAD（`952be37`）用 `git archive` 物化到 `/tmp/lucy-head-verify`，全量跑出 **8 文件 / 22 用例失败**；改到仓库内 `inbox/p1-head-verify` 重跑 ⇒ **331 文件 / 3877 用例 / 0 失败**。**同一份提交物，差异只在树的位置** —— 那 22 条红是环境假象，不是提交物缺陷。

### 8.1 Hive 接入 MCP 入口的**接入面**（只读勘察，零改动）

本轮**没有**改 `mcp-proxy.ts`（外部 agent 并发清单）。为了让 PM 能带着事实决策，而不是对着一句「没做」拍板，这里记下只读勘察到的接入面。

**`lucy_query` 的真实执行路径**（Lucy 侧不做 SQL 执行，而是**转发给 KTX**）：

```
tools/call
  → aclCheck()                      mcp-proxy.ts:3593   ACL 准入
  → forwardAuthorizedLucyQuery()    mcp-proxy.ts:3454 / 5250
      → authorizeAndRewrite()        同一道准入 ＋ forced_filters 改写
      → forwardToKtx("POST","/mcp", tools/call lucy_query)   转发给 KTX 上游
```

因此 Hive 编译链的**唯一钩子点**是 `forwardAuthorizedLucyQuery()` 内部「转发给 KTX 之前」那一处：按请求的 `connectionId` 判断是否为 Hive 连接，是则改走 Hive 链，其余连接**完全不动**。

**这个判断有 Spec 依据**（[P1-4 Hive 直连 Spec](../specs/lucy-20261025-v0p25-hive-direct-connection-spec.md) §3 工具／入口合同表）：`lucy_query` 与获准的 `sl_query` 别名「同一 Lucy 准入后进入 Hive 编译／执行链」—— 即 Hive 链接在**同一道准入之后**，而不是另开入口。

**改动面估计**：

| 位置 | 改动 |
|---|---|
| `webui/server/hive/`（新增 1 个文件，如 `mcp-bridge.ts`） | 全部新逻辑放这里。`hive/index.ts` 这个 barrel 已经是「其他波次唯一应 import 的入口」，接线代码**不需要**碰 `mcp-proxy.ts` 以外的东西 |
| `webui/server/proxy/mcp-proxy.ts` | **1 处分支**：`forwardAuthorizedLucyQuery()` 里按连接类型分流 |

**不改的部分**：ACL、预算、审计、行策略改写、KTX 转发路径（非 Hive 连接）**一律不动**。

**当前能力边界（必须说清）**：Hive 管线 13 个阶段中，`jdbc` 阶段由 `HIVE_UNIMPLEMENTED_STAGES` 显式标为未实现（属 H25-03）。所以即使接线，`lucy_query` 对 Hive 连接也只走到「编译 ＋ AST 校验 ＋ 准入账本」，随后在 `jdbc` 阶段以 `hiveNotImplementedFailure` 如实返回，**不会**假装查询已执行 —— 这正是 V01（只编译、不连库）要求的形态。

**结论**：接入**在技术上没有障碍**，卡点是**文件归属冲突**（外部 agent 仍持有 `mcp-proxy.ts`）＋**本轮计划明确不做**（§7.3／§14 第 9 条）。建议 PM 二选一：① 等外部 agent 收工后按上表做一次独立变更；② 授权在隔离分支上提前做（届时需同时裁决是否接受与外部 agent 的合并冲突）。**本轮不擅自扩范围。**
