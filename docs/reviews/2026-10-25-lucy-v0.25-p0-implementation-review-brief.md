## 5. 影响设计的裁决记录

以下裁决**改变了设计语义或口径**，审阅时值得优先回看。

### 5.1 N1（Forrest 裁定，2026-10-25）—— L25-14 的 G5 归因：改法 1

- v0.25 **只做可归因诊断、不修 G5**；目录加载锚定实际请求路径 `bidm.yaml`，**不做真实大小写解析**。
- G5 下判定 `manifest_unavailable` 且 `stage=resolve` → 归因「清单不可用，指向运维」。
- 真实大小写解析留 **0.20.Z 维护线**；**D-03 保持 `fixedIn: null` / status open**；V19／V22 仍是「D-03 集成回归」条件项，保持成立。

### 5.2 D-12（冻结判据的自保）—— `combinedComplete` 不得有第四个合取项

`combinedComplete = scopeComplete AND fileHashOk AND relationCheckOk` 是 audit-trust R1 验收矩阵的**冻结判据 #6**，有双向防漂移守卫测试。本轮修 D-10（as-of 上界）时，最初把闸门写成第四个合取项 `&& asOfBoundEnforced` —— 这会**让冻结判据被自身的修复判为 fail**。

最终修法：把 as-of 闸门**折进 `scopeComplete`**（as-of 边界无法落到行上 → 范围不可证明完整 → `scopeComplete=false` → 正式导出 fail-closed），使三项 AND **由构造保证**。生产行为不变（`access_log.ledger_seq` 是 additive 列，由 `ensureColumn` 保证存在）。

> **审阅提示**：这是本轮唯一一个「修复动作差点破坏冻结契约」的案例，且是自伤。请重点核对折进后的判定式与 §12.5 的 fail-closed 是否仍然等价。

### 5.3 D-13（不可观测 ≠ 0）

配置读不到时，配置计数／分母／比率／三个配置相关差异 `count` 一律为 **`null`**（不是 0），`ratioNullReason=not_collected`、`flagged=false`、`reason=configuration_not_observable`；CSV 的 `configured` 段显式写不可观测，差异集合写 `not_collected` **不写** `empty`。

### 5.4 D-11 的范围更正（声明过宽）

D-11（ZIP 解压无输出上限）的限幅**只覆盖了 `semantic-maintenance-package.ts` 一条路径**；生产发布／校验入口 `semantic-assets.ts` 的解包仍无上限。D-11 在台账按「部分修复」记，剩余缺口另立 **D-19** 跟踪。**不得**据此认为解包风险已关闭。

### 5.5 D-14（本轮未修，预存在）

交付种子 `customer-config.example/webui/config/access.yaml` 的 `customer_readonly.allow.tools` 列了代码基线 `ABSOLUTE_DENY_TOOLS` 里的 `sl_query` / `sl_read_source` → `/api/health` 报 `status=degraded`、`degradedAgents=[customer_agent]`、`policy.healthy=false`；行级预览对该角色的任何表返回 `role_resolution_failed:customer_readonly:tool_absolute_deny:sl_query`。W7 复验在运行容器中确认复现。修它要改交付种子的有效能力 → 属冻结目标集合变更，已交 PM。

### 7.3 D-25 的完整取证链（本轮唯一的「新缺陷」）

1. 现象：`usage` 间歇性 503（连续三次 → 200 / 200 / 503），错误 `RECONCILIATION_READ_REFUSED`。
2. 容器日志：失败请求的 id 是 `req-9` 与 `req-d`。
3. 直查容器内 `security.sqlite`：`security_events` 已存在 `reconciliation-read-req-9`（seq 7）与 `reconciliation-read-req-d`（seq 8），时间戳来自**上一轮**容器。
4. Schema：`event_id TEXT NOT NULL UNIQUE` → 本轮同名写入撞唯一约束 → `SECURITY_CONFLICT` → 守卫把「id 撞车」误判成「安全账本不可用」。
5. 根因：Fastify 的 `request.id` 是**每进程计数器**（base-36），进程重启后复用。全仓**仅**本轮新增的 P0-4 对账路由把 `request.id` 用作 `event_id`（既有路由用 `audit-association-revision-${row.id}` 这类内容派生的稳定 id，跨重启唯一）→ **本轮实现引入**。
6. 修法：`event_id` / `operation_id` 改由每次读取的 `randomUUID()` 派生；`request.id` 降级为 `trace_id` 保留可追溯性。**拒绝语义未放宽**（actor 不可解析 401／账本不可用 503／meta-audit 写入失败 503 全保持）。

> 这条恰好证明：**单元测试全绿不能替代重建后的运行时复验**。D-25 在 3559 个用例全绿的状态下依然存在。
