### 3.3 新增发现与关闭（F-09–F-17，均为实施前待办，不退回）

#### F-09 L25-04 §3.1 字符规则与 §6 伪代码的检查对象不一致

- **现象**：§3.1 长度行写「trim 后 0–80 code point」，字符行只写「禁止 C0／C1 控制字符和换行」，未说检查对象；§6 伪代码是 `codePointLength(normalized) > 80 or containsControlCharacter(value)`——**控制字符检查在 trim 前的原始值**上。
- **分歧**：原始值 `"数据治理组\n"` 按伪代码判非法，按散文（trim 后检查）判合法。SKO-05「首尾空白」与 SKO-06「控制字符」在边界值上会得出相反结论。
- **关闭（已回写）**：§3.1 字符行明确「控制字符检查作用于 trim 前的原始值，首尾 `\n`／`\t` 同样判非法」；SKO-06 通过标准补该边界值。

#### F-10 L25-04 §3.2 未指定 validator issue 的 `type`，可能让既有 Skill 的校验结论翻转

- **代码事实**：`webui/server/skills/validator.ts:66-69` 为 `valid: issues.every((issue) => issue.type !== "error")`——**只有 `type:"error"` 才使 `valid` 变为 false**；`SkillValidationIssue.type` 是 `"error" | "warning"`（`types.ts:44-55`）。最接近的同构字段 `roles_allowed` 损坏用的是 `type:"error"`（`validator.ts:38-45`）。
- **影响**：Spec §3.2 只写「validator 增加 `skill_owner_invalid`，字段为 `owner`」，未写 `type`。若实施者按 `roles_allowed` 的既有模式取 `error`，则一条既有 Skill 会因 owner 损坏而 `validation.valid` 由 true 翻转为 false，进入工作台「校验未通过」筛选桶——这是对**存量内容**的可观察回归，而 D04 只约束「负责人缺省」，未授权「损坏即判校验失败」。§5.2 的「使用既有 warning 样式」只是显示层，不足以约束 `valid`。
- **关闭（已回写）**：§3.2 明确该 issue `type` 固定为 `warning`，且**不得使 `validation.valid` 翻转为 false**；owner 损坏（只披露、不阻断）与 `roles_allowed` 损坏（影响运行时授权，故 error）的差别写入同段；SKO-06 补该断言。

#### F-11 L25-04 §7「码／展示」未钉死文案归属，且前端映射表未列入合同

- **代码事实**：skills 错误信封是**单字符串**——`webui/server/admin/skills.ts:25-33` 的 `writeErrorReply` 发送 `{ ok:false, error: err.message }`；`SkillWriteError` 仅有 `message` 与 `statusCode`（`writer.ts:15-22`）。既有码（`skill_write_conflict` 等）是**当作 message 字符串**抛出的。前端 `webui/src/lib/skills.ts:103-118` 按已知码查表映射为中文，查不到时**直接回显原始字符串**。
- **影响**：§7 把「码」与「展示」并排列出，但同一个响应里只有一个字符串字段，两种合法实现后果不同：后端发中文 → 前端查表落空、无稳定码可自动化；后端发 `skill_owner_invalid` 而**前端映射表未扩** → 界面直接显示裸码 `skill_owner_invalid`。§5 WebUI 合同七条**没有一条**要求登记前端映射表，验收矩阵也没有任何一项断言用户可见文案。
- **关闭（已回写）**：§5 增加第 8 条——后端 `error` 只回稳定码，`skill_owner_invalid` 必须登记到 `webui/src/lib/skills.ts` 错误映射表，界面不得显示裸码；§7 表后补「两者不出现在同一个响应里，后端不得把中文塞进 `error`」并指向前端查表实现位置。

#### F-12 L25-04 SKO-16 的 selector contract 门禁在既有基线即为红，验收项不可达

- **实测**：`npm --prefix webui run e2e:selector-contract` → `[FAIL] 24 issue(s) require attention`（含 OIDC 面板多个 `UNREGISTERED` testid）。工作区未改动 `webui/src`／`webui/tests`／`docs/qa`，故为**既有欠账**，与 L25-04 无关。
- **影响**：SKO-16 原写「…selector contract…通过」，实施方要么去修 24 项越界 issue（超出 L25-04 授权），要么该验收项永远为红。另：若为负责人单元格新增 `data-testid`，未登记进 `docs/qa/selector-contract.md` 即触发 `UNREGISTERED`。
- **关闭（已回写）**：SKO-16 改为「selector contract **不新增 issue**（既有基线为红，不在 L25-04 授权范围内）」；§9 S3 明确新增 `data-testid` 须登记进 `docs/qa/selector-contract.md`。

#### F-13 L25-05 §4.1 缺抖动抑制：一次瞬时故障会被翻译成一对事故＋恢复邮件

- **代码事实**：`webui/server/security/ledger.ts:113`（store 不可用）、`:125`（批次成功）、`:133`（**批量内逐事件** `recordLedgerAppend(result.ok)`）都会翻转 `audit-write-health.ts:43` 的 `ledgerUnavailable` 布尔位；该模块是**无计数、无边沿检测**的（`:46-57`）。
- **影响**：一个批次内部分事件失败、部分成功时，标志可在同一批次内 ok→unavailable→ok 翻转。照 Spec §4.1 的事件定义（ok→unavailable 为事故、unavailable→ok 为恢复）直译，一次瞬时单事件失败即产出**一对**事故与恢复邮件，多次抖动即刷屏——这正是 §4.1「持续失败不重复刷屏」想避免的结果。现有按随机 `incidentId` 的去重对抖动**完全无效**（每次翻转都是新 incident）。
- **关闭（已回写）**：§4.1 增加「抖动抑制（必须）」段：事故需连续 3 次失败或失败持续 60 秒，恢复需连续 3 次成功或成功持续 60 秒，窗口内翻转不发事件，一次事故共用同一 `incidentId`；常量为固定口径，不进 profile、不增 Helm 参数。SMTP-08／09 补该验收口径。

#### F-14 L25-05 §5.1 未钉死 outbox 表创建责任，也未提 audit.sqlite 的独立 schema 版本

- **代码事实**：`webui/server/admin/audit.ts:338` 的 `getAuditDb` 与 `webui/server/proxy/audit.ts:378` 的 `getDb` 是**两个独立连接句柄**，各自执行自己的 `CREATE TABLE IF NOT EXISTS` 块，指向同一 `.ktx-ui/audit.sqlite`。另有 `webui/server/proxy/audit.ts:219-223` 的 `AUDIT_DB_SCHEMA_VERSION = 3`，注释明示其为「独立于 SQLite `PRAGMA schema_version`」的版本，且「Bump together with new audit_meta entries」。
- **影响**：① Spec 只写「复用 `getAuditDb` 的幂等初始化」，但 worker 若在 admin 句柄首次被调用前启动并写库，会命中 `no such table`；② Spec §5.1／§10.2 只说「不修改 security schema 版本」，而 outbox 表落在 **audit.sqlite**——它有自己的版本机制与 `audit_meta` 登记约定，「不改 security 版本」不能替代「audit 版本是否递增」这一治理动作，漏做即版本漂移。
- **关闭（已回写）**：§5.1 增设「创建责任与版本口径」——outbox 表由 notifier 自身初始化路径幂等创建、worker 领取任务前必须完成该初始化、失败按 §5.3 outbox 不可用处理；新增表须在 `AUDIT_DB_SCHEMA_VERSION` 机制下登记（递增并同步 `audit_meta`），并明示 security 版本与 audit 版本是两件事。

#### F-15 L25-05 §6 伪代码把两类 503 混成一个码，与 §9 封闭错误码表冲突

- **现象**：§6 伪代码 `POST test as owner` 只写 `if not persisted: return 503 NOTIFICATION_UNAVAILABLE`；§9 表则把「outbox 满或不可用」定为 `NOTIFICATION_QUEUE_UNAVAILABLE`。
- **影响**：配置无效与队列满／存储不可用两种根因落到同一码，运维排障与用户提示都失去区分度；§7 的 `degraded` 状态分层也随之失真。
- **关闭（已回写）**：§6 伪代码区分「配置无效／未启用 → `NOTIFICATION_UNAVAILABLE`」与「队列满／存储不可用／未持久化 → `NOTIFICATION_QUEUE_UNAVAILABLE`」；SMTP-15 补错误码断言。

#### F-16 L25-05 §7／§9 的 403 文案与 `requireOwner` 硬编码文案冲突

- **代码事实**：`webui/server/auth/guard.ts:149-154` 的 `requireOwner` 硬编码 `message: "仅所有者可管理管理员账户"`，**不接受文案参数**。
- **影响**：§1.1 说「复用 owner 裁决」、§9 却给通知接口写「仅所有者可管理邮件通知」。直接复用会让通知接口显示「管理管理员账户」（误导）；要按 §9 显示则必须改 `requireOwner` 签名，而该函数被多个既有管理路由共用，改动面与回归范围 Spec 未提、§12 S2 也未列。
- **关闭（已回写）**：§7 增设「403 文案归属必须二选一」——① 直接复用并接受既有文案（§9 相应删去自定义文案），或 ② 给 `requireOwner` 增加可选文案参数、仅通知路由传入，并把该签名改动及对既有路由的回归范围列入 §12 S2；明令通知接口不得显示「管理管理员账户」。§9 该行指向 §7。

#### F-17 L25-05 重新启用后历史行是否投递，无验收落点

- **现象**：§3.2 写「`enabled=false` 时…历史 outbox 保留但不投递，**重新启用后再处理未过期任务**」；§5.3 与 SMTP-11 只约束「关闭期间不产生新行、不补发关闭期间事件」，**没有任何验收项断言重新启用后关闭前排队的行是否投递**。SMTP-21 只覆盖「重启后使用新配置、历史行按原收件人快照和有效期处理」，未把「重新启用」明确纳入。
- **影响**：两种合法实现（重新启用后投递 7 天内的历史事故邮件，或不投递）在验收上无法判别；用户可能收到一周前的「审计账本不可用」提醒。
- **关闭（已回写）**：SMTP-11 明确「重新启用并重启后，关闭前已排队且未过期的历史行按原收件人快照投递，过期行不投递」。
