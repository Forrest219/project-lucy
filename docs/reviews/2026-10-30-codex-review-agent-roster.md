# Agent 名册：Codex 交叉审阅

- 审阅方式：本机 Codex CLI 0.163.0，`codex exec -s read-only`，只读，未改 Spec / Plan 正文。
- 对象：Spec v1.0 与 Plan v1.0（`lucy-20261030-agent-roster`）。
- 结论：**退回修订，不批准交付开发。** 阻塞 0，高 3，中 3，低 0。

## 发现

1. **R1｜高｜分类关键分支缺少可证伪验收**
   - 位置：Spec §6，SC-05–SC-09。
   - 问题：没有 SC 验证「协议量为 0，只靠时间条件判为仅连接」。实现删掉时间条件后，现有 SC 仍可能全部通过。也未覆盖 `usageCallsLast7d` 缺失但没有显式 `unavailable`，以及 `usageCallsLast7d = 0` 且 `lastBusinessSeen` 落在窗口内的反例。
   - 最小修复：补时间条件的正反路径、窗口起点包含与终点排除、分别缺少两端窗口、缺失或 null 的 usage 进入 unknown。写明窗口内已有业务时间但 usage 为 0 时的分类。

2. **R2｜高｜SC 没有守住筛选互斥**
   - 位置：Spec §5.4，SC-08。
   - 问题：SC-08 只要求选项和顺序。实现若把「闲置」写成所有 `usageCallsLast7d = 0`，仅连接会同时进入闲置，现有 SC 仍然通过。
   - 最小修复：用同一组 business、connect_only、idle、unknown 夹具，逐档断言完整行集合。后三档互斥，unknown 只在全部，顺序保持接口返回顺序。

3. **R3｜高｜抽屉把审计不可用的时间误写成从未使用**
   - 位置：Spec §5.5，SC-10。
   - 问题：抽屉规定最近业务使用空值写「未使用」，没有先判断不可用。审计读取失败时，空的派生时间会显示成「未使用」或「未访问」，与 Spec 155 的失败分支冲突。
   - 最小修复：抽屉先处理不可用，再处理正常空值。协议量和两个时间都要有不可用断言。正常无历史记录仍用既定空值文案。

4. **R4｜中｜核心伪代码传入不存在的窗口路径**
   - 位置：Spec 核心流程。
   - 问题：伪代码写 `response.summary.window`。`AgentsResponseSummary` 只有平铺的 `windowStart` 和 `windowEnd`。照抄会使时间条件一直失效。
   - 最小修复：改成实际字段。缺少 summary 时按缺窗口处理。

5. **R5｜中｜Token 回退规则正确，但 SC 没覆盖其边界**
   - 位置：Spec §5.3，SC-04。
   - 问题：SC-04 只有两个显式可用数。盖不住缺 `availableTokens` 时启用与禁用的不同回退，也挡不住配置为 0 时误用 warning。
   - 最小修复：补启用且字段缺失、禁用且字段缺失、配置为 0。禁用且仍有配置时，同时断言「已禁用」和「无可用 Token」。

6. **R6｜中｜Plan 未点名必须迁移的旧断言**
   - 位置：Plan S1。
   - 问题：现有 `agent-list.test.tsx` 仍断言六张卡、三列网格、十二列表头，以及主表上的最近 MCP 访问。这些断言在实现时会失败，Plan 没有点名。
   - 最小修复：S1 写明替换这些断言。主表时间改为断言 `lastBusinessSeen`。MCP 时间的断言放到 S2。

已核对且没有问题的点：§6 的分支顺序本身不重叠；Token 回退与现有列表一致；仅连接、仅连接会话、使用过的凭据、可用 Token 没有混称；闭口层级没有把浏览器、整库旅程或 Docker 写成出口；S1 与 S2 的阶段顺序没有提前验收。

本次未运行测试。开发不授权。修订 R1–R3 之前，不把状态改回可开发。
