## 6. Debug & 优化：全量回归失败的定位与修复

### 6.1 现象

首轮全量回归出现 2 条失败（`admin-audit.test.ts`、`admin-tokens.test.ts`）；单独跑两文件 **43/43 全过** ⇒ 指向全量运行时的相互干扰。

### 6.2 定位过程（可复现的证据链）

| 步 | 动作 | 结论 |
|---|---|---|
| 1 | 在 HEAD 基线 worktree 跑同一失败文件 | 通过 ⇒ **对照必须同工作区**（基线 worktree 缺 gitignored 本地数据，环境不等价） |
| 2 | 同工作区 `git stash` 到 HEAD 再跑 | 通过 ⇒ 失败与本次改动相关 |
| 3 | 逐文件二分（先回退 `server/index.ts`） | 通过 ⇒ 收敛到 `registerOidcRoutes` 的 import 链 |
| 4 | `oidc-routes.ts` 换空 stub | 3/3 通过 ⇒ 确在 import 链侧 |
| 5 | 分组二分（`oidc-client`／`auth-events`） | `auth-events` 链 1/3 失败 ⇒ **竞态**，非确定性 |
| 6 | 在 `display-snapshot.ts` 加**仅失败路径**打印（正常路径零开销） | `pending=true` 但 **`metaAge=3341ms`** > `METADATA_FRESH_MS=3000` ⇒ `displayCacheVerified()=false` ⇒ 读立即返回 503 busy ⇒ 断言「60ms 内不得结算」失败 |
| 7 | HEAD 与本分支各跑 10 次 | **HEAD 失败 1/10，本分支 3/10** ⇒ **既有的时间预算脆弱性**，本改动因启动开销放大了触发概率 |

### 6.3 根因

`webui/server/__tests__/display-rollback-races.test.ts` 的 beforeEach 以 `metadataIntervalMs: 60_000` 启动 reconciler，而 `display-snapshot.ts` 的 `METADATA_FRESH_MS = 3000`：**快照只在其元数据摘要新鲜时才可服务**，否则立即 503 `DISPLAY_SNAPSHOT_BUSY`。该文件含故障注入的长耗时真实 HTTP 事务，一旦从 reconciler 启动到读请求超过 3 秒，断言「故障未解决期间读不得结算」就会以 503 立即结算而失败。**这是既有测试的时间预算依赖，不是产品缺陷**（barrier 与 pending 检查均正确）。

### 6.4 修复

**只改测试，不改产品语义**：把该文件的 `metadataIntervalMs` 由 `60_000` 改为 `500`，使快照在测试期间保持新鲜。断言强度未降低——读在 barrier 打开期间仍必须不结算（走 `waitForDisplayWritesSettled` 挂起路径）。修复后**连跑 10 次全部通过**。

> 未采用「放宽 `METADATA_FRESH_MS`」：那是产品安全语义（陈旧快照必须 busy），为让测试通过而放宽安全约束不可接受。

### 7.2 变异测试：新增断言非恒真

「测试通过」不等于「断言在测目标」。新增的 claims 拒绝断言用**变异测试**验证：临时破坏被测逻辑，断言必须转红。

| 变异（临时改生产代码） | 观察结果 |
|---|---|
| 去掉 `verifyIdToken` 的**单 audience `azp` 不匹配**检查 | OIDC-07 用例**失败**：`expected '/overview' to contain 'oidc_error=OIDC_LOGIN_INVALID'`（无 `azp` 检查时该令牌会被接受并登录成功） |
| 去掉 `jwtVerify` 的 **`requiredClaims: ["exp"]`** | OIDC-07 用例**失败**（同上；缺 `exp` 的令牌本应被拒绝） |
| 去掉回调里的 **`runtime.profileDigest !== tx.profileDigest`** 比对 | OIDC-05 用例**失败**：`expected '/overview' to contain 'oidc_error=OIDC_LOGIN_INVALID'`（配置变了却仍然放行） |
| 去掉解绑前的 **`narrowAccount(current, "revoke_sessions")`** | OIDC-13 用例**失败**：`expected 200 to be 401`（绑定已解、旧会话却仍有效） |
| 去掉解绑前的 **`AUTH_CREDENTIAL_REQUIRED`** 凭据校验 | OIDC-12「无凭据不可解绑」用例**失败**：`expected 200 to be 400` |
| 去掉回调里 **账本失败即中止** 的判断（`if (!(await recordAuthEvent(...)))`） | OIDC-19「账本失败不交付会话」用例**失败**：`expected '/overview' to contain 'oidc_error=AUTH_STATE_UNAVAILABLE'`（账本写失败却仍签发会话） |
| 让回调**总是**为 state 建事务桶（`Boolean(pending)` → `true`） | OIDC-19「随机 state 不建事务桶」用例**失败**：`expected 429 to be 303`（第 6 次起被事务桶拒绝） |
| 把 **`sourceTotal` 限值放大**（30 → 100000） | OIDC-19「OIDC 洪水不能绕过本地登录限制」用例**失败**：`expected 200 to be 429`（本地登录不再被共享预算挡住） |
| 让 **owner 保护底线**恒为 false（`recoveryOwnerFloorBroken`） | 两个 OIDC-12 用例**失败**：`expected 200 to be 400` |

每次变异**恰好**只有对应用例转红，其余仍通过 ⇒ 失败确实来自被破坏的那条逻辑，而非用例本身不稳定。

**三处自我纠错（记录在案，因为它们正是「测试通过 ≠ 断言有效」的实例）**：

1. **OIDC-05** 最初改的是 profile 的 `clientId`——该用例会因「aud 不匹配」而被拒，**与 digest 检查无关**，属于恒真断言。改为只改 `scopes`（移动摘要但不动 audience）后，再变异即转红。
2. **OIDC-19「随机 state 不建事务桶」**最初每次用**不同**的 state——每个 state 落在**不同的**桶里，桶阈值（5）根本触不到，断言恒真。改为**同一个**未知 state 连发 10 次后，变异即转红。
3. **OIDC-19「限速」**最初只断言「若干次后被 429」——但 `sourceTotal` 与 `oidcStartSource` 阈值相同（均 30），行为上**无法区分是哪个桶在拒**，断言恒真。改为锁定 Spec 的真实意图——**「OIDC 洪水不能为调用方多买本地尝试」**（打满 OIDC start 后本地登录同样被拒）后，变异即转红。

**生产代码在每次验证后都逐字节还原**（`git diff` 为空，工作区只有测试文件变更）。

**一处诚实说明**：HS256 与 `alg: none` 的拒绝是**双保险**——我们的算法白名单会拒绝它们，`jose` 本身也不支持用 JWKS 公钥验证这两类签名。因此这两条断言证明的是「整体被拒绝」（这正是 Spec §6.2 的要求），**不能**单独区分是哪一道防线生效。
