## 三轮审阅的核心结论：不是设计想错了，是同一个工程缺陷反复出现

三轮审阅各自独立，都指向**同一个失败模式**：

> **新增机制写进了「声明」，却未同时落到「规范流程（Spec 正文/伪代码）」「Plan 阶段任务」「SRR 验收断言」三处，或三处内容不相容。**

- **v0.4** 首次暴露：新增「删除后强制索引重建、reindex 前全量 upsert 范围、可恢复终态审计协议、目录级重命名、遗留布局」五项能力，全部只写在目标声明，Plan 与 SRR 没有对应落点。这直接导致了第一轮的 4 项阻塞。
- **v0.5** 修掉 4 条，复审仍发现 6 条部分闭合——因为是**逐条修补**，而非按「落点三处齐全且相容」的系统性检查。
- **v0.6** 修掉大部分，复审仍发现 2 项阻塞 + 2 项高——同样是逐条修补的残留。
- **v0.8** 起改为**按该标准逐条复核**：每个新增机制必须同时具备三处落点，且内容相容而非仅关键词齐全。

这条经验本身比任何单条发现更有价值：**新增机制时，「声明→流程→任务→断言」是四步，不是一步。**

## 第一轮（R01–R10）发现与处置

### R01［阻塞］Spec 错述现有 journal 生命周期，伪代码把提前终结写成规范流程

**问题**：Spec 现状描述称「全部目标写完后关闭恢复日志」，伪代码把 `completeFailureRecoveryJournal` 放在 reindex **之前**。而现有代码相反——`semantic-assets.ts:2612` 的注释明确写着 journal 在文件保存后**不得**关闭，要留到索引、最终 digest、终态审计全部可核对后才终结（`:2779` 才 `completeRecoveryJournal`）；L25-11 §7.2 亦明文规定「不能提前 `completed`」。

**影响**：按 Spec 实施会**倒退这条既有安全护栏**，使索引、终态审计或状态持久化失败时失去未终结 journal 的准入保护。

**处置（v0.5–v0.8）**：纠正 §1.2 现状描述；新增 §5.4 条款明确日志只有在索引、最终 digest、终态审计与 release 状态均可核对后才终结；伪代码改为写盘后只推进到「文件已保存、索引待确认」阶段；v0.7 进一步把该标记**前移至幂等转 applied 与 release 转 reindexing 之前并纳入失败处理块**，且 §4.3 续跑条件改为「journal 已推进到文件已保存阶段（**不是**已终结）」，补明停在 `write_in_progress` 时必须先按实际字节判定。

### R02［阻塞］全量 upsert 会写计划外文件，与「不修改无关文件」冲突

**问题**：§2.3 同时要求「只修改恢复目标及其镜像，不修改无关文件」与「执行全量 upsert」。但通用镜像同步覆盖四类内容目录，会把既有漂移一并复制到兄弟视图；这些文件不在 journal 中，故障时无法回滚，而 SRR-09 的「无关文件 hash 不变」断言必然失败。

**处置（v0.5–v0.8）**：§2.3 重构为两个独立概念——**恢复写集**（本功能负责，进 CAS／journal／失败回滚）与**镜像同步写集**（既有漂移，由全量 upsert 复制，不进 journal）；「不修改无关文件」精确化为「内容根侧不变；镜像侧允许变化集合为**恢复镜像目标 ∪ 已确认的镜像同步写集**的并集，两类变化方向不同且可分别核对」；预检新增镜像同步写集分区披露；§5.2 第 8 步改为**先核验漂移集合、未披露漂移立即阻断、upsert 只复制已核验集合**；v0.8 进一步把索引前内部 prepare、启动恢复的 runtime mirror 同步、垃圾清理与历史目录迁移全部纳入**受控路径**要求，并在 SRR-09／24 补子断言。

### R03／N01［阻塞］删除恢复的索引模式与读回义务不自洽

**问题**：§3.1 要求含删除计划用 `--force`，§5.2 与伪代码却无条件走增量。更深一层：「删除一个文件」被统一解释为「整张表消失」，但 Lucy 是**双层合并模型**——`semantic-layer.ts:310` 在 overlay 缺失时返回 `{}`（表仍存在），`:562` 按 Manifest 中的表继续构建模型。删除 overlay 只应使业务扩展不可见，表结构仍可见。

**处置（v0.5–v0.8）**：新增 §5.5 统一四种情形的索引模式，模式持久化到 release 记录并进入 `planDigest`；引入**语义删除集合**——由恢复前后**合并模型差异**推导，包含「Manifest 原地回写删表（文件仍为 restore，不是 absent）」；读回预期按分类持久化：删除 overlay → 业务扩展不可见但表结构仍可见；语义删除集合中的表 → 整表不可检索／不可读取；v0.8 进一步把读回义务扩展到**所有存在删除类目标的恢复**（不限强制重建场景），并让伪代码消费持久化的分类预期。

### R04［阻塞］终态审计协议被引用但从未定义，pending 成功记录被启动流程漏掉

**问题**：Spec:197 指向「§8 的 terminalAuditPending 协议」，但 §8 只有一般性失败要求。允许内部先写 `published / confirmed`、再由 pending 屏蔽公开成功，但**协议本身没有定义**，且启动流程只扫 `promoting` / `reindexing`。

**处置（v0.5–v0.8）**：新增 §8.1 定义终态审计可恢复协议。关键源码依据：`semantic-batch-audit.ts:174` 的守卫检查的是**审计载荷**的 `payload.recovery.activationStatus`，**不读磁盘 release 状态**——因此不需要「为满足守卫而先写内部成功记录」这一前置。

v0.8 最终收敛为**唯一四步顺序**：落终态审计 → 写 release 终态并置 pending → 核对审计并清 pending → 终结 journal。`terminalAuditPending` 具备**唯一含义（终态审计尚未被核对）、唯一设置点（步骤 2，与 published 同一次写入）、唯一清除点（步骤 3）**。

### R05［高］「重试索引」不是现有接口已提供的能力

**问题**：现有手动 reindex 接口（`index.ts:2426` body 只有 `{ force?: boolean }`，`semantic-assets.ts:1463` 创建 `newManualReindexId()`）无法结算恢复批次；Spec §5.3 又规定已 applied 的幂等键不得再次索引，两条叠加使恢复批次的索引重试**没有可执行链路**。

**处置**：新增 §5.6 定义批次级索引重试链路，并明确**范围确认对象独立于内容恢复预检**（内容恢复预检以来源批次发布后 digest 做 CAS，恢复已写盘后对原来源预检通常冲突）；重试前须处理 `reindexProject` 内部 `prepareSemanticLayerForKtx` 的全量同步副作用。

### R06［高］100 条 release 保留与 24 小时幂等重放存在依赖断裂

**问题**：`semantic-assets.ts:351` `MAX_RELEASE_RECORDS = 100`、`:1232` 直接 `slice(-MAX_RELEASE_RECORDS)`。一次合法恢复后 24 小时内新增 100 条历史，其 release 即被淘汰，旧幂等键仍有效却撞「release 不存在」异常。

**处置**：§4.2 增加发布记录保留与幂等重放的依赖条款——截断时必须保留被未过期幂等记录引用的 release，幂等过期后解除，列表展示仍限 100 条；§5.3 交叉引用；SRR-24 断言。

### R07［高］幂等查询置于排他锁之后，进行中重放不可达

**问题**：锁覆盖后台 reindex 直到终态，锁内查询会使进行中的同键重放先撞 `semantic_publish_busy`（`publish-coordinator.ts:319`），无法返回规范要求的「真实进行中批次」。现有发布路径顺序相反（`semantic-assets.ts:2195` 先查幂等，`:2244` 才取锁）。

**处置**：只读幂等查询前移至取锁之前，取锁后**完整重做**三态判定与恢复准入检查；锁外查询严格只读，`intent` 分支改为「仍在进行中则直接返回，需要结清则转入锁内」。

### R08［高］现有共享路径实际在终结前释放锁

**问题**：`semantic-assets.ts:2693` 在 reindex 返回后即释放锁，而最终 digest 复核（`:2718`）与终态审计（`:2743`）都在其后；手动 reindex 同样在锁退出后才创建历史记录（`index.ts:2465` → `:2481`）。这与 L25-11 §7.2「锁覆盖……终结审计／历史／状态持久化」不符。

**处置（登记为显式依赖，非顺带修复）**：新增 §5.2.1 登记该偏差，要求 S0 二选一裁决——列为开工前置单独授权修复，或在本功能内显式阻断该交错窗口；**未裁决不得进入 S1**；SRR-23 承载并发注入证据。**（2026-10-29 PM 已裁定取 (a)，本条开工前置解除，见下文「PM 裁定更新」节）**

### R09［中］目录重命名与遗留布局无实施落点

**处置**：§2.2 展开为可执行条款（纳入共享发布互斥或恢复期间显式阻断、路径 CAS 与范围复核、不产生恢复写集、不作为恢复来源）；遗留布局 `LUCY_CONTENT_ROOT=.` 补「不重复登记、不重复执行、回读一次、CAS 强度不放宽」；Plan 补 `project.ts` 服务落点；SRR-23／24 承载。

## 定稿后的产品语义（与 v0.4 一致，未被审阅推翻）

审阅全程确认 L25-15 的**产品语义本身成立**。以下决策经三轮审阅认为自洽，**不因审阅而改变**：

- **恢复到本批次发布前**：以所选发布批次的批次前快照为目标做整批逆向恢复，不是「撤销之后所有批次」，也不是回到某个全库时间点。
- **恢复也是新发布**：每次恢复产生新的 `webui_restore` 批次和新的批次前快照，可被反向恢复；来源批次的记录、Diff 与审计历史不被改写。
- **默认不覆盖后续或外部改动**：所选批次每个目标的当前 digest/absent 必须等于该批次的预期新 digest/absent，任一不匹配即整批阻断、零正式写入；本期不提供强制覆盖。
- **批次按实际写盘目标界定**，不按页面或表数量界定；单表保存若同时改写 overlay 与共享 Manifest，两者都进同一批次。
- **保留策略三上限**：最多 20 个发布记录仍存在的可恢复批次 / 30 天 / 512 MiB，任一先到即清理最旧可清理快照；所有限值落入 `SEMANTIC_BATCH_LIMITS` 单一事实源。
- **只读恢复包导出**：ZIP + `semantic-release-snapshot/v1` manifest，使用 `restorePackage*` 独立限额；不提供上传入口。
- **不宣称无限历史、不回填上线前历史**：旧记录显示「快照不可用」。
