## 1. 裁决

保持 `livez` 轻量、在真实 K8s 上验证同一候选镜像、覆盖纯 MCP 恢复与误杀防护，均是正确方向。但现稿存在 **7 项开发前阻断**：核心自愈承诺可被人工处置替代，恢复窗口不可证伪，liveness 逃生与排空宽限冲突，断路器持久化异常 fail-open，故障注入不能确定性覆盖退出 75，OQ-1=C 与配置机制不可直接实现，以及合法业务仍失败时仍可假绿。

这些问题不是单纯文档措辞，也不能仅靠关闭 OQ-1 解决。应先完成本记录阻断项，再申请终稿确权；运行代码、Chart、探针和测程改动仍须委托人另行授权。

本记录是设计评审与代码／合同静态核对，**不是 K8s UAT 结果**。对集群行为的推断须在改前基线和后续正式合同台上验证，不能写成客户现场已复现或已通过。

## 3. 阻断项与整改要求

### B-01：SC-03 允许「永久不可用＋人工处置」通过，掏空 P0 自愈目标

**证据：**

- Spec 总承诺与 Plan 目标均强调自动恢复、不依赖人工：`docs/specs/lucy-20261124-k8s-self-healing-spec.md:33`、`docs/plans/lucy-20261124-k8s-self-healing-plan.md:20`。
- SC-03 却允许「实例不恢复，只要集群侧存在可读信号且运维可按交付说明处置」通过：`docs/specs/lucy-20261124-k8s-self-healing-spec.md:153`。
- OQ-1 又写方案 A「人工处理」不满足 SC-03：`docs/specs/lucy-20261124-k8s-self-healing-spec.md:164`。

三者直接矛盾。按 SC-03 字面，A 可以在没有自动恢复的情况下通过，Plan 的「不依赖人工」反而没有验收约束力。

**整改要求：**

1. 将「自愈合同」与「不可恢复外部故障的可观测合同」拆开。
2. 对声明的「整容器重启可清除」故障，必须要求在预算内自动恢复；人工处置不得作为替代通过条件。
3. 对数据库、网络等持续外部故障，只承诺有界重试、明确 NotReady、可读原因与运维入口，不得宣称业务已自愈。
4. 若选择 A，应将本条收窄为可观测性与人工恢复合同，不得按 P0 自动自愈收口。

### B-02：恢复窗口不可证伪，且漏算用户真实不可用时间

**证据：**

- OQ-3 写「先在合同台实测，冻结为 SC-06 基线；实测前不预写数字」：`docs/specs/lucy-20261124-k8s-self-healing-spec.md:166`。若最终实测值反过来定义通过线，任何恢复时长都可能被接受。
- SC-06 只记录「STUCK 判定到 Ready」：`docs/specs/lucy-20261124-k8s-self-healing-spec.md:156`。
- 现有默认检测窗口 W 已为 60 秒：`webui/server/runtime/stuck-watchdog.ts:85`。首次合法业务失败到 STUCK 的时间被排除；Ready 到 Endpoint 恢复、真实 MCP 成功及结果稳定的时间也未纳入。

**整改要求：**

1. 开发前由委托人冻结数值上限；改前基线可提供决策依据，但最终候选实测不得事后自定通过线。
2. 至少分别记录：
   - 首次合法业务失败→STUCK：检测时延；
   - STUCK→退出→容器启动→Ready：编排恢复时延；
   - Ready→Endpoint 恢复→非降级展示读及正确 MCP 查询连续成功：用户可见恢复时延。
3. 总不可用窗口必须从首次合法业务失败起算，到最后一次业务稳定成交止，不能只取中间编排段。

### B-03：OQ-1=B 与现有排空预算存在确定的 K8s 配置冲突

**证据：**

- 方案 B 通过 liveness 让 kubelet 杀容器：`docs/specs/lucy-20261124-k8s-self-healing-spec.md:112`。
- P1-63 要求完整退出预算最长 40 秒，外部停止宽限至少 45 秒：`webui/server/runtime/process-drain.ts:22`、`docs/specs/lucy-20261119-process-drain-lifecycle-spec.md:44`。
- 当前 Deployment 未设置 `terminationGracePeriodSeconds`：`deploy/k8s/helm/lucy/templates/deployment.yaml:69`。
- K8s 默认宽限为 30 秒，可能在 supervisor／KTX 清理完成前强杀，破坏有序排空与审计守恒承诺。实际退出码和审计影响仍需合同台验证，但配置冲突已在静态事实层成立。

**整改要求：**

1. Chart 显式设置并结构化门禁 `terminationGracePeriodSeconds >= 45`。
2. 用真实 liveness 失败构造最长排空，记录 TERM、退出码、是否强杀、在途请求及审计水位。
3. 分别定义退出 75 的自退出路径和 liveness 触发的 143／137 路径，不得继续把所有自愈都写成退出 75。
4. 将回滚、`kubectl delete pod` 与 liveness 杀的宽限及证据要求统一纳入 Chart 合同。

### B-04：断路器在持久化异常时 fail-open，抑制态状态机未闭合

**证据：**

- 任意坏 JSON 行或读盘错误都会让重启计数返回 `0`：`webui/server/runtime/self-heal.ts:54`。
- 事件写入失败仅被忽略：`webui/server/runtime/self-heal.ts:43`。
- 因此 PVC 损坏、权限异常或部分写入可能把「重启抑制」静默变成「继续允许重启」。
- Spec 只覆盖正常 PVC 保留，没有规定损坏、不可写、重启后如何重建抑制态、何时解抑及稳定期如何影响计数。
- `emptyDir` 分支与 Chart 现实冲突：Chart 明确拒绝 `persistence.enabled=false`：`deploy/k8s/helm/lucy/templates/deployment.yaml:13`。

**整改要求：**

1. 明确计数／证据不可读时是失败关闭、交由 K8s 退避，还是进入显式降级态；禁止静默按零次处理。
2. 增加坏行、截断文件、只读 PVC、权限错误和重启后恢复测试。
3. 写清 `suppressed` 的跨重启重建、解抑、老化与稳定恢复语义；A／B／C 各分支分别说明。
4. 删除不受支持的 `emptyDir` 验收分支，或先另立支持该部署形态的合同；不能只登记「可能重启风暴」后放行。
5. 若需修改 P1-81 共用持久化逻辑，应纳入本条公共白名单或另开明确依赖项，不得借「不重写判定逻辑」回避。

### B-05：R0 不能确定性地走到退出 75，K8s 故障控制面未进入实施范围

**证据：**

- P1-81 用例文档写自然混压或 CPU 限额：`docs/qa/uat/suites/self-healing/cases.md:22`。
- 正式跑次实际使用 SIGSTOP：`docs/qa/uat/suites/self-healing/runs/2026-11-24-cursor-p181-formal.md:26`。
- 实际退出 75 路径不是停止一次 KTX 即可完成；runner 必须每 3 秒重新冻结 reload 后的新 KTX，直到整容器重启：`inbox/p181-p182-uat-20261124/p181-heal-runner.mjs:335`。
- K8s 交付合同明确尚无 K8s fault-control 控制面：`deploy/k8s/K8S_CONTRACT.md:253`。

因此，「复用 R0」不能保证原位恢复一定失败、一定走到退出 75、重启后故障恰好清除，或测试中不需要手工改变故障。

**整改要求：**

1. 在版本化 UAT fixtures／runner 中分别定义：
   - A 类故障：能够由原位 KTX reload 恢复；
   - B 类故障：持续压住原位恢复，但整容器重启后清除；
   - 持续故障类：用于断路器、CrashLoopBackOff 和可读信号验证。
2. 写明 `kubectl exec`／RBAC、PID 发现、故障生效证明、自动清理、原始证据与禁止产品内 fault switch。
3. 将关键逻辑迁入受版本控制的测程，不得只依赖临时 `inbox/` runner。
4. 故障构造不出或不能证明生效时，相关必做项记 BLOCKED，不得以 mock 看门狗或人工重启替代。

### B-06：OQ-1=C 与配置暴露方案尚不可执行

**证据：**

- Plan 声称步骤 4 是严格白名单，但只有 B 明确列出 `stuck-watchdog.ts`／`self-heal.ts`；C 只写「配置与证据语义调整」：`docs/plans/lucy-20261124-k8s-self-healing-plan.md:40`。
- 当前 `maxRestarts` 只接受正数，其他值回落默认值：`webui/server/runtime/stuck-watchdog.ts:96`。C 所需「关闭／放宽」没有完整配置语义。
- 当前没有定义如何识别「K8s 档」，不能把 Docker customer 模式一并改变。
- OQ-4 也不能只靠「是否进 values」控制配置，因为 `extraEnvFrom` 已能注入这些变量：`deploy/k8s/helm/lucy/templates/deployment.yaml:215`。
- 暴露关闭开关还可能让支持配置直接进入「无自愈」状态，与本条核心承诺冲突。

**整改要求：**

1. 为 A／B／C 分别列出准确的运行时、Chart、测试文件和配置机制。
2. 定义唯一的 K8s 档选择字段，不靠隐式环境猜测；Docker 与 K8s 的断路器语义分别冻结。
3. 冻结每个值的类型、默认值、合法范围、非法值处理和版本兼容。
4. 明确 `extraEnvFrom` 的覆盖／拒绝规则及渲染负例。
5. 明确关闭自愈后是否仍属于本条支持配置；若属于，必须显式改变合同范围和运维提示，不能继续宣称同等自愈保障。

### B-07：成功断言可以把「业务仍失败」判成恢复成功

**证据：**

- SC-01／06 只要求展示读 `200`、MCP「成交」：`docs/specs/lucy-20261124-k8s-self-healing-spec.md:151`、`docs/specs/lucy-20261124-k8s-self-healing-spec.md:156`。
- 现有看门狗明确把 `grace`／`stale`／`pending` 等降级 200 归一化为失败：`webui/server/runtime/stuck-watchdog.ts:128`。
- SC-04 对 CAV STD 合法负载只要求「自愈重启次数为 0」：`docs/specs/lucy-20261124-k8s-self-healing-spec.md:154`。即使 CAV 自身 FAIL、吞吐明显下降或合法查询持续失败，也可能满足该条。

**整改要求：**

1. 展示读必须为新鲜、非降级结果，不只是 HTTP 200。
2. MCP 查询结果必须与独立 SQL 核对值一致，不能用 RPC 返回或 HTTP 成功代替业务正确性。
3. CAV STD 自身判定必须通过，且相对无自愈基线没有合同外退化。
4. Ready、Service 恢复与真实业务恢复分别判定，不能互相替代。
5. 合法负载与恢复用例同时覆盖「约束生效」和「合法用户仍能完成原任务」。

## 4. 重要整改项

### M-01：探针阶段表与证据身份不足

SC-02 要求「与合同表一致」，但 Spec 没有完整的阶段×HTTP 状态×reason×Ready／Endpoint×重启预期矩阵：`docs/specs/lucy-20261124-k8s-self-healing-spec.md:152`。

`startupProbe` 是 kubelet 探针机制，不是第三个 HTTP 接口；应分别记录 `/api/readyz` 响应和 kubelet 探针结果／事件。升级、删除 Pod 后 `restartCount` 会随新 Pod 重置，也不能单独作为误杀证据。

**整改要求：**补阶段矩阵；证据至少包含 Pod UID、containerID、StartedAt、退出原因、自愈事件增量和 Probe／Endpoint 原始样本。需要累计断路器次数的用例与独立恢复用例使用隔离 namespace／PVC，避免前一用例污染后一用例。

### M-02：最终镜像、升级与回滚证据链不完整

Plan 从「实现」直接进入「同一最终镜像测试」，没有明确的最终镜像构建、digest 固定和部署步骤：`docs/plans/lucy-20261124-k8s-self-healing-plan.md:40`。

SC-04 的升级／回滚也只要求自愈重启为零，没有要求回滚后业务可用。若新增探针路径或运行配置，旧镜像＋新 Chart 可能直接形成重启循环。

**整改要求：**

1. 增加最终候选只构建一次、绑定 digest、Chart／values 摘要和运行中 imageID 闭合步骤。
2. 增加 N-1 镜像与新旧 Chart 的兼容矩阵，以及升级、回滚、再次升级后的正确业务查询。
3. 使用结构化 YAML 断言及非法值负例，不能只靠字符串「存在」。
4. 核对当前 Chart 与 `K8S_CONTRACT.md` 的版本镜像，避免在已有漂移上继续叠加自愈配置。

### M-03：B 层台的选择权与前置依赖矛盾

Plan 步骤 0 写「选定 kind 或 K3s」，同时又说「不替 P1-52 裁 OQ-3」：`docs/plans/lucy-20261124-k8s-self-healing-plan.md:36`。实际上步骤 0 已经在做该选择，而 P1-52 的 OQ-3 仍未闭合：`docs/specs/lucy-20261118-customer-upgrade-reliability-gate-spec.md:320`。

**整改要求：**在 P1-52 中先裁定并冻结合同台，或把 P1-83 的 harness／正式跑次明确保持 BLOCKED；不能由本条临时选一个台后形成既定事实。P1-75 X3 对齐后的最终复跑要求应保留，最终证据不得建立在已知的中间看门狗定义上。

### M-04：交付说明中的「可读」必须转化为可执行入口

SC-03 接受 `readyz` reason、Pod 事件或日志之一，但实例 NotReady 后，`readyz` 未必仍能通过原 Service 入口读取；Pod 事件也有保留期限，多代重启后旧日志可能不可达。

**整改要求：**交付说明应写明每类信号的实际读取入口、所需 RBAC、保留窗口和故障时替代入口。至少证明抑制态当前容器的 `restart_suppressed` 日志或等价结构化信号可按说明取得，不得只写「集群侧可读」。
