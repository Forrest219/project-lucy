## 4. 审查发现

### 4.1 签核前必须关闭（4 条）

#### M-01 建议书 L25-06 正文与 Spec 的恢复凭据模型冲突，且建议书内部自相矛盾 —— 须 PM 裁定

- **现象**：建议书 §2.1 两处表述互斥，且 Spec 采用的是其中之一、却未声明相对基线的偏离。
  - 建议书 `:103`（§2.1 引言）：「找回密码仍是：还有其他所有者时由其重置；全部凭据丢失时按系统手册做 break-glass」→ **Lucy 侧**找回。
  - 建议书 `:117`（L25-06 正文）：「密码和找回留在身份源。」→ **IdP 侧**找回。
  - 同节两句话互斥；本轮 diff 只改了 §2.1 标题、新增状态段与验收句，**未同步 `:117`**。
- **Spec 实际采用的**：Lucy 侧。D05（至少一名启用中且具本地密码的所有者）、§3.2（本地密码＋OIDC 绑定为双凭据形态）、§3.3／§5.3（owner 可设置／重置／**移除**本地密码）、§7.2（「仍有其他可登录 owner：可重置本地密码」）、§9 `LOCAL_OWNER_REQUIRED`、OIDC-12。
- **另一处加强**：建议书 `:119` 的验收只保证「身份源不可用时本地账户 id 仍能完成引导和 break-glass」；Spec 进一步保证 **身份源可用时本地 owner／operator 仍可用本地密码登录**（D05、OIDC-14「本地 owner／operator 登录…不受影响」）。这是对基线的收紧，Spec 元数据只写「需求来源：建议书 §2.1 L25-06」，**全文未声明任何偏离**。
- **影响**：若按建议书 `:117` 实现（密码完全交给 IdP），直接违反 D05／OIDC-12／`LOCAL_OWNER_REQUIRED`，并使「全部凭据丢失时的 break-glass」失去前提；若按 Spec 实现，`:117` 即为错误陈述，且 PM 未必知情。两种落法后果相反，必须先裁定再签核。
- **处置（二选一，推荐 A）**：
  - **A（推荐）**：把建议书 `:117` 改为与 Spec 一致的表述，例如「身份源承担认证与多因素认证；Lucy 侧保留本地密码作为恢复与降级路径（至少保留一名启用中的本地密码所有者）」，并把 `:119` 的验收句补上「身份源可用时本地 owner／operator 的本地密码登录仍可用」。同时在 Spec 元数据或 §0 增加一条「相对建议书基线的两处加强」说明，使偏离显式可追。
  - **B**：以建议书为准回退 Spec 的本地密码保留设计——会推翻 D05／OIDC-12／`LOCAL_OWNER_REQUIRED` 与 break-glass 合同，代价远大于 A，不建议。

> **关闭（2026-10-25，Forrest 批准 A）**：建议书 v1.19 已明确 OIDC 凭据与 Lucy 本地恢复凭据分工，并补足身份源可用／不可用时的本地登录验收；Spec 文首已显式登记两处基线加强。原始两句按“不同凭据的不同恢复路径”解释，不再存在未声明偏离。

#### M-02 §8.1「本地密码移除」事件写成「或」，且与现有实现直接冲突

- **现象**：§8.1 记「本地密码移除 | `password_rotated` 或新增明确 `password_removed`，不得伪装成普通资料修改」。
- **代码事实**：`webui/server/auth/routes.ts:457` 为 `if (nextRecord.password_hash !== current.password_hash) events.push({ kind: "password_rotated", targetId: adminId })` —— 只要 hash 变化就记 `password_rotated`。**移除密码时 hash 变为 undefined，恰好落成 `password_rotated`**，正是本条自己禁止的「伪装成普通资料修改」。即：不改代码直接满足现契约，但违反 Spec。
- **约束**：`AuthEventKind` 是封闭联合类型（`webui/server/security/auth-events.ts:14-24`），新增 `password_removed` 需扩类型与既有事件集，「或」并非等价二选一。
- **处置**：Spec 必须二选一写死：① 明确复用 `password_rotated` 并同时记录「是否仍有本地密码」以供区分；或 ② 明确新增 `password_removed` 事件种类并列入 S1 改动清单。不得保留「或」。

> **关闭（2026-10-25）**：采用②。最终 Spec §8.1 明确新增 `password_removed`，`password_rotated` 只用于实际轮换；§12 S1 明确扩展 `AuthEventKind`、本地密码移除路径与测试。代码改动尚待实施授权。

#### M-03 §8.1 的审计 allowlist 未枚举：三个拟用键会被现有实现静默丢弃

- **现象**：§8.1 写「复用 `security_events`，新增事件摘要字段采用 allowlist」，并要写 `method=oidc`／`method=local`／`bindingDigest`／「是否仍有本地密码」，以及 issuer/sub 的截断 SHA-256 digest——但**从未给出 allowlist 键表与 reason 词表**。
- **代码事实**：`auth-events.ts:33` 的 `SUMMARY_KEYS` 固定为 `["targetId", "role", "reason", "attemptedIdDigest"]`；`:39-46` 的 `allowlisted()` **只挑这四个键**，其余键被**静默丢弃（不是报错）**。⇒ `method`、`bindingDigest`、`hasLocalPassword` 三个键若不显式扩 `SUMMARY_KEYS`，审计里会**无声消失**。issuer/sub digest 也没有承载位（`targetId` 语义不同）。
- **reason 词表同样缺失**：现有 `login_failure` 的 reason 是 `invalid_credentials`（`routes.ts:139`）；Spec 新引入 `invalid_state`／`profile_changed_or_invalid`／`code_exchange_failed`／`id_token_invalid`／`account_not_bound`／`oidc_config_unavailable`／`allowlistedIdpError(...)` 等，却未给出封闭词表。§8.2 强调「IdP 错误描述视为不可信输入」，若 allowlist 靠实现者临场判断，正是原始 IdP 错误串漏进账本的入口。
- **处置**：Spec §8.1 补两张封闭清单：① 扩展后的 `SUMMARY_KEYS`（含 `method`／`bindingDigest`／`hasLocalPassword`／`subjectDigest`）及各自取值域与截断长度；② `login_failure` 的 reason 枚举全集，并明确「不在表内的 reason 归一为固定值」。同时把「扩 `SUMMARY_KEYS`／扩 `AuthEventKind`」显式列入 §12 的 S1 退出条件（否则 S2 协议主链会漏改）。

> **关闭（2026-10-25）**：最终 Spec §8.1 已列五个新增 summary 键的值域、摘要算法与 32 hex 截断长度，保留四个既有键；reason 采用九值封闭枚举，IdP 与未知错误统一归一为 `provider_error`。§12 S1 已明确扩展 `AuthEventKind`／`SUMMARY_KEYS` 并补本地 `method=local`。

#### M-04 §8.2「限速」未定义维度与桶，而伪代码使用的 API 不存在

- **现象**：§6.1／§6.2 伪代码调用 `applyPersistentRateLimit(request, class="oidc_start")` / `class="oidc_callback"`。该 API **在仓库中不存在**：现有只有 `gateLoginAttempt(request, adminId)`、`gateBootstrapAttempt(request)`、`clearLoginFailures`、`clearBootstrapFailures`（`webui/server/auth/rate-limit.ts:112-140`），桶名硬编码在 `AUTH_RATE_LIMITS` 内，**无 class 概念**。
- **实质缺口（不止 API 形状）**：现有登录限速是 **(accountId, source) 双维**桶（`rate-limit.ts:112-118`）；OIDC 的 start／callback 发生在**认证之前**，没有 accountId，只能 **source 单维**。Spec 只说「限速」与「不创建可被他人触发的永久账户锁定」，未写维度、未写桶名、未写阈值来源，实施者无从推导。
- **具体风险**：企业客户常共用出口 NAT。source 单维桶会让 A 用户的失败回调把同出口 B 用户的登录一并锁死；若为「不锁他人」而放弃限速，callback 限速形同虚设（state 一次性消费已提供重放防护，但仍无法抑制 IdP 侧无效往返）。
- **处置**：Spec §8.2 明确：① 限速维度（start：source 单维；callback：优先按登录事务/state 维度，source 为辅）；② 新桶名与阈值来源（既有 `AUTH_RATE_LIMITS` 扩展）；③ 共享出口（NAT／代理）下的容忍口径；④ 明确「不新增永久账户锁定」的落地判据。同时把伪代码签名改为仓库既有的 gate 形态，避免凭空造 API。

> **关闭（2026-10-25）**：最终 Spec §8.2.1 固定 `sourceTotal`／`oidcStartSource`／`oidcCallbackSource`／`oidcTransaction` 四类桶、阈值、TTL、可信 source 与共享上限；事务桶只为已存在的真实 stateHash 创建，随机 state 不建桶。NAT 只产生临时 429，不建账户级或永久锁。§6 已改为具体 `gateOidcStartAttempt()`／`gateOidcCallbackAttempt()` 形态，OIDC-19 覆盖反例。

### 4.2 实施前待办（5 条，不退回）

#### F-01 §8.1「本地登录成功 → `method=local`」实际需要改动既有本地登录路径

现有本地登录事件不带任何 summary：`routes.ts:160` 为 `recordAuthEvent({ kind: "login_success", request, actor: account.id })`；`login_failure` 的 summary 为 `{ reason, attemptedIdDigest }`（`routes.ts:134-139`）。Spec §8.1 把 local／oidc 两行并列写成「复用」，实际是**给既有事件补 `method` 字段**。实施时须同步改本地登录路径，否则账本内 `login_success` 的 summary 形态不一致（部分事件无 `method`）。

#### F-02 未引用「权限路线图冻结」ADR，未声明不触发其 SSO claim 重开条件

企业安全 Spec `:60` 在列出 SSO/OIDC 为非目标的同时「遵守 [权限路线图冻结]」。该 ADR `:59-63` 的 F3／F4 明确「无产品级多租户／SSO claim 事实源前禁止开波」，`:79-83` 的重开条件为「产品范围明确包含多租户或 SSO claim；租户边界与身份事实源已设计；另立 WO + Gate A」。OIDC Spec §2.2 明确不做 IdP 组→角色映射、不做 SSO claim（**符合冻结**），但全篇未引用该 ADR、也未声明不触发 F3／F4 重开条件。**处置**：在 §2.2 或 §13 增一句——本功能不引入 SSO claim 事实源、不重开 F3／F4；若未来做 claim 映射须另立 WO + Gate A。这使 PM 签核时能一眼确认未越冻结线。

#### F-03 「运行时配置变化后新登录使用新 profile」缺变化检测机制；未认证端点不应每次读盘

- §4.3 规定「运行时配置变化后，新登录使用新 profile」，但**未说如何检测变化**（文件监听？轮询？每次读盘算摘要？）。D11 的登录事务里已有 `profileDigest` 概念（§6.1），却未与「何时重算 profile」打通。
- 同时 §5.2 把 `methods` 变为「按有效 OIDC 配置派生」，而 `GET /api/auth/status` 是**未认证**入口（`routes.ts:53-67`）：若每次请求都读 profile 文件与 secret 文件，未认证端点即成为文件 IO 放大面。`ACTIVE_LOGIN_METHODS` 现为模块级常量（`oidc-profile.ts:9`），派生意味着要改成启动期缓存的 profile 视图。
- **处置**：§4.3 明确 profile 的加载与摘要**由启动期缓存持有**、失效信号（mtime／摘要轮询／显式重载）是什么；并写明 `methods` 由该缓存派生，不在未认证请求路径上读盘。

#### F-04 新术语只登记在 Spec 内，未进术语标准

术语标准全文检索「OIDC／身份源／单点登录／登录方式」**零命中**，Spec 的 Terminology Compliance 是唯一登记处。按 AGENTS.md「新模块新增产品概念时，必须先补充术语标准**或**在功能 Spec 的 Terminology Compliance 小节登记」，形式上合规（与 P1 需求审查 F-04 同型处理）。但本功能会产出真实 UI 文案（「使用单点登录」「身份源」「登录方式」），而标准 `:205-207` 已有 WebUI Admin 族（登录账户／所有者／运维）。**处置**：实施期写登录页与账户页文案前，按 AGENTS.md 把这些词条补入术语标准 §4.x。

#### F-05 §4.2 的 profile 契约变更未列入实施拆分

既有 `parseOidcProfile` **不校验 scopes 必含 `openid`**，而 `endSessionEndpoint`／`logoutStyle` 是**必填**（`oidc-profile.ts:66-69`、`:91`）——即现契约强制部署方填写两个 D07 声明「本期不使用」的字段，同时本期真正需要的 `openid` 约束不在现契约里。§1.1 承诺「不重造第二套 profile」，§12 只要求「实施 Plan 确定所选 OIDC 库…」，**未把 profile 契约扩展列入 S1**。**处置**：S1 退出条件补一条——扩既有 `parseOidcProfile`：`scopes` 必含 `openid`；logout 两字段在「本期不使用」前提下可选或明确保留必填。

### 8.2 终审新发现（2 条，均不退回、不阻断定稿）

#### N-01 `issuerDigest` 已定义但全文无写入点

- **现象**：§8.1 键表定义了 `issuerDigest`（用途「登录失败对账」），但 §6.2 唯一的绑定缺失分支只写 `auditFailure(reason="account_not_bound", subjectDigestOnly=true)`（Spec `:337`），**全文没有任何写入 `issuerDigest` 的位置**。
- **影响**：按字面实现，该键成为死键。更实质的是，`sub` 只在 issuer 命名空间内唯一——只记 `subjectDigest` 而缺 issuer 维度，owner 拿到摘要后**无法与本地 `oidc_bindings` 做对账**（不同 issuer 下相同 sub 不可区分），使该键声明的「登录失败对账」用途落空。
- **处置（二选一）**：① §6.2 的 `account_not_bound` 分支写明同时记录 `issuerDigest` 与 `subjectDigest`（推荐，与键表用途对齐）；② 在 §8.1 键表把 `issuerDigest` 标注为「本期预留，本期不写入」。二者不可留悬空。

#### N-02 共享 `sourceTotal` 与 D10／OIDC-14 的措辞在共享出口场景下冲突

- **代码事实**：`gateLoginAttempt` 用桶键 `src:<source>`（`webui/server/auth/rate-limit.ts:116`），`gateBootstrapAttempt` 用**同一个**桶键（`:125`）——两者本就共用同一物理桶。§8.2.1 又让 OIDC start／callback 命中 `sourceTotal`，因此**本地密码登录、bootstrap、OIDC start、OIDC callback 四类入口共用同一个 30 次／5 分钟的桶**。
- **后果场景**：客户内网共用出口 NAT＋身份源不可用＋用户反复点「使用单点登录」→ 30 次／5 分钟耗尽后，**同一 source 的本地密码登录与 bootstrap 同样返回 429**，直至窗口到期。
- **与合同的冲突**：D10「OIDC 校验失败只拒绝 OIDC 登录，**不改变**本地登录、bootstrap 和 break-glass」；OIDC-14「本地 owner／operator 登录、bootstrap 与 break-glass **不受影响**」。
- **定性**：**不是安全漏洞，是合同措辞与已实现机制的精度问题**。该 429 临时、自愈（窗口到期自动恢复），且 break-glass 走配置卷与一次性 bootstrap 密钥、不经过 WebUI 登录端点，恢复路径本身仍在。
- **处置（二选一，建议 ①）**：① 措辞对齐——在 D10 与 OIDC-14 补一句「当同一 source 的共享总量桶被 OIDC 流量耗尽时，本地登录与 bootstrap 同样返回 429＋`Retry-After`，直至窗口到期」；② 隔离——OIDC 改用独立总量桶（新增 `oidcSourceTotal`），D10 措辞不动。建议 ①：共享总量本就是 §8.2.1 的有意设计（明写「和其他认证入口共享总量」），隔离会削弱整体防洪能力，只需把合同写准。
