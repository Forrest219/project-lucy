## 4. 🔴 阻断项

### CR-01 `never_begun` ＋ 多钉选被静默放行，违反必做项 SC-E06

- **落点**：`webui/server/proxy/source-selection-tolerance.ts:52-58`（配合 `webui/server/proxy/source-ambiguity-gate.ts:924`、`:1003-1008`）
- **触发**：客户端未调用 `lucy_begin_question`，直接 `lucy_query` 引用 ≥2 个可见来源（例：`measures:["orders.order_count"]` ＋ `dimensions:[{field:"returns.returned"}]`）→ `resolveTermHits` 在 `never_begun` 直接返回空 hits（`:924`）→ `decideSourceSelection` 的 `inHits = (termHits.length < 2)` 恒真 → 命中 `connected` 分支 → **档① plain allow**。
- **影响**：违反 Spec [`SC-E06`](../specs/lucy-20261116-source-ambiguity-mcp-escape-spec.md:270)（**必做**：「never_begun＋双钉选／未钉选 → `context_missing`」）与 §3 修订表（`:119`，D1＝恰好一个钉选）；且走档①时**不带 `sourceSelection` 披露、不写 tolerated 审计**，D14「无审计则容错不可度量」对该场景失效。另：该路径同时跳过 `catalogHealthFailed` 的 `index_unreliable` 判定。
- **测试掩盖**：`webui/server/__tests__/source-ambiguity-tolerance.test.ts:272-285` 直接断言该行为为「正确」，与 SC-E06 相反，CI 不会拦。
- **最小修复**：在 `gateForRequestedSources` 内、`resolveTermHits` 之前，对 `state === "never_begun" && keys.length !== 1` 恢复 `denyEmpty(input, "need_begin_or_confirm")`；若判定实现即新意图，则改 Spec 并由委托人确权。

### CR-02 运行时契约（工具描述 ＋ initialize instructions）与实现相反

- **落点**：`webui/server/proxy/mcp-proxy.ts:1271`（`lucy_begin_question` 工具描述）＋ `webui/config/data-qa-instructions.md:49-51`
- **触发**：客户端按新描述**不钉选来源**直接发问（业务词匹配多个可见来源）→ 走 `webui/server/proxy/source-ambiguity-gate.ts:825-864` 的 keys=0 分支（注释明写「保持 v0.3 行为」）→ 命中 ≥2 个可见来源 → `denyWithCandidates` **硬拒**（Spec [`M12`](../specs/lucy-20261116-source-ambiguity-mcp-escape-spec.md:256) 列为档③ `context_missing`／`explicit_table_required`）。
- **影响**：新描述写「When multiple visible sources may match the same business term, Lucy **allows** the query but discloses the selection」且门闩「only for hard failures (unresolved refs, catalog health, cross-connection, more than 4 sources)」——**描述点名的那个场景恰好走的是会硬拒的分支**，且该 reason 不在列举的任何一项内。客户端会等一个永远不会出现的 `answer_verifiability.sourceSelection`。同一提交还删掉了唯一覆盖该分支的句子「未形成唯一钉选时，多表歧义仍会硬拦。」
- **说明**：拒绝本身带 `repair` 载荷与 `usableTargets`，仍有可执行下一步，故不违反「拒绝必须有可执行下一步」；问题是**声明的拦截面与实际不一致**。
- **最小修复**：把 keys=0 档③（`context_missing`／`explicit_table_required`／`need_begin_or_confirm`）写进工具描述与 instructions 的拦截清单；或让实现把 keys=0 也走容错披露（后者与 Spec M12 冲突，须委托人确权）。

## 5. 🟡 应修项

### CR-03 join 图节点键丢 `schema` → 无关表被认证为「已声明 join 连通」

`webui/server/proxy/source-join-graph.ts:96`、`:101-102`（`lastSegment` 见 `:22-26`）。同一连接内两个 sourceName 同名、schema 不同的表（`sales.orders` ＋ `archive.orders`）塌成 1 个节点 → `visited.size === nodes.size` 恒真 → `connected = true`；且 `to:` 走 lastSegment，`to: archive.orders` 可跨 schema 搭桥。**影响**：D12 档①的前提「语义层已声明 join」被伪造 → 命中集内多表查询走档①**无披露、无审计**；SC-E21／E22／E30 的正反例只在单 schema 下成立。**修复**：节点键改用完整身份 `connectionId|schema|sourceName`。

`webui/server/security/redaction.ts:88-98`（本次新增函数；`STORAGE_PATH_RE` 见 `:53-58`，只含 `hdfs`／`s3`／`s3a`／`file`）。实测：

### CR-06 导出 manifest 两处口径矛盾

- `webui/server/admin/audit-export-v2.ts:724`：`spans: { ledgerUpperSeq: upperSeq, unsequenced: 0 }` 硬编码 `0`，而同一 manifest 的 `spanCoverage.unsequenced` 是真值；pack 路径（`:924`）才覆盖成真值 → **两条导出路径对同一事实给出不同数字**，且 Spec §6.3「不静默忽略，须在 manifest 报出」被绕过。**修复**：用 `computeSpanCoverage` 已算出的 `unsequenced` 填充。
- `webui/server/admin/audit-export-v2.ts:704`：`derivationVersion` 取 `DERIVATION_VERSION`（`webui/server/proxy/audit-derivation.ts:25`＝`"v2p5-1"`），而带 span 的行写入的是 `"v2p5-2"`（`webui/server/proxy/audit.ts:1254`）→ 归档 manifest 声明的派生口径与行内版本不符，同 manifest 的 `spanCoverage.version` 已是 `v2p5-2`。**修复**：随 `SPAN_DERIVATION_VERSION` 升版，或同时给出「行版本」与「派生版本」两字段。

### CR-07 既有封存文件 `calls-v2.csv` 列集被追加 3 列，且等价守卫未登记

`webui/server/admin/audit-export-v2.ts:254-262`：`HEADERS_V2` 追加 `ip_source`／`trusted_source`／`rejection_fingerprint`，行同步多 3 列。与 P1-36 Spec「不改已收口的导出文件列与顺序」的豁免条款冲突；而 `webui/server/__tests__/equivalence/` 的 FINDINGS 登记表里**既无 `calls-v2.csv` 也无 `spans.csv`**（24 文件／282 测试全绿，说明门禁确实没覆盖）。**修复**：需委托人裁定豁免与 D8 的冲突；至少把 `spans.csv` 登记进等价守卫并给 `calls-v2.csv` 冻结 golden。

### CR-08 事件环直方图漏采样 → TRC-11 门槛测不到真实冻结

`webui/scripts/span-ledger-scale.mts:81-94`：`disable()` 前未让定时器补记最后一次 `await` 之后的同步尾段。跑次记录（`docs/qa/uat/suites/trace-span-ledger/runs/2026-11-17-claude-wide-sandbox-tierA.md:30`）自证：`spans.csv` 渲染墙钟 **2.26 s** 而上报 max 仅 **48 ms**；`computeSpanCoverage` 墙钟 828 ms 而 max 41 ms——差额正是未采样的尾段（97 MB `parts.join("")`／`hash.digest`／打包与全表同步循环）。**影响**：TRC-11 的 P99 ≤ 400 ms／max ≤ 1000 ms 门槛会在真实冻结时判「无超标」。**修复**：`disable()` 前先 `await new Promise(r => setImmediate(r))`；`lagHistogram.count === 0` 判为「未采样 → 不算通过」。

### CR-09 UAT 探针恒退出 0 → 假 PASS

`scripts/uat/mcp-ux-resilience-probe.mjs:77-108`：`deny` 不校验响应确实是「拒绝」（token 过期／代理 401 时把 ~1 ms 的错误响应当「拒绝延迟」样本）；`scripts/uat/mcp-ux-resilience-wide.mjs:41-76`：`stale-session` 自称「确认代理恢复而非把 404 透给客户端」，即使 `unknownSessionLeaked === true` 也 exit 0。**影响**：跑次里「门闩拒绝 P50 568→193 ms」这类前后对照数字**没有失败语义**，SC-07 想抓的会话泄漏脚本判不出来。**修复**：`deny` 先断言 `isError`／`decision_reason` 属被拒族；`stale-session` 断言 `unknownSessionLeaked === false`；不满足即 `process.exit(1)`。

### CR-10 沙箱脚本的删除目标完全由 env 决定，无护栏

`scripts/uat/uat-wide-sandbox.mjs:27-28`：`NAME`／`VOLUME` 取自 `UAT_WIDE_CONTAINER`；`down()`（`:197-201`）执行 `docker rm -f ${NAME}` ＋ `docker volume rm -f ${NAME}-data`；`restart()`（`:217-222`）同样。**触发**：`UAT_WIDE_CONTAINER=compose-lucy-1 node scripts/uat/uat-wide-sandbox.mjs down` → 删掉本机 demo 栈容器与数据卷。**修复**：删除前断言 `NAME` 以 `lucy-uat` 开头并打印待删目标，否则拒绝执行。
