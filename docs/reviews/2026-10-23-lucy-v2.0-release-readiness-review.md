## 1. 结论

**1.1 「v2.0 已成功部署验收」在交付层成立，在发版列车层不成立。** 两者不冲突，指的不是同一件事：

| 层面 | 状态 | 证据 |
|---|---|---|
| 交付层（客户包可用性） | 候选包 `20261021-r7`（镜像 `a93880e`）在 Mac 上 G1–G4b 与 G8 已通过 | `docs/plans/2026-10-21-customer-20260828-v1-upgrade-package-plan.md` 状态行 + HEAD 提交 `8e10792` |
| 放行层（`productionReady`） | **仍为 `false`**；原生 amd64 的 P0-3 至 P0-6 未执行 | 同上；[升级计划 v0.3](../plans/2026-10-21-customer-20260828-v1-to-lucy-2.0-upgrade-plan.md) §3 P0-2 判定列 |
| 流水线层（CI 门禁链） | **从未在分支上跑起来**（2026-10-18 起） | §4.1 |
| 发布标记层 | **无 `v2.0.0` tag、无 GitHub Release** | §4.4 |
| 治理层（`main` 保护） | **无分支保护、无 ruleset** | §4.5 |

**1.2 合流技术上无障碍，流程上未就绪。** `lucy-v2.0` 领先 `origin/main` 214 个提交、落后 0，`origin/main` 是 `lucy-v2.0` 的祖先，可纯 fast-forward。合并冲突不是风险；风险在于**在流水线是死的、发布标记缺失、必需检查未强制的前提下合流**，这会把"发版列车"变成一个只有名义的流程。

**1.3 客户放行链路当前结构性地不可用，与合并无关。** 即使工作流文件修好，GitHub 路径也产不出客户放行包，原因见 §4.2。这一项决定了 2.5 期间客户交付必须走哪条路。

**1.4 「2.5」不能直接作为产品版本号，建议交付时切 `2.10.0`。** 依据是仓库自己的版本矩阵规则，不是我的偏好。推导见 §4.3。

**1.5 合并前必须先落盘当前工作区的 8 个修改 + 2 个新增，且其中 1 个修改是必需检查的硬依赖。** `webui/docs/03-api-spec.md` 的路由补录是**其他 agent 的未提交改动**；若不随本次合流落地，合流后的 `main` 会在 `lint:spec` 上失败——而这是计划中的 Required check。详见 §4.6。

### D3｜被护栏拒绝的调用，是否计入问询预算？（2026-10-24 新浮出，待裁定）

| | 内容 |
|---|---|
| **背景** | `365f3ca` 之后，`mcp-proxy.ts` 的**问询预算扣减块位于调用护栏之前**。因此一次**被护栏拒绝**的 `lucy_query` **会先扣掉预算**，然后才被拒绝——即「没拿到答案的提问也要付费」。 |
| **背景的更正（2026-10-24 复核）** | 上文原举的典型例子「没有 source 的 `count(*)` 被 `source_not_found` / `ambiguous_field` 拦下」**与代码不符**。无 source 的 `count(*)` 走的是**早护栏** `countWithoutSourceBeforeAcl`（`mcp-proxy.ts:3389`），在 `3430` 就 `return`，**早于预算扣减（`:3505`）——不扣预算**；这是 Spec 162 §7.8 专门加的（`query-guardrails.ts:261-276`）。而 `source_not_found` 只出现在 `lucy_read_source` 路径（`query-guardrails.ts:332`），与 `count(*)` 无关。**真实「先扣费再被拒」的只有 4 类**，全部在预算之后的 `applyLucyCallGuard`（`mcp-proxy.ts:4319`）里，且**全部属「用法与语义」维度**：度量写法 repair（`query-guardrails.ts:252`）、度量 reject（`:255`）、`ambiguous_field`（`:309`）、`source_not_found`（`:332`）。**影响面比原文描述窄得多**；结论（需裁定）不变，但依据的事实基础已更正。 |
| **为什么现在才浮上来** | 修 §4.10 的 `query-guardrails` 断言时才暴露。`365f3ca` 本身**是有意为之**的：动机是本地工具路径会提前 return，旧顺序下会漏扣预算。 |
| **规范空白** | Spec 162、WO-202610-15 与所有 runbook 都**没有**规定「被护栏拒绝的调用是否计入问询预算」。这是规范空白，不是实现偏离。 |
| **口径 A：计费（现行行为）** | 护栏拒绝也扣预算。代价：用户可能为「问错了」付费；除非护栏拒绝给出可诊断提示，否则体感像乱扣。 |
| **口径 B：不计费** | 护栏拒绝不扣预算。代价：客户端可以把护栏当免费探测反复试错，预算护栏被绕过；需要在别处补限流。 |
| **口径 C：分维度** | 「用法与语义」维度不计费，「权限/安全」维度计费。语义最贴近问题本质，但需 Spec 补一张「拒绝维度 → 是否计费」对照表，实现侧要能区分拒绝维度。 |
| **口径 C 的可行性复核（2026-10-24）** | **按字面实施不可行**。护栏侧**根本不存在「权限拒绝」维度**——`query-guardrails.ts` 里所有 stop 都写死「用法与语义」。要让「权限/安全计费」成立，就得把 ACL 拒绝（`mcp-proxy.ts:3436`）改成计费，等于**把预算扣减移到 ACL 之前**，那是回归 `365f3ca` 修掉的漏扣缺陷，且用户在无权限时每问一次烧一次预算。**C 要么改写语义，要么不实施。** |
| **本文不擅自决定** | 三种口径会改变客户可感知的计费行为，属于产品策略，裁定人 = Forrest。 |
| **对 2.0 合流的影响** | **无。** 不要在 2.0 合流前改实现——`365f3ca` 的现行顺序是有意修复，回归它会重新引入漏扣预算的缺陷。 |
| **实现面的硬约束（2026-10-24 复核）** | 无论选 A 还是 B，**都不能把预算扣减块整体后移到护栏之后**。因为 3505 与 4319 之间有 data tool 的**本地 handler 提前 return**：`lucy_explain_query` / `lucy_freshness`（`mcp-proxy.ts:3620`）、`wiki_read`（`:3668`）都在此区间 return，后移会让这几个工具**完全不计数**，正是 `365f3ca` 修掉的漏扣缺陷。因此若选 B，**只有 refund 一条路**：`QuestionBudget` 加 `refund(turnId)`，护栏 stop 分支调一次。 |
| **建议归属** | 2.5 线第一批判定，落在 L25-09 审计运行时契约（问询事件流口径）旁边；若选 C，先补 Spec 162 的对照表再动实现。 |

## 4. 证据台账

每条给出可复现的取证命令。所有命令于 2026-10-23 在工作区 HEAD `8e10792` 上执行。

### 4.1 CI 工作流文件在 2026-10-18 起整体失效（已修）

**现象**：分支上最近 7 次 CI 全部 0 秒失败、无任何 job。GitHub 提示："This run likely failed because of a workflow file issue."

```bash
gh run list --branch lucy-v2.0 --limit 7
# completed failure ... 0s  （全部 0 秒）
gh run view 39889187032 --json jobs
# {"jobs":[]}   ← 连 check-run 都没生成，说明失败在"加载工作流文件"阶段
```

**根因**：`real-e2e` job 在 **job 级 `env:`** 中引用 `${{ runner.temp }}`。GitHub 的 context 可用性表中，job 级 `env` 可用的 context 为 `github` / `needs` / `strategy` / `matrix` / `vars` / `secrets` / `inputs`，**不含 `runner`**。后果不是该 step 失败，而是整个工作流文件在加载阶段被拒——所有 job 静默消失。

**取证**：

```bash
actionlint .github/workflows/lucy-release.yml
# .github/workflows/lucy-release.yml:354:43: context "runner" is not allowed here.
#   available contexts are "github", "inputs", "matrix", "needs", "secrets", "strategy", "vars"
```

**引入提交**：

```bash
git log --oneline -S 'LUCY_EVIDENCE_SIGNING_KEY_FILE: ${{ runner.temp }}' -- .github/workflows/lucy-release.yml
# e8e931e feat(ci): wire amd64 customer-release jobs without buildx --use (T14)   2026-10-18
```

### 4.16 `docker-smoke` 挂死真根因：孙进程链持有管道，`await once(child, "close")` 永不触发（已修）

**这是第八个门禁缺陷，也是 §4.14 挂死的真根因。**

**机理**（三条同时成立才会挂）：

1. `npm run start` 在 `webui` 目录里拉起的是 `npm → sh → tsx → node` 的**孙进程链**，WebUI server 是链尾的 `node`；
2. 拆卸时 `child.kill("SIGTERM")` **只发给 npm**，npm 不转发给孙进程 → WebUI server 继续存活；
3. 原代码用 `stdio: ["ignore", "pipe", "pipe"]` 起子进程，孙进程**继承了这条 stdout/stderr 管道**；Node 的 `'close'` 事件要等这些流全部关闭才触发 → 管道被存活着的孙进程握着 → **`'close'` 永不触发** → `await once(child, "close")` 无限期挂起。

**证据**：CI 侧孤儿进程链 `npm(2198) → sh(2209) → node(2210) → node(7102) → node(7113)` 与上述机理逐环吻合（server 7113 存活）；本地复现用 `npm run start` 起链同样复现，早先的 43ms 探针之所以"不挂"，是因为它没有走 npm 包装层。

**修复**（`scripts/gates/p0-smoke.mjs`）：

| 改动 | 作用 |
|---|---|
| `stdio: ["ignore", "inherit", "inherit"]` | 子进程直接写父进程终端，**不再有可被孙进程持有的管道** |
| `detached: true` | 子进程独立进程组，可整体终止 |
| 拆卸改为 `terminateGroup()`：SIGTERM → 有界等待（5s）→ `process.kill(-pid, SIGTERM)` → `SIGKILL` → 兜底 `child.kill("SIGKILL")` | 拆干净整条链，不留孤儿 |
| `run()` 新增可选 `timeoutMs`；超限时终止整个进程组并抛出**指名命令与超时时长**的异常 | 门禁只可能"带诊断失败"，不可能静默挂死 |
| `run()` / `spawnSync("docker", ["run", ...])` 全部给出超时上限 | 覆盖 compose 阶段、探针阶段与镜像隔离检查 |
| `SIGINT` / `SIGTERM` 处理器清理已跟踪的进程组 | Ctrl-C 与 CI 取消不会留下孤儿 |

**实现期发现并修正的第二个缺陷（结算顺序）**：第一版实现里，超时拆卸期间的 `'close'` 事件会**抢先 reject** `run()` 的 promise；外层 catch 随即 `process.exit(1)`，于是脚本在 `terminateGroup()` 执行到进程组 kill **之前**就被杀掉，孙进程因此残留（实测：`sleep` 以 `PPID=1` 存活）。修法是让 `'close'` 处理器在 `timedOut` 为真时**不参与结算**，结算权归超时回调；并在顶层失败分支补 `killTrackedGroups()`。这条是本地实测发现的，不是推测。

**本地验证**（含真实超时路径）：

| 验证 | 结果 |
|---|---|
| `node scripts/gates/p0-smoke.mjs`（正常路径） | **PASS**（`[p0-smoke] PASS`，退出码 0）；webui **283 文件 / 3264 测试全绿**；结束后 `ps` 无残留孤儿进程，55174 / 57879 端口已释放 |
| 挂死的 `npm` shim（`bash → sh → sleep`，复刻孙进程链）触发超时路径 | 门禁**按预期报出"命令名 + 超时时长"并以退出码 1 结束**，不静默挂起 |
| 同一超时路径的进程组残留检查 | **无残留**——超时后 `ps` 里找不到 `sleep`，进程组被完整拆掉（第一版实现会留下 `PPID=1` 的孤儿，此项已随上面的结算顺序修正一并通过） |

**这是本次唯一还没拿到绿证据的 Required check 的直接修复**；绿证据须以 PR #45 head 上的 CI 轮为准（§4.14 的误判已在本节更正）。

### 4.18 WebUI 套件的三类时序脆弱点：固定睡眠、默认 5s 超时、迟挂的 rejection 处理器（已修）

**这是第十个门禁缺陷。** run `40034559271` 上 `spec-and-webui` 失败——这是它修好之后的**第一次红**。两条失败：

| 用例 | 失败信息 | 根因 |
|---|---|---|
| `api.semantic-assets.publish.test.ts` → "returns reindexing immediately, finishes async reindex, and updates release status to published" | `expected 'reindexing' to be 'published'` | `resolveReindex()` 之后用**固定 50ms 睡眠**等异步 reindex 完成。状态翻转发生在事件循环里，CI 负载下 50ms 不够 |
| `audit-export-paging.test.ts` → "reads row 10,001 on the second page without dropping overflow" | `Test timed out in 5000ms` | 串行写 **10,001 行**审计记录。本机空载实测 1547ms，CI 负载下超过 vitest 默认的 5s 超时 |

两条在本地连跑 3 次均全绿 → 确认为**负载相关的时序脆弱点**，不是稳定缺陷。

**修复**：

1. publish 用例：固定 50ms 睡眠改为**轮询到目标状态**（5s 上限）。同文件另外两处同类等待（等 `reindex_failed` 状态、等 sidecar 落盘）一并改为轮询。
2. paging 用例：给 10,001 行写入的用例**显式 60s 超时**（同文件其他重用例已用 30s）。

**另一条同源 flake（本地全量复跑时暴露，与 CI 那两条无关）**：`display-snapshot.test.ts` 的 "verification lost during a build" 用例里，`await expect(owner).rejects...` 与 `await expect(attached).rejects...` 是**先后**挂载的。owner 的断言 await 期间 `attached` 已经拒绝却还没有处理器 → Node 报**未处理 rejection** → vitest 在 **283/283 用例全过**的情况下**仍以退出码 1 结束**，整轮 CI 判红。修法：两个 rejection 处理器在让出事件循环**之前**就挂上。

**教训（值得写进发版列车规范）**：

> **`Test Files 283 passed` 不等于门禁绿。** vitest 会在"全部断言通过"时仍因未处理 rejection 退出 1；反之，固定睡眠类断言失败是随机出现而非必现。**判绿必须看退出码，不能只看用例计数**——这一条直接决定了 §4.18 的第三类问题为什么能长期潜伏：它不在任何用例的断言里，只在进程退出码里。

**第四类：跨文件 `process.env` 污染（已加固，**未完全根除**）**。本地全量复跑还抓到一类 **404**：偶发出现在 `GET /api/admin/agents`、`POST /api/catalog/assets/validate`、`POST /api/semantic-assets/reindex` 这类**普通管理路由**上——这些路由在 `buildServer()` 里是**无条件注册**的，404 只能来自"这个 app 实例的路由树里没有这条路由"。Vitest 的 283 个套件共用进程，而大量套件各自设置 `process.env`（`KTX_PROJECT_ROOT` / `LUCY_CONTENT_ROOT` / `LUCY_ACCESS_CONFIG_PATH` / `LUCY_AUDIT_DB` …）却**清理不一致**（例如 `admin-agents.test.ts` 的 `afterEach` 只还原 `KTX_PROJECT_ROOT`，不还原 `LUCY_CONTENT_ROOT`）。

**已做的加固**：在共享的 `webui/test/setup.ts` 里，对每个套件文件**恢复 worker 启动时的环境快照**（`Symbol.for` 挂在 `globalThis` 上，第一个套件取快照，其后每个套件先恢复再跑）。这样"套件只能看到自己设过的东西"，污染这一类从根上被堵住。

**未根除的部分（诚实记录）**：加固后本地全量**并行**跑仍有 1/3 概率复现 404（这次落在 `api.semantic-assets.reindex`）。已排除的因素：该文件**单跑 20 次全绿**；CI 条件（`vitest run --maxWorkers=1`）**连跑 3 次全绿**；CI 上的两轮 `spec-and-webui` 也都是绿的。**机制仍未定位**——最可疑的是并行多 worker 下某个套件对路由树/模块注册的影响，而不是环境变量本身。

**处置**：这一类**不作为 2.0 合流的阻塞项**——CI 的门禁配置是 `--maxWorkers=1`，本地在该配置下 3/3 全绿，CI 上 2/2 全绿。**列为 2.5 线待办**（`docs/` 下另立条目跟进），理由：它需要一个能稳定复现的最小用例，而现在的复现窗口只在全量并行下出现，每次命中的路由都不同。

### 4.19 `docker-smoke` 重复跑 WebUI 全量套件，以及一个被它放大的 generation 计数竞态（已修）

**这是第十一个门禁缺陷。** run `40037556376` 上 `docker-smoke` 红了——但**挂的不是 docker**，而是它内部 `localSmoke()` 里的 `npm test`：

```
FAIL  server/__tests__/display-invalidation.test.ts > DI-01 barriers open before the write and close after it, with or without audit; wiki writes do not touch D/P
AssertionError: expected 6 to be 5
```

**根因**：`display-invalidation.test.ts` 的 DI-01 是全文件里唯一用**精确增量**断言 generation 的用例（`expect(mid.D).toBe(before.D + 4)`）。但显示 reconciler 的**文件监听器会异步再打一次 D generation bump**——采样 `before` 之后、采样 `mid` 之前，监听器可能已经落地。监听器的触发时机取决于负载，于是这条断言**时绿时红**。其余用例用的是 `toBeGreaterThan`（对额外 bump 免疫）或在动作**之后**再采样快照（同样受影响），只有这一条是脆的。

**修复**：DI-01 测的是**写屏障**语义，不是监听器，因此在用例开头 `stopDisplayReconciler()`，让增量只由同步写路径贡献。

**更重要的一处治理问题——重复跑全量套件**：`docker-smoke` 的依赖是 `needs: spec-and-webui`，而 `spec-and-webui` **已经跑过并通过了 WebUI 全量套件**。`docker-smoke` 里的 `localSmoke()` 又把同一套 3264 个用例跑了一遍——**纯粹重复**，而且**把每一个套件 flake 的暴露面翻倍**：同一个 flaky 用例可以同时打红 `spec-and-webui` 和 `docker-smoke` 两个 Required check（本轮就是如此：套件失败先打红 `spec-and-webui`，再经 `localSmoke()` 打红 `docker-smoke`）。

**修复**：`scripts/gates/p0-smoke.mjs` 新增 `--skip-webui-suite`，`docker-smoke` job 改为 `npm run smoke:p0:docker -- --skip-webui-suite`。**门禁覆盖面不变**（套件仍由 `spec-and-webui` 强制），只是去掉了重复执行——少跑一遍 3264 个用例（约 6 分钟），也把套件 flake 的暴露面减半。本地用例仍默认跑全套（本地是开发者的完整闸门）。

**教训**：

> **同一个套件在一张门禁链上跑两次，等于把它的 flake 概率翻倍。** 发版列车的每个 job 应当有**单一职责**：版本/Spec/安全基线/WebUI 套件归 `spec-and-webui`，镜像与容器形态归 `docker-smoke`，H1 静态归 `k8s-static`，真实 N-1 升级归 `k8s-upgrade-gate`。重复不是"更保险"，是"更容易红"。

### 4.21 新增门禁（发版台账）在浅克隆检出下误报「commit 不存在」（已修）

**这不在 2.0 的 11 项缺陷之内**，是 2026-10-24 新增「发版台账」机制时**由本次改动引入、又由 CI 当场抓住**的一个缺陷。记录在此，因为它暴露的是一条**通用**的门禁设计教训。

**症状**：PR #46 的 `spec-and-webui` job 失败，报

```
[release-ledger] FAIL
- docs/releases/v2.0.0.json: commit 14a8bee16c55b5d9885c8ab4c3464614503735dc does not exist in this repository
```

**根因**：台账门禁要交叉校验「台账记录的 commit 确实存在于对象库、且 release tag 正好指向它」。而 CI 的 gate job 用 `actions/checkout` **默认浅克隆**检出——`14a8bee` 是上一个发布周期的提交，**不在浅克隆的窗口内**，对象库里根本没有它。

**为什么本地复现不出来**：本地仓库是完整克隆，`14a8bee` 就在对象库里，门禁是绿的。**只有 CI 的浅克隆才暴露它。**

**两个层面的修法**：

| 层面 | 修法 |
|---|---|
| 让校验真的跑起来 | `spec-and-webui` 与 `release-package` 改为 `fetch-depth: 0`（完整历史 + tags）。否则这项校验在 CI 里等于没有 |
| 浅克隆下的措辞 | 当检出确实是浅克隆、commit 因而无法确认时，报「**无法验证**（检出是浅克隆，该提交不在对象库内）」，而**不是**断言「该提交不存在」 |

**教训（可复用到任何门禁）**：

1. **门禁里凡是依赖 git 历史的断言，都必须显式确认 CI 检出是完整的。** 浅克隆下 `git rev-parse --verify <sha>` 对**不存在**的对象也会原样回显并 exit 0——它只校验形状；真正问对象库的是 `git cat-file -e <sha>^{commit}`。
2. **「查不到」和「不存在」是两件事。** 浅克隆里查不到，正确的说法是「无法验证」；说成「不存在」是**一个更强的、错误的断言**。门禁的失败信息会直接变成修复指引，措辞不准会误导排查方向。
3. **本地绿 ≠ CI 绿**，当门禁触及 git 历史、tag、对象库这类**环境相关**的状态时。本地完整克隆与 CI 浅克隆是两种不同的运行环境。

**验证**：用 `file://` 协议构造真实浅克隆（本地路径的 `git clone --depth` 会被忽略，必须走传输层），断言其报错为「无法验证」而非「不存在」；完整克隆下门禁通过。

### 4.22 发版台账把「跑了并失败」记成「没跑」——三态模型修正（已修，在首次使用台账之前）

**发现时点**：2026-10-24，为 `v0.2.0` 起草台账条目时，对照 CI run 的实际 job 结果逐条核对，发现台账自身失实。

**症状**：台账的 `gates[].status` 只允许两个取值——`passed` 与 `notExecuted`。而 `demo-db-smoke` 与 `postgres-demo-db-smoke` 在 run `40039319546`（v2.0.0 条目所引用的那次）与 run `40048966796`（v0.2.0 条目所引用的那次）里**都真的执行了，也都真的失败了**（`conclusion: failure`），不是「没跑」。它们之所以被记成 `notExecuted`，只因为 `notExecuted` 是当时唯一能表达「没通过」的取值。

**为什么这是缺陷而不是风格问题**：台账的职责是**记录事实**。把「跑了并失败」记成「没跑」，会让读台账的人得出一个**比事实乐观**的结论——他以为那条门禁根本没执行，于是不会去追它的失败原因。历史版本 `v2.0.0.json` 里这条理由本身已经写着「First real execution exposed a deployment-layer gap」，**理由文字与状态字段自相矛盾**。这是一次由台账自身的文案暴露出来的失实。

**修法**：把状态模型从两态扩为**三态**，并加两条硬约束。

| status | 含义 | 必填 | 校验规则 |
|---|---|---|---|
| `passed` | 跑了，过了 | `run` | 缺 `run` → 判失败 |
| `failed` | 跑了，**没过** | `run` + `reason` | 缺 `reason` → 判失败；`required: true` → 判失败 |
| `notExecuted` | 没跑（skipped / 被阻塞 / 手工项） | `reason` | 缺 `reason` → 判失败 |

两条新增的硬约束，各有理由：

1. **`failed` 且 `required: true` 直接判门禁失败。** 一份带红 Required check 的发版记录**不应该存在**——若真存在，那不是记录问题，是发版本身不该发生。把它变成结构性不可能，比留给人工判断更可靠。
2. **`passed` 与 `failed` 必须写 `run`。** 门禁记录的价值在于「指向哪一次跑批」；没有 run id 的记录无法被第三方复核，也无法在事后确认当时到底是哪次执行的结果。

**连带修正**：两条历史/当前条目的 demo smoke 记录从 `notExecuted` 改为 `failed` + `run` + `required: false` + 明确原因；`docs/releases/README.md` 补三态表；台账校验器补 5 个测试（接受非 Required 的 `failed`、拒绝红 Required、拒绝无 reason 的 `failed`、拒绝无 `run` 的 `passed`、拒绝未知状态）。

**教训（可复用到任何"记录状态"的机制）**：

> **状态枚举的取值集合本身是一项设计决策。** 当枚举里**缺少**「确实执行了但没通过」这一档时，记录系统不会报错——它会**静默地把这件坏事塞进语义最接近的那一档**。而塞进去的那一档往往比事实乐观，因为「没做」听起来比「做了但失败」轻。所以：凡是枚举里会出现负面事实的地方，**必须**给负面事实留一档；事后发现缺档，要趁该机制**尚未产生第一份对外记录**时改掉，否则历史记录会被迫带着旧口径长期存在。

**时机判断**：本项修正在 `v0.2.0` 首次使用台账**之前**完成，`v0.2.0` 的条目直接以三态模型写就。若等到台账已对外发布后再改，就会出现「历史版本用两态、新版本用三态」的割裂，且旧条目的失实无法回改。
