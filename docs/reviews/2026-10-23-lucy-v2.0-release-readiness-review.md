## 1. 结论

**1.1 「v2.0 已成功部署验收」在交付层成立，在发版列车层不成立。** 两者不冲突，指的不是同一件事：

| 层面 | 状态 | 证据 |
|---|---|---|
| 交付层（客户包可用性） | 候选包 `20261021-r7`（镜像 `a93880e`）在 Mac 上 G1–G4b 与 G8 已通过 | `docs/plans/2026-10-21-customer-20260828-v1-upgrade-package-plan.md` 状态行 + HEAD 提交 `8e10792` |
| 放行层（`productionReady`） | **仍为 `false`**；原生 amd64 的 P0-3 至 P0-6 未执行 | 同上；[升级计划 v0.3](../plans/2026-10-21-customer-20260828-v1-to-lucy-2.0-upgrade-plan.md) §3 P0-2 判定列 |
| 流水线层（CI 门禁链） | **从未在分支上跑起来**（2026-10-18 起） | §4.1 |
| 发布标记层 | **无 `v2.0.0` tag、无 GitHub Release** | §4.4 |
| 治理层（`main` 保护） | **无分支保护、无 ruleset** | §4.5 |

**1.2 合流技术上无障碍，流程上未就绪。** `lucy-v2.0` 领先 `origin/main` 214 个提交、落后 0，`origin/main` 是 `lucy-v2.0` 的祖先，可纯 fast-forward。合并冲突不是风险；风险在于**在流水线是死的、发布标记缺失、必需检查未强制的前提下合流**，这会把"发版列车"变成一个只有名义的流程。

**1.3 客户放行链路当前结构性地不可用，与合并无关。** 即使工作流文件修好，GitHub 路径也产不出客户放行包，原因见 §4.2。这一项决定了 2.5 期间客户交付必须走哪条路。

**1.4 「2.5」不能直接作为产品版本号，建议交付时切 `2.10.0`。** 依据是仓库自己的版本矩阵规则，不是我的偏好。推导见 §4.3。

**1.5 合并前必须先落盘当前工作区的 8 个修改 + 2 个新增，且其中 1 个修改是必需检查的硬依赖。** `webui/docs/03-api-spec.md` 的路由补录是**其他 agent 的未提交改动**；若不随本次合流落地，合流后的 `main` 会在 `lint:spec` 上失败——而这是计划中的 Required check。详见 §4.6。

## 3. 待决策项（本文需要你裁定的两件事）

### D1｜受保护 self-hosted runner：本期 provisioning 吗？

| | 内容 |
|---|---|
| **背景** | `real-e2e` 跑在 `[self-hosted, lucy-protected, linux, amd64]`；仓库注册 runner 数 = **0**。链条后果：无 runner → `real-e2e` 永不调度（BLOCKED，不退化为 headless 或本地结果）→ `customer-release-readiness` 依赖它亦无法完成 → `release-package` 永不执行。 |
| **选项 A** | **本期 provisioning**：一台 amd64 节点，具备 kubectl/helm 访问隔离 E2S namespace、真实 Claude Code + OpenClaw CLI（`real-e2e-clients.yaml` v5 要求的最小产品对，Hermes 不计入两个产品）、测试用模型凭据、证据签名密钥。 |
| **选项 B** | **本期不 provisioning**：客户交付明确走本地出包路径（`scripts/gates/build-k8s-delivery-package.sh` + 人工原生验收），在放行材料中写明"未经 GitHub 门禁链验证"，把 runner 列为 2.5 期间的并行基础设施项。 |
| **我的建议** | **B，但带死线**：不阻塞现在合流与开线；runner 作为 2.5 期间的并行基础设施项推进，**必须在 2.5 首次客户交付前就位**。理由：provisioning 是一次性基础设施采购 + 凭据治理，不是发版流程的一部分；2.0 收尾的客户包本来就走本地路径，runner 缺失不改变它的放行结论；而 2.5 交付节奏加快后再补就晚了。 |
| **不选 B 的代价** | 2.5 期间每次客户交付的证据都缺"自动门禁链复验"这一环，审计叙事上要靠人工证据补，强度弱一档。 |
| **选 A 的代价** | 需要一台机器 + 隔离 K8s namespace + 两套模型凭据 + 签名密钥治理；在没有明确交付日期前投入，属于提前建设。 |

### D2｜2.5 波次交付时的产品版本号

| | 内容 |
|---|---|
| **背景** | `version-matrix.md` §1.1 只承认两条递增规则：客户交付包 → 第二段 +1；大能力 / 破坏性配置 / 捆绑 KTX 主版本变化 → 第二段 +10；补丁段保持 `0`（hotfix 规则尚未定义）。"2.5"不落在这两条规则的任何一条上。 |

## 4. 证据台账

每条给出可复现的取证命令。所有命令于 2026-10-23 在工作区 HEAD `8e10792` 上执行。

### 4.1 CI 工作流文件在 2026-10-18 起整体失效（已修）

**现象**：分支上最近 7 次 CI 全部 0 秒失败、无任何 job。GitHub 提示："This run likely failed because of a workflow file issue."

```bash
gh run list --branch lucy-v2.0 --limit 7
# completed failure ... 0s  （全部 0 秒）
gh run view 39889187032 --json jobs
# {"jobs":[]}   ← 连 check-run 都没生成，说明失败在"加载工作流文件"阶段
```

**根因**：`real-e2e` job 在 **job 级 `env:`** 中引用 `${{ runner.temp }}`。GitHub 的 context 可用性表中，job 级 `env` 可用的 context 为 `github` / `needs` / `strategy` / `matrix` / `vars` / `secrets` / `inputs`，**不含 `runner`**。后果不是该 step 失败，而是整个工作流文件在加载阶段被拒——所有 job 静默消失。

**取证**：

```bash
actionlint .github/workflows/lucy-release.yml
# .github/workflows/lucy-release.yml:354:43: context "runner" is not allowed here.
#   available contexts are "github", "inputs", "matrix", "needs", "secrets", "strategy", "vars"
```

**引入提交**：

```bash
git log --oneline -S 'LUCY_EVIDENCE_SIGNING_KEY_FILE: ${{ runner.temp }}' -- .github/workflows/lucy-release.yml
# e8e931e feat(ci): wire amd64 customer-release jobs without buildx --use (T14)   2026-10-18
```

**已执行的修复**（`.github/workflows/lucy-release.yml`，+4/-1 行）：把 `LUCY_EVIDENCE_SIGNING_KEY_FILE` 从 job 级 `env` 下沉到"Verify, then archive and sign"这一步的 step 级 `env`，并在原地留注释说明原因。

**配套修复**（新增 `.github/actionlint.yaml`）：声明 `lucy-protected` 与 `amd64` 为本仓库的自托管 runner 标签。**没有这个文件，actionlint 虽只报 2 条 finding，但退出码是 `1`**——它不认识自定义标签，而这两条并非工作流缺陷。有了配置，"零 finding"与"退出码 0"才是同一件事，P0-2 判据才可被钩子直接使用。

**修复后校验**：

```bash
actionlint .github/workflows/lucy-release.yml     # exit 0（依赖 .github/actionlint.yaml；无配置时 exit 1）
python3 -c "import yaml; print(len(yaml.safe_load(open('.github/workflows/lucy-release.yml'))['jobs']))"   # 14
```

**语义未变**：修复只改写变量的作用域位置，门禁清单逐项相同（`spec-and-webui` / `business-eval-catalog` / `ktx-diff-audit` / `docker-smoke` / `k8s-static` / `k8s-upgrade-gate` / `headless-config` / `demo-db-smoke` / `postgres-demo-db-smoke` / `ktx-upgrade-compat` / `customer-amd64-native` / `real-e2e` / `customer-release-readiness` / `release-package`）。`LUCY_EVIDENCE_SIGNING_KEY_FILE` 仅在归档签名步骤使用（`scripts/e2e/archive-evidence.mjs` 读取该环境变量），step 级作用域足以覆盖。

### 4.2 受保护 runner 数量为 0 → GitHub 放行链路结构性不可用

