### 5.1 J01-07 真实 Agent 腿：为什么 blocked（不是"测不过"）

| 观测 | 值 | 含义 |

| 客户端探针 | claude-code `ready`（2.1.305）、openclaw `ready` | 二进制与登录态正常 |

| 判定被误读 | 探测器把这段 exec 失败当成了「客户端可达裸 DB 端点／控制面」 | 文件类探测被**巧合**判为已拒绝，网络类被判为可达 ⇒ 结论与事实相反 |

### 5.1.1 证据措辞的更正：探针"没结论"≠"隔离已破"

上表「修复后」那一行的探针输出是**空的**（子进程被信号杀死，`exitCode=-1`）。而当时的判定逻辑只有"被拒绝"与"未被拒绝"两态，**未被拒绝**一律写成：

```text
isolation_not_established: the client reached checker-gold, synthetic-seed, raw-db-endpoint,
test-source, control-plane, checker-secrets, os-private under the boundary; isolation is broken
```

这句话**不成立**：客户端什么也没读到，它只是没能给出判定。这是一句落在证据文件里、会被发布读者当成"沙箱漏了"的安全断言。

**已修正**（`classifyProbeOutcome()` 三态判定：`denied`／`leaked`／`inconclusive`）：

| 判定 | 触发条件 | 证据措辞 |
|---|---|---|
| `denied` | 出现内核级拒绝信号（`Permission denied`／`ECONNREFUSED` 等） | 边界已阻断 |
| `leaked` | 输出含 canary 标签，或含"我拿到了数据"这类肯定性成功信号 | `the client reached … isolation is broken`（**只有证据坐实了才这么说**） |
| `inconclusive` | 探针跑完但既无拒绝信号也无泄漏信号 | `the boundary probe produced no verdict for … isolation is NOT established` |

**门禁结论一字未松**：只有 `denied` 才有资格授予隔离；`inconclusive` 与 `leaked` 一样让客户端保持阻断（`isolated:false`、全部 case `blocked`、退出码 2）。改的只是**诊断**，不是**门槛**。

真实复跑（run `v025-agent-probe-20261025-1500`，真实 Claude Code ＋ OpenClaw ＋ 真实 Postgres 夹具）：

```text
isolated: false | attemptCompleted: true
leaked: []
inconclusive: ["checker-gold","synthetic-seed","raw-db-endpoint","test-source","control-plane","checker-secrets","os-private"]
attempts[0]: { "verdict": "inconclusive", "reason": "the probe produced neither a denial signal nor a leak signal",
               "observed": "", "exitCode": -1, "timedOut": false, "completed": true }

blockedBy: isolation_not_established: the boundary probe produced no verdict for checker-gold, …
           (the client produced neither a denial signal nor a leak signal); isolation is NOT established
modelCalls: 0 | 144 个 case 全部 blocked | exitCode 2
```

顺带把探针的原始子进程结果（`exitCode`／`timedOut`／`completed`／`verdict`／`reason`）一起写进证据，审计者可以自行复算判定，而不必只信一句结论。

## 6. 本轮发现并修复的缺陷

### 6.1 产品缺陷：连接探测结构性丢弃密码（**产品行为错误**）

* **现象**：新建连接抽屉的「测试连接」对**任何带口令的引擎**（postgres／mysql／sqlserver／oracle）必然失败，报「数据库密码为必填项」。
* **根因**：`CreateConnectionDrawer.tsx` 的 `connectionRequest()` 仅在 `dryRun=false` 时携带 `password`；而探测请求用 `dryRun=true` 构造、随后又把 `dryRun` 剥掉 ⇒ **密码被结构性丢弃**；服务端 `/api/connections/probe` 明确要求 `password`（`CONNECTION_PASSWORD_REQUIRED`）。
* **修复**：探测路径单独补回密码；**dry-run 预览保持不带**（该路径的服务端语义是回一个 secret 文件引用而非收明文）。
* **证据**：新增单测 `sends the password to the connectivity probe (the endpoint requires it)`，**已验证红→绿**（去掉修复即失败：`expect(payload.password).toBe("s3cret")`）；抽屉单测 21/21 通过。

### 6.2 隔离边界缺陷：客户端二进制被 `denyHome` 挡住

### 12.3 两个真产品缺陷（**服务进程崩溃**）

**① 非 owner 建账号被拒 ⇒ 进程退出。** `requireOwner` 用 `void reply.send()` 发 403 后不等待、路由 `return;` 返回 `undefined`，Fastify 于是**再发一次**；`reply.sent` 只有在响应**结束**后才为 true ⇒ 两次 send 竞态 ⇒ `writeHead` 撞上已写出的响应头 ⇒ `ERR_HTTP_HEADERS_SENT` ⇒ onSend hook 链里的未捕获异常 ⇒ **整个 Node 进程退出**。

Fastify 自己的警告就在产物日志里：`Reply was already sent, did you forget to "return reply" in the "/api/admin/admins" (POST) route?`

影响面：全仓只有这一处 `void reply...send`，只有 3 个路由调用它 ⇒ **任何已登录的 operator 一次请求就能把实例打挂**。

**② wiki 原文下载 ⇒ 进程退出。** `GET /api/wiki/:key/raw` 同样"send 完不 return"，同样的双写、同样的进程退出。

修法都是"把回复交回框架"：`requireOwner` 改 async 并 `await reply.send(...)`（Fastify 的 reply 是 thenable）；`/raw` 路由改 `return reply.send(...)`。

**实证**（真实进程、真实请求）：

| 场景 | 回退修复 | 带上修复 |
|---|---|---|
| `POST /api/admin/admins`（operator，403） | 进程退出；单测捕获到 unhandled rejection ⇒ 硬失败 | 403 ＋ 服务存活，单测 20/20 |
| `GET /api/wiki/<key>/raw` × 5 | 进程退出（日志 `ERR_HTTP_HEADERS_SENT` 计数 3→6） | 5 × 200，服务仍在监听 |

回归测试在 `webui/server/__tests__/webui-admin-auth.test.ts`（显式捕获 `unhandledRejection` 并断言为空——`app.inject()` 下双写只表现为 unhandled rejection，Vitest 默认**只报告不失败**）。隔离树 webui 服务端测试 **234 文件／2606 例全通过**。

### 12.4 泄漏扫描器自身的假阳性（产品是对的）

`SEC-03-V04` 报 `no_leak: 4 leak hit(s)`。产品把哈希写进审计 diff 时**正确脱敏**为 `password_hash: [REDACTED]`（落库即脱敏，API 返回的也是脱敏值）。错的是扫描器的正则：值前的 `\s*` 在否定前瞻**之外**，引擎可回退成零宽再在前瞻位置重测 ⇒ 脱敏行被当成泄漏。修法：把空白挪进否定前瞻内部。回归 9 例（6 种脱敏写法零命中 ＋ 具体哈希仍命中）。

## 13. 遗留项收口轮五：先把"打分器"修对，再谈产品

本轮没有新增产品功能，全部工作量花在**让分数变成可信**：前一轮复跑里 110 条用例的结论其实是被 harness 自己吃掉的；随后查出的 deny 识别、请求形状、响应形状三层不匹配，让一批"看起来像产品缺陷"的失败其实是**打分器读不懂产品**。本轮把这些逐层修掉，并把**修完仍然过不了的那一层**（共享夹具与冻结 gold 的口径冲突）查到底、给出证据。

### 13.1 先修的不是产品，是打分器

**现象**：run `v025-security-uat-20261025-1600-d` 里，`SEC-02-V05` 报 `Lucy exited during startup (code=1)`，**随后 110 条用例在 43 毫秒内全部 `handler_error: fetch failed`** —— 那是**服务端没在跑**时的连接被拒，那一轮的分数整体作废。

**根因**：`scripts/e2e/lib/instance.mjs` 用 `tsx` CLI 起服务，而 `tsx` 会 **fork** 子进程 ⇒ harness 握着的只是 wrapper，`child.once("exit")` 报的不是服务退出 ⇒ stop/start 可能与**仍占端口的旧服务**赛跑 ⇒ 新实例 `EADDRINUSE` 退出 ⇒ 此后整条腿都在对着死服务打分。

**修复**：改用 `node --import tsx server/index.ts` **单进程**启动（`serverLaunchSpec()` 单一真源），`exit` 即"服务已消失"；`EADDRINUSE` 有限重试。配套：目标不可达判 **blocked**（`service_unreachable`）而不是 failed，并在故障后**自动重启实例**，让后续用例仍对着活服务打分。详见[实施记录 §13.1–§13.2](2026-10-25-lucy-v0.25-e2e-implementation-record.md)。

### 13.2 deny reason 识别：产品是对的，harness 认不出

W‑03 过去被记成"冻结用例形状过期"。逐层拆开后，其中一层是**harness 的白名单落后于产品**：

- 产品按 `webui/server/proxy/acl.ts` 的 `AclDecision.reason` 发拒绝，**绝大多数带 `:detail` 后缀**（`table_forbidden:<table>`、`explicit_table_required:<table>`、`role_resolution_failed:<roleId>`……），而 harness 的白名单写的是**不带后缀的类名**且做**精确匹配** ⇒ 永远匹配不上；
- harness 切 reason 的正则要求 `Access denied: ` 之后**整串**都是 token，而产品把人类提示用**空格**分隔 ⇒ 整串提示被当成 reason ⇒ 同样匹配不上。

两者叠加 ⇒ **产品正确地拒绝了，harness 报"不是拒绝信封"**（`mcp_iserror_unmatched_reason`）—— 这正是 38 条的共同签名。修复后按**类**识别（与产品自己的审计分类同一纪律），但 `denyReasonMatches()` 仍比对**完整 reason**，所以"要求具体 reason"的用例不会被别的 reason 顶替。

### 13.3 W‑03 的另一半：请求形状与响应形状

现行契约要求语义 measure（`total_spend_cents` / `order_count` / `cac_cents`）、**限定名对象**维度（`{field:"marketing_daily.region"}`）、限定名过滤；响应是 `{ headers:[...], rows:[[...]] }`，**没有** `aggregate` 字段。冻结用例两样都停在旧契约上，而**旧形状先被产品自己的入参校验拒掉** ⇒ 产品**根本没走到 ACL / 行策略层**，用例想验的东西一次都没验。

本轮适配（**同 ID、同断言 token、同 gold 值、同分母**）：请求形状 + 新增 `measureValue(parsed, measureNames)` 从现行信封按列名取度量值（**取不到就是 null，绝不猜数**）。

### 13.4 W‑03 剩下的真正堵点：夹具的 `cac_cents` 复现的是 gold 的 **decoy**

形状适配之后，`Q-CAC-*` 仍然过不了。查到底后发现**不在 harness 侧**：

gold 的口径（`examples/security-e2e/gold/v025-gold.mjs`）＝**只取 actual 行** ＋ **`new_customers` 为 NULL 的行分子分母同除** ＋ **半进位整数除法**。用 run `-1600-f` 的数据集实测（`gold.Q-CAC-28D.cents = 9706`）：

| 口径 | 值 | 判定 |
|---|---|---|
| gold 定义的口径 | **9706** | ✅ 与 gold 完全一致 |
| 共享夹具现行 `cac_cents` | **9802** | ❌ **这正是 gold 自己标注的错误答案 `wrongAnswers.spendOverAllRowsCents = 9802`** |
| 同上但不取整 | 9706.2676… | ❌ gold `toleranceCents = 0` |

差值 9802 − 9706 **恰好等于那条 `new_customers IS NULL` 的行被计入分子的投放额**（109705 分）。

⇒ **现行夹具下，任何请求形状都无法复现冻结 typed gold**。这需要两个裁决（W‑06）：共享夹具 `cac_cents` 表达式的分子口径（**共享夹具语义变更**，与 W‑02 同性质）、以及金额 measure 是否由产品取整到整数分。本轮**不擅改**，但把失败从"看不懂的信封"变成了"数值对不上"——可定位、可比较。
