## 决策一：G34 — 幂等认领与审计绑定的事务边界 ⚠️ 硬阻塞

| 项 | 内容 |
|---|---|
| **状态** | ✅ **已定案（2026-10-29 PM）**：(a) 幂等存储与审计行同库同事务，并叠加最小恢复协议覆盖文件写窗口 |
| **性质** | 已按下方「两层叠加」修正后的 (a) 签字。选项分析保留作依据 |
| **约束范围** | **同时约束 W-A 与 W-B**（W-A 前置集合含 G32–G34；W-B 含 G1–G34 全部） |

### 事实（已回查源码核实）

- `webui/server/admin/audit.ts:802-807`：审计行插入为 `INSERT INTO config_change_log ... ON CONFLICT(idempotency_key) DO NOTHING`——幂等靠 `idempotency_key` 去重。
- `webui/server/admin/audit.ts:835-861`：`updateConfigChangeStatus` 是**另一条** `UPDATE ... WHERE id = ?`，按 id 更新 `write_status` 等字段。
- `webui/server/admin/audit.ts` **全文无 SQL 事务包装**——精确检索 `BEGIN` / `COMMIT;` / `ROLLBACK;` / `.transaction(` / `db.exec('BEGIN` **零命中**（另一路交叉校验：作为 SQL 事务控制关键字的 `BEGIN`/`COMMIT`/`ROLLBACK`/`SAVEPOINT` 排除同形词后 0 命中；事务 API `.transaction(` / `db.transaction` / `prepare('BEGIN` 0 命中）。⚠️ **取证方法提醒**：不可用大小写不敏感的「transaction / BEGIN / COMMIT」粗检索下结论——该文件有 **9 处会被误命中**：`write_status` 家族的 `"committed"` / `"rolled_back"` 字面量 **8 处**（`:285`、`:533`、`:686`、`:794`、`:825`、`:2684`、`:2774`、`:3862`），另 **1 处**是 `:2383` 的 `description` 描述串里的英文单词 "begin"（与事务无关）。实质结论成立，但表述须按上述精确口径。
- `webui/server/project.ts:700-712` 等真实调用点：**先写业务文件**（`writeKtxYaml`），**后插审计行**（`recordConfigChange` → 拿 `auditId`）；`write_status` 更新再单独一次调用。
- **写路径的性质（决定 (a) 的边界，关键事实）**：`writeKtxYaml`（`webui/server/project.ts:440-460`）是**文件系统写**（`readFile` → `parseDocument` → `mutator` → 写 `ktx.yaml`），互斥靠 `withKtxYamlWriteLock` 的**进程内队列**，**不是数据库事务**。⇒ **业务文件写无法纳入 SQLite 事务**，这是文件系统写的固有限制，不是实现选择。
- 审计表的位置：`webui/server/admin/audit.ts:364,366` —— `dbPath = path.join(dir, "audit.sqlite")` / `db = new Database(dbPath)`（better-sqlite3）。

⇒ **「原子认领并绑定」今天不成立**：业务副作用（文件写）、幂等认领、审计状态更新是三个分离步骤，任意一步崩掉都会留下「文件已改、审计无记录」或「审计 pending 悬垂」的窗口。

### 两个选项

| 选项 | 内容 | 代价 |
|---|---|---|
| **(a) 同库同事务** | 业务幂等存储与审计表**同库同事务**，保留「认领与绑定原子」声明 | **事务范围 = 幂等认领记录 + 审计行插入**（better-sqlite3 `db.transaction()`），**不含业务文件写**——文件写是文件系统写，进不了事务。代价：幂等存储须落 SQLite 且与 `audit.sqlite` 同库；SQLite 写事务串行化会**降低并发写吞吐** |
| **(b) 完整恢复协议** | 改为**完整恢复协议**并**删除原子性声明** | 语义降级：不承诺原子性，改为「可恢复」；需补恢复流程与补偿动作；对外措辞须从「原子」改成「幂等且可恢复」 |

> ⚠️ **重要修正：(a) 与 (b) 不是互斥的二选一，而是可叠加的两层。** 原文把 G34 表述为「同库同事务 **或** 完整恢复协议」会误导：即使选 (a)，**「文件已改、幂等/审计未提交」窗口依然存在**（文件写不在事务内）。因此 **(a) 必须叠加一份最小恢复协议**——幂等存储中有记录但状态未终结时，凭幂等记录重放或对账。正确的表述是：
> **(a) = 幂等存储与审计行同库同事务（消除「认领↔审计」窗口）+ 最小恢复协议（覆盖「文件写」窗口）**；
> **(b) = 仅恢复协议 + 删除原子声明（对外只承诺「幂等且可恢复」）**。
> 二者的实质差别在于**是否保留「认领与绑定原子」这一有限承诺**，而非「有无恢复能力」。

### 建议

**倾向 (a) + 最小恢复协议（两层叠加）**。(a) 的可行前提**不是**「KTX 写入能否入事务」——文件写本就入不了，也不因此失效——而是：**业务幂等存储落 SQLite 且与审计表同库**。这一点**可行**：审计表位于 `audit.sqlite`（`audit.ts:364,366`），而**业务幂等存储是本功能新建的**，落 SQLite 无既有约束。理由：本 Spec 的授权模型与审计绑定是同一个合同的组成部分，保留「认领与绑定原子」这一有限承诺比删掉它更符合合同完整性；而文件写窗口只能靠恢复协议覆盖，删掉原子声明也并不能消除该窗口——**(b) 并不比 (a) 更能覆盖它**。

**裁定（2026-10-29）**：PM 签 **(a) + 最小恢复协议**。文件写不进入该事务。Spec §6.2 与 Plan v0.9 已按此改写。

## 决策三：D8 — staged 批次归属与消费（仅挡 W-B）

| 项 | 内容 |
|---|---|
| **状态** | ✅ **已定案（2026-10-29 PM）**：**(b) 显式批次交接**——保留既有批次 `actor`／`instanceId` 校验，另设独立授权与审计归因，把「谁建的批次」与「谁消费批次」拆成两笔独立授权；**不得以伪装 actor 绕过**。**D8 已解除，但 W-B 仍不可交付开发**（仍须 L25-11 审阅通过 + G30／G31 由 L25-11 维护者关闭） |
| **约束范围** | **只约束 W-B**（`lucy_ops_semantic_publish`）。**不挡 W-A**（连接表配置／源表导入） |

### 事实（已回查源码核实）

`webui/server/semantic-assets.ts:2941-2950`：

```
if (batch.actor !== context.actor)      → 403「该批次属于其他操作者，不能直接消费」
if (batch.instanceId !== context.instanceId) → 403「该批次属于其他实例，不能直接消费」
```

⇒ 底层读计划**严格校验批次 actor 与 instance**；既有 staging 是**管理员流程**，因此 **Agent 身份无权消费管理员批次**。

### 三个选项

| 选项 | 内容 | 代价 |
|---|---|---|
| **(a)** | 新增 **Agent 身份下的 staging 能力** | 最直接，但扩大了 Agent 可写面，须同步扩授权模型与审计归因 |
| **(b)** ✅ **PM 已选** | **显式批次交接**：保留原校验 + 独立授权 + 审计归因 | 改动面最小、审计链最清晰；多一道交接手续，消费方须持有独立授权 |
| **(c)** | 控制面以**受信委托人身份**代为 staging | Agent 侧最省事；但代理身份与审计归因须显式声明归属，否则审计链上「谁做的」会失真 |

### 建议

**倾向 (b)**。理由：(a) 扩大 Agent 写面，与本 Spec「授权模型 C 混合 + owner 门禁」的方向相反；(c) 会让审计归因出现一层代理歧义，而本轮七轮审阅里最反复被提的就是审计链可信度。(b) 把「谁建的批次」和「谁消费批次」拆成两个独立授权，正好复用已有的 actor/instance 校验机制。

> **裁定（2026-10-29 PM）：选 (b)。** 落地要求：① 批次消费方须**持有独立授权**（不得继承建批方授权）；② 交接须**留审计归因**（谁建、谁消费两笔都要可查）；③ **严禁以伪装 actor 消费他人批次**——既有 `actor`／`instanceId` 校验不得放宽。本条只挡 W-B；W-A 的连接表配置与源表导入不受影响。
