## 发现的问题

> 每条含：编号、严重性、位置（Codex 原文）、问题、影响、Codex 建议修法、**MiniMax Code 独立核实结论**。

### F01［阻塞］语义专用流程与通用门禁没有连接合同

**位置（Codex）**：Spec §6.1 步骤 9、§6.2 C1–C3、§6.4；Plan §4 S5。

**问题**：通用入口始终调用 `runPreview/runCommit`；专用 preview 仅返回 validationId，没有建立通用计划所需的 actor/tool/expiry 等记录。绕行专用 commit 又没有计划对象再授权。

**影响**：经过通用入口无法证明计划加载和成功重放可达；绕过它则无法证明硬线 (a)。底层完整计划还包含候选之外的待生效变更，不能只授权 `args.targets`。

**Codex 建议修法**：明确工具分派及计划适配；从完整实际影响集生成可授权对象，对无法解析的对象拒绝；统一计划归属、再授权、已有操作重放与审计顺序。

**核实结论：属实。** 「底层完整计划包含候选之外的待生效变更」已逐字核实：批量计划的类型定义把三类集合分开——`candidates`（本批暂存候选）、`unrelatedDiskChanges`（**不属于本批但会被一并索引的既有待生效磁盘变更**）、`effectiveTargets`（「everything the batch would write — candidates plus unrelated disk changes」），见 `webui/server/semantic-batch-service.ts:814-829`（注释见 `:827`），返回体见同文件 `:872`。因此**只授权 `args.targets` 或只用 `candidates` 都会漏授权**，Codex 判断与源码事实一致。

### F02［阻塞］新增 C5 不是覆盖执行失败的组级状态机

**位置（Codex）**：Spec §6.2 C4–C6，特别是 L581–602。

**问题**：C4 将目标设为 prepared/reused，C5 仅检查这些状态；C6 c 仍逐目标执行并称「失败不外溢」，只有 ktx 分支 d 写了整组失败。

**影响**：同组 A 执行成功、B 随后失败时，当前步骤允许 e 分别终结成功与失败，直接违反 D7 和硬线 (d)。

**Codex 建议修法**：改为组级 prepare→认领→执行→确认→统一终结；任一成员运行失败先整组撤销并核验，撤销未完成则整组保持恢复阻断，不逐成员发布成功终态。

**核实结论：属实。** 组边界的物理约束已核实：同 Schema 多表共享同一 Manifest 文件（`webui/server/semantic-layer.ts:862-897`），Overlay 写入路径不含 schema（`webui/server/overlay.ts:70-74`），版本历史索引是全局单文件（`webui/server/table-yaml-history.ts:13-15`）。在这种写集模型下「逐目标执行、失败不外溢」无法保证原子性，组级状态机是必需的；Codex 判断与代码事实一致。

### F03［阻塞］两级认领仍只写在散文中；失败重试没有完整 attempt 初始化

**位置（Codex）**：Spec §6.2 C3、C4、C7；§4.2、§4.4。

**问题**：C4 无 target claim／pending 审计，已有 failed operation 分支不设置新 `opAuditId`。

**影响**：照抄流程不能满足硬线 (c)；失败重试无法按指定句柄终结 operation 审计，也无法落实每目标每尝试一条审计。

**Codex 建议修法**：在正式效果前显式认领本次待执行目标并创建／绑定 pending 审计；为 failed→新 attempt 定义原子转换，持久化 attempt 与所有 auditId，再允许执行。

**核实结论：属实。** 审计链的两端行为已核实：`webui/server/admin/audit.ts:802-807` 的 `INSERT ... ON CONFLICT(idempotency_key) DO NOTHING` 会**静默丢弃同键第二行**，因此「同一次尝试内按 auditId 更新既有行、重放另建 attempt」是唯一可落地的口径；按 id 更新的接口确为 `updateConfigChangeStatus`（`:835-836`，入参含 `id`）。这既证明 F03 所指的「必须显式绑定 auditId」，也证明**失败重试若不创建新 attempt 审计，就无法终结 operation 审计**。Codex 判断与源码事实一致。

### F04［高］新增恢复流程没有恢复所有权与组级终结规则

**位置（Codex）**：Spec §6.2 C3、恢复四分支；§4.3 D7。

**问题**：任何已存在 pending 都进入 recovery，没有区分活跃请求；分支 2 按未终结目标继续，分支 3 按效果阶段补记或组回滚，但没有统一已有成员终态。

**影响**：并发同键请求可能对仍在执行的操作启动恢复；组效果完成、只终结了部分成员时崩溃，恢复可能混合「复用成功成员」和「撤销整组」（Codex 标注为推断）。

**Codex 建议修法**：恢复前取得排他所有权并排除活跃执行；按持久化组日志恢复，核验整个组后统一更新所有成员、审计和 operation，再开放相关读写。

**核实结论：属实。** 「恢复不能靠进程内锁状态推断」这一前提已核实：发布协调器的锁回收判据是**持锁进程是否死亡**（`webui/server/publish-coordinator.ts:130-140`，已知活 pid 永不回收），这只能识别锁的归属，不能证明效果是否发生；效果核验必须依赖持久化组日志。因此「活跃请求与遗留 pending 必须靠持久化所有权区分」的前提在代码层成立。Codex 自身的「混合复用与整组撤销」后果在原文中标注为**推断**，本报告保留该标注，不将其升格为已证事实。

### F05［高］重放分流没有贯彻到执行集

**位置（Codex）**：Spec §6.2 C2、C4、C6 a；§4.3。

**问题**：C4 标记 reused，C6 a 却仍比较全部成员；`args.targets` 没有成为重放选择集，也没有组完整性检查。

**影响**：部分成功重放仍可能被自身基线阻断；请求只重放失败组 B 时，计划中的其他失败组也可能再次执行。另建子集计划又会遇到同键异计划冲突。

**Codex 建议修法**：定义「原计划身份＋本次执行子集」；校验子集属于原计划并满足组完整性，reused 不进入基线比较和效果执行，摘要绑定原计划。

**核实结论：属实。** 「同键异计划必然冲突」已核实：底层发布对同一幂等键绑定不同 planDigest 会抛 `SEMANTIC_IDEMPOTENCY_CONFLICT`（`webui/server/semantic-assets.ts:2195-2215`），且该幂等查询刻意置于读快照之前（`:2195` vs `:2223`）。因此另建子集计划会撞同键冲突，而复用原计划又要求执行集与摘要口径分离——与 Codex 判断一致。

### F06［高］激活失败直接进入 failed，缺少效果处置分支

**位置（Codex）**：Spec §6.2 C6 d–e；Plan §4 S3 第 6 项。

**问题**：写盘成功后 catalog 重载或策略提交失败，步骤 d 只规定整组 failed，e 随后终结。

**影响**：文件已改变但记录已 failed；下次按原 before 基线重试会冲突，pending 恢复入口也不再自然适用。成功记录顺序修正后，失败状态仍无法可靠重放。

**Codex 建议修法**：区分无效果失败与有残留效果失败；后者先核验、补齐激活或回滚并确认，无法确认时保持恢复状态及相关读写阻断，不能直接终结为可重试 failed。

**核实结论：属实。** 「写盘成功 ≠ 已生效」是源码明确事实：发布先落文件、记录 `status:"reindexing"` 与 `activationStatus:"unconfirmed"`（`webui/server/semantic-assets.ts:2615-2635`），随后**异步**启动索引且不等待（`:2662-2674`），索引失败时**文件保留已写入**、状态转 `reindex_failed`、activation 仍为 `unconfirmed`（`:2677-2689`）。因此「写盘后失败」必然存在残留效果的可能，把该状态直接记为可重试 `failed` 与代码事实冲突。Codex 判断与源码事实一致。

### F07［高］实际写集分组与全局索引「跨组共享」相互矛盾

**位置（Codex）**：Spec §4.3、§6.3 组划分；Plan §4 S4。

**问题**：两个需新增版本快照的目标都写同一个历史索引，按「有交集即合组」应全部合并；文档却仍要求存在跨组共享索引。严格执行会使这些导入退化为一个大组；保留多组又违反当前分组规则。实现者必须自行改变 D7 的原子性边界。

**影响**：原子组边界不可实现，组级回滚的隔离性无法证明。

**Codex 建议修法**：明确区分决定业务原子组的共享内容文件与可按条目隔离的公共元数据；规定索引条目合并、串行化、撤销和恢复规则，并同步 D7。

**核实结论：属实。** 索引的全局性与重写行为已核实：`webui/server/table-yaml-history.ts:13-15` 定义**单一全局**索引路径 `.ktx-ui/table-yaml-history/table-yaml-index.json`；创建版本快照会在写完新快照后**改写该索引**（`:330-339`，其中 `:331-337` 重建 `index.tables[key]` 并追加版本，`:338` 先裁剪、`:339` 再写索引）。因此两个需要快照的目标**必然**共享同一索引文件，Codex 指出的矛盾在代码层成立。

### F08［中］新增旧入口加锁要求与 source import 的锁表、复用规则不统一

**位置（Codex）**：Spec §4.5 规则 6、§6.3 锁表；Plan §3.3、§4 S3/S4。

**问题**：旧导入服务要求进入 ktx 锁，控制面 source import 却仅「如涉 ktx」取锁；绕过重复认领的标记只明确给了 `writeKtxYaml`。

**影响**：无法逐字确定源表批量的最终锁顺序和嵌套边界；按全局固定锁顺序外层持锁再直接调用改造后的导入服务，存在自等待风险（Codex 标注为推断）。

**Codex 建议修法**：为各工具给出唯一锁调用树；明确旧服务的已持锁调用方式，所有基线重读均在最终互斥窗口内，禁止内层重复取非重入锁。

**核实结论：属实。** 自等待前提已核实：`withKtxYamlWriteLock` 是**非重入**的进程内 Promise 队列（`webui/server/ktx-yaml-write-lock.ts:1-11`，队列尾串行化，无重入判据），而既有写路径依赖 `writeKtxYaml` 的 `lockHeld: true` 递归参数绕开重复取锁（`webui/server/project.ts:445-451`）。**Codex 标注为「推断」的结论在代码层成立**：外层持锁再调用只包了 `withDisplayWriteBarrier` 的 `writeSourceYamlImport`（`webui/server/semantic-layer.ts:950-953`）与直接写 `auditedWriteFile` 的 enabled-tables 入口（`webui/server/index.ts:1817-1818`），若不改造，内层再次取非重入锁即自等待。

### F09［中］新增验收与分期修订未同步所有门禁

**位置（Codex）**：Spec §7.2、§10；Plan §2 S0、§4 S1/S3/S4/S5、§5、§6.2。

**问题**：最终功能验收仍只列到 VOPS-47；S0 仍引用旧版本和旧矩阵；VOPS-22 未落实所声明的 S3/S4 责任，风险表仍把 G15 放在所有写工具之前。
