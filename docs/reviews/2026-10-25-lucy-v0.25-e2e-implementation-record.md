## 4. 本轮发现并修复的缺陷

### 4.1 产品缺陷：连接探测结构性丢弃密码（**产品行为错误**）

* **现象**：新建连接抽屉的「测试连接」对**任何带口令的引擎**必然失败，报「数据库密码为必填项」。
* **根因**：`CreateConnectionDrawer.tsx` 的 `connectionRequest()` 仅在 `dryRun=false` 时携带 `password`；探测请求以 `dryRun=true` 构造后又剥掉该标志 ⇒ 密码被结构性丢弃；而服务端 `/api/connections/probe` 明确要求 `password`（`CONNECTION_PASSWORD_REQUIRED`）。
* **修复**：探测路径单独补回密码；dry-run 预览**保持不带**（该路径的服务端语义是回 secret 文件引用而非收明文）。
* **证据**：新增单测 `sends the password to the connectivity probe (the endpoint requires one)`，**已验证红→绿**；抽屉单测 21/21。

### 4.2 隔离边界缺陷：客户端二进制被 `denyHome` 挡住（**阻断真实 Agent 腿**）

* **现象**：真实 Agent 旅程 144 例全部 `blocked`、`modelCalls = 0`；探测器报「客户端可达裸 DB 端点／控制面」。
* **根因**：profile 的 `denyHome` 覆盖整个 `$HOME`，客户端装在 `~/.local/...` ⇒ `sandbox-exec` 拒绝 `execvp` ⇒ **客户端从未启动**；探测器随后把自己的 exec 失败误读为「可达」。
* **修复**：`buildBoundaryBundle` 接受**已定位的客户端二进制路径**，只放行这些精确文件与其所在目录（`$HOME` 其余仍 deny）；探测与官方问答共用同一份边界。
* **证据**：`isolation*.test.mjs` **35/35**；修复后客户端可 exec，剩余阻断点收敛为 §6 的模型 API 出口缺失。

### 4.3 既有坏门禁：`p0-postgres-demo-smoke` 自 2026‑08‑08 起必然失败

* **根因**：该 smoke 对着 **Lucy 代理**调用上游工具名 `sl_read_source`／`sl_query`，而自 `1062bf4`（2026‑08‑08）起二者进入 `ABSOLUTE_DENY_TOOLS`，代理只暴露包装名 `lucy_query`／`lucy_read_source`。
* **修复**：改用代理暴露的包装名，断言内容不变。
* **证据**：修复后 **PASS**。同类排除：`p0-customer-path-smoke.mjs` 起的是原生 KTX MCP（上游名正确）、`lucy-r1-*` 断言的是「上游工具被隐藏」⇒ 均未改动。

### 4.4 既有失败（非本轮引入，已对照）

冻结目录管理面的 UX‑01‑V01／V02／V03 判 `failed`。用**既有 spec** 对照复现：`mainline-journey.spec.ts` 在**更早一步**（step 1b，`admin-accounts-create-operator` 超时）即失败，后续步骤 `did not run` ⇒ 既有环境缺陷。佐证：P1 交付记录已记载真实后端在本环境 ACL 降级（`policy_degraded_deny … role_resolution_failed`），上一轮因此退回 `page.route` mock 路径。**本轮未用 mock 掩盖。**

## 6. 遗留项与责任人

### 6.1 隔离边界缺模型 API 出口（交付工程）

`isolation.mjs` 的 `sidecarPorts`／`sidecarPort` 是**已定义但从未被提供**的扩展点（注释原文："a sidecar egress proxy **if the caller provides one**"）。当前边界只放行 MCP 端口，模型 API（api.anthropic.com）**无出口** ⇒ 任何真实客户端在强制边界内都无法发起模型调用。

> 本轮**未**擅自新建「模型 API 出口代理」：它既是新增基础设施，也是安全边界的改动（要决定放行哪些模型 host、如何处理凭据），应由 PM 单独裁决。

### 6.2 J01-02 与 e2e 夹具的 Schema 冲突（PM）

夹具在本轮运行里已注册 `fin-db`／`sales-db`，指向同一 Postgres 与同一 `analytics` Schema；主线 J01-02 的定义是**新建**连接，服务端对已覆盖 Schema 只提供「返回已有连接」。

> 二选一：① 夹具为主线预留专用 Schema（同步 seed／dataset digest 合同）；② J01-02 改为复用既有连接（同步 Spec 与 `j01-state` 阶段合同）。

**本轮已做的改进**：helper 过去以「等待一个永远不会出现的 `create-connection-confirm-btn`」超时收场；现改为**精确报错**并写入 `j01-state.json` 的 `failureRef`。

### 6.3 安全台账 15 条 `fixed` 缺 `verifiedBy`（PM）

既有欠账（`git show a3f45f0^` 可见 D‑04 更早即如此），违反台账自身合同，导致 `case-catalog.test.mjs` 失败。两条路：① 无真实 E2E 证据 → 状态回退 `open`；② 补入真实冻结 catalog id。**不得为让门禁变绿填入不存在的证据。**

### 9.2 为什么必须换注解命名空间（这是一个真实缺陷，不是风格问题）

同一批 v025 id 此前被推成三种注解类型：`case`（4 份 spec）、`execution`（2 份）、`v025-case`（1 份）。冻结收集器 `collect-management-results.mjs` 只认 `case`，且只遍历**冻结目录**里的 management case ⇒ 两种后果：

1. 推成 `case` 的 v025 id **污染冻结命名空间**，并被冻结收集器**静默丢弃**；
2. 无论用哪种类型，v025 id 的浏览器维度**都不进入任何结果文件** ⇒ 173 个执行项在验收面上**不可见**。

现在：`case` 只承载冻结目录 id（门禁机械断言），`v025-case` 只承载 v025 执行 id（门禁机械断言），两者互不串台。

### 11.2 归因途中查出的三个更深真相

**① 管理腿从不启动上游，`ktx-upstream` 却可以被"声明"出来。**
Lucy 代理把每次数据面调用转发给 KTX 上游（`LUCY_PROXY_UPSTREAM_HOST/PORT`，默认 `127.0.0.1:7878`）。管理腿只起 Lucy，**不起上游**；而 `LUCY_REAL_E2E_CAPABILITIES` 里的声明被 `managementCapabilities()` 与 spec 侧 `capabilities()` **无条件采信**。实测：7878 全程关闭，每个查询都空 ⇒ 失败被记成"产品缺陷"，实际是"环境缺失"。
⇒ 修法：runner **自己起上游**（`ktx --project-dir <project> mcp start`，与升级腿同一配方），并把 `ktx-upstream` 改成**只能被证明**的能力。

**② 本地模式的 DB 口令路径指向容器路径。**
`ktx.yaml` 渲染成 `password: file:/var/run/secrets/lucy/db/password`——那是**客户 pod 里的**路径，主机上不存在；本地跑起来的 WebUI 与上游都读不到口令 ⇒ 数据库永远连不上（上游能起，但连不上库）。
⇒ 修法：本地模式把口令放进运行目录下的真实主机路径。

**③ 夹具角色与产品的失败关闭规则冲突。**
`finance_east_west` 在**一个角色**里对同一张表声明 East 与 West 两个行策略。产品按"同表行权限冲突即失败关闭"处理（`row_grant_conflict`，UI 文案：「角色 X 里同一张表的行权限互相冲突。请统一成一种后再保存」），而 Spec §9 V08 的并集来自**两个受限 Role**。
⇒ **产品是对的，夹具是错的**。用 tsx 直接对真实运行工程编译复现：`role_resolution_failed:finance_east_west:row_grant_conflict`，`candidateDigest` 与失败断言里记录的完全一致 ⇒ **归属：共享夹具**，不擅改（见 §11.5）。

**④ 一轮真实管理腿在结构上就撞登录限流。**
产品的登录限流是"每账号每来源 15 分钟 5 次"（`webui/server/auth/rate-limit.ts`：`loginAccountSource`），而一轮管理腿**每个 spec 开一个新浏览器上下文并重新登录**（≈12 次）。
⇒ 真实复跑第 4 轮时 `POST /api/auth/login` 返回 **429**，后续 spec 全部登录超时；失败页快照还把口令写进了产物，被产物扫描拦下（扫描是对的，但根因是限流）。
⇒ 修法：`ownerContext()` **一轮只登一次**，其余 spec 复用同一会话的 storage state（并用**受保护端点**校验会话是否仍然有效——`/api/auth/status` 只报模式，报不了会话有效性）。
