## 4. 本轮发现并修复的缺陷

### 4.1 产品缺陷：连接探测结构性丢弃密码（**产品行为错误**）

* **现象**：新建连接抽屉的「测试连接」对**任何带口令的引擎**必然失败，报「数据库密码为必填项」。
* **根因**：`CreateConnectionDrawer.tsx` 的 `connectionRequest()` 仅在 `dryRun=false` 时携带 `password`；探测请求以 `dryRun=true` 构造后又剥掉该标志 ⇒ 密码被结构性丢弃；而服务端 `/api/connections/probe` 明确要求 `password`（`CONNECTION_PASSWORD_REQUIRED`）。
* **修复**：探测路径单独补回密码；dry-run 预览**保持不带**（该路径的服务端语义是回 secret 文件引用而非收明文）。
* **证据**：新增单测 `sends the password to the connectivity probe (the endpoint requires one)`，**已验证红→绿**；抽屉单测 21/21。

### 4.2 隔离边界缺陷：客户端二进制被 `denyHome` 挡住（**阻断真实 Agent 腿**）

* **现象**：真实 Agent 旅程 144 例全部 `blocked`、`modelCalls = 0`；探测器报「客户端可达裸 DB 端点／控制面」。
* **根因**：profile 的 `denyHome` 覆盖整个 `$HOME`，客户端装在 `~/.local/...` ⇒ `sandbox-exec` 拒绝 `execvp` ⇒ **客户端从未启动**；探测器随后把自己的 exec 失败误读为「可达」。
* **修复**：`buildBoundaryBundle` 接受**已定位的客户端二进制路径**，只放行这些精确文件与其所在目录（`$HOME` 其余仍 deny）；探测与官方问答共用同一份边界。
* **证据**：`isolation*.test.mjs` **35/35**；修复后客户端可 exec，剩余阻断点收敛为 §6 的模型 API 出口缺失。

### 4.3 既有坏门禁：`p0-postgres-demo-smoke` 自 2026‑08‑08 起必然失败

* **根因**：该 smoke 对着 **Lucy 代理**调用上游工具名 `sl_read_source`／`sl_query`，而自 `1062bf4`（2026‑08‑08）起二者进入 `ABSOLUTE_DENY_TOOLS`，代理只暴露包装名 `lucy_query`／`lucy_read_source`。
* **修复**：改用代理暴露的包装名，断言内容不变。
* **证据**：修复后 **PASS**。同类排除：`p0-customer-path-smoke.mjs` 起的是原生 KTX MCP（上游名正确）、`lucy-r1-*` 断言的是「上游工具被隐藏」⇒ 均未改动。

### 4.4 既有失败（非本轮引入，已对照）

冻结目录管理面的 UX‑01‑V01／V02／V03 判 `failed`。用**既有 spec** 对照复现：`mainline-journey.spec.ts` 在**更早一步**（step 1b，`admin-accounts-create-operator` 超时）即失败，后续步骤 `did not run` ⇒ 既有环境缺陷。佐证：P1 交付记录已记载真实后端在本环境 ACL 降级（`policy_degraded_deny … role_resolution_failed`），上一轮因此退回 `page.route` mock 路径。**本轮未用 mock 掩盖。**

## 6. 遗留项与责任人

### 6.1 隔离边界缺模型 API 出口（交付工程）

`isolation.mjs` 的 `sidecarPorts`／`sidecarPort` 是**已定义但从未被提供**的扩展点（注释原文："a sidecar egress proxy **if the caller provides one**"）。当前边界只放行 MCP 端口，模型 API（api.anthropic.com）**无出口** ⇒ 任何真实客户端在强制边界内都无法发起模型调用。

> 本轮**未**擅自新建「模型 API 出口代理」：它既是新增基础设施，也是安全边界的改动（要决定放行哪些模型 host、如何处理凭据），应由 PM 单独裁决。

### 6.2 J01-02 与 e2e 夹具的 Schema 冲突（PM）

夹具在本轮运行里已注册 `fin-db`／`sales-db`，指向同一 Postgres 与同一 `analytics` Schema；主线 J01-02 的定义是**新建**连接，服务端对已覆盖 Schema 只提供「返回已有连接」。

> 二选一：① 夹具为主线预留专用 Schema（同步 seed／dataset digest 合同）；② J01-02 改为复用既有连接（同步 Spec 与 `j01-state` 阶段合同）。

**本轮已做的改进**：helper 过去以「等待一个永远不会出现的 `create-connection-confirm-btn`」超时收场；现改为**精确报错**并写入 `j01-state.json` 的 `failureRef`。

### 6.3 安全台账 15 条 `fixed` 缺 `verifiedBy`（PM）

既有欠账（`git show a3f45f0^` 可见 D‑04 更早即如此），违反台账自身合同，导致 `case-catalog.test.mjs` 失败。两条路：① 无真实 E2E 证据 → 状态回退 `open`；② 补入真实冻结 catalog id。**不得为让门禁变绿填入不存在的证据。**

### 9.2 为什么必须换注解命名空间（这是一个真实缺陷，不是风格问题）

同一批 v025 id 此前被推成三种注解类型：`case`（4 份 spec）、`execution`（2 份）、`v025-case`（1 份）。冻结收集器 `collect-management-results.mjs` 只认 `case`，且只遍历**冻结目录**里的 management case ⇒ 两种后果：

1. 推成 `case` 的 v025 id **污染冻结命名空间**，并被冻结收集器**静默丢弃**；
2. 无论用哪种类型，v025 id 的浏览器维度**都不进入任何结果文件** ⇒ 173 个执行项在验收面上**不可见**。

现在：`case` 只承载冻结目录 id（门禁机械断言），`v025-case` 只承载 v025 执行 id（门禁机械断言），两者互不串台。

### 11.2 归因途中查出的三个更深真相

**① 管理腿从不启动上游，`ktx-upstream` 却可以被"声明"出来。**
Lucy 代理把每次数据面调用转发给 KTX 上游（`LUCY_PROXY_UPSTREAM_HOST/PORT`，默认 `127.0.0.1:7878`）。管理腿只起 Lucy，**不起上游**；而 `LUCY_REAL_E2E_CAPABILITIES` 里的声明被 `managementCapabilities()` 与 spec 侧 `capabilities()` **无条件采信**。实测：7878 全程关闭，每个查询都空 ⇒ 失败被记成"产品缺陷"，实际是"环境缺失"。
⇒ 修法：runner **自己起上游**（`ktx --project-dir <project> mcp start`，与升级腿同一配方），并把 `ktx-upstream` 改成**只能被证明**的能力。

**② 本地模式的 DB 口令路径指向容器路径。**
`ktx.yaml` 渲染成 `password: file:/var/run/secrets/lucy/db/password`——那是**客户 pod 里的**路径，主机上不存在；本地跑起来的 WebUI 与上游都读不到口令 ⇒ 数据库永远连不上（上游能起，但连不上库）。
⇒ 修法：本地模式把口令放进运行目录下的真实主机路径。

**③ 夹具角色与产品的失败关闭规则冲突。**
`finance_east_west` 在**一个角色**里对同一张表声明 East 与 West 两个行策略。产品按"同表行权限冲突即失败关闭"处理（`row_grant_conflict`，UI 文案：「角色 X 里同一张表的行权限互相冲突。请统一成一种后再保存」），而 Spec §9 V08 的并集来自**两个受限 Role**。
⇒ **产品是对的，夹具是错的**。用 tsx 直接对真实运行工程编译复现：`role_resolution_failed:finance_east_west:row_grant_conflict`，`candidateDigest` 与失败断言里记录的完全一致 ⇒ **归属：共享夹具**，不擅改（见 §11.5）。

**④ 一轮真实管理腿在结构上就撞登录限流。**
产品的登录限流是"每账号每来源 15 分钟 5 次"（`webui/server/auth/rate-limit.ts`：`loginAccountSource`），而一轮管理腿**每个 spec 开一个新浏览器上下文并重新登录**（≈12 次）。
⇒ 真实复跑第 4 轮时 `POST /api/auth/login` 返回 **429**，后续 spec 全部登录超时；失败页快照还把口令写进了产物，被产物扫描拦下（扫描是对的，但根因是限流）。
⇒ 修法：`ownerContext()` **一轮只登一次**，其余 spec 复用同一会话的 storage state（并用**受保护端点**校验会话是否仍然有效——`/api/auth/status` 只报模式，报不了会话有效性）。

### 12.3 真产品缺陷①：非 owner 建账号被拒 ⇒ **整个服务进程崩溃**

安全腿跑起来之后，第一个真实产品缺陷就掉了出来。

**机制**（`webui/server/auth/guard.ts` + `webui/server/auth/routes.ts`）：`requireOwner()` 用 `void reply.status(403).send(...)` 发出拒绝**但不等待**，路由随后 `return;` 返回 `undefined`。Fastify 看到"处理器没回响应"，会**再发一次**——而 `reply.sent` 只有在响应**结束**之后才为 true，所以框架这次 send 与第一次**竞态**，后者的 `writeHead` 撞上已写出的响应头 ⇒ `ERR_HTTP_HEADERS_SENT`。这个异常发生在 onSend hook 链里，**不在请求的错误处理范围内** ⇒ 未捕获 ⇒ **整个 Node 进程退出**。

Fastify 自己的警告就在产物日志里：

```
Reply was already sent, did you forget to "return reply" in the "/api/admin/admins" (POST) route?
Error [ERR_HTTP_HEADERS_SENT]: Cannot write headers after they are sent to the client
```

**影响面**：全仓只有 `requireOwner` 一处用 `void reply...send`（`guard.ts:125/132`），只有 3 个路由调用它（`POST /api/admin/admins`、`PATCH|DELETE /api/admin/admins/:adminId`）⇒ **任何已登录的 operator 一次请求就能把实例打挂**。安全腿里 107 条 `handler_error: fetch failed` 就是这个崩溃的级联（进程死后连接被拒），不是 107 个独立故障。

**修法**：`requireOwner` 改 async 并 `await reply.send(...)`（Fastify 的 reply 是 thenable，`await` 等的是响应**结束**），路由改 `if (!(await requireOwner(request, reply))) return;` ⇒ 处理器返回时 `reply.sent` 已为 true，框架不再发第二次。

**回归测试**：`webui/server/__tests__/webui-admin-auth.test.ts` 新增"非 owner 建账号被拒 403 **且服务仍存活**"。注意：`app.inject()` 下双写表现为 **unhandled rejection**，Vitest 默认只报告不失败 ⇒ 测试**显式捕获 `unhandledRejection` 并断言为空**，否则它只是一句警告。已双向验证：回退修复 ⇒ 该测试**失败**（`expected [ …(1) ] to deeply equal []`）；带上修复 ⇒ 20/20 通过。

### 12.4 真产品缺陷②：wiki 原文下载 ⇒ **整个服务进程崩溃**

同一缺陷的**第二处**：`GET /api/wiki/:key/raw`（`webui/server/index.ts`）`reply.send(page.rawMarkdown)` 之后没有 return ⇒ 同样的双写 ⇒ 同样的进程退出。安全腿里 `SEC-15-FM-*` 那 30 条 `fetch failed` 就是它造成的。

**实证**（真实进程、真实请求）：

| 版本 | 5 次 `GET /api/wiki/<key>/raw` | 服务进程 |
|---|---|---|
| 回退修复 | 响应异常 | **进程退出**（日志里 `ERR_HTTP_HEADERS_SENT` 计数 3→6） |
| 带上修复 | 5 × `200`（`text/markdown`） | **仍在监听** |

修法同 §12.3：`return reply.send(page.rawMarkdown);`。

### 12.5 产品是对的，扫描器错了：泄漏扫描把**已脱敏**的哈希判成泄漏

`SEC-03-V04` 报 `no_leak: 4 leak hit(s)`，命中 `password-hash-value`。查下来**不是产品泄漏**：产品把哈希写进审计 diff 时**正确脱敏**成 `password_hash: [REDACTED]`（`config_change_log.diff` 落库即脱敏，API 返回的也是脱敏值）。

错的是扫描器自己的正则：

```
/password_hash["']?\s*[:=]\s*(?!\[?REDACTED\]?|\*+|null\b|"",|'',)/gi
```

值前面的 `\s*` 在**否定前瞻之外**，引擎可以把它回退成零宽，再在前瞻位置（即那个空格处）重测——那里 `\[?REDACTED\]?` 匹配不上，否定前瞻于是**通过**，脱敏行被当成泄漏。注释里写明的意图（"A masked `password_hash: [REDACTED]` line in a diff is the intended output"）**没有被实现**。

修法：把值前的空白挪进否定前瞻内部，让回退无处可躲：

```
/password_hash["']?\s*[:=]\s*(?!\s*(?:\[?REDACTED\]?|\*+|\bnull\b|""|''))/gi
```

回归测试加在 `scripts/e2e/__tests__/leak-scan.test.mjs`：6 种脱敏写法必须**零命中**，具体哈希值仍必须命中（9 例全绿）。

### 12.6 登录限流与安全腿的**结构性**碰撞

产品的限流是安全控制，**不得为测试放宽**（R‑17）：`sourceTotal` 每来源 30 次/5 分钟、`loginAccountSource` 每账号+来源 5 次/15 分钟。安全腿**每个用例都要新建一个 operator 账号并登录**（"fresh session" 是它的设计前提），一次跑下来 43 次登录 ⇒ **结构性地**撞穿每来源预算（上一轮实跑日志里 18 次 429）。

本轮修的是**判定**，不是限流：登录被限流时，`freshOperatorSession()`／`ownerCookie()` 抛带 `blockedReason: "login_rate_limited"` 的错误；runner 把带 `blockedReason` 的处理器错误判为 **blocked**（缺前置条件，R‑16），**不再记成产品失败**。

⇒ 腿的"每用例一个新 operator 会话"与产品限流怎么共处，仍需裁决（§12.10 W‑04）。

### 12.7 冻结安全腿的用例形状已经过期（W‑03）

行策略用例（`scripts/e2e/security/row-policy-cases.mjs`）与 Lucy 的**现行契约**不符，两处：

1. **请求形状**：`SCOPED_QUERY`／`UNION_QUERY` 用 `measures: ["spend_cents"]`（物理列）＋ `dimensions: ["region"]`（字符串且非限定名）。现行契约要求语义 measure（`total_spend_cents`）＋ 维度对象且限定名（`{field:"marketing_daily.region"}`），否则分别被拒于 `Measure 'spend_cents' does not reference any source` 与 `dimensions_items_must_be_objects`。
2. **期望的响应形状**：用例期望 `parsed.parsed.aggregateCents`（`row-policy-cases.mjs:105/126`），而现行上游返回的是 `headers` ＋ **数组** `rows`，**没有** `aggregateCents` 这个字段。

影响面与"会不会假通过"：`extractDenyReason()`（`scripts/e2e/security/context.mjs:82`）只认 allowlist 里的 reason 或 `Access denied:` 前缀，参数校验错误会落到 `mcp_iserror_unmatched_reason`（`matched: null`）⇒ **不会假通过**，但用例会失败。

⇒ 修它要改**冻结实现**的语义并**重推 gold 绑定**（`Q-CAC-EAST` 等 typed gold 的分母），属裁决范围（§12.10 W‑03），本轮**不擅改**。

### 12.8 安全腿的独立观测通道从未接线（W‑05）

## 13. 遗留项收口轮五：把"服务宕机"从"产品失败"里摘出来，并把 W‑03 的真正堵点查到底

本轮起点是一条被"看起来像产品缺陷"的现象：安全腿复跑后 110 条用例同时报 `handler_error: fetch failed`。逐条归因后，它既不是产品缺陷，也不是环境问题，而是 **harness 自己的一处缺陷**；顺着它查下去，又把 W‑03 这条"形状过期"的待裁决项拆成了**三层**，其中最底下一层是**共享夹具与冻结 gold 的口径冲突**——它不是改形状能解决的。

### 13.1 一个 harness 缺陷吞掉了 110 条用例的真实结论

**现象（run `v025-security-uat-20261025-1600-d`，分母 162）**：

| 时刻 | 事件 |
|---|---|
| 08:12:01.971 | `SEC-02-V05` 失败：`handler_error: Lucy exited during startup (code=1 signal=null)` |
| 08:12:02.595 | 新实例 pid 62002 打印 `Server listening at http://127.0.0.1:15197`，紧接着 `Error: listen EADDRINUSE: address already in use 127.0.0.1:15197` |
| 08:12:03.790–08:12:03.832 | **110 条用例在 43 毫秒内全部 `fetch failed`** |
| 08:12:04.133 | pid 62019 起来，服务恢复，后续用例恢复正常（1.8s/条） |

43 毫秒跑完 110 条 ⇒ 那是**服务端确实不在跑**时连接被拒，不是每条各坏一次。而这一轮的分数（43 通过 / 96 失败 / 23 阻塞）**整体作废**：110 条是"对着一个没在跑的服务打的分"。

**根因**：`scripts/e2e/lib/instance.mjs` 用 `tsx` CLI 起服务。`tsx` 会 **fork** 一个子进程真正跑脚本，于是 harness 手里握着的只是 **wrapper**：

- `child.once("exit")` 报的是 **wrapper 退出**，不是服务退出 ⇒ `stop()` 认为"服务已停"时，真服务可能还活着、还占着端口；
- `stop()` 与 `start()` 之间因此可能与**仍占端口的旧服务**赛跑 ⇒ 新实例 `EADDRINUSE` 退出（code=1）⇒ `instance.start()` 抛 `Lucy exited during startup` ⇒ 此后整条腿都在对着死服务打分。

**实证**：单独复现脚本（`node --import tsx` 单进程 vs `tsx` CLI）在**干净**环境下 stop/start 完全正常 ⇒ 竞态只在真实时序下暴露，不能靠"再跑一遍"消失。

**修复**（`scripts/e2e/lib/instance.mjs`）：

1. 改用 **`node --import tsx server/index.ts` 单进程启动**（`serverLaunchSpec()` 是唯一真源，`LucyProcess#launch` 与 `Instance.probeVariant` 共用）⇒ `exit` 即"服务已消失"，stop/start 不再与残留端口赛跑；
2. `start()` 对 `EADDRINUSE` 做**有限重试**（3 次，间隔 1s，仅在日志尾部出现 `EADDRINUSE` 时）；其它启动失败原样抛出。

**回归测试**（新增 `scripts/e2e/__tests__/instance-launch.test.mjs`）：断言启动规格是单进程（不再出现 forking 的 `tsx` CLI），并**行为性**证明"被 spawn 的 pid 就是真正跑代码的 pid"（fork 层被消除）。

### 13.2 "目标不可达"判 blocked 而不是 failed，并自动恢复实例

对着**没在跑的服务**打分不是产品失败，是**根本没被评估**（R‑11 / R‑16）。

- `scripts/e2e/run-security.mjs` 新增 `classifyHandlerError(error)`：前置条件缺失 ⇒ `blocked`（`precondition_unavailable`，沿用本轮之前对登录限流的同一纪律）；**目标不可达** ⇒ `blocked`（`service_unreachable`）；其余 ⇒ `failed`（`handler_error`）。
- 判定依据 `isServiceUnreachable(error)`：消息里的 `fetch failed` / `ECONNREFUSED` / `exited during startup` 等，以及 `fetch` 聚合错误 `cause.errors[]` 里的连接错误。
- 出故障后 runner 会 **`lucy.restart("SIGKILL")` 尝试恢复**，让后面的用例仍然对着**活的服务**打分；恢复失败也会在进度日志里明说。

**回归测试**（同文件）：`classifyHandlerError` 的三分支 + `isServiceUnreachable` 的识别表。

### 13.3 冻结安全用例自身的三个真代码缺陷

|---|---|---|

### 13.4 deny reason 识别：harness 的白名单落后于产品的真实词汇表

这是 W‑03 里被误判为"用例形状过期"的一层，真实原因是 **harness 认不出产品的合法拒绝**。

产品按 `webui/server/proxy/acl.ts` 的 `AclDecision.reason` 发拒绝，**绝大多数带 `:detail` 后缀**：`table_forbidden:<table>`、`explicit_table_required:<table>`、`role_resolution_failed:<roleId>`、`unknown_or_forbidden_connection:<conn>`…… 而 harness 的 `DENY_REASON_ALLOWLIST` 是**精确匹配**，里面写的是**不带后缀的类名** ⇒ 这些 reason **永远匹配不上**。

第二层：harness 切 reason 的正则要求 `Access denied: ` 之后的**整串**都是 token，而产品把人类提示用**空格**分隔（`table_forbidden:analytics.x 可用连接：fin-db。 可用来源：…`）⇒ 整串提示被当成 reason ⇒ 同样匹配不上。

⇒ 两者叠加的效果是：**产品正确地拒绝了，harness 报"不是拒绝信封"**（`mcp_iserror_unmatched_reason`）——这正是那 38 条的共同签名。

**修复**（`scripts/e2e/security/context.mjs`）：

1. `denyReasonToken(message)`：剥掉 `Access denied: ` 前缀后取**首个 token**（token 字母表含 `.`，来源名 `analytics.orders_masked` 带点）；空格后的提示不再污染 reason。
2. `isAllowlistedDenyReason(reason)`：**按类识别**——reason 等于某条目、或以 `条目:` 开头即算产品的合法拒绝类（与产品自己的审计分类 `audit-classification.ts` 同一纪律）。
3. 白名单补齐产品**真实发出**的类：`tool_forbidden`、`tool_forbidden_global`、`tool_unclassified`、`agent_disabled`、`query_concurrency_exceeded`、`sensitive_metadata_forbidden`、`table_forbidden`、`source_map_compile_failed`、`policy_degraded_deny`、`wiki_forbidden`，以及 `tool_absolute_deny` 类。

**识别与匹配仍然分开**：`denyReasonMatches()` 比对的是**完整 reason**，所以要求具体 reason 的用例（如 `tool_absolute_deny:sl_query`）不会被别的 reason 顶替 —— 放宽的是"这是不是一次合法拒绝"，不是"是不是那一次拒绝"。

**回归测试**（新增 `scripts/e2e/__tests__/deny-reason-vocabulary.test.mjs`）：逐条覆盖产品词汇表、带空格提示的 reason、403 JSON-RPC 形状，以及三条反向断言（**校验错误不是拒绝**、未知 reason 不是拒绝、5xx 不是拒绝）。

### 13.5 W‑03 的另一半：请求形状与响应形状（本轮已适配的部分）

现行契约与冻结用例的形状确实对不上，且**对不上到产品根本走不到它要验的那一层**：

| 冻结用例 | 旧形状 | 现行契约 |
|---|---|---|
| 来源 | `analytics.orders` | 夹具的规范来源是 `analytics.orders_masked` |
| 度量 | `spend_cents` / `count_distinct_order_id`（物理列） | 语义 measure `total_spend_cents` / `order_count` / `cac_cents` |
| 维度 | `["region"]`（裸字符串） | `[{ field: "marketing_daily.region" }]`（限定名对象） |
| 过滤 | `[{ field: "region", ... }]` | 限定名 `orders_masked.region` |
| 响应 | `{ aggregate, rows: [{ count_distinct_order_id: 16 }] }` | `{ headers: [...], rows: [[...]] }` |

**实测**：旧形状先被产品自己的**入参校验**拒掉（`invalid_arguments:lucy_query:dimensions_items_must_be_objects`）⇒ 产品**根本没走到 ACL/行策略层**，用例想验的东西一次都没验。

本轮适配（**保持同 ID、同断言 token、同 gold 值、同分母**）：

- 请求形状：`SCOPED_QUERY` / `UNION_QUERY` / SEC‑09 / SEC‑12 / SEC‑13 / SEC‑10‑V02 的来源、语义 measure、限定名维度与过滤；
- 响应形状：新增 `measureValue(parsed, measureNames)`，从现行 `{ headers, rows }` 里**按列名**取出度量值；**取不到就是 `null`，绝不猜数**（空行、非数值、列名对不上都判"未测到"）；
- `data-cases-contract.test.mjs` 里钉死的字面量 `analytics.orders` 一并改齐 —— **依据是 git 历史**：夹具把来源改名成 `orders_masked` 是在**冻结目录那次提交**（`86d0773`）里做的，而契约测试里的 `analytics.orders` 来自更早的 `efb46fb` ⇒ **契约测试里的字面量比冻结夹具还旧**，它要守的意图（命中被授权连接、发出跨库拒绝请求、用规范来源名）没有被削弱。

### 13.6 W‑03 剩下的真正堵点：夹具的 `cac_cents` 复现的是 gold 的 **decoy**

形状适配之后，`Q-CAC-*` 这一族 typed gold **仍然过不了**，而且原因不在 harness 侧。

**gold 的口径**（`examples/security-e2e/gold/v025-gold.mjs` 的 `computeGold`）：只取 **actual 行**（forecast 行不进集合）、`new_customers` 为 NULL 的行**分子分母同除**、**半进位整数除法**。

**实测（run `-1600-f` 的数据集，`gold.Q-CAC-28D.cents = 9706`）**：

| 口径 | 值 | 判定 |
|---|---|---|
| gold 定义的口径（actual + NULL 行同除 + 半进位） | **9706** | ✅ 与 gold **完全一致** |
| 共享夹具现行 `cac_cents` 表达式（`sum(spend_cents)/nullif(sum(new_customers),0)`） | **9802** | ❌ **这正是 gold 自己标注的错误答案 `wrongAnswers.spendOverAllRowsCents = 9802`** |
| 同上但**不取整** | 9706.2676… | ❌ gold `toleranceCents = 0` ⇒ 差一个取整 |

**⇒ 决定性结论**：共享夹具的 `cac_cents` 度量**复现的是 gold 的 decoy，不是 gold**；差值（9802 vs 9706）**恰好等于那条 `new_customers IS NULL` 的行被计入分子的投放额**（109705 分）。再叠加"金额 measure 未取整到整数分"，**现行夹具下任何请求形状都无法复现冻结 typed gold**。

⇒ **W‑03 不是纯机械适配**，它至少还需要两个裁决：

1. **共享夹具语义变更**：`examples/security-e2e/project-template/semantic-layer/fin-db/marketing_daily.yaml` 的 `cac_cents` 表达式要不要改成治理口径（NULL 行分子同除）——**与 W‑02 同性质**（共享夹具语义变更，本轮不擅改）；
2. **金额 measure 是否由产品取整到整数分**：gold 的 `toleranceCents = 0` 意味着必须是整数，而现行度量是 numeric 除法。

⇒ 本轮把形状与响应适配到位，让这类用例的失败**从"看不懂的信封"变成"数值对不上"**（可定位、可比较），但**没有**替 PM 决定上面两件事。

### 13.7 W‑05：观察器为什么"接了也测不到"，以及正确接线的硬要求

`run-security.mjs` 的注释写着"the runner is responsible for calling `ensureStarted(upstreamUrl)`"，代码只把一个 sample 存进 `activeObserver`，**从未调用** ⇒ `observeUpstream()` 永远返回 `unknown` ⇒ 凡是断言 `upstream_exec_zero` 的用例都拿不到观测。

**为什么"只是补一行调用"不行**：`createDefaultObserverFactory` 返回的工厂**每次调用都新建一个 closure**（`started` 状态不共享）⇒ 即便 runner 调了自己的那份，SecurityContext 每次观测拿到的仍是**从未启动**的新实例。

**更关键的是接错的风险**：`LocalLoopbackObserver` 必须在**请求路径上**（Lucy → 观察器 → 真上游）。如果观察器不在路径上，`upstream_exec_zero` 会恒为 0 —— 而**目前没有任何用例断言"上游执行次数 > 0"** ⇒ 接线接错会**把 ~40 条"拒绝后零上游执行"的断言变成静默通过**。这正是本项目明令禁止的"友好默认值"。

⇒ **正确接线必须自带正向对照**：在跑用例之前，先发一次**被授权**的查询，断言观察器**确实看到 ≥1 次上游执行**；看不到就不放行（失败关闭），而不是照常跑用例。

⇒ 另外，"观测缺失 ⇒ 判 failed（而不是 blocked）"是**已评审并有契约测试钉住的**语义（`data-cases-contract.test.mjs` 的 C1‑#1："`upstream_exec_zero` 不能是伪造的 true"）⇒ **本轮不推翻它**，而是把"让观测真的发生"作为 W‑05 的验收要求。
