# Spec 190 方案与工单交叉审阅意见

| 元数据 | 内容 |
|---|---|
| 审阅日期 | 2026-10-26 |
| 审阅对象 | [Spec 190 v0.1](../../webui/docs/190-live-table-discovery-and-continuous-sync-spec.md)、[WO-202610-26](../../webui/docs/plans/wo-202610-26-live-table-discovery-and-continuous-sync.md) |
| 审阅方式 | 交叉核对目标、数据契约、核心流程、任务依赖、回滚及验收标准 |
| 结论 | **方向认同，但不建议按当前 v0.1 直接批准生产代码实施；只放行 T0 调研，P0 项修订后再审** |

## 1. 总体结论

Spec 190 的方向和安全边界正确，WO-202610-26 的任务拆分也基本覆盖了 Spec 的表面交付物。但交叉审阅后发现，成功发现结果、基线、当前差异和历史事件之间的数据关系尚未闭合，差异清单也缺少完整读取与展示路径。

此外，两段式探测没有进入工单，S2 与 S3 的顺序和依赖不准确，部分强制要求没有对应验收项。建议先形成 Spec 190 v0.2 和修订后的工单，再放行 T1～T3。

## 2. 认同的意见

### 2.1 发现与授权严格分离

认同“不写 Schema Manifest、不写 `enabled_tables`、不自动删除本地条目”的边界。持续感知只报告事实和差异，不改变角色有效 source，避免自动任务悄悄扩大或破坏 Agent 可见范围。

### 2.2 S1／S2／S3 分期合理

先提供 Schema 级库内表清单，再接入导入范围预览，最后交付持续感知，比一次性交付完整平台更容易验证、定位问题和回滚。

### 2.3 `import-scope` 不同步连库

认同以下来源优先级：

1. 显式传入结果；
2. 同代次的持续感知结果；
3. 无结果时返回空并标记未执行。

该设计保持 Spec 183 的纯装配语义，避免预览请求意外访问真实数据库。

### 2.4 缓存代次与失败隔离

认同 10 分钟 TTL、连接配置代次隔离、Schema 级失败隔离、满页即失败、不静默截断等约束。这些措施能防止旧连接配置结果被复用，也能避免单 Schema 故障阻断整个连接。

### 2.5 落盘与基线推进纪律

认同原子写、`0600`、每连接保留有限历史，以及“差异记录落盘成功后才推进基线”。后者可以防止写盘失败后静默吞掉变更。

### 2.6 KTX 前置实测与零 AI 依赖

认同先实测交付镜像 KTX 0.16.0 的 `scan` 能力，再决定 S3 provider 路径。若路径 A 必须依赖 AI／enrichment，应改用只读 SQL 路径，不应把 LLM 配置变成核心链路的前置条件。

## 3. 反对或要求修改的意见

## 3.1 P0：阻断审批的问题

### P0-1：S2 所需的持久化成功结果没有存储契约

Spec 190 §7.2 要求 S2 消费“sidecar 中该 Schema 的最近一轮成功记录”，但当前只定义：

- `live-table-diffs.json`：只有差异非空才写入；
- `live-table-discovery.json`：保存开关、状态和代次；
- S1 完整表清单：只进入内存 TTL 缓存。

因此，持续感知成功但没有差异时，恰恰没有可供 S2 消费的完整表清单。WO 的 T2 排在 T3 之前，也无法独立获得真实发现结果。

**修改建议：**

新增明确的 discovery snapshot 契约，至少保存：

- `connectionId`、`schema`、`generation`；
- 最近一轮成功完成时间；
- 完整表清单及列数指纹；
- provider／来源信息；
- 必要的过期或新鲜度语义。

差异历史不能兼任成功快照。S2 应消费最新成功快照，而不是消费差异记录。

### P0-2：Manifest 对账与物理库前后轮变化被混为一种差异

Spec 目标描述的是“物理库与本地 Schema Manifest 的差集”，但 §8.2 实际比较的是“本轮物理库结果与上一轮物理库基线”。

这两种语义不同：

- 物理库与 Manifest 对账：回答“本地缺什么、本地多什么”；
- 前后两轮物理库比较：回答“物理库新增、删除或变化了什么”。

同时，§8.3 使用 `union(records.added/missing/changed)` 生成读取结果，会把历史事件永久累积。表恢复、再次变化或本地后来补齐后，旧差异仍可能继续出现。

**修改建议：**

明确拆成两个数据概念：

1. **当前对账状态**：根据最新快照、Manifest 和 `enabled_tables` 重新计算，允许后续结果消除旧差异；
2. **变更事件历史**：记录曾经发生的变化，仅用于审计和追踪，不通过 `union` 冒充当前状态。

还应明确首轮基线行为：是“只建立基线，不报全量新增”，还是“立即执行一次物理库与 Manifest 的全量对账”。两种行为都可行，但必须写清楚并分别验收。

### P0-3：差异清单缺少完整读取与展示交付物

当前 `GET /api/connections/:connId/discovery` 只返回 `diffCount`，没有返回 `added[] / missing[] / changed[]` 的端点。工单也没有连接概览 UI 任务。

这与 Spec 的“差异清单只读呈现”和“连接概览显示持续感知已暂停”不闭合。

**修改建议：**

- 增加明确的差异读取 API，返回当前对账状态及必要的历史记录；
- 若 `/connections` 属于本轮适用范围，增加连接概览的展示与状态任务；
- 若本轮明确不做 UI，则删除展示承诺，并把适用范围改为纯后端能力，避免验收口径含混。

### P0-4：“结构差异”实际只覆盖列数变化

当前指纹只有 `columnCount`。同列数下的列改名、类型变化、可空性变化、主键变化均不会被发现。这与来源需求中的“L1 表目录与 L2 表结构都要”存在落差，“结构差异清单”的名称也会形成过宽预期。

**修改建议：**

二选一：

- 保留轻量实现，但改称“表清单与列数差异”，明确不承诺完整结构变化检测；
- 或定义稳定结构摘要，覆盖列名、类型、可空性、主键及需要支持的注释字段，再以摘要检测变化。

## 3.2 P1：实施前应澄清的问题

### P1-1：两段式探测未进入核心流程和工单

Spec §6.3 要求多数轮次只执行段 1，但 §8.2 仍逐 Schema 调用 `readLiveTables`。WO T3 没有段 1、Schema 轮转、段 2 升级条件等任务。

同时，最小轮询间隔为 5 分钟，而 S1 缓存 TTL 为 10 分钟。后台使用 `refresh=false` 时，5 分钟轮询可能直接消费缓存，实际感知频率退化为 10 分钟。

**修改建议：**

- 明确段 1 与段 2 的查询形状、轮转顺序和升级条件；
- 明确 Schema 集合不变时，表新增和删除如何被发现；
- 明确后台轮询是否绕过面向人工读取的 TTL 缓存；
- 将上述行为加入 WO T3 和验收标准。

### P1-2：工单错误扩大了 KTX 前置阻塞和双 provider 范围

Spec §6.2 明确 S1／S2 走 `ktx sql`，只有 S3 被 KTX `scan` 调研阻塞。WO 却要求 T1 同时实现路径 A／B，并让 T0 阻塞 T1 之后的所有写码任务。

这会增加关键路径和不必要的双实现维护成本。

**修改建议：**

- S1 的 SQL provider 不被 KTX `scan` 调研阻塞；
- 保留统一 provider 接口与测试假实现；
- 生产 provider 按 T0 结论实现一种，不要求同时交付两套生产实现；
- 若确实要求双实现，应单独说明收益、维护责任和测试预算。

### P1-3：任务依赖和“三段互不依赖”回滚声明相互矛盾

WO 实现顺序明确 T2／T3 依赖 T1 的结果形状，T2 又消费 T3 的发现结果；回滚部分却声称三段互不依赖、可单独回滚。

**修改建议：**

按真实依赖重写：

- T1 是 T2／T3 的共同基础；
- T2 的消费端可以先实现并用夹具测试，但真实连续数据来源依赖 T3；
- 回滚 T1 会影响 T2／T3，不能称为独立回滚；
- 回滚 T3 后，T2 应明确降级为 `discoverySource: "none"`，而不是仍宣称功能完整。

### P1-4：连接级状态无法准确表达 Schema 级部分失败

一个 Schema 失败、其他 Schema 成功时，伪代码最后仍执行连接级 `recordPass`。当前连接级 `lastStatus / lastReason` 也只有一份，无法准确表达部分失败、暂停与恢复。

**修改建议：**

- 增加 `partial` 状态，或定义等价的聚合规则；
- 保存每 Schema 的最近状态与原因；
- 明确指数退避后是自动恢复，还是进入需要人工干预的暂停态；
- 明确连接级 `lastRunAt` 是开始时间、完成时间，还是最后一次尝试时间。

### P1-5：错误码词表没有覆盖自身流程

正文使用了 `PROBE_QUEUE_FULL`，但 `LiveTableFailureReason` 词表未包含它；排队超时、代次失效也只有“明确 reason”的笼统要求。

此外，`SCHEMA_NOT_FOUND` 与 `SCHEMA_NOT_VISIBLE` 被要求必须区分，但没有说明权限不足时如何可靠判定。

**修改建议：**

- 补全封闭式 reason 词表及映射；
- 为队列满、排队超时、代次失效、写盘失败分别定义语义；
- 对无法可靠区分的数据库错误采用保守分类，不制造看似精确但实际不可验证的原因；
- 为每种新增 reason 增加测试。

### P1-6：SC-1～SC-17 没覆盖全部强制要求

当前验收项未覆盖：

- 首轮基线行为；
- 差异恢复或被消除后的读取结果；
- 差异写盘失败时基线不推进；
- 退避、暂停与恢复；
- 审计事件内容及频率；
- 原子写和文件权限；
- 独立队列配额；
- 配置及失败状态在重启后的恢复；
- 5 分钟轮询与 10 分钟 TTL 的交互；
- 当前对账状态与历史事件的区分。

因此，“SC-1～SC-17 全过”不足以证明 Spec 和工单的全部关键承诺已经实现。

**修改建议：**

补充对应 SC，并在 WO T5 中逐项映射测试文件和测试层次。对无法自动化的真实存量连接验收，单独列出夹具或客户样本的前置条件和证据要求。

## 4. 建议的数据闭环

建议 Spec 190 v0.2 至少明确以下四类数据，避免继续混用：

| 数据 | 内容 | 主要消费者 | 生命周期 |
|---|---|---|---|
| 最新成功快照 | 每连接、每 Schema 的完整表清单与结构指纹 | S2、持续感知 | 同代次最近成功结果，可持久化 |
| 物理基线 | 上一轮用于变化检测的物理结果 | reconciler | 首轮建立，成功处理后推进 |
| 当前对账状态 | 最新快照与 Manifest／`enabled_tables` 的当前差异 | 差异读取 API、连接概览 | 随最新快照和本地资产重算 |
| 变更事件历史 | 曾经发生的新增、消失、结构变化及失败 | 审计、问题追踪 | 每连接限量保留，不冒充当前状态 |

## 5. 建议的实施顺序

1. **只批准 T0**：完成 KTX 实测、文档对账和验收样本确认，不写生产代码。
2. **修订 Spec 190 v0.2**：关闭 P0-1～P0-4，并澄清 P1 项。
3. **先实现 S1 provider 与表清单端点**：不必等待 KTX `scan` 路径结论，也不要求双生产 provider。
4. **实现 T3 的快照、基线、当前差异和历史事件**：明确首轮、重启、失败和退避语义。
5. **接入 S2**：消费真实持久化快照；此前可用夹具完成来源优先级单测。
6. **补差异读取与展示**：按最终产品范围交付 API／UI。
7. **扩充验收后收口**：不仅检查原 SC-1～SC-17，也覆盖本审阅列出的强制行为。

## 6. 最终审阅意见

**继续推进该方案，但当前不建议整体批准 WO-202610-26 的生产代码实施。**

最先需要解决的不是代码细节，而是“最新成功快照、物理基线、当前对账状态、变更事件历史”四者的职责和存储关系。该闭环明确后，S2 的数据来源、S3 的差异语义、读取 API、UI 和验收标准才能一致。
