## 一、结论

v1.1 相对 v1.0 的修订**方向正确、内部自洽**，唯一实质缺口是**实现级**的：G34 已定案「幂等存储与审计表同库同事务」，但「独立存储」这一措辞没有冻结**物理落点**，实现者若按字面另建独立库，G34 的落地条款即落空。该缺口已修（见第二节）。

## 二、发现与处置

### T-01（中高）幂等表的物理落点未冻结，G34 同事务条款可能落空

- **位置**：Spec §4.4「业务幂等记录存于**独立存储**（非配置审计表）」；Plan §3.2 新增文件表 `webui/server/ops/ops-idempotency.ts`「**独立幂等存储**」；Plan §4 S1 第 2 步
- **冲突条款**：Plan §4 S2 第 23 条（G34 定案落地）——「本 attempt 的 operation 认领、operation 审计、待执行 target 的认领与 target 审计在 **`audit.sqlite` 的同一次 `db.transaction()`** 中提交」
- **问题**：「独立存储」只澄清了**逻辑独立**（不复用 `config_change_log` 表、字段与状态机自成一套），**未澄清物理位置**。实现者按字面理解为「另建一个存储」时，幂等表可能落在另一个 SQLite 文件 ⇒ **跨库无事务** ⇒ 第 23 条要求的「同一次 `db.transaction()`」无法成立，G34 定案在实现层失效。文档内部因此存在**未被察觉的自相矛盾**（一处说独立、一处说同库同事务）。
- **处置（已修）**：三处统一冻结物理落点——
  1. Spec §4.4：改为「存于**独立存储**（**逻辑独立**：非 `config_change_log` 表…），**但物理上与审计表同库**——幂等表建在 **`audit.sqlite`** 内（与 `config_change_log` **同库不同表**）…**不得另建独立库**（另建库即跨库，跨库无事务，G34 落地条款随之落空）；「独立存储」指**逻辑独立**，不是**物理独立**。」
  2. Plan §3.2 `ops-idempotency.ts` 行：补「**幂等表建在 `audit.sqlite` 内**（与 `config_change_log` 同库不同表）…**不得另建独立库**」
  3. Plan §4 S1 第 2 步：补「**物理落点冻结在 `audit.sqlite` 内**…**不得另建独立 sqlite 文件**」
- **源码依据**：`webui/server/admin/audit.ts:364,366` —— `dbPath = path.join(dir, "audit.sqlite")` / `db = new Database(dbPath)`（better-sqlite3）。审计表 `config_change_log` 建于该库（`:415`），且 `better-sqlite3` 的 `db.transaction()` 仅在同一连接内有效。
