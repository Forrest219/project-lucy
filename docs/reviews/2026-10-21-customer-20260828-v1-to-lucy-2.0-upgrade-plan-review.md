## 1. 结论

1. **技术判断质量高，可作为修订基线。** 逐条核验计划引用的 12 组代码断言：10 组完全属实，2 组部分属实（均为行号与措辞问题，不影响主结论）。计划的核心主张——三件套同升、认证模式迁移、角色编译失败是最危险断点、审计库纯增量、`helm rollback` 单独不够——**全部成立**。

4. **有一处产品决策被写成了物理定律。** 计划把「开放模式 → 管理员登录」表述为不可回避的技术必然；但仓库同期文档给出的结论是：**0.16.0 → 0.17.0 / Chart 0.2.4 这条已发布的快路径，既能修复 400，又能保留开放模式**。因此这不是「400 修复的代价」，而是 2.0 自身的产品决策（且有 P0 安全整改依据）。客户因此失去了选择权。

## 4. 反对项（按严重性排序）

### R1｜致命：反向代理信任契约完全缺失，而它直接命中「https 域名映射」

**计划全文 0 处涉及反向代理。**

代码事实：`webui/server/web-security.ts:36-55` 的 `csrfDenied()` 对**所有** `/api/` 的 POST / PUT / PATCH / DELETE 生效：

```js
const origin = firstHeaderValue(request.headers.origin);
const host = effectiveHost(request);
return new URL(origin).host.toLowerCase() !== host;   // 不等 → 403 CSRF_ORIGIN_DENIED
```

`effectiveHost`（`web-security.ts:29-34`）**只在 `LUCY_TRUST_PROXY` 开启时**才采信 `X-Forwarded-Host`，否则回落 `request.headers.host`；而 `LUCY_TRUST_PROXY` 在整个 `deploy/k8s/helm/lucy/` 目录**零命中**（Chart 从不设它）。拦截在 `web-security.ts:57-67` 的 `onRequest` 钩子，**先于**认证钩子执行。

**后果**：客户网关若把 Host 改写成内网 Service 地址（nginx 默认 `proxy_set_header Host $proxy_host;` 即取上游地址；自建网关常见此写法），则浏览器 `Origin: https://客户域名` ≠ `Host: 内网地址` → 403。而 `POST /api/auth/login` 与 `POST /api/auth/bootstrap` **都在拦截范围内** → **客户认领不了 owner、登不了 WebUI**。

计划的三个阶段都发现不了它：§5.1 的 13 项必改 values 无此项；P1 无采集项；P3 的 `/api/health` 是 GET，命中豁免。

**同一开关的第二个后果**，官方口径就在仓库里——`deploy/k8s/K8S_CONTRACT.md:165`：

> Behind an ingress, supply `LUCY_TRUST_PROXY=1` and `LUCY_TRUSTED_PROXY_CIDRS` (comma-separated CIDRs of the ingress controller) through `extraEnvFrom` so login/bootstrap rate limits use the real client address. **Without CIDRs, forwarded headers are ignored and all clients share the ingress address as the throttling source.**

即：不配这两个变量，计划 §5.5 自己写的「登录 5 次失败 / 15 分钟、bootstrap 5 次失败 / 15 分钟」会变成**全站共享一个计数器**——任何人输错 5 次，所有人一起被锁 15 分钟。对一个刚从没登录切到登录的客户，这是可预见的踩踏。相关实现：`webui/server/auth/rate-limit.ts:30`、`webui/server/proxy/request-client-meta.ts:260`。

**建议修改（三处）**

1. §5.1 增第 14 项：`extraEnvFrom` 提供 `LUCY_TRUST_PROXY=1` + `LUCY_TRUSTED_PROXY_CIDRS=<网关出口 IP / CIDR>`。可行性已核：`deploy/k8s/helm/lucy/values.yaml:240` 已有 `extraEnvFrom: []`；K8s 上 `env` 优先于 `envFrom`，但这两个变量本就不在 Chart 的 `env` 里，加得进去。
2. P1 增一条：现场确认网关**是否透传原始 Host**，以及网关出口 IP（CIDR 必须覆盖真实出口，否则转发头仍被忽略）。
3. P3 / L4 增一条断言：**实际发一次 `POST /api/auth/login`，不得返回 403**。这是唯一能提前暴露该问题的探针。

### R2｜严重：`enabled_tables` 风险被当成「条件性漂移」，对本客户接近必然

代码事实链：

- `acl.ts:1037-1049` `loadEnabledTablesByConnection()` 对**每个**连接执行 `map.set(id, new Set(conn.enabledTables ?? []))` —— 缺省即空集。
- `acl.ts:1076-1083` `isInEnabledTableRange()` 对空集一律返回 false。
- `acl.ts:1209-1213` 在 `selectorMatches` 之后、零命中判断之前做该过滤；`:1225-1237` 过滤后为空 → `selector_zero_match` → **角色编译失败**。
- 该规则为 2.0 新增（Spec 182，2026-10-18）；0.16.0 的 acl.ts 中 `enabled_tables` 命中数为 0，即**完全不查**。

**因此**：客户 `ktx.yaml` 中某连接只要没写 `enabled_tables`，该连接下所有使用 `tableSelectors` 的角色在 2.0 全部编译失败，且**启动期无报错**。

`enabled_tables` 属较新的配置形态，而客户是 2026-08-28 的配置；客户授权角色的常规写法正是 `tableSelectors`。计划 §5.4 已把它列为「四类 preflight 未覆盖的漂移」之首、§10.3 也承认「这是本次升级最容易在客户侧造成 Agent 突然查不到数的原因」——**定位正确，但处置力度不足**：P1-7 只是人工扫描一次，而 §10.5 同时承认「本计划没有自动化门禁」。

**验收侧同样偏弱**：L4 只写「每个角色仍有可用的有效 source」，**没有要求与 P1-7 基线逐角色比对数量**。只测一个角色的验收会漏掉其余已失权角色——而角色编译失败只在真正调用时暴露。

**建议修改**

1. 新增门禁项：用**目标镜像对 PVC 副本做一次只读角色编译自检**（隔离 namespace，不触生产），把「角色是否编译成功、有效 source 数」固化为可复现证据，替代纯人工扫描。
2. L4 增加硬断言：**每个角色的有效 source 数 ≥ 升级前基线**（P1-7 产出的是基线表，本来就具备比对条件）。
3. §5.4 的「后果」列补一句：客户 ktx.yaml 若无 `enabled_tables`，受影响的是该连接下**全部**带 selector 的角色，不是个别角色。

计划 §1.4 把「开放模式 → 2.0 管理员登录」写成最大行为变更，§5.5 写成技术必然。但仓库同期有一份直接冲突的结论——`docs/runbooks/customer-mcp-session-400-upgrade.md:88-97`：

**结论：0.16.0 → 0.17.0 / Chart 0.2.4 这条已发布的快路径，既能修复 400，又能保留开放模式。** 因此「必须上登录」不是 400 修复的代价，而是 2.0 自身的产品决策。

### R4｜中：https 私有 CA / 外部 TLS 网关分支没进计划

客户是 https 域名映射，则 Checklist C03 的「**HTTPS 私有 CA 随实例交付**」是必经路径而非可选项。计划 §5.1 第 11 项只写了「`security.access` 选 http / https」，完全未涉及：

- `externalTlsReviewed: true` —— https 模式下实例配置**必须**填，否则 helper 报 `EXTERNAL_TLS_REVIEW_REQUIRED`（`scripts/deploy/customer-deployment-helper.py:417`）
- 私有 CA：实例 JSON 填 `tlsCaFile`，程序校验并复制为 `tls-ca.pem`，哈希不符报 `TLS_CA_IDENTITY_MISMATCH`（同文件 `:261-262`、`:516-517`）
- 取证可信度：L2 / L4 用 `curl` 与 UAT 脚本取证，私有 CA 签发且取证机不信任时取证直接失败；更糟的是有人用 `-k` 绕过，则取证结论不可信

**建议修改**：§5.1 增「TLS 网关与私有 CA」条目（指向包内 `deploy/k8s/CUSTOMER-UPGRADE.md:27`）；P1 增加「确认外部 https 域名的证书链是公有 CA 还是私有 CA；私有 CA → 随实例交付并确认取证机信任」。

## 5. 针对本客户状态的三个专项判断

### 5.1 登录迁移的真实影响面，比计划暗示的小

- **WebUI 没有问数 / 聊天页面**：`webui/src/app/App.tsx:504-548` 的路由全表为 `/overview`、`/ops/calls`、`/onboarding`、`/connections*`、`/catalog*`、`/sources*`、`/joins*`、`/publish*`、`/wiki`、`/skills`、`/admin/*`、`/eval/*`、`/help`；`path="/ask"` / `path="/chat"` 命中数为 **0**。问数走 MCP（Bearer Token），与 WebUI 会话完全独立——计划 §5.5「Agent 侧不受影响」这一行**是对的**。
- **真正需要登录的是 WebUI 浏览 / 管理面**：`webui/server/index.ts:643` 的 `requireWebuiAuthHook` 是全局 `onRequest` 钩子；`webui/server/auth/guard.ts:38-52` 的免登录白名单只有 9 条（`GET /api/health`、`GET /api/auth/status`、`POST /api/auth/login`、`POST /api/auth/bootstrap`、`POST /api/auth/logout`、`GET /api/help*`、`GET /api/branding`、`GET /api/branding/logo`），其余全部 `/api/*` 需登录。
- **2.0 没有只读 WebUI 角色**：`webui/server/auth/admins-store.ts:10` 的 `WebuiAdminRole = "owner" | "operator"`；`webui/docs/143-call-monitoring-ops-page-spec.md:61` 明写「不新增细粒度只读角色」。要用 WebUI 的人必须建成 owner / operator。
- **因此**：需要安置的是「用 WebUI 管数据的人」，数量应不大，但须**逐个建成 operator / owner**。计划只写了「认领首个 owner」，**未写后续账号如何创建**——这是升级当天最可能引爆的业务问题，建议补入 §5.5。

### 5.2 域名映射带来两个静默断点，第二个计划完全没提

1. **CSRF Origin-vs-Host**（R1）——会挡住登录与认领本身。
2. **公开 URL 必须显式配置**：`webui/server/runtime-config.ts:33-48` 与 `webui/docs/03-api-spec.md:236` 明确「后端不会从 Host / X-Forwarded-* 推断 endpoint；只读取环境变量 `LUCY_PUBLIC_MCP_URL`」，未配置则回落 `http://127.0.0.1:7879/mcp`（`status=fallback`）——正是「目录能看、数据查不了」的半通成因。客户现值必须**原样搬入新 values**（计划 §5.1 第 13 项写「原样保留」，这点是对的）。Chart 的 `webui.publicUrl` 是 v2.5 OIDC 保留字段，v2.0 不读取（`deploy/k8s/helm/lucy/values.yaml:206-222`）。

补充一条**不是**问题的结论：TLS 终止在反代侧**不会**导致误下发非 Secure Cookie——`webui/server/auth/session.ts:171-178` 的 `setSessionCookie` 只读 `resolveCookieSecure()`，后者只看环境变量（`deployment-mode.ts:46-68`），完全不看请求协议。外部 https + 内部 http 是受支持形态。

### 5.3 好消息：客户的 MCP 取数链路不受登录迁移影响

Agent Token 路径与 WebUI 管理员会话完全独立，升级前后客户 Agent 客户端的取数行为不变。这让「开放 → 登录」成为一个**可以只在 WebUI 面发生、可沟通、可排期**的变更，而不是一次业务中断。这条应当写进对客户的沟通稿，用于降低抵触。
