## 产品简介

**KTX WebUI** 是 Lucy context package 的治理控制台，面向数据工程师和团队管理员。它让你在浏览器里完成数据库接入管理、语义层维护、业务知识沉淀、评测管理和访问管控，把数据库、文档、人工口径整理成 Agent 可安全使用的上下文资产，而不必打开终端或手写 YAML。

KTX WebUI 解决的核心问题：**AI Agent 回答数据问题的准确率与可治理性**。通过维护 Semantic Pack（"利润率怎么算"）、Knowledge Pack（"这张表的口径注意事项"）和 Quality Pack（"改完之后准确率还在吗"），让 Lucy 的 governed MCP runtime 有可靠上下文可交付给 Agent。

## 功能使用说明

### 一、数据库接入

所有后续工作的起点。在 KTX CLI 完成初次 `ktx setup` 之后，日常的连接管理（改白名单、验连通、触发扫描）都在这里完成，不需要再回终端。

> **说明**：新建数据库连接仍需在终端执行 `ktx setup`（一次性操作）。WebUI 负责接入后的日常运维。

#### 连接概览

**什么时候用**：想确认当前接了哪些数据库，或者检查某个连接的基本信息。

**怎么用**：
1. 点击侧边栏「连接概览」，列表展示所有在 `ktx.yaml` 中配置的连接
2. 每条连接显示：连接 ID、数据库类型（MySQL / StarRocks 等）、密码存储方式（文件/环境变量）、已启用的 Schema
3. 点击某个连接查看详情，包括当前白名单中的表列表

---

#### 表白名单

**什么时候用**：需要把一张新表加入 Agent 的可见范围，或者把某张表从白名单中移除。

**怎么用**：
1. 点击侧边栏「表白名单」，选择目标连接
2. 左侧展示数据库中所有可见的表，右侧展示当前白名单（`enabled_tables`）
3. 勾选/取消勾选表名，点击「保存」，变更写入 `ktx.yaml` 的 `enabled_tables` 字段
4. 保存后点击「触发扫描」，系统在后台执行 `ktx ingest <连接ID>`，将新表的 schema 信息同步到语义层
5. 扫描完成后，新表出现在语义层维护的表目录中，可以开始补充描述

> **提示**：移除白名单只影响后续扫描，不会删除已有的语义层定义文件，如需清理需手动操作。

---

#### 添加 schema

**什么时候用**：需要给一个已有的数据库连接追加一个 schema（或 database，例如新建了一张业务库 `finance_mart`），而又不想打开 `ktx.yaml` 编辑。

**怎么用**：
1. 点击侧边栏「连接概览」，找到目标连接卡片
2. 点击「+ 添加 schema」按钮，弹出三步抽屉
3. **输入**：填写 schema 名。对 MySQL / Doris / StarRocks 提示为「Schema 或 database」，对 PostgreSQL 提示为「Schema」。规则：字母或下划线开头，字母/数字/下划线，最多 63 字符。前端 zod 与后端正则双重校验
4. **预览**：点击「下一步」后系统先跑 `ktx connection test <connId>` 预检，再生成 unified diff 预览 ktx.yaml 变更（只追加一行 `- <新 schema>`，其它字段如 `host / password / llm / scan / ingest` 保持不变）
5. **确认**：点击「确认写入」，系统调用 `POST /api/connections/:connId/schemas?dryRun=false`，写入审计写入 `config_change_log`，新增一条 `change_type=schema_add` 记录
6. 抽屉提示「现在 ingest」按钮，点击后即触发 `ktx ingest <connId>` 把新 schema 的表扫到语义层

> **安全边界**：新建连接、删除 schema、修改凭据仍必须回终端执行 `ktx setup`；WebUI 内的「添加 schema」只追加 `connections.<connId>.schemas` 一行 YAML，不触碰任何其它字段，且写入必须显式 `dryRun=false`。

---

#### 连通测试

**什么时候用**：怀疑数据库连接中断（例如密码轮换、网络变更后），或排查 Agent 查询失败的原因。

**怎么用**：
1. 点击侧边栏「连通测试」，选择要测试的连接
2. 点击「测试连接」，系统在后台调用 `ktx connection test <连接ID>`
3. 约 5 秒内返回结果：
   - **成功** — 显示连接延迟和数据库版本信息
   - **失败** — 显示错误原因（认证失败 / 网络不通 / 端口不可达等）
4. 若失败，根据错误提示检查 `.ktx/secrets/` 中的密码文件或网络配置，修复后重新测试

### 二、语义层维护

语义层是 Agent 问答准确率的基础。这里定义的内容决定了 Agent 在回答问题时"知道什么"。

#### 表目录

**什么时候用**：想了解哪些表已经维护好，哪些还需要补充，或者要快速定位某张表进行编辑。

**怎么用**：
1. 打开 KTX WebUI，默认进入表目录页面
2. 用顶部筛选器按 **Schema**、**完成度状态** 缩小范围：未开始 / 部分完成 / 已完成 / 校验失败
3. 在搜索框输入表名关键字即时过滤
4. 点击任意一行进入该表的语义编辑页

**完成度状态说明**：
- **未开始** — 表已被 KTX 扫描到，但还没有任何人工描述
- **部分完成** — 有描述但不完整（缺字段描述、缺 grain 等）
- **已完成** — 字段描述、grain、至少一个指标均已填写
- **校验失败** — 最近一次 `ktx sl validate` 报错，需要修复

---

#### 表语义编辑

**什么时候用**：为一张表补充业务描述、定义业务指标、设置分群过滤规则。

**怎么用**：
1. 在表目录中点击目标表
2. 在 **字段列表** 区域，点击任意字段填写「人工描述」（不要修改 AI 描述栏，两者分开存储）
3. 在 **Grain** 区域，用一句话描述"这张表一行代表什么"（例如：一行 = 一个订单行项目）
4. 在 **Measures** 区域，点击「添加指标」定义业务指标，填写名称、SQL 公式和业务含义
5. 在 **Segments** 区域，定义常用过滤规则（例如：`WHERE is_deleted = 0`）
6. 修改完成后，点击「预览变更」查看与当前文件的差异
7. 确认 diff 无误后点击「保存」，系统自动执行校验；若校验失败，根据提示修正

> **提示**：Measures 里的指标公式一旦确认，所有 Agent 问答都会用这个口径聚合。修改前请确认与业务方已对齐。

---

#### 关联关系管理

**什么时候用**：需要告诉 Agent 哪些表可以安全地 JOIN，或者明确拒绝某些错误的关联路径。

**怎么用**：
1. 在表语义编辑页顶部点击「关联关系」标签，或从表目录对应行的快捷入口进入
2. 页面展示 KTX 自动检测出的候选关联列表，每条关联显示关联表名和推断的 join key
3. 对每条候选关联，选择三态之一：
   - **确认** — Agent 可以使用这个关联路径
   - **候选** — 待确认，Agent 会谨慎使用
   - **拒绝** — Agent 禁止使用这个路径（例如误检的笛卡尔积关系）
4. 保存后变更写入 `.ktx-ui/join-candidates.json`，立即生效

### 三、业务文档

Wiki 是业务知识的沉淀地。当语义层定义了"怎么算"，Wiki 解释"为什么这么算"以及"这里有哪些坑"。

#### Wiki 文档

**什么时候用**：为某个指标、某张表或某类业务场景补充背景说明、口径注意事项、历史坑点。

**怎么用**：
1. 点击侧边栏「Wiki 文档」，左侧列表展示所有已有的 Wiki 文件
2. 点击「新建文档」或直接点击已有文档进入编辑器
3. 在顶部 **Frontmatter** 区域填写结构化元数据：
   - `summary`：一句话摘要（Agent 会用这个判断是否相关）
   - `tags`：业务标签，例如 `财务指标`、`折扣`
   - `sl_refs`：关联到哪些语义层表，例如 `dataforai.superstore_orders`
4. 在正文区域用 Markdown 写说明内容
5. 点击「预览变更」确认 diff 后保存

> **提示**：从表目录点击某张表旁边的「新建 Wiki」快捷入口，会自动预填 `sl_refs` 为当前表，省去手动关联步骤。

### 四、审阅与校验

在一次工作会话里改了多张表之后，用这个模块统一做最终审查和提交。

#### 变更审阅

**什么时候用**：本次工作结束，提交所有改动前的最后一道检查。

**怎么用**：
1. 点击侧边栏「变更审阅」
2. 页面列出本次会话中修改过的所有文件及其差异（逐行 diff）
3. 逐条确认每个变更符合预期
4. 点击「批量校验」，对所有改动过的表统一执行 `ktx sl validate`
5. 若有校验失败的项，点击对应条目跳回表编辑器修复，再回来重新校验
6. 全部通过后，本次改动即完成

---

### 五、质量评测

改了语义层之后，需要验证准确率没有下降。这个模块让你管理测试用例、跑评测、看结果趋势。

#### Case 管理

**什么时候用**：添加新的测试用例（例如线上出现了一个新的错误模式，需要固化为回归测试）。

**怎么用**：
1. 点击侧边栏「Case 管理」，左侧选择 Domain（例如 `superstore`）
2. 右侧列表展示该 Domain 下所有已有 Case 及其状态
3. 点击「新建 Case」填写：
   - **问题**：一个自然语言提问
   - **期望结果**：正确答案的关键数值
   - **必须出现的 SQL 模式**：正确写法的关键片段（例如 `SUM(discount * sales)`）
   - **禁止出现的 SQL 模式**：已知的错误写法（例如 `AVG(discount)`）
   - **快照日期**：锚定到某个数据快照，防止数据更新导致期望值失效
4. 保存后 Case 写入对应 YAML 文件，下次运行评测时自动包含

---

#### 运行历史

**什么时候用**：触发一次评测运行，或查看历史运行结果。

**怎么用**：
1. 点击侧边栏「运行历史」查看所有历史运行记录，每条显示运行时间、总 Case 数、通过数
2. 点击「新建运行」选择 Domain 和 Agent 配置，提交后后台开始执行
3. 点击任意一条历史记录查看详情：每个 Case 的通过/失败状态，失败 Case 的实际 SQL 和期望 SQL 对比
4. 发现失败 Case 后，点击对应 Case 链接跳到 Case 管理页进行修复

---

#### 趋势监控

**什么时候用**：定期查看准确率的历史走势，发现退化拐点，判断某次改动是否引入了回归。

**怎么用**：
1. 点击侧边栏「趋势监控」，页面以时间轴展示各次运行的通过率折线
2. 鼠标悬停某个点查看该次运行的详细数据
3. 若看到某个时间点通过率明显下滑，点击对应点跳转到「运行历史」查看具体失败 Case，再追溯是哪次语义层改动导致的

---

### 六、访问治理

控制谁可以用、能用哪些表、查询记录是否合规。

#### Agent 实例

**什么时候用**：新增团队成员时为其创建 Agent 账号，或调整某个人的权限范围。

**怎么用**：
1. 点击侧边栏「Agent 实例」，列表展示所有已注册的 Agent 用户
2. 点击某个用户查看详情：显示该用户被允许查询的表清单和可调用的 MCP 工具列表
3. 在详情页点击「新建 Token」，填写备注后生成一个 Bearer Token，复制后发送给对方
4. 对方将 Token 配置到自己的 MCP 客户端即可开始使用
5. 若需要撤销访问，在 Token 列表里将对应 Token 标记为已撤销

> **注意**：Token 只在生成时显示明文，离开页面后不可再查看，请确认对方已安全保存。

---

#### 访问日志

**什么时候用**：排查某次异常查询的来源，或定期审计 Agent 的使用情况。

**怎么用**：
1. 点击侧边栏「访问日志」，页面以时间倒序展示所有 Agent 的查询记录
2. 用筛选器按**用户**、**工具类型**（如 `sl_query`、`wiki_search`）、**时间范围**缩小结果
3. 点击任意一条记录查看完整请求内容（问题、生成的 SQL、执行耗时、返回行数）
4. 若发现被拒绝的调用（Agent 请求了无权限的表），可在「Agent 实例」页为其补充授权或做进一步核查

## 典型工作流

### 场景：把一张新表纳入 Agent 可见范围

```
数据库接入 → 表白名单 → 勾选新表 → 保存 → 触发扫描
  → 语义层维护 → 表目录 → 找到新表（状态：未开始）→ 开始补充描述
```

### 场景：补充一张新表的语义定义

```
表目录 → 找到"未开始"状态的目标表
  → 表语义编辑：填写 grain、字段描述、至少一个核心 Measure
  → 关联关系管理：确认或拒绝 KTX 检测出的候选 JOIN
  → 业务文档：新建 Wiki 补充口径说明
  → 审阅与校验：批量校验，确认通过
```

### 场景：线上发现一个错误查询模式，固化为回归测试

```
质量评测 → Case 管理 → 新建 Case
  → 填入出错的问题、期望正确结果、forbidden_sql_pattern（错误写法）
  → 运行历史 → 新建运行，验证 Case 已被覆盖
  → 趋势监控：确认通过率未下降
```

### 场景：新同事加入，需要授权数据访问

```
访问治理 → Agent 实例 → 新建用户
  → 配置允许访问的表（ACL）
  → 新建 Token，发送给新同事
  → 访问日志：数天后检查其查询记录是否符合预期
```
