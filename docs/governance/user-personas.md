## 0. 定位与边界

### 0.1 为什么存在

Spec 评审长期缺一条判断链：**这个功能究竟影响哪一类人，他们的体验是被增强还是被降低。**

缺了它，评审只能按「技术面是否正确」判定：接口对不对、门禁有没有漏、状态机完不完整。这些都能验。但**取舍类变更**（收紧一条路径、加一道门禁、换一种失败语义、改一次默认行为）在技术面上全都「正确」，却在体验上可能把某一类人挡在门外。仓库里已经为此付出过代价——见 §4.3 的真实案例。

本文件补的是这条判断链：**先说清影响谁，再说清对谁变好或变差，最后说清变差时拿什么补偿。**

### 0.2 是什么／不是什么

| 是 | 不是 |
|---|---|
| 人类使用者的**画像**（谁在用、想要什么、什么算体验好／坏） | 运行时**授权角色**（`Role` / `Agent` / `Token` / ACL / Row Policy）——那是**身份与授权轴**，见 §3 |
| 评审时**定位影响面**与**判定方向**的工具 | 需求优先级排序、代排期、代做取舍决策 |
| 一份**事实源**：4 画像定义 ＋ 判定口径 ＋ Spec 小节模板 | 逐份 Spec 的画像结论（那些写在各自 Spec 里，本文件只定口径） |
| 治理层的流程概念 | 产品用户可见术语（不进 [`webui/docs/00-product-terminology-standard.md`](../../webui/docs/00-product-terminology-standard.md)；只有画像进入 WebUI 文案时才登记） |

### 0.3 与既有治理条款的关系

| 既有条款 | 本文件的关系 |
|---|---|
| `DEVELOPMENT.md`「第一性原理：主路径可用性优先」 | **上位条款**，本文件是它在「谁」这一维的展开。该条保护「最终用户（含纯 MCP）」的主路径；本文件把「最终用户」拆成可定位的画像，并要求写清负向补偿。**不改该条口径**，只做单向引用。 |
| `DEVELOPMENT.md` 落盘清单第 17 条 | 本文件是第 17 条的事实源与模板出处。 |
| `docs/access-control/` 运行时 RBAC | **正交**。RBAC 决定「谁能被授权做什么」；画像决定「**谁的体验**因此变了」。一次变更可能只动授权面而完全不动任何人的体验（判 `＝`），也可能不动授权却让某个画像的日常路径变难（判 `↓`）。 |
| 三台账（需求台／开发台／测试台） | 画像**不另立台账**。受影响画像写在对应功能 Spec 里，随开发台状态流转；UAT 仍是体验判定的证据来源。 |

## 1. 画像集（4 个）

画像按「**在平台上要达成什么、且是否需要配置平台**」划分，不按部门、不按角色名、不按是否用 MCP 划分。

| 代号 | 画像 | 一句话 | 主要接触面 |
|---|---|---|---|
| **P1** | 问数方 | 通过平台拿数的人——不配置平台，只消费数据 | MCP 客户端（Claude Code／Codex／Cursor 等）、Live Report 固定 URL |
| **P2** | 治理方 | 把企业口径与授权写进平台的人 | WebUI 治理控制台（语义层／Wiki／Skill／Eval；角色／ACL／行策略／Token） |
| **P3** | 运维方 | 保证平台可用、可升级、可恢复的人 | Docker／K8s 部署面、`/api/health`／`/api/version`、备份恢复、发布台账、运行日志 |
| **P4** | 管理层 | 判断平台是否兑现承诺的人 | 概览与审计摘要、指标与口径覆盖率、报告刷新与失败记录 |

### 1.1 P1 问数方

- **典型岗位**：业务分析师、业务运营、投融资／经营分析、乃至「让 Agent 替自己问数」的普通员工。
- **接触面**：在宿主 Agent 客户端里提问（**纯 MCP**，无 WebUI 账号是常态）；或打开别人托管的 Live Report 固定 URL。
- **核心目标**：问一个业务问题，拿到**和业务签字口径一致**的数，并且**知道这个数从哪来、能不能信**。
- **体验成功的可观察标准**：提问后拿到可直接用的数；口径冲突时看到的是**披露与澄清**，不是无出口的拒绝；出了错有可执行的下一步，而不是误导性文案。
- **不可牺牲**：① 主路径不得变成无逃生不可用；② 拒绝必须给可引用重试／确认／钉选路径；③ 不得把「安全／正确性已验」当理由降低真实可用体验。
- **典型负向体验（判 `↓` 的具体形态）**：本来能问出来的数问不出来，且没有替代问法；为了防误报而弹「Schema 不可判定」这类误导文案；口径分歧时不披露、硬选一张表。

### 1.2 P2 治理方

- **典型岗位**：数据工程师、数据治理／BI 负责人、懂业务的 IT 对接人。**在中小企业常常同一人兼任两个任务面**——这也是画像不能切太细的现实原因。
- **接触面**：WebUI 治理控制台为主，辅以语义文件／`access.yaml` 等配置面与发布流程。
- **核心目标**：把「这个数怎么算、谁能看、口径什么时候变的」一次写对并能持续维护；改完能验证口径没坏、权限没漏。
- **体验成功的可观察标准**：配置有明确反馈（校验／诊断／影响面预览）；批量与模板能复用；变更可回滚可审计；**不必为新需求重学一套新操作模型**。
- **不可牺牲**：① 配置动作的后果可预期（改什么影响什么，事前可见）；② 不得因安全加固而让「合法配置」无处可配；③ 口径改动不静默影响既有授权与报告。
- **典型负向体验（判 `↓` 的具体形态）**：每加一个能力就多一套入口，治理方被迫记住第二套心智模型；保存后才发现影响面；审批／发布链条变长且不可并行。

### 1.3 P3 运维方

- **典型岗位**：客户侧 IT／运维、交付实施工程师、供应方运维。**多数不具备业务口径知识**。
- **接触面**：Docker compose／K8s Chart、容器日志、`/api/health`／`/api/version`、备份与恢复、发布与回滚台账。
- **核心目标**：**在客户现场把这套东西稳稳跑起来，并在出事时能定位、能恢复、能说清跑的是哪个版本**。
- **体验成功的可观察标准**：升级不返工；备份恢复可验证；版本／镜像／交付物可双向定位；故障时有可执行的下一步而不是「联系开发」。
- **不可牺牲**：① 交付形态与产品版本解耦（部署方式不绑架产品版本）；② 出包到现场的可执行步骤不依赖口头知识；③ 单实例单副本边界必须诚实，不得暗示支持多副本。
- **典型负向体验（判 `↓` 的具体形态）**：升级要人工兜底某一步且没有 runbook；版本／镜像／交付物对不上导致现场判不清；备份恢复无法自证。

### 1.4 P4 管理层

- **典型岗位**：企业负责人、数据／财务负责人、平台战略决策者。**通常不直接操作平台**，消费的是别人产出的事实。
- **接触面**：概览与指标、审计与质量摘要、Live Report 与看板、对外交付材料。
- **核心目标**：判断平台**是否兑现承诺**——口径对齐周期、语义覆盖、口径用例通过率、客户侧真实业务结果。
- **体验成功的可观察标准**：看到的口径可解释；指标口径不随版本漂移；能区分「我们做了什么」与「客户好了没有」；有据可查而非叙事。
- **不可牺牲**：① 衡量口径必须是客户真实关心的数，外部基准只作辅助解释；② 不得用「门禁全绿」冒充价值兑现；③ 战略定位与能力边界不得随版本漂移。
- **典型负向体验（判 `↓` 的具体形态）**：指标口径悄悄变了；看到的是工程指标而不是业务结果；无法回答「这个数可不可信、谁在用」。

## 2. 画像子面（facets）与判定粒度

一个画像内部常有**互不相容的日常路径**。为守住「4 画像」的精简，又不丢精度，规定**子面**：

| 画像 | 子面 |
|---|---|
| P1 问数方 | **P1·问数面**（Agent／MCP 提问）· **P1·报告面**（打开 Live Report 固定 URL） |
| P2 治理方 | **P2·语义口径面**（语义层／Wiki／Skill／Eval）· **P2·权限授权面**（角色／ACL／行策略／Token） |
| P3 运维方 | **P3·交付运维面**（部署／升级／备份恢复／出包）· **P3·运行观察面**（health／version／日志／审计） |
| P4 管理层 | **P4·口径质量面**（覆盖率／用例通过率／可解释性）· **P4·业务结果面**（对外结果与叙事） |

**规则：**

1. 画像表**按 4 行填**；子面**不单独占行**。
2. 同一画像的两个子面**方向不一致**时，该行必须写复合判定（如 `P1·问数面 ↓／P1·报告面 ＝`），并**逐子面各给一条依据**。不得只写整体方向。
3. 变更**完全没触碰**某画像的任一子面时，判 `＝`，并在「依据」列写一句"未触碰路径"的说明（指向该路径的归属文件或面）。**不得留空**，也不得写「无影响」二字了事。
4. 子面是**判定粒度**，不是新的画像；新增子面需委托人批准并升本文件版本。

## 3. 画像 ↔ 运行时身份映射

**这张表存在的唯一目的：防止把画像当成权限角色。** 评审时常见的错误是"这功能只影响管理员"——但"管理员"是运行时身份，而**画像问的是体验**。

| 画像 | 主要接触面 | 现行运行时身份 | 备注 |
|---|---|---|---|
| P1 问数方 | MCP 客户端；Live Report 固定 URL | MCP Token ＋ 解析出的 Role；Report Viewer 用**独立本地账户／Session** | 首个客户交付里**不需要** WebUI 管理账号；不复用 WebUI 管理员身份 |
| P2 治理方 | WebUI 治理控制台；语义／配置文件面 | WebUI 管理员（Owner／Operator）＋ `webui/config/access.yaml` 中的 Role | 语义口径面与权限授权面常由**同一人**承担，故合并为一个画像 |
| P3 运维方 | 容器／K8s、只读运维面、交付仓 | 服务器与容器访问权；`/api/health`／`/api/version` 只读字段 | 当前**单实例单副本**；不含多副本运维面 |
| P4 管理层 | 概览、审计摘要、报告与看板 | **无独立系统身份** | 消费的是 P1／P2／P3 产出的事实的可读性，不是功能权限 |

**推论（评审时可直接用）：**

- 改 `access.yaml`／ACL／行策略 → 通常影响 **P2·权限授权面** 与 **P1** 的可见结果，但**不一定**影响 P1 的提问路径。
- 改 MCP Proxy 门禁／拒绝语义 → 影响 **P1·问数面** 与 **P3·运行观察面**（拒绝码可观测性），一般不动 P2。
- 改出包／版本／升级流程 → 影响 **P3·交付运维面**，并经由「可追溯性」间接影响 **P4**。
- 改语义层／Wiki／Skill／Eval → 影响 **P2·语义口径面** 与 **P1** 的答案质量，以及 **P4·口径质量面**。

## 4. 体验判定口径

### 4.1 三个判定值

| 判定 | 定义 | 成立条件 |
|---|---|---|
| **↑ 增强** | 该画像完成其主任务的成功率、可信度或成本被改善 | 依据必须指向**可观察事实**：验收编号（`SC-xx`／`U-xx`）、UAT Suite ID、代码锚点（`file:line`）、实测输出 |
| **＝ 持平** | 该画像的主路径**可观察行为**未变（含「无影响」与「行为不变但内部实现变了」） | 必须写明**哪条路径未变**（指向具体面／文件）；空理由不成立 |
| **↓ 降低** | 该画像的主任务**更难、更慢、更容易失败或更不可信** | 除依据外，**必须**有补偿路径（见 §4.2） |

**不接受**的写法：「应该更好」「体验更顺了」「更安全更规范」「对用户友好」。这类句子不可观察，不可核对，等于没判。

### 4.2 负向门槛：判 `↓` 必须有补偿路径且纳入验收

> **判为 `↓` 而没有补偿路径，或补偿路径未纳入验收编号的 Spec，不得收口。**

- **补偿路径**＝该画像在变更后**仍能完成原主任务**的具体可达路径（重试／确认／钉选／降级／换入口／管理员代为放行……）。补偿路径必须写清**在哪个部署实况下可达**（纯 MCP／有 WebUI／有宿主）。
- 补偿路径必须**挂至少一条验收编号**，并按 `DEVELOPMENT.md`「第一性原理」的同一标准验：既验「约束触发」，也验「合法路径仍能成交」。
- 若**确实没有**补偿路径（该变更就是要让这条路径彻底不可用），则该 Spec 必须由**委托人明示批准**，并写明代价由谁承担；不得由实现方或评审方自行认定「可接受」。
- 这条门槛**不禁止**负向变更：它禁止的是**没有补偿、没有批准、也没有说清代价**的负向变更。

### 4.3 真实案例：门槛为什么存在

| 时间 | 事实 | 画像判定 | 收口方式 |
|---|---|---|---|
| 2026-11-16 | 表级歧义门闩（P0-3）能拦住误报表，但**纯 MCP 主路径无逃生**：合法用户本来能问出来的数也问不出来。已登记错题 [`docs/lessons/2026-11-16-source-ambiguity-gate-deadlock.md`](../lessons/2026-11-16-source-ambiguity-gate-deadlock.md) | **P1·问数面 ↓**（无补偿）；P3·运行观察面 ＝；其余 ＝ | 「拦得住」PASS **不得**单独结案；补 P1-35 逃生路径（放行＋披露＋审计，钉选可达）后才收口 |

同一条链路上的另一个例子：2026-11-17 版本轴命名规约（P1-51）让交付包可双向定位、私有化分叉可判定 —— **P3·交付运维面 ↑**（可定位、可追溯）、**P4·口径质量面 ↑**（可信度可解释）、**P1·问数面 ＝**（不改提问路径）、**P2·语义口径面 ＝**。

### 4.4 冲突与最差口径

1. **同一画像多子面方向不一致** → 按**最差**子面判定整体方向，同时保留逐子面明细（§2 规则 2）。禁止用「总体提升」掩盖局部负向。
2. **不同画像方向相反**（例：P2 ↑ 以 P1 ↓ 为代价）→ **不许用总体收益盖过负向**。P1 的 `↓` 仍须走 §4.2 门槛；P2 的 `↑` 不得作为跳过该门槛的理由。
3. **一个 `↓` 判定触发产品级复核**：当 `↓` 命中 **P1·问数面** 或 **P3·交付运维面** 时，除补偿路径外，还要在 Spec 里写明**该负向是否构成「主路径可用性优先」原则的违反**。是 → 退回；否 → 写明理由。

## 5. Spec「受影响画像」小节（模板）

### 5.1 必填形态

新功能 Spec 必须包含以下小节（标题二选一：`## 受影响画像` / `## Affected Personas`）：

```md
## 受影响画像

> 事实源：[`docs/governance/user-personas.md`](governance/user-personas.md)。4 画像逐行判定；不得写「所有用户」。

| 画像 | 变更前体验 | 变更后体验 | 判定 | 依据（验收编号／证据） | 负向时的补偿路径 |
|---|---|---|---|---|---|
| P1 问数方 | | | ↑／＝／↓ | SC-xx | — |
| P2 治理方 | | | ↑／＝／↓ | SC-xx | — |
| P3 运维方 | | | ↑／＝／↓ | SC-xx | — |
| P4 管理层 | | | ↑／＝／↓ | SC-xx | — |

（判 `↓` 的行：补偿路径必须写明**在哪个部署实况下可达**，并挂验收编号。无补偿需委托人明示批准并写明代价承担方。）
```

### 5.2 字段填写规则

| 字段 | 规则 |
|---|---|
| 变更前体验 | 写**当前可观察行为**，不写意图。允许「当前行为」＋来源（现有 Spec／代码锚点／实测） |
| 变更后体验 | 写**本 Spec 承诺后的可观察行为**。不写「优化」「提升」等不可观察词 |
| 判定 | `↑` / `＝` / `↓`；子面不一致时写 `P1·问数面 ↓／P1·报告面 ＝` |
| 依据 | **必须**含至少一个可核对锚点：`SC-xx`／`U-xx`／UAT Suite ID／`file:line`／实测输出。无锚点不得判定 |
| 补偿路径 | 判 `↓` 时**必填**；其余填 `—` |

### 5.3 反例（评审时直接退回）

| 反例 | 为什么退回 |
|---|---|
| 「本功能面向所有用户，整体体验提升」 | 没定位画像，等于没判 |
| 「P1 用户体验不变」（无路径说明） | `＝` 未写哪条路径未变，不可核对 |
| 「P1 体验下降，但为了准确性可以接受」 | `↓` 无补偿路径、无委托人批准、无代价承担方 |
| 「P1 ↑（体验更好）」，依据只有「优化了交互」 | 不可观察；须换成验收编号或实测 |
| 只写画像不写子面，而该变更跨两个子面 | 粒度不足，见 §2 |
| 四个画像全 `↑` 但正文只改了一处 | 判定不可信；需回到可观察事实 |

### 5.4 缺省写法

- **纯技术内部重构**（不改任何用户可见行为）：四行全 `＝`，每行「依据」写一句「本变更不触碰该面：未改 `X` 路径（引用文件）」。
- **纯文档／术语／文案修正**：若文案本身面向某一画像可见，须判该画像（多为 P1 或 P2）；否则按上一条处理。
- **纯治理／流程变更**（例如本文件本身、索引、台账）：四行全 `＝`，依据写「不改变任何用户可见路径，仅改仓库内文档」。

## 6. 评审接入口径

### 6.1 评审新增问项

Spec／Gate 评审在既有落盘清单之外，**必须逐项回答**（答不出即退回，不是「风险自担」）：

1. 本次变更**触及哪几个画像的哪几个子面**？依据是什么（哪个文件／哪条路径）？
2. 每个被触及的画像，变更前后的**可观察行为**分别是什么？
3. 判定为 `↓` 的行：补偿路径是什么、在哪个部署实况下可达、挂哪条验收编号？
4. 是否触发 §4.4 的「最差口径」或「产品级复核」？结论是什么？
5. 是否存在**未列出但实际受影响**的画像（画像集漏检）？

### 6.2 评审记录怎么写

评审记录（[`docs/reviews/`](../reviews/)）里，画像结论**并入逐项审查意见表**作为一行（或一节），不要另起一套编号体系：

```md
| # | 审查项 | 结论 | 核对依据 | 意见 |
|---|---|---|---|---|
| n | 受影响画像判定（4 画像） | 通过／退回 | Spec §受影响画像；SC-xx；file:line | 无补偿路径的 `↓` 已补齐／某画像漏检已补 |
```

**不得**在评审记录里出现「画像判定通过」而正文无对应小节——即 Spec 缺小节时，评审结论也必须是「退回」。

### 6.3 常见退回情形（快查）

- Spec 无「受影响画像」小节 → 退回（形态问题，先修文档形态）。
- 四行留空或写「所有用户」 → 退回。
- 判 `↓` 但无补偿路径 → 退回；若委托人已明示批准且写明代价承担方，可通过并记为显式取舍。
- 判定依据不可观察（无验收编号／代码锚点／实测） → 退回。
- 跨子面变更只给整体方向 → 退回（补复合判定）。
- 变更确实只碰内部实现却未说明为何全 `＝` → 退回（补依据）。

## 8. 已知不足

1. **4 画像的合并代价**：P2 治理方把「语义口径」与「权限授权」合在一处，中小客户常由同一人兼任两面的现实被压缩了。**缓解**：强制子面判定（§2）；当一个 Spec 同时触碰两面且方向相反时，必须写复合判定并逐面给依据。**残余风险**：两面方向一致时仍可能掩盖其中一面的具体退化。
2. **未覆盖外部角色**：客户侧业务 IT、乙方实施方、审计／合规角色未单列。当前按其主要诉求归入 P3（运维）与 P4（管理层）。若某类外部角色的诉求明显不同于这两者，须新开画像（委托人批准）。
3. **判定仍有主观性**：画像提供锚点与门槛，但「体验变差多少算 `↓`」不是纯客观量。缓解靠**依据必须可观察** ＋ **负向须有补偿或委托人明示批准**；**不能**声称本文件消除了主观性。
4. **画像与产品定位漂移**：若产品定位变化（如 `vision.md` §1.2 主张调整），画像集须同步复核。**当前无人自动比对**——属已知缺口。
