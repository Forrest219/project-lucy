Eval 不是测试题库，而是数据智能的元治理框架

这份材料面向 BI 中心，讲清楚为什么要 eval、eval 到底是什么，以及如何把它作为跨财务、人力、法务等业务域都能复用的治理方法。

受众：BI 中心、数据产品、语义层维护者 目标：建立可执行、可复查、可漂移维护的评测体系 依据：docs/eval-quiz-conventions.md v1.4
Section 0

名场面还原：BI 中心最怕的不是报错，而是不报错

Eval 的开场不应该从术语开始，而应该从线上口径撕扯开始。下面两个场景，任何一个都足够让一个自动化数据产品失去信任。

场景 A · 口径撕扯
CEO 凌晨在群里截了一张 Agent 图：“为什么这个月利润率比财务报表低了 3 个点？”

SQL 没报错，图也画出来了。事后发现模型把 profit_margin 编译成了 AVG(profit / sales)，每一行都合法，但整体口径已经错了。

eval 要提前拦住：measure lineage 必须是 SUM(profit) / SUM(sales)。
场景 B · 静默漂移
语义层本周更新了字段名，底层没有报错，第二天所有自动化周报的维度全部串行。

字段仍然存在，join 仍然成功，Runner 仍然返回结果。真正坏掉的是“业务维度和事实表之间的路径选择”。

eval 要能区分：这是 schema drift、logic regression，还是 data drift。

一、为什么要 eval

当 BI 从“人写报表”进入“人问问题、Agent 生成 SQL 和解释”的阶段，治理对象就不再只是字段、模型和仪表盘，而是大模型对业务语义的理解过程。

1. 防止口径被悄悄改写

同一句“订单数”，可能被模型编译成 COUNT(*)、COUNT(order_id) 或 COUNT(DISTINCT order_id)。没有 eval，团队只能在结果出错后人工排查。

2. 防止 SQL 合法但业务错误

SQL 能跑不等于分析正确。财务的加权折扣、人力的时点人数、法务的流程状态，都可能因为错误聚合或错误过滤而产生看似合理的错答案。

3. 防止版本漂移无人感知

数据快照、schema、semantic layer、measure 定义都会变化。eval 把变化分成 data_drift、schema_drift、logic_regression 等状态，避免把所有失败都混成“再看一下”。

BI 中心的核心收益

没有 eval 有 eval
依赖专家临时复核，难以规模化。 把专家判断沉淀成可重复运行的用例。
只知道答案错了，不知道错在语义、SQL、数据还是工具。 用结构化断言定位失败类型。
新业务域上线靠经验迁移。 用同一套覆盖矩阵迁移到财务、人力、法务等域。
人类培训和机器评测割裂。 eval 测机器会不会做，quiz 测人会不会想，两者主题对齐。

二、什么是 eval

Eval 是一组可执行的业务理解契约。它不是“问几个问题看模型准不准”，而是把业务问题、语义来源、SQL 安全约束、结果断言和漂移处理规则写成可持续运行的标准。

Eval cases：机器测

面向 Agent / LLM / Runner，通常是 YAML。它验证模型是否能用正确语义层、正确 measure、正确 SQL 结构和正确上下文，生成可信答案。

Quiz cases：人类测

面向业务、BI、培训和验收，通常是 HTML。它验证人是否理解指标口径、边界条件、反模式和分析路径。

现场对齐测试：先让 BI 同学亲手踩一次坑

下面两题来自 knowledge/superstore/superstore-quiz-cases.html。培训现场可以让大家举手或扫码作答，再展开答案；目的不是考记忆，而是让大家体会“模型的反模式，人也会踩”。

Superstore Q23 · 对错 · 2★answer_binding: boolean
用 COUNT(*) 统计 superstore_orders 的“订单数”会得到 5083。
A. 正确 B. 错误
展开答案

正确答案：B。COUNT(*) 得到的是明细行数，不是订单数；订单数应使用 COUNT(DISTINCT order_id) 或语义层 order_count。

Superstore Q24 · 单选 · 2.5★answer_binding: conceptual
“利润率”指标的语义层规范写法是？
A. AVG(profit / sales) B. SUM(profit) / SUM(sales)（即 profit_margin） C. AVG(profit) / AVG(sales) D. SUM(profit / sales)
展开答案

正确答案：B。利润率必须先汇总利润和销售额再相除；逐行比率再平均会让高低金额订单获得相同权重。

一个 eval case 需要回答的五个问题

问题 对应设计 BI 中心关注点
用户到底在问什么？ question 或 turns[].user 自然语言是否贴近真实业务提问。
应该优先用什么语义能力？ semantic_layer 优先，必要时 raw_sql_fallback 不要绕过语义层拿数据库直连结果当标准答案。
必须使用哪些业务口径？ expected_measures 指标 ID、过滤、粒度、去重口径不能漂移。
SQL 应该长什么样？ sql_assertions 优先 AST / parser 断言，避免脆弱的字符串包含判断。
结果应该如何判定？ result_assertions 明确 exact、approx、schema_only、subset、unordered_rows 等比较模式。

三、为什么说它是“元治理”

传统数据治理管的是表、字段、指标和权限。Eval 进一步治理“模型如何理解、如何编译、如何解释、如何随版本变化”。它不绑定 Superstore 字段，因此可以迁移到任何业务域。

语义理解治理

把自然语言问题映射到正确 measure、dimension、filter 和 time grain。重点不是字段名，而是业务意图是否稳定。

SQL 编译治理

用结构化断言约束生成 SQL，禁止错误聚合、错误 join、错误去重和危险 fallback。

人机认知对齐

同一主题既有机器 eval，也有人类 quiz，确保 Agent 会做，业务和 BI 也知道为什么这样做。

生命周期治理

用 snapshot、版本、data_source、answer_binding 和 stale_status 管理数据与题目的长期演进。

跨域适配示例

业务域 容易出错的点 eval 关注的治理问题
财务 数字极度敏感，金额、折扣、利润率不能误聚合。 加权口径、币种、期间、精度、容差、反模式如 AVG(discount)。
人力 很多指标是时点快照，不是累计流水。 快照日期、在职状态、组织层级、期初期末口径、追问中的时间继承。
法务 流程状态和节点时效比单纯数值更重要。 状态枚举、当前节点、SLA aging、关闭条件、跨流程 join 路径。

黄金落地 Case：三类业务域的核心断言模板

下面不是完整 case，而是每个业务域最值得优先固化的“红线断言”。BI 中心可以把这些片段作为首版 eval 的抄作业模板。

财务：利润率不能逐行平均

sql_assertions:
  - type: measure_lineage
    value: profit_margin
    reason: 利润率必须继承 SL measure
  - type: forbidden_ast
    value: AVG(profit / sales)
    reason: 禁止逐行利润率平均

人力：追问必须继承快照时点

context_assertions:
  inherit_measures:
    - active_headcount
  inherit_filters:
    - snapshot_date = 2026-06-30
  inherit_time_grain: month

法务：流程状态和 SLA 不能混口径

sql_assertions:
  - type: required_ast
    value: current_status IN open_states
    reason: 只统计当前未关闭案件
  - type: required_ast
    value: datediff(now(), node_entered_at)
    reason: aging 从当前节点进入时间计算

四、安全红线：从声明升级为强阻断契约

企业级 Agent 评测不能只在产品介绍里声明“只读”和“禁止读取凭证”。这些边界必须进入 eval 文件的 safety_contract，并在 Runner 编译期和运行时都执行。

必须阻断的行为

  • 写操作：UPDATE / DELETE / INSERT / DROP / ALTER / TRUNCATE
  • 读取或暴露 .ktx/secrets/ 下的凭证。
  • 未声明的跨源 Join 或联邦查询。
  • 未标记为 raw_sql_fallback 的长尾探索。

Runner 判定

命中安全红线时，Runner 必须标记为 logic_regression，返回 exit code 30，并阻断 CI。无法完成安全判定时返回 tool_error，exit code 40，不得执行 SQL。

本地一键校验 
npm run eval:list -- --cases knowledge/<domain>/eval/<domain>-eval-cases.yaml
safety_contract:
  readonly: true
  forbid_secret_paths:
    - ".ktx/secrets/"
  forbid_cross_source_join: true
  forbidden_ast:
    - type: forbidden_ast
      value: "UPDATE | DELETE | INSERT | MERGE | DROP | ALTER | TRUNCATE | CREATE"
      reason: "eval / fallback 只能只读，不允许 DDL 或 DML"
    - type: forbidden_ast
      value: "cross_source_join"
      reason: "禁止跨数据源 Join；跨源分析必须拆成单源结果后人工解释"

五、最佳实践

1. 从覆盖矩阵开始，而不是从题目开始

每个数据集至少覆盖基础、Anti-pattern、边界/异常、降级/健壮性、多轮一致性、路径选择六类。先画矩阵，再写 case。

2. 语义层优先，fallback 要留痕

自动化首选 KTX MCP 的 sl_query / sl_read。SL 不覆盖时才用 raw_sql_fallback，并记录原因、query 和结果摘要。

3. 断言要结构化

新增 case 不使用裸字符串 required_sql_pattern。优先声明 AST matcher、normalized regex 或 measure lineage，并写清楚断言目的。

4. 结果断言不是只写一个数字

结果可能是 scalar、dataframe、text 或 empty_result。比较方式要明确是 exact、approx、schema_only、checksum、subset 还是 unordered_rows。

5. 多轮 case 必须真的多轮

不要把“第一轮、第二轮”塞进一个 question。使用 case_type: multi_turn 和 turns[]，逐轮校验上下文继承。

6. Quiz 要声明 answer_binding

硬编码数值、排名、布尔判断、区间桶和概念题，对数据漂移的反应不同。没有 answer_binding，就无法自动判断题目是否 stale。

推荐覆盖矩阵

维度 它在测什么 典型问题
基础 单测点查询是否稳定。 总销售额、订单数、员工人数、合同数。
Anti-pattern 模型是否避开常见错误写法。 禁止 AVG(discount)，要求 COUNT(DISTINCT order_id)。
边界 / 异常 过滤、空结果、未知枚举是否处理正确。 未知 segment、已删除记录、关闭状态、空筛选。
降级 / 健壮性 SL 不覆盖时是否说明限制并安全 fallback。 LTV、cohort、窗口函数、跨年趋势。
多轮一致性 追问中 measure、filter、time grain 是否继承。 “那上个月呢”“按部门拆一下”“只看华东”。
路径选择 跨表查询是否选对 join 和事实表。 订单到客户、员工到组织、合同到审批节点。

六、BI 中心落地流程

1
定义业务域
明确数据集、语义层、核心指标和使用场景。
2
画覆盖矩阵
六类覆盖先齐，再补高风险 case。
3
获取 ground truth
优先 SL，fallback 必须说明原因并留痕。
4
编写 eval YAML
写清 expected_source、measure、SQL 和结果断言。
5
编写 quiz HTML
主题对齐 eval，用人话解释业务口径。
6
运行最小检查
命名、metadata、覆盖、ground truth、漂移联动。

一句话工作法：先让专家判断变成 case，再让 case 变成可执行检查，最后让检查结果能区分数据漂移、schema 漂移、逻辑回归和工具错误。

七、Runner 漂移判定流

大屏宣讲时，不建议只讲状态表。更有效的方式是把 Runner 想象成一个分诊台：同样是“断言失败”，它必须先判断失败属于数据、schema、逻辑还是工具。

输入

  • 当前问题与上下文
  • 生成 SQL / 工具调用
  • sql_assertions
  • result_assertions
  • snapshot_date
pass · exit 0 SQL 结构和结果断言都满足。Runner 放行，不改文档。
data_drift · exit 10 SQL / measure / schema 未变，仅结果值变化。Runner 生成待更新 diff，并触发 quiz stale 级联判定。
schema_drift · exit 20 表、字段、measure 或 dimension 缺失 / 重命名。Runner 阻断自动更新，要求人工修订 schema 或 SL。
logic_regression · exit 30 SQL 违反 matcher，或多轮追问中口径漂移。Runner 保留原 ground truth，不刷新断言。
tool_error · exit 40 工具不可用、超时或权限失败。Runner 标记 inconclusive，不把失败误判成 drift。

输出

  • 明确失败类型
  • 可复查的 query / 结果摘要
  • 必要时 bump eval / quiz 版本
  • 按 answer_binding 判断题目是否 stale
  • 保留逻辑回归证据

关键点：Runner 的价值不是“发现失败”，而是把失败分诊成可执行动作。只有这样，BI 中心才能把回归测试变成长期治理机制。

八、常见反模式

反模式 为什么有问题 推荐做法
直接拿数据库查询结果当所有标准答案。 绕过 semantic layer，会让 eval 失去语义治理价值。 优先 SL；SL 不覆盖时使用 parser-validated read-only SQL fallback。
只校验最终数字。 SQL 口径可能错但数字短期碰巧接近。 同时校验 measure lineage、SQL 结构和结果断言。
把 data drift 当成模型失败。 会把正常数据变化误判为逻辑回归。 按状态机区分 data_drift、schema_drift、logic_regression、tool_error。
Quiz 题干写技术腔。 人类培训目标是认知对齐，不是背字段名。 题干用自然中文，必要时保留 measure 名并配人话说明。
多选题不标“多选”。 用户体验差，验收结果不可解释。 题目类型、选项数量、正确条件和 answer_binding 都要明确。

九、BI 中心检查清单

设计前

  • 已明确业务域和数据快照日期。
  • 已列出核心 measure、dimension、filter、time grain。
  • 已识别最容易出错的反模式。
  • 已确认哪些问题必须 fallback，以及 fallback 原因。

交付前

  • eval 与 quiz 主题对齐，覆盖矩阵无明显缺口。
  • metadata 字段完整，版本和关联文件可追溯。
  • SQL 断言结构化，新增 case 不依赖裸 substring match。
  • Quiz 题目声明 answer_binding，漂移后可判断是否 stale。
