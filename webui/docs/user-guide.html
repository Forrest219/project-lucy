KTX Local WebUI

KTX WebUI 产品使用说明书

KTX WebUI 是一个在本机运行的语义补充工作台，用可视化界面帮助维护 KTX 语义层的团队成员补充表描述、字段口径、指标、分群、Join 关系与 Wiki 文档，同时保留 YAML、Markdown 和 Git 作为最终事实源。日常补充无需手写 YAML，但会接触表、字段、指标等概念（不熟悉的术语见文末术语表）。

产品定位

KTX WebUI 面向需要维护 KTX 语义层的团队成员（数据工程、分析与业务口径维护者）。它把原本需要手写的 semantic-layer/**/*.yaml 和 wiki/**/*.md 转成可浏览、可编辑、可预览差异的页面。

它不是云端 BI 平台，也不是数据库管理工具。它更像一个本地工作台：帮助用户把表、字段、指标和业务口径整理清楚，再通过 KTX 校验和 Git diff 完成交付审阅。

本机运行 文件优先 保存前 diff 保存后 validate 不读取 secrets

快速开始

开始前你需要

  • 一个 KTX 项目目录（根目录含 ktx.yaml）。
  • 本机已安装 Node（≥20）。
  • ktx 命令行工具已在 PATH 中（用于保存后的校验）。

启动 WebUI

  1. 在 WebUI 目录执行 npm install（仅首次需要，需联网）。
  2. 执行 npm run dev 启动本地服务。
  3. 打开浏览器访问 http://localhost:5173。

它怎么知道编辑哪个项目

WebUI 默认从当前目录向上查找 ktx.yaml 来定位你的 KTX 项目；也可以用 --project <目录> 参数或 KTX_PROJECT_ROOT 环境变量显式指定。

WebUI 只在本机运行并绑定 127.0.0.1，不对外暴露，也不会上传任何数据。

核心能力

表目录工作队列

扫描当前 KTX 项目中的语义层表，按 schema、完成状态、表名和字段名筛选，快速找到需要补充的对象。

单表语义编辑

编辑表描述、行粒度、字段描述、指标 measures 和过滤分群 segments，并实时查看拟写入的 YAML 和 diff。

Join 关系治理

查看正式 Join，基于字段名生成候选 Join，可标记 candidate、rejected，确认后再写入正式语义层。

业务 Wiki 沉淀

创建和编辑 Markdown Wiki，维护 frontmatter、业务摘要、标签、引用关系，并可从表页面创建关联 Wiki。

保存前审阅

任何编辑都会先生成 diff preview，用户可以在落盘前看到具体修改内容，降低误改 YAML 的风险。

保存后校验

保存语义层后调用 ktx sl validate，并在 Review 页面集中查看改动文件和校验结果。

典型使用流程

1. 找表 从 Catalog 搜索或筛选待补充的表。
2. 补语义 在 Table Editor 中补充描述、grain、指标和分群。
3. 看 diff 保存前检查右侧 diff preview 和 proposed YAML。
4. 保存校验 点击 Save 写回文件，并自动触发 KTX 校验。
5. Review 到 Review 页面查看所有改动，再交给 Git 流程审阅。

功能页面说明

功能页面及其用途
页面 主要用途 适合做什么
Catalog 表目录与工作队列 查看全部表，按 schema、状态、关键词筛选，了解字段数、Join 数、指标数和完成状态。
Table Editor 单表语义编辑 维护表描述、行粒度 grain、字段描述、measures、segments，并查看 YAML 预览。
Join Editor 表关系编辑 查看正式 Join，处理基于字段名推断出的候选 Join，确认可信关系后写入正式 YAML。
Wiki Editor 业务口径文档编辑 创建或编辑 Wiki Markdown，维护摘要、标签、语义层引用和正文说明。
Review 改动复核与批量校验 查看 editable 目录下的文件 diff，运行 changed sources 校验，确认交付前状态。

完成状态的含义

Catalog 可按完成状态筛选，帮助你优先处理未补充的表。各状态含义如下：

完成状态说明
状态 含义
未开始 没有表描述、没有行粒度，字段也没有任何描述。
部分完成 已有表描述或行粒度，但核心字段尚未全部补齐描述。
已完成 表描述、行粒度、主键、核心字段描述与指标齐备。
校验失败 最近一次 KTX 校验未通过，需要回到对应表修正。

编辑与保存说明

表和字段描述

人工补充的描述会写入 descriptions.human，不会覆盖已有的 descriptions.ai。展示时优先使用人工描述，未填写时回退到 AI 描述。

Grain、Measures、Segments

行粒度、指标和分群会写入表级 overlay 文件，例如 semantic-layer/<connection>/<table>.yaml。这样可以在不破坏原始 schema YAML 的前提下扩展语义定义。

Join

候选或拒绝的 Join 会保存在 .ktx-ui/join-candidates.json。只有用户确认的 formal Join 才会写入正式语义层 YAML。

Wiki

Wiki 页面保存在 wiki/**/*.md。页面支持 frontmatter 和 Markdown 正文，可用于沉淀业务口径、指标解释、使用场景和外部引用。

保存前请看 diff。 右侧 diff preview 展示的是本次编辑即将写入的内容。确认无误后再点击 Save。

校验与审阅

保存表语义后，系统会调用 KTX CLI 对对应 source 做校验。Review 页面会列出本次可编辑目录内的改动文件，并提供 Validate changed 做集中校验。

校验状态及建议动作
状态 含义 建议动作
通过 KTX 能读取并校验当前语义定义。 继续检查 diff，准备提交 Git review。
校验失败 写入内容不符合 KTX 语义层规则，或引用的字段/表不存在。 回到对应表页面修正表达式、字段名、Join 条件或 YAML 内容。
无改动 当前 editable 目录没有可展示的 diff。 确认是否已经保存，或检查是否编辑了非白名单目录。

安全边界

KTX WebUI 按本地单用户工具设计，只绑定 127.0.0.1。它会直接读写当前 KTX 项目文件，因此核心安全策略是限制可读写范围。

可读写范围与安全边界
范围 行为
semantic-layer/ 允许读写，用于正式语义层和 overlay。
wiki/ 允许读写，用于业务口径 Markdown。
.ktx-ui/ 允许读写，用于 WebUI 自身 sidecar，例如候选 Join。
.ktx/secrets/ 禁止读取和展示，避免泄露连接密码或密钥。
raw-sources/ 禁止写入，避免污染扫描得到的原始证据。
.git/ 禁止写入，版本历史和提交动作仍由用户自己控制。

故障排查

常见故障与处理
现象 可能原因 处理
页面打不开 本地服务未启动，或端口被占用。 确认已执行 npm run dev，并访问 http://localhost:5173。
表目录是空的 没有定位到 KTX 项目，或 semantic-layer/ 下没有语义层文件。 在含 ktx.yaml 的项目下启动，或用 --project / KTX_PROJECT_ROOT 指定项目目录。
保存后校验失败 表达式、字段名或 Join 条件不符合 KTX 规则，或 ktx 命令不在 PATH。 按 Review 页提示修正语义；确认 ktx 命令可用。
某些字段属性保存不了 visibility、已有列的 role 覆盖等暂不作为正式落盘能力。 这是预期行为；详见下方常见问题。

常见问题

WebUI 会替我提交 Git 吗？

不会。WebUI 只负责编辑文件、展示 diff 和运行校验。提交、创建 PR、回滚版本仍由用户通过 Git 完成。

为什么要先看 diff 再保存？

语义层 YAML 是项目事实源。diff 能让用户在写入前确认具体变化，避免误改字段、Join 或业务口径。

为什么有些字段属性不能保存？

当前 KTX 已确认支持 grain、measures、segments 的 overlay 合并；部分字段属性如 visibility 或已有列 role 覆盖暂不作为正式落盘能力。

Wiki 和表语义有什么区别？

表语义用于 KTX 结构化理解和校验，Wiki 用于沉淀更长的业务说明、指标口径、背景解释和使用建议。两者可以通过 sl_refs 关联。

普通用户需要懂 YAML 吗？

日常补充语义不需要直接手写 YAML。YAML preview 和 diff 主要用于审阅，让用户知道系统最终会改哪些文件。

术语表

语义层 / semantic layer
用 YAML 描述表、字段、指标等结构化语义的文件集合，位于 semantic-layer/。
schema
数据库中的一组表的命名空间；语义层按 schema 组织文件。
行粒度 / grain
一行数据代表的业务粒度，例如"每天每家医院一行"。
指标 / measure
可聚合计算的业务度量，例如 sum(amount) 表示金额合计。
分群 / segment
常用的过滤条件，例如"仅正向金额"。
关系 / join
表之间的关联条件与方向（多对一、一对多、一对一）。
overlay（扩展文件）
不改动原始 schema 文件、单独存放 grain/指标/分群的补充 YAML，路径形如 semantic-layer/<连接>/<表>.yaml。
frontmatter
Markdown 文件顶部的结构化元信息（摘要、标签、引用等）。
diff（差异预览）
保存前展示"将要写入的内容与现有内容的区别"。
事实源 / source of truth
最终以文件（YAML/Markdown）和 Git 为准，WebUI 只是编辑器。
