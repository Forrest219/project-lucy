# 06 · 导航与信息架构优化

本文定义 KTX WebUI 的导航口径。目标是让普通用户能一眼看出当前页面在维护什么内容，避免只看到 Catalog、Table、Wiki、Review 等技术页面名。

## 1. 问题

历史页面导航偏实现视角：

- `Catalog` 像数据表列表，但没有明确告诉用户这是“语义建模”的表目录。
- 单表页只显示表名，用户不容易区分“表语义”和“业务 Wiki”的职责。
- `Wiki` 独立存在，缺少与语义对象的关系提示。
- `Review` 更像 diff 页面，未清晰表达“审阅与校验”。
- 页面之间主要靠局部按钮跳转，缺少稳定的全局导航和面包屑。

## 2. 导航原则

1. 按维护对象组织导航，而不是按技术组件组织导航。
2. 页面标题必须说明当前维护的是“数据接入”“语义建模”“语义发布”“质量评测”还是“访问治理”。
3. 面包屑必须展示当前位置，尤其是 `connection / schema / table`。
4. Wiki 不替代表语义；Wiki 是人读的业务口径文档，semantic-layer 是机器可校验的结构化语义。
5. 第一阶段只改信息架构和展示文案，不改 API、文件格式和写入逻辑。

第一阶段落地为左侧固定主导航：

| 分组 | 导航项 | 路由 | 说明 |
| --- | --- | --- | --- |
| 运行状态 | 系统概览 | `/overview` | 查看 Lucy MCP、KTX Runtime、语义资产和 Agent 接入状态，集中处理异常与待办 |
| 运行状态 | 调用监控 | `/ops/calls` | 准实时查看 MCP 工具调用量、成败与请求时效（Spec 142） |

| 语义建模 | 语义资产 | `/catalog` | 管理表、字段、指标、分群与关联等结构化语义资产 |
| 语义建模 | 业务 Wiki | `/wiki` | 管理业务口径、指标说明与分析指引等业务文档 |

| 访问治理 | 使用概况 | `/admin/usage` | 查看 Agent、Token 和数据表的活跃度、调用量与响应耗时 |
| 访问治理 | Agent | `/admin/agents` | 管理 Agent 身份、角色、Token 及数据访问边界 |
| 访问治理 | Token 凭据 | `/admin/tokens` | 全局查看、签发与定向吊销 Agent 访问凭据 |
| 访问治理 | 角色权限 | `/admin/roles` | 管理角色的数据库连接、数据表与 MCP 工具授权范围 |
| 访问治理 | 访问日志 | `/admin/audit` | 按问询和工具调用追溯 Agent 访问行为、权限裁决与执行耗时 |

`表语义编辑` 和 `关联关系` 是上下文页面，不作为固定入口直接列出空态路由；从表目录或单表页进入。

## 5. 页面标题与说明

### 表目录

标题：`语义维护工作台`

说明：`浏览当前 KTX 项目的语义层数据表，按 schema、状态和关键词定位需要维护的对象。`

表行操作应显式表达维护动作：`维护语义`。

### 表语义编辑

标题：`维护表语义：<table>`

说明：`这里维护会写入 semantic-layer 的结构化语义，包括表描述、字段描述、行粒度、指标、分群和正式 Join。`

页面内分区：

- 基础语义：表描述、行粒度
- 分析语义：指标、分群
- 字段语义：字段描述
- 变更预览：diff 和拟写入 YAML

### 关联关系

标题：`维护关联关系：<table>`

说明：`候选关系先保存在 .ktx-ui sidecar，只有确认后的正式关系才写入 semantic-layer。`

分区命名：

- 已确认关系
- 候选关系

### 业务 Wiki

标题：`业务 Wiki：<key>`

说明：`Wiki 用于维护人可阅读的业务口径、使用场景和注意事项，不替代表字段描述。`

### 变更审阅

标题：`变更审阅与校验`

说明：`集中查看本次可编辑目录中的文件变更，并对本次保存过的语义对象运行校验。`

## 6. 第一阶段实施范围

第一阶段只做低风险信息架构优化：

1. 增加左侧主导航。
2. 增加全局面包屑。
3. 重命名页面标题、按钮和空状态文案。
4. 为表目录、表语义、关联关系、Wiki、Review 增加解释性说明。
5. 表目录行增加明确操作文案：`维护语义`。

不做：

- 不改 API。
- 不改 YAML/Markdown 写入格式。
- 不改保存、validate、diff 逻辑。
- 不引入新的 UI 框架。

## 7. 验收

- 普通用户从左侧导航能识别 6+1 结构：运行状态、数据接入、语义建模、语义发布、质量评测、访问治理、系统设置（Spec 142：原置顶「系统概览」单项并入「运行状态」分组）。
- 任一上下文页面能通过面包屑看出当前位置。
- 单表页能明确区分结构化语义建模和业务 Wiki。
- `npm test`、`npx tsc --noEmit`、`npm run build` 通过。
