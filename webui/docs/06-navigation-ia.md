# 06 · 导航与信息架构优化

本文定义 KTX WebUI 的导航口径。目标是让普通用户能一眼看出当前页面在维护什么内容，避免只看到 Catalog、Table、Wiki、Review 等技术页面名。

## 1. 问题

当前页面导航偏实现视角：

- `Catalog` 像数据表列表，但没有明确告诉用户这是“语义维护工作台”。
- 单表页只显示表名，用户不容易区分“表语义”和“业务 Wiki”的职责。
- `Wiki` 独立存在，缺少与语义对象的关系提示。
- `Review` 更像 diff 页面，未清晰表达“审阅与校验”。
- 页面之间主要靠局部按钮跳转，缺少稳定的全局导航和面包屑。

## 2. 导航原则

1. 按维护对象组织导航，而不是按技术组件组织导航。
2. 页面标题必须说明当前维护的是“语义层”“业务文档”还是“变更审阅”。
3. 面包屑必须展示当前位置，尤其是 `connection / schema / table`。
4. Wiki 不替代表语义；Wiki 是人读的业务口径文档，semantic-layer 是机器可校验的结构化语义。
5. 第一阶段只改信息架构和展示文案，不改 API、文件格式和写入逻辑。

## 3. 全局导航结构

```text
KTX WebUI

部署向导
- 上线检查

数据库接入
- 连接概览
- 表白名单
- 连通测试

语义层维护
- 表目录
- 表语义编辑
- 关联关系

业务文档
- Wiki 文档
- 关联 Wiki

审阅与校验
- 变更审阅
- 校验结果

质量评测
- Case 管理
- 运行历史
- 趋势监控

访问治理
- Agent 实例
- 访问日志
- 数据源热力
- 配置变更
```

第一阶段落地为左侧固定主导航：

| 分组 | 导航项 | 路由 | 说明 |
| --- | --- | --- | --- |
| 部署向导 | 上线检查 | `/onboarding` | 聚合数据库、语义、校验、Agent 和 MCP 配置状态 |
| 数据库接入 | 连接概览 | `/connections` | 查看连接、schema、enabled table 与语义覆盖 |
| 数据库接入 | 表白名单 | `/connections/whitelist` | 维护进入语义层的表范围 |
| 数据库接入 | 连通测试 | `/connections/test` | 验证连接可访问 |
| 语义层维护 | 表目录 | `/` | 浏览、搜索、筛选待维护表 |
| 业务文档 | Wiki 文档 | `/wiki` | 维护业务口径和使用说明 |
| 审阅与校验 | 变更审阅 | `/review` | 查看 diff、运行 changed validate |
| 质量评测 | Case 管理 | `/eval/cases` | 维护业务 eval case |
| 质量评测 | 运行历史 | `/eval/runs` | 查看 eval run 结果 |
| 质量评测 | 趋势监控 | `/eval/monitor` | 查看 eval 趋势和阈值 |
| 访问治理 | Agent 实例 | `/admin/agents` | 管理 Agent、role 和 token |
| 访问治理 | 访问日志 | `/admin/audit` | 查询 MCP proxy 访问日志 |
| 访问治理 | 数据源热力 | `/admin/audit-sources` | 查看数据源调用分布 |
| 访问治理 | 配置变更 | `/admin/config-audit` | 查看 WebUI 写配置的审计记录 |

`表语义编辑` 和 `关联关系` 是上下文页面，不作为固定入口直接列出空态路由；从表目录或单表页进入。

## 4. 面包屑规则

| 页面 | 面包屑 |
| --- | --- |
| 上线检查 | `部署向导 / 上线检查` |
| 连接概览 | `数据库接入 / 连接概览` |
| 表目录 | `语义层维护 / 表目录` |
| 表语义编辑 | `语义层维护 / <schema> / <table>` |
| 关联关系 | `语义层维护 / 关联关系 / <table>` |
| Wiki 文档 | `业务文档 / Wiki 文档` |
| 变更审阅 | `审阅与校验 / 变更审阅` |

## 5. 页面标题与说明

### 表目录

标题：`语义维护工作台`

说明：`浏览当前 KTX 项目的语义层数据表，按 schema、状态和关键词定位需要维护的对象。`

表行操作应显式表达维护动作：`维护语义`。

### 表语义编辑

标题：`维护表语义：<table>`

说明：`这里维护会写入 semantic-layer 的结构化语义，包括表描述、字段描述、行粒度、指标、分群和正式 Join。`

页面内分区：

- 基础语义：表描述、行粒度
- 分析语义：指标、分群
- 字段语义：字段描述
- 变更预览：diff 和拟写入 YAML

### 关联关系

标题：`维护关联关系：<table>`

说明：`候选关系先保存在 .ktx-ui sidecar，只有确认后的正式关系才写入 semantic-layer。`

分区命名：

- 已确认关系
- 候选关系

### Wiki 文档

标题：`业务文档：<key>`

说明：`Wiki 用于维护人可阅读的业务口径、使用场景和注意事项，不替代表字段描述。`

### 变更审阅

标题：`变更审阅与校验`

说明：`集中查看本次可编辑目录中的文件变更，并对本次保存过的语义对象运行校验。`

## 6. 第一阶段实施范围

第一阶段只做低风险信息架构优化：

1. 增加左侧主导航。
2. 增加全局面包屑。
3. 重命名页面标题、按钮和空状态文案。
4. 为表目录、表语义、关联关系、Wiki、Review 增加解释性说明。
5. 表目录行增加明确操作文案：`维护语义`。

不做：

- 不改 API。
- 不改 YAML/Markdown 写入格式。
- 不改保存、validate、diff 逻辑。
- 不引入新的 UI 框架。

## 7. 验收

- 普通用户从左侧导航能识别三类维护内容：语义层、业务文档、审阅校验。
- 任一上下文页面能通过面包屑看出当前位置。
- 单表页能明确区分结构化语义维护和业务 Wiki 文档。
- `npm test`、`npx tsc --noEmit`、`npm run build` 通过。
